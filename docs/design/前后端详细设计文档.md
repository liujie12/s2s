## 1. 工程结构与功能域划分

### 1.1 技术底座

Spring Boot 3 + Java 21 **单体**应用，**功能域垂直切分**。
单实例部署，因此定时任务用 Spring 进程内调度（`@Scheduled`），**无需分布式锁**。

## 2. `common` 三组件（**必须在第一个业务接口之前落地**）

这三个组件是全系统契约的物理载体。若先写业务接口后补它们，
每个已写的 controller 都要返工。

### 2.1 组件一：统一响应包 + 响应包装器

```java
/**
 * 统一响应包。所有接口无论成功失败均返回该结构。
 *
 * @param <T> 业务负载类型
 */
public record ApiResponse<T>(
        int code,          // 业务码，0 成功；非 0 见 ErrorCode，前 3 位与 HTTP 状态码对齐
        String message,    // 中文文案，非 0 时可直接呈现给用户
        T data,            // 业务负载，失败时恒为 null
        String requestId   // 服务端生成，UI 报错唯一回显值
) { }
```

**包装器职责**（`ResponseBodyAdvice`）：

1. controller 直接返回业务 DTO（不手写 `ApiResponse.ok(...)`，避免遗漏）
2. 包装器统一套壳，注入当前请求的 `request_id`
3. 序列化用 snake_case（`data` 内字段名与 OpenAPI 一致）

**排除路径**：`/track/events` 也走统一包装（无例外）。

### 2.2 组件二：全局异常处理器

| 异常类型 | 映射 |
| --- | --- |
| `BizException` | 取其 `ErrorCode` 的 code/message/httpStatus；若 `retryAfterSec != null` 则写 `Retry-After` 头 |
| `MethodArgumentNotValidException` / `MissingRequestHeaderException` / `ConstraintViolationException` | `40001`，message 拼出具体字段名 |
| `OptimisticLockException`（自定义，mapper 更新 0 行时抛） | `40903` |
| 其余 `Exception` | `50001`，**日志打全栈**，响应体不含堆栈信息 |

**纪律**：`Retry-After` 的写入**只在这一处**发生，业务代码只负责在 `BizException`
里带上剩余秒数，不各自写 header。

### 2.3 组件三：错误码枚举（25 个，唯一定义处；24 业务码 + `OK(0)`，条目[121] 回写，依据 docs/plans/2026-09-10-1038-feat-item121-backend-bootstrap-plan.md（s2s-wt-backend））

## 3. 请求横切链路（Filter → Interceptor → Controller）

### 3.1 执行顺序

```text
[1] RequestIdFilter          生成 request_id 入 MDC；读取 X-Interaction-Id 入 MDC
[2] AuthInterceptor          解析 Bearer JWT，未登录/失效 → 40101
[3] RateLimitInterceptor     按注解声明的维度做 Redis 计数 → 429xx（带 Retry-After）
[4] IdempotencyInterceptor   写接口校验 Idempotency-Key，命中缓存则直接返回首次结果
[5] Controller               入参校验 → service
```

`RateLimit` 在 `Idempotency` **之前**：幂等重放不应消耗限频额度以外的资源，
但限频本身必须先拦住洪水。

### 3.2 两个 ID 的分工（**极易混淆，必须逐条守住**）

| | `interaction_id` | `request_id` |
| --- | --- | --- |
| 生成方 | **客户端** | **服务端** |
| 传递 | 请求头 `X-Interaction-Id` | 响应体 `request_id` 字段 |
| 覆盖范围 | 缓存 → 网络 → 聚合 → 渲染**四段** | 单次 HTTP 请求 |
| 服务端用途 | **仅日志串联** | 日志 + UI 报错回显 |
| **严禁**用于 | 鉴权、限流、幂等判定 | — |
| 缓存命中时 | 存在（客户端自有） | **不存在**（预期行为，不得判为异常） |

### 3.3 幂等实现

```text
Redis 键：idem:{userId}:{Idempotency-Key}     TTL = NfrApi.idempotencyWindowHours
Redis 值：首次【成功】响应的完整 JSON
```

处理流程：

1. 校验 Key 格式（正则见 OpenAPI `IdempotencyKey` 参数）→ 不符或缺失回 `40001`
2. `SETNX` 占位 → 失败说明并发/重放：轮询取首次响应，**原样返回**
3. 执行业务
4. **仅当业务成功**才把响应写入 Redis；失败则**删除占位键**

四类必测输入（写成单元测试，缺一不可）：

| 输入 | 期望 |
| --- | --- |
| 缺失 `Idempotency-Key` | `40001`，**不得放行** |
| `9B1DEB4D-...`（大写）或 v1 UUID | `40001` |
| 同 Key、**请求体不同** | 返回**首次结果**，不按新请求体执行 |
| 首次失败 → 同 Key 重放 | **重新执行**（只有成功响应进缓存） |

### 3.4 限频键设计（账号级 vs 渠道级分流）

| 场景 | 键维度 | Redis 键 | 阈值 | 超限码 |
| --- | --- | --- | --- | --- |
| 短信发送（手机号） | **渠道级** | `rl:sms:phone:{phone}:{1m|1h|1d}` | 1/min、5/h、10/d | `42905` |
| 短信发送（IP） | 渠道级 | `rl:sms:ip:{ip}:1h` | 20/h | `42905` |
| 登录失败锁定 | 渠道级 | `rl:login:fail:{phone}` | 5 次 → 锁 15min | `40105` |
| 联系（账号） | **账号级** | `rl:contact:uid:{userId}:1d` | 30/d | `42902` |
| 联系（设备） | 账号级辅助 | `rl:contact:dev:{fingerprint}:1d` | 30/d | `42902` |
| 联系（IP） | 渠道级 | `rl:contact:ip:{ip}:1d` | 100/d | `42902` |
| 联系熔断 | 账号级 | `rl:contact:burst:{userId}:1m` + `fz:contact:{userId}:{date}` | 1min ≥10 次 → 当日冻结 | `42903` |
| 举报频次 | 账号级 | `rl:report:uid:{userId}:1d` | 熔断同上 | `42903` |
| 埋点上报 | 账号级 | `rl:track:uid:{userId}:1m` | 60 请求/min | `42906` |
| **未登录详情（设备）** | **无账号维** | `rl:guestdetail:dev:{deviceId}:1d` | 30/d | `42907` |
| **未登录详情（IP）** | 渠道级 | `rl:guestdetail:ip:{ip}:1d` | 100/d | `42907` |

**未登录详情限频的两点特殊性**（口径源：PRD §12.3 / §12.5，2026-09-06 G2 裁定）：

1. **只对未登录请求生效**：`GET /posts/{post_id}` 携带有效 Token 时**跳过此限频**，因为已登录行为可按 `user_id` 追溯。判定点在拦截器读取鉴权上下文之后，不可放在 Token 解析之前。
2. **它是唯一没有账号维的限频轨** —— 恰恰因为对象是未登录用户，所以纪律 1「账号级一律用 `user_id`」在此不适用，只剩设备与 IP 两个可低成本更换的维度。因此阈值直接沿用联系方式的设备 30 / IP 100，**不新造数字**，其定位是提高批量采集成本而非绝对阻断。

**两条纪律**：

1. **账号级风控一律用 `user_id`**（联系次数、AI 配额、举报频次、熔断），
   不用手机号——用户换绑手机号不应重置风控。
2. 渠道级（短信、登录失败）**保留手机号维度**——此时用户尚未登录，无 `user_id` 可用。
3. 限频计数键**允许丢失**（Redis 重启即清零），这是可接受的：
   限频是防滥用而非账务，不为此引入持久化成本。

## 4. 加解密与盲索引

### 4.1 双列范式

每个敏感字段落库为**两列 + 一个版本号**：

| 列 | 算法 | 类型 | 用途 |
| --- | --- | --- | --- |
| `xxx_hash` | HMAC-SHA256 + pepper（**确定性**） | `BINARY(32)` | 承载唯一索引与等值查询（盲索引） |
| `xxx_enc` | AES-GCM-256 + **随机 IV** | `VARBINARY` | 仅用于解密展示 |
| `key_version` | — | `TINYINT` | 密钥轮转标识 |

**为何必须两列**：AEAD 带随机 IV，同一明文两次加密结果不同，**无法建唯一索引也无法等值查询**；
而确定性哈希不可逆，**无法展示**。二者缺一不可。

### 4.2 AAD 绑定表（防跨行密文搬运）

| 字段 | AAD |
| --- | --- |
| `user_identity.identity_value_enc` | `user_id` + `identity_type` |
| `user.real_name_enc` | `user_id` |
| `post.contact_value_enc` | `post_id` |

AAD 的作用：即便攻击者把 A 帖子的密文复制到 B 帖子行，解密也会失败。

### 4.3 解密入口收敛

**全系统只有 `common.crypto.CryptoFacade` 一处可以解密。**
每次解密调用点必须显式传入 AAD 材料，且解密行为**同步写 `audit_log`**。

Batch1 的解密调用点**只有一个**：`contact.ContactService#viewContact`
（服务 `GET /posts/{id}/contact`）。任何新增解密调用点都视为架构变更，须评审。

## 5. 九个功能域的分层设计

### 5.1 `auth` 域

| 接口 | Service 方法 | 关键实现点 |
| --- | --- | --- |
| `POST /auth/sms/send` | `SmsService#sendCode` | 四维限频；验证码存 Redis（`sms:{phone}`）；不落库 |
| `POST /auth/sms/login` | `AuthService#loginBySms` | `agreed=false`→`40002`；失败计数达 5 → `40105` + `Retry-After`；手机号盲索引查 `user_identity`，未命中则注册；写 `device`；签发 JWT（30 天） |
| `POST /auth/token/refresh` | `AuthService#refresh` | 校验旧 Token 签名（允许已过期）+ 用户状态；重签发 |
| `POST /auth/logout` | `AuthService#logout` | Token 加入 Redis 黑名单至原过期时刻；清 `device.push_token` |
| `GET /users/me` | `UserService#getMyProfile` | 出参严格走对外视图白名单 + 本人可见 `phone_mask`/`default_radius` |
| `PATCH /users/me` | `UserService#updateMyProfile` | 昵称过敏感词→`40901`；头像 `media_id` 须 `audit_status=pass` 否则 `40902` |

**登录时的手机号处理**（三步，顺序不可换）：

1. `phoneHash = BlindIndex.hmac(phone)` → 查 `user_identity` 唯一索引
2. 命中 → 取 `user_id`；未命中 → 建 `user` + `user_identity`（`identity_value_enc`
   的 AAD 为 `user_id + identity_type`，故必须**先拿到 `user_id` 再加密**）
3. `user.phone_mask` 写脱敏串（仅本人视角展示用）

**`user` 对外视图白名单**（数据库设计文档 §3.1）：

```text
允许出现在响应中：id / nickname / avatar_url / realname_status / qualification_badges[]
本人视角额外允许：phone_mask / default_radius
禁止出现在任何 API 响应中：real_name_enc / id_card_hash
```

落地手段：`AuthorBrief` / `MyProfile` 两个 DTO 是**唯一**的 user 出参类型，
`UserEntity` **不得**直接返回。写一条集成测试扫描全部响应 JSON，
断言不含 `real_name`、`id_card` 字样。

### 5.2 `category` 域

| --- | --- | --- |

### 5.3 `post` 域（最重的域）

#### 5.3.1 媒体两步式直传

```text
POST /media/upload/ticket
  ├─ 校验 content_type ∈ 白名单、size ≤ 上限（不符 → 40001）
  ├─ 服务端生成 media_id 与 object_key（客户端不可指定）
  ├─ 插入 post_media（post_id = NULL 的孤儿行，audit_status = pending）
  └─ 返回带签名的短时效 upload_url

（客户端直传 OSS → OSS 回调服务端）

POST /media/{media_id}/commit          【由 OSS 回调触发为主，客户端调用为兜底】
  ├─ HeadObject 二次校验实际 size 与 content-type
  ├─ 生成审核任务，写 audit_status
  ├─ ★ 原图删除与本次 commit 在【同一事务内同步完成】（不走异步补偿）
  └─ commit 成功后对象标记不可覆写
```

七条安全约束（逐条对应实现落点）：

| # | 约束 | 落点 |
| --- | --- | --- |
| 1 | 客户端不持长期密钥 | 只下发单次签名 URL |
| 2 | 桶不开公共读 | 所有读取走带签名临时 URL |
| 3 | **原图删除与 commit 同事务同步** | `commitMedia` 方法内 `@Transactional` |
| 4 | 不挂 CDN，或禁用图片处理过滤参数 | 运维配置 + 启动自检 |
| 5 | `media_id` 与 `object_key` 服务端生成 | `createTicket` 内生成 |
| 6 | OSS 侧强制 length-range + type 白名单，commit 二次校验 | 签名策略 + `HeadObject` |
| 7 | OSS 回调为 commit 触发源；24h pending 清理；commit 后不可覆写 | 回调接口 + 定时任务 #P1 |

`audit_status` 三态双视角的**代码落点**：
在 `MediaAssembler` 里做视角分流，签名为
`toDto(PostMediaEntity e, boolean isOwner)`。**禁止**在 controller 里判断视角——
一处漏判就等于把未过审图片下发给了他人。

#### 5.3.2 发布链路

```text
POST /posts
 [1] 幂等 + 参数校验
 [2] 类目校验：banned → 40303；sensitive 且用户无资质 → 40302
 [3] 未实名发布上限（40304）—— 同 40301，Batch1 由开关关闭
 [4] 敏感词：title + description + attributes 全文过滤 → 40901
 [5] 媒体校验：media_ids 全部属于当前用户且非 reject → 40902
 [6] grid_id = GridIdCalculator.of(lng, lat)
 [7] contact 双列加密（AAD = post_id）→ ★ 因此必须先 INSERT 拿到 id 再 UPDATE 密文
 [8] attributes 写 JSON；required_full / address_precise / leaf_matched 三条件写入
     → l2_category_id 与 completeness_level 由【STORED 生成列】自动派生
 [9] expire_at = now + NfrPostLifecycle.validDays
 [10] 异步产出埋点 post_published
```

**第 7 步的顺序陷阱**：`contact_value_enc` 的 AAD 绑定 `post_id`，
但 `post_id` 要 INSERT 后才有。故实现为**同一事务内**「INSERT（密文列留空）→
取自增 id → UPDATE 密文列」，**不可**为了少一次 UPDATE 而改用其他 AAD。

**两个 STORED 生成列（不可写，写入报 `ERROR 3105`）**：

| 生成列 | 表达式 |
| --- | --- |
| `l2_category_id` | `leaf_category_id DIV 100` |
| `completeness_level` | 由 `attributes` 中 `required_full` / `address_precise` / `leaf_matched` 三条件 `JSON_EXTRACT` 后计数，`CASE` 映射 3→2、2→1、else→0 |

Entity 上这两列必须标注为只读（MyBatis 的 `insert`/`update` SQL 里
**不出现**这两个列名），否则一写就报错。

#### 5.3.3 `post` 状态机与写守卫分流

```text
        ┌──── renew（顺延 expire_at）
        ↓
   ┌─────────┐  offline   ┌──────────┐  republish  ┌─────────┐
   │ active  │ ─────────→ │ offline  │ ──────────→ │ active  │
   └─────────┘            └──────────┘             └─────────┘
        │                       │
        │ 定时任务：到期            │ 定时任务：超 autoArchiveDays
        ↓                       ↓
   ┌─────────┐            ┌──────────┐
   │ expired │ ─────────→ │ archived │
   └─────────┘            └──────────┘
```

**写守卫分流（本设计最关键的一条）**：

| 变更来源 | 守卫条件 | 理由 |
| --- | --- | --- |
| **用户意图变更**（`PATCH /posts/{id}/status`） | `WHERE id=? AND version=?` | 用户看到的是某个版本的数据，必须防覆盖 |
| **系统派生变更**（定时任务到期下架、归档） | `WHERE id=? AND status IN (合法前驱集)` | 定时任务不持有用户视图的 version，若也守 version 则会被用户的并发编辑饿死 |

`version` 缺失时**服务端不得兜底**（不允许「没传就跳过校验」）——直接回 `40001`。
更新影响行数为 0 → 抛 `OptimisticLockException` → 全局处理器映射为 `40903`。

### 5.4 `map` 域（性能最敏感）

#### 5.4.1 `grid_id` 算法（三方逐位一致）

```java
/**
 * 计算约 500m 网格的 grid_id。
 *
 * 算法（客户端 Dart / 服务端 Java / SQL 三方必须逐位一致）：
 *   1. 先把坐标向下取整到 5 位小数：floor(x * 100000) / 100000
 *   2. 转入【整数微度域】运算，避免浮点累积误差
 *   3. 以 0.0045°（约 500m，即 450 微度）为步长，用 floor（向负无穷）取整
 *   4. 编码为 "{gx}_{gy}"
 *
 * @param lng GCJ-02 经度
 * @param lat GCJ-02 纬度
 * @return 形如 "26700_6728" 的网格标识，落 varchar(24)
 */
public static String of(double lng, double lat) {
    long lngMicro = floorToMicroDegree(lng);   // 步骤 1+2
    long latMicro = floorToMicroDegree(lat);
    long gx = Math.floorDiv(lngMicro, STEP_MICRO);   // STEP_MICRO = 450
    long gy = Math.floorDiv(latMicro, STEP_MICRO);
    return gx + "_" + gy;
}

/**
 * 将度数向下取整到 5 位小数并转为整数微度（1 微度 = 1e-5 度）。
 * 必须用 Math.floor 而非强制类型转换：负数场景下 (long) 是向零截断，
 * 会让 -0.000015 落到 0 而不是 -1，与测试向量第 9 条冲突。
 */
private static long floorToMicroDegree(double deg) {
    return (long) Math.floor(deg * 100_000d);
}
```

**10 条测试向量**（三端共用同一份，任一端不过即视为实现错误）：

| # | 输入 (lng, lat) | 期望 grid_id | 考察点 |
| --- | --- | --- | --- |
| 1 | (120.15000, 30.28000) | `26700_6728` | 常规正数 |
| 2 | (0, 0) | `0_0` | 原点 |
| 3 | (0.00450, 0.00450) | `1_1` | 步长边界（含） |
| 4 | (0.00449, 0.00449) | `0_0` | 步长边界（不含） |
| 5 | (-0.00001, -0.00001) | `-1_-1` | 负数最小偏移 |
| 6 | (-0.00450, -0.00450) | `-1_-1` | 负数边界（含） |
| 7 | (-0.00451, -0.00451) | `-2_-2` | 负数跨格 |
| 8 | (0.004500049, 0.004500049) | `1_1` | 5 位小数截断 |
| 9 | (-0.000015, -0.000015) | `-1_-1` | **关键探针，须额外断言中间微度值为 -2** |
| 10 | (120.15000, -30.28000) | `26700_-6729` | 混合正负 |

第 9 条是**唯一能暴露「用截断代替 floor」的向量**：
若误用 `(long)` 截断，中间值会得 `-1` 而非 `-2`，最终 grid 仍是 `-1_-1`（结果偶然正确），
所以**必须断言中间值**，否则这条测试形同虚设。

#### 5.4.2 `/map/pins` 查询与覆盖索引

```sql
-- EXPLAIN 结论（实测）：type=range, key=idx_pins_cover,
--   Extra = "Using where; Using index" —— 完全走覆盖索引，不回表。
--   实测 p95 = 1.37ms（500 条打满）。
-- 纪律：任何写在 XML 里的查询都要附一条 EXPLAIN 结论作为注释（技术栈选型 §7）。
SELECT id, lng, lat, leaf_category_id, type, completeness_level
FROM post
WHERE grid_id IN (...)              -- 索引第 1 列，按半径展开的网格集合
  AND leaf_category_id IN (...)     -- 第 2 列
  AND type = ?                      -- 第 3 列
  AND status = 'active'             -- 第 4 列
  AND expire_at > NOW()             -- 第 5 列
LIMIT 500;                          -- 上限见 NfrPerf.renderMaxPins
```

覆盖索引 `idx_pins_cover` 的 10 列 = **前 5 列过滤 + 后 5 列即响应字段**：

```text
(grid_id, leaf_category_id, type, status, expire_at,   ← 过滤
 id, lng, lat, completeness_level, user_id)            ← 响应/回表规避
```

**历史教训**：早期只用前 5 列 + `id` 验证过「覆盖索引成立」，
但真实响应契约还要 `lng`/`lat`/`completeness_level`，
一上真实字段立刻回表。**验证覆盖索引必须用响应契约的真实列集合**。

#### 5.4.3 紧凑序列化

```java
/**
 * 将 Pin 查询结果序列化为紧凑二维数组。
 *
 * 采用 schema + 数组而非对象数组，是为了满足体积红线：
 * gzip 后 ≤ NfrPerf.mapPayloadMaxBytes，原始 ≤ NfrPerf.mapPayloadMaxRawBytes。
 * 对象数组在 500 条时仅键名就要重复 500 次。
 *
 * 列序固定为 [id, lng, lat, category_id, type, completeness_level]，
 * 与响应中的 schema 字段一致，客户端按此列序解析。
 * type 编码：0=resource，1=demand（枚举转整数进一步压体积）。
 * 坐标保留位数见 NfrPerf.mapPinCoordDecimals。
 */
```

**聚合模式切换按 `zoom` 而非点数**：
由 `zoom` 换算 metersPerPixel，与 `NfrPerf.clusterModeSwitchMetersPerPixel` 比较。

- 远景 → `mode=cluster`，**服务端预聚合**返回 `clusters[]`
- 近景 → `mode=pin`，返回 `pins[]`，**客户端 Dart 侧**做视觉聚合
  （网格尺寸见 `NfrPerf.clusterGridSizePx`）

该阈值标注为「待 POC 实测校准」——它是体验拐点，不是可以拍脑袋的常量。

#### 5.4.4 缓存键五要素

```text
Redis 键：pins:{categoryIdsHash}:{postType}:{radius}:{gridId}:{categoryVersion}
TTL    ：NfrCache.pinSetTtlSec
```

五要素**任一缺失即回 `40001`**（不允许用默认值兜底）——
缺任一要素都会导致不同语义的请求共用缓存，返回错误数据。

网格边长见 `NfrCache.keyGridMeters`。客户端单设备缓存键上限
`NfrCache.maxKeys`，按 LRU 淘汰。

#### 5.4.5 分类树版本协商（**不报错**）

### 5.8 `track` 域

写 `s2s_track` 库。**禁止跨库 JOIN**（两个 database 物理隔离）。

```text
[1] 必须登录态（user_id 取登录态，请求体传了也忽略）
[2] 限频：同用户 1min 60 请求 → 42906 + Retry-After
[3] 单请求事件数 ≤ NfrApi.trackBatchMaxEvents → 超出 42906
[4] 按每条事件的 ts 归入 track_event_YYYYMM 月表
[5] 目标月表不存在（预建失败的兜底）→ 写 track_event_fallback
[6] 校验 layer_switch 四段之和 == duration_ms（容差 ±1ms），
    不符不拒收但标记异常，进数据质量看板
[7] 落库语句固定为：
      INSERT INTO track_event_YYYYMM (...) VALUES (...)
      ON DUPLICATE KEY UPDATE id = id
    命中唯一索引 uk_event_dedup(interaction_id, event_name, user_id, ts)
    即视为重复，静默跳过。
```

**第 [7] 步是客户端「每批换新 `Idempotency-Key`」的对价，不是可选优化。** 客户端为避免更严重的事故（沿用旧 Key → 命中幂等缓存 → 整批事件静默丢失，见 §17.4.1）而放弃了幂等键保护，因此「同一批被上报两次」的去重责任完整地落在这条 SQL 上。

三条实现纪律：

- **严禁 `INSERT IGNORE`。** 它把数据截断、非空列插 NULL、类型转换失败一并降级为 warning，等于在埋点写入路径上关掉全部数据质量报错。
- **严禁写成 `ON DUPLICATE KEY UPDATE props = VALUES(props)`。** 这个写法看起来更"合理"（用新值更新），但会让后到的重复批次**覆盖**首次落库的事件属性，且行数校验完全看不出异常。必须是无副作用的 `id = id`。
- **`ts` 必须用客户端上报的值，不得替换为服务端到达时刻。** 否则同批重传会拿到不同 `ts`，唯一键当场失效而不报任何错。

约束定义与完整论证见《数据库设计文档》§3.16.1，行为由 `assert_behavior.sh` 的 A8 守护。

#### 10.2.1 埋点队列与 Pin 缓存不能放 `shared_preferences`

原设计把「Token、`device_id`、分类树、埋点队列」一并写给 `shared_preferences`，这是错的。算一下量级：

| 数据 | 量级估算 | 结论 |
| --- | --- | --- |
| 埋点队列 | 上限 2000 条（§17.4），`layer_switch` 单条 12 字段 + 信封元数据，序列化后按 200–500 字节／条计 → **400 KB ～ 1 MB** | 不能放 |
| Pin 集合缓存 | `NfrCache.maxKeys` 个键，每键载荷上限受 `NfrPerf.mapPayloadMaxRawBytes` 约束 → 数百 KB 至数 MB | 不能放 |
| Token / `device_id` / 分类树版本号 / 各类开关 | 合计 < 10 KB | 可以放 |

`shared_preferences` 放不下的两个技术原因（不是「容量硬限制」，而是性能形态不匹配）：

1. **启动期全量同步加载。** Android 端 `SharedPreferences` 在首次访问时把整个 XML 读进内存并解析。把 1 MB 的埋点队列塞进去，等于给每次冷启动加一笔纯粹浪费的 I/O + 解析开销 —— 而首屏时延正是 `NorthStar` 盯的指标。
2. **每次 `setString` 全量重写。** 追加 1 条埋点 → 序列化整个 2000 条队列 → 覆写整个文件。写 n 条事件的总代价是 **O(n²)**。队列越满，越写不动，而队列变满恰恰发生在弱网／离线积压时 —— 也就是最不该雪上加霜的时刻。

**改法：分三层存储，各归其位。**

| 层 | 存什么 | 用什么 |
| --- | --- | --- |
| 键值层 | Token、`device_id`、分类树版本号、开关 | `shared_preferences`（保留） |
| 队列层 | 埋点事件队列 | **追加写文件**（`path_provider` + `dart:io`，JSON Lines 每行一条），追加是 O(1)；出队后重写文件或做标记位。**上报成功即从文件头部截断** |
| 缓存层 | Pin 集合、静态数据 L1/L2/L3 | **内存 LRU 为主 + 文件落盘为辅**。Pin 缓存 TTL 是 `NfrCache.pinSetTtlSec`（秒级），本就不需要跨进程存活；跨启动只需保留静态 L1/L2 |

**为什么不上 `sqflite`：** Batch1 唯一需要「追加 + 顺序读 + 头部截断」的是埋点队列，这是文件天然擅长的形态，没有任何查询需求。引数据库要付出 schema 迁移、异步初始化、平台插件三笔成本，换不到收益。若后续埋点要做本地聚合查询，再评估。

**因此新增一项依赖：`path_provider`**（取应用私有目录路径）。它是 Flutter 官方包，不违反「不引第二个 HTTP 客户端」类纪律，且无替代（Dart 拿不到 Android/iOS 的沙盒目录）。

三条硬纪律（技术栈 §12）：

1. **不引第二个 HTTP 客户端。** 两个客户端 = 两套拦截器 = 幂等/续期/重试各漏一半。
2. **`mem_peak_mb` 不引库。** Android 走平台通道读 `Debug.MemoryInfo`，iOS 上报空值。不为一个可观测性字段引 `device_info_plus`。
3. **版本锁定 `pubspec.lock` 并入库。** 内测包必须可复现构建。

### 10.3 DTO 手写 `fromJson` 的落地纪律

技术栈 §12 已定案**不引** `json_serializable` / `freezed`。因此每个 DTO 手写，纪律如下：

| 纪律 | 说明 |
| --- | --- |
| 字段名以 OpenAPI schema 为唯一来源 | 服务端 snake_case，Dart 侧字段名用 camelCase，映射写在 `fromJson` 里 |
| 可空性必须与 schema `required` 一致 | schema 未标 `required` 的字段在 Dart 侧必须可空。**不允许用 `?? 默认值` 把可空掩盖成非空** —— 那会把「服务端没下发」和「服务端下发了默认值」混为一谈 |
| 枚举一律用 `switch` 显式映射 | 不用 `values.byName`。服务端加枚举值时 `byName` 会抛异常，`switch` 的 `default` 分支能降级 |
| 解析失败抛 `ApiException(ErrorCode.parseError)` | 不返回 null，不静默吞。契约不符是缺陷不是业务状态 |

### 10.4 既有本地模型与服务端契约的语义迁移（改造最高风险区）

现有 `lib/domain/` 与 `lib/features/` 的模型是在「无后端、本地样例数据」阶段写的，它们的字段语义与服务端契约**不一致但都能编译通过**。这一节把每一处不一致列清并给出迁移方案。

**共同的危险特征：类型相同、语义不同。** 编译器一个字都不会报，问题只在运行时以「配色错乱」「筛选筛不出东西」「越界崩溃」的形式暴露 —— 而且往往只在 release 包或只在某些数据下暴露。

#### 10.4.1 `category_id`：从「枚举 index 0..4」到「叶子类目 ID 10101」

**这是 P0，会在 release 包直接崩溃。**

现状（[listing_category.dart](file:///d:/developer/code/aicoding/s2s/lib/domain/listing_category.dart#L94-L112)）：

```dart
int get id => index;            // 取值 0..4

ListingCategory listingCategoryFromId(int id) {
  assert(
    id >= 0 && id < ListingCategory.values.length,
    'categoryId 越界：$id，合法区间 0..${ListingCategory.values.length - 1}',
  );
  return ListingCategory.values[id];    // ← 传 10101 进来会怎样
}
```

契约（`openapi.yaml` → `PinsCompactResponse`）：`schema` 第 4 列 `category_id`，example 值为 **`10101`**，是**叶子类目 ID**，不是枚举下标。

接上后端后的实际后果，分 debug / release 两种，而**两种都不可接受**：

| 构建模式 | `listingCategoryFromId(10101)` 的行为 | 为什么危险 |
| --- | --- | --- |
| debug | `assert` 触发，抛断言错误 | 至少能发现，但发现点是 UI 渲染时，离根因（网络层解包）很远 |
| release | **`assert` 不参与编译**（Dart 语言行为），直接执行 `values[10101]` → 抛 `RangeError` | 内测包白屏／崩溃，且崩溃栈指向一个「看起来只是取个枚举」的工具函数 |

> 这正是本项目历史教训清单里「Dart `assert` 在 release 不参与编译，不能当兜底」的又一次现场。`assert` 是**开发期契约声明**，不是运行时防线。

同时 `grid_cluster.dart` 的分桶键把它拼进了 key（[grid_cluster.dart](file:///d:/developer/code/aicoding/s2s/lib/features/map/clustering/grid_cluster.dart#L100-L102)）：

```dart
final String key = '$gx:$gy:${p.categoryId}';
```

这行**不会崩，但会静默变味**：语义从「按 5 个一级大类分桶」变成「按数十个叶子类目分桶」。桶数量暴增，每桶点数骤降，聚合直接失效 —— 地图上该聚成一个大圈的地方散成一片小点。它不报错，只是「效果不对」，是最难归因的一类缺陷。

**迁移方案（三步，顺序不可颠倒）：**

1. **把两个概念拆成两个字段，禁止复用一个 `int`。**

   ```dart
   class ClusterPoint {
     final String id;
     final double x;
     final double y;
     /// 叶子类目 ID（服务端口径，如 10101）。仅用于透传与请求参数。
     /// 注意：不能拿它做 ListingCategory.values 下标 —— 取值范围完全不同。
     final int leafCategoryId;
     /// 一级大类（本地渲染口径，决定配色与图标）。
     /// 由 leafCategoryId 经分类树查表得到，不做算术推导。
     final ListingCategory topCategory;
   }
   ```

2. **一级大类只能查表得到，不许用「取前两位」之类的算术推导。** `10101` 的前两位是 `10`，看起来能映射，但这依赖服务端类目编码规则永不变 —— 而分类树是有版本号（`YYYY-MM-DD.N`）且会演进的数据。正确来源是 `GET /categories/tree` 返回的树结构，逐级找父。查不到时的处理见第 3 步。

3. **`listingCategoryFromId` 整个删除，替换为显式的查表函数，且带真实兜底（不是 `assert`）。**

   ```dart
   /// 由叶子类目 ID 反查一级大类。
   ///
   /// 数据来源是 GET /categories/tree 下发的分类树，不做编码规则推导 ——
   /// 类目编码规则属于服务端实现细节，且分类树带版本号会演进。
   ///
   /// [leafCategoryId] 服务端下发的叶子类目 ID（如 10101）
   /// [tree] 当前生效的分类树（版本协商见 §16.4）
   /// 返回：对应的一级大类；查不到时返回 null
   ///
   /// 返回 null 而不是抛异常的理由：分类树版本落后于服务端数据时，
   /// 新增类目查不到是【预期内】的正常状态（§16.4 明确规定版本不一致不报错），
   /// 调用方应降级为「中性配色 + 触发异步拉树」，而不是崩溃或吞掉这个 Pin。
   ListingCategory? topCategoryOf(int leafCategoryId, CategoryTree tree) { ... }
   ```

   调用方拿到 null 时：用中性配色渲染该 Pin（**不丢弃**，丢弃会让用户觉得"东西不见了"），同时触发 §16.4 的异步拉树。

4. **`ListingCategory.id => index` 这个 getter 删除。** 只要它还在，就还会有人拿它当服务端 ID 用。枚举下标是纯本地实现细节，不该有对外的 `id` 名义 —— `id` 这个名字本身就在诱导误用（属「神秘命名」坏味道：名字承诺了一个它不具备的语义）。

**验收断言：** 造一条 `category_id = 10101` 的 `/map/pins` 响应，在 **release 模式** 下跑通渲染。必须是 release —— debug 下 `assert` 会拦住，反而掩盖了「release 崩溃」这个真问题。

#### 10.4.2 供需态：三套表示法，其中一半同名

同一个概念在三处有三种写法，且**不是简单的一一对应**：

| 位置 | 表示 | 取值 |
| --- | --- | --- |
| 本地枚举 [listing_category.dart](file:///d:/developer/code/aicoding/s2s/lib/domain/listing_category.dart#L115-L121) | `SupplyDemand` | `supply` / `demand` |
| 契约 JSON 字段 `openapi.yaml` → `PostTypeEnum` | 字符串 | `"resource"` / `"demand"` |
| 契约紧凑数组 `openapi.yaml` → `PinsCompactResponse` 第 5 列 `type` | 整数 | `0`（resource）/ `1`（demand） |

**最危险的地方在于它「一半能跑」**：`demand` 三处同名，`supply` 与 `resource` 不同名。于是如果有人图省事写了 `SupplyDemand.values.byName(json['post_type'])`：

- 传 `"demand"` → 正常返回 `SupplyDemand.demand`，测试通过；
- 传 `"resource"` → 抛 `ArgumentError`。

一半用例通过的缺陷，比全错的缺陷难查得多 —— 它会让人相信"映射逻辑是对的，只是某条数据有问题"。这也正是 §10.3 那条「枚举一律用 `switch` 显式映射，不用 `values.byName`」纪律的具体由来。

**落地：两个方向的转换都显式写死，各自单测。**

```dart
/// 供需态：契约字符串 → 本地枚举。
///
/// 必须显式 switch，不能用 values.byName：
/// 服务端用 "resource"，本地枚举叫 supply，两者不同名；而 "demand" 恰好同名，
/// 会让 byName 的错误实现「一半能跑」，掩盖问题。
///
/// [raw] 契约 PostTypeEnum 值，取值 "resource" / "demand"
/// 返回：对应的本地枚举
/// 抛出：ApiException(parseError) —— 出现契约外的值
SupplyDemand supplyDemandFromApi(String raw) => switch (raw) {
      'resource' => SupplyDemand.supply,
      'demand' => SupplyDemand.demand,
      _ => throw ApiException.parse('未知 post_type: $raw'),
    };

/// 供需态：紧凑数组整数码 → 本地枚举。
///
/// 用于 /map/pins 的 schema 第 5 列。0/1 的含义由契约 PinsCompactResponse
/// 固定，不得按枚举 index 推导 —— SupplyDemand 的 index 恰好也是 0/1，
/// 这个巧合会让错误实现在当前版本能跑，等枚举新增值时才炸。
///
/// [code] 紧凑数组中的 type 列，取值 0 或 1
SupplyDemand supplyDemandFromCompact(int code) => switch (code) {
      0 => SupplyDemand.supply,
      1 => SupplyDemand.demand,
      _ => throw ApiException.parse('未知 type 码: $code'),
    };
```

注意第二个函数注释里那个巧合：`SupplyDemand.supply.index == 0`、`demand.index == 1`，与契约的 0/1 **当前恰好一致**。所以 `SupplyDemand.values[code]` 现在能跑。但它是靠巧合跑的 —— 枚举顺序一变或中间插值就错，而那时没人会想到去查这里。**显式 switch 不是啰嗦，是把巧合换成约定。**

#### 10.4.3 两处基础类型不匹配

| 字段 | 契约 | 本地现状 | 迁移 |
| --- | --- | --- | --- |
| 帖子 ID | `PostIdPath`：`integer` / `format: int64` | [listing.dart](file:///d:/developer/code/aicoding/s2s/lib/domain/listing.dart#L25) `final String id;` | 统一为 **`int`**。理由见下 |
| 搜索半径 | `RadiusEnum`：`['1','3','5','10','city']`，**字符串** | [discovery_filter.dart](file:///d:/developer/code/aicoding/s2s/lib/features/discovery/discovery_filter.dart#L20-L32) `SearchRadius.km` 为 `int?`，全城为 `null` | 保留本地 `int?` 语义，**在 DTO 层做双向映射**，见下 |

**帖子 ID 为什么必须改成 `int`，而不是「反正 JSON 出来能 toString」：**

服务端是 `int64`。若本地用 `String`，会引入三个不对称：

1. **相等性陷阱。** `"1001"` 与 `"1001 "`、`"01001"` 在 Dart 里是三个不同的 String，但对服务端是同一个（或非法）ID。用 String 作 Map key、作列表去重键、作 `==` 判断时，任何一次多余的格式化都会静默产生重复项。
2. **`int64` 精度。** 若中途经过 `dynamic` → `double` 的转换（JSON 解析在某些路径上会），大于 2^53 的 ID 会丢精度。虽然 Batch1 数据量到不了，但用 `int` 直接消除这个隐患，代价为零。
3. **路径拼接方向单一。** 请求侧 `String` 转数字要校验，`int` 转字符串永不失败。选 `int` 是把校验点收敛到唯一入口（`fromJson`）。

`ClusterPoint.id` 目前是 `String`（聚合模块刻意不 import Flutter，只用基础类型）—— 它可以继续用 `String`，因为它只做分桶标识不回传服务端；但**必须在注释里写明这是本地标识、回传前需转 `int`**，否则下一个人会直接把它塞进 URL。

**半径的双向映射：**

```dart
/// 搜索半径：本地枚举 → 契约字符串。
///
/// 契约 RadiusEnum 是【字符串】枚举 ['1','3','5','10','city']，
/// 不是整数 —— 因为它要容纳 'city' 这个非数值档。本地则用 int? 表示，
/// null 代表全城（不做距离过滤）。两侧对 "全城" 的编码方式不同，
/// 必须显式映射，不能靠 km.toString()（null 会变成字面量 "null"）。
///
/// 返回：契约要求的 radius 参数值
String toApiRadius(SearchRadius r) => r.km?.toString() ?? 'city';

/// 搜索半径：契约字符串 → 本地枚举。
///
/// [raw] 契约 radius 值
/// 抛出：ApiException(parseError) —— 契约外的值
SearchRadius searchRadiusFromApi(String raw) => switch (raw) {
      '1' => SearchRadius.km1,
      '3' => SearchRadius.km3,
      '5' => SearchRadius.km5,
      '10' => SearchRadius.km10,
      'city' => SearchRadius.city,
      _ => throw ApiException.parse('未知 radius: $raw'),
    };
```

`km?.toString() ?? 'city'` 这一行是整个映射的要点：**如果写成 `km.toString()`，全城档会得到字符串 `"null"`**，服务端收到后按 §16.2 的规则回 `40001`（缓存键五要素不允许兜底），而客户端的报错文案只会说"参数错误"，不会告诉你是哪个参数 —— 排查成本极高。

## 11. 网络层：dio 拦截器链

### 11.1 五个拦截器的执行顺序

顺序影响「续期后请求头是否更新」「压缩体积统计在哪一层」这类问题，所以顺序在此定死。但请注意：**顺序解决不了幂等键沿用问题**，那件事必须靠 §11.1.1 的幂等注入，与位置无关。

```
【发出方向 onRequest，按添加顺序 1→5】
  1. HeaderInterceptor      注入 Authorization / X-Interaction-Id / X-Device-Id / Idempotency-Key
                            （四者均为「缺失才写」，见 §11.1.1）
  2. GzipInterceptor        不注入 Accept-Encoding（§11.5 已实测：dart:io 自动协商+自动解压，
                            手动注入零收益，开关默认关）；发出方向无动作
  3. EnvelopeInterceptor    （发出方向无动作）
  4. AuthRefreshInterceptor （发出方向：若续期正在进行，挂起本请求）
  5. RetryInterceptor       （发出方向：记录首次发出时间与重试计数）
        ↓
      dio → 服务端
        ↓
【返回方向 onResponse / onError，同样按添加顺序 1→5（实测订正，见下方图注）】
  1. HeaderInterceptor      （返回/错误方向无动作）
  2. GzipInterceptor        dio 已自动解压；此处先于 Envelope 运行，记录「完整信封」压缩前后体积
  3. EnvelopeInterceptor    拆 {code,message,data,request_id}；code != 0 → reject(err, callFollowing=true)
  4. AuthRefreshInterceptor 40101 → 单飞续期 → 重放挂起队列
  5. RetryInterceptor       可重试码 → 退避后 dio.fetch(err.requestOptions) 重发；链尾错误归一
```

> **图注订正（2026-09-10，U4 第一天实测）**：dio 5.11.1 的三个方向**都按 `Interceptors.add` 添加顺序执行（FIFO）**，并非本图早期版本所写「返回/错误方向自下而上倒序」。源码 `dio_mixin.dart` 对同一 future 依添加序逐个 `.then`（请求/响应）与 `catchError`（错误）串联，无 reversed。实测与源码核对用例见 `test/core/network/gzip_interceptor_test.dart`「实测二」。
>
> 这个订正对设计是**安全**的，且正是计划 KTD2/KTD10 的承重前提：`EnvelopeInterceptor` 在 onResponse 内 `reject(err, true)` 后，错误沿添加序继续向第 4/5 位前进，AuthRefresh（40101 续期）与 Retry（链尾错误归一/重试）因此能接到错误；若返回向真是倒序，前序拦截器 reject 出的错误反而到不了后添加的 AuthRefresh/Retry。Gzip 因 FIFO 而在 Envelope 拆包**之前**统计，量到的是完整信封明文，与压缩后的线上字节（`content-length`）同口径。

#### 11.1.1 重发时的幂等键保全：靠幂等注入，不靠拦截器位置

> **本节修正了本文档早期版本的一处错误论证**，原文写「`RetryInterceptor` 在最内层，重发时复用原始 `RequestOptions`，因此 `Idempotency-Key` 天然沿用」。这个结论是错的，且错得很隐蔽 —— 它在大多数情况下看起来能跑。

错在哪：dio 的拦截器**不是嵌套调用栈**，而是一个列表，三个方向（onRequest/onResponse/onError）均按添加顺序遍历（2026-09-10 U4 实测订正，旧版「返回方向倒序」表述有误，见 §11.1 图注）。而重发的标准写法是：

```dart
// RetryInterceptor.onError 里的重发
final response = await dio.fetch(err.requestOptions);
```

`dio.fetch(...)` 会**重走完整的 onRequest 链**，`HeaderInterceptor` 因此会被再执行一次。如果它无条件写头，`uuid.v4()` 就会生成一个**新的** `Idempotency-Key` —— 服务端把这次重发当成一笔全新的写请求，幂等保护当场失效。「Retry 在最内层」这个位置事实保护不了任何东西。

正确做法：`HeaderInterceptor` 注入前先判存在性。

```dart
/// 注入幂等键（仅写接口）。
///
/// 必须先判 containsKey 再写：重试链路上 dio.fetch(err.requestOptions) 会
/// 重走一遍 onRequest，此时 headers 里已带上首次生成的 Key，若无条件覆盖，
/// 重发就会携带新 Key，服务端视为新请求 —— 违反架构 §6.6「重试必须沿用原
/// Idempotency-Key」的硬要求。
///
/// [options] dio 请求配置，重试时为首次请求的同一对象副本
void _injectIdempotencyKey(RequestOptions options) {
  if (!_isWriteMethod(options.method)) return;
  // 关键：已存在即视为重试路径，逐字保留原值，不重新生成
  if (options.headers.containsKey('Idempotency-Key')) return;
  options.headers['Idempotency-Key'] = _uuid.v4();
}
```

`X-Interaction-Id` 同理，且更严格 —— 它由交互起点生成（§11.2），拦截器**只做「缺失时补一个」的兜底，不做覆盖**。

**为什么这个写法必须落地，而不是「等实测 dio 行为再决定」：**

| dio 实际行为 | 加了幂等注入 | 没加幂等注入 |
| --- | --- | --- |
| 重发**会**重走 onRequest | 正确（保留原 Key） | **错误**（生成新 Key，幂等失效） |
| 重发**不**重走 onRequest | 正确（本就不会被覆盖） | 正确（但纯属侥幸） |

加了在两种情况下都对，不加则至少一种情况错。所以这不是待验证项，是无条件纪律。

**编码期必须断言的三点**（写进单测，不靠人眼看）：

1. 构造一个必然触发重试的场景（服务端返 `50001`），断言两次请求的 `Idempotency-Key` **字符串逐字相同**；
2. 断言两次请求的 `X-Interaction-Id` 也逐字相同；
3. 断言 `uuid.v4()` 在这条链路上**只被调用 1 次**（用可注入的 uuid 生成器计数，否则第 1、2 条在「两次都恰好没生成」的假实现下也能通过）。

**唯一例外：`POST /track/events`。** 埋点批次重发必须**换新** `Idempotency-Key` 与 `X-Interaction-Id`，理由见 §17.4.1 —— 沿用旧键会让服务端命中幂等缓存跳过写入，事件静默丢失。实现上，该接口的请求由 `TrackReporter` 自己组装并**显式带上**两个头，`HeaderInterceptor` 的「缺失才写」逻辑自然不会覆盖它。这个例外必须在 `TrackReporter` 的类注释里写明，否则下一个人会以为这是漏了幂等保护而"顺手修好"。


### 11.2 请求头注入规则

| 头 | 值 | 规则 |
| --- | --- | --- |
| `Authorization` | `Bearer <JWT>` | 从 `authSessionProvider` 读；未登录时**不注入该头**（不注入空串，否则服务端要多判一种非法态）。这一项是**每次都重写**的唯一例外 —— 续期后重放必须带上新 Token |
| `X-Interaction-Id` | UUID v4 | **由交互起点生成并向下透传**，不在拦截器里生成。拦截器仅在缺失时兜底补一个，**已存在时不覆盖**。一次「切图层」交互可能触发多个请求，它们必须共用同一个 id（见 §17.2） |
| `X-Device-Id` | UUID v4 | 首次启动生成写入 `shared_preferences`，此后固定。**明确不采集 IMEI/MAC/IDFA/OAID** |
| `Idempotency-Key` | UUID v4 | **仅写接口注入**（POST/PATCH）。GET 不注入。**已存在时不覆盖**（§11.1.1） |

除 `Authorization` 外，其余三个头一律「`containsKey` 为真则跳过」。`Authorization` 之所以反过来（每次重写），是因为 §13 的续期重放依赖它换成新 Token；若它也走「缺失才写」，重放会带着已失效的旧 Token 再吃一次 `40101`，形成死循环。

`X-Interaction-Id` 的透传方式：作为方法参数逐层传递，不用 Zone / 不用全局变量。理由：全局变量在并发交互（用户切图层的同时后台在补报埋点）下会串号，而串号后的埋点数据无法事后修复。

### 11.3 统一解包

```dart
/// 统一响应解包。
///
/// 服务端所有响应（含错误）都是 {code, message, data, request_id} 信封，
/// HTTP 状态码只用于粗分类，真正的业务语义在 code 里。因此这里必须先拆信封
/// 再判 code，不能只看 HTTP 状态码。
///
/// [response] dio 原始响应
/// 返回：信封中的 data 字段（可能为 null，如 GET /categories/tree 版本相同时）
/// 抛出：ApiException —— 当 code != 0
Object? unwrap(Response response) {
  final body = response.data as Map<String, dynamic>;
  final code = body['code'] as int;
  final requestId = body['request_id'] as String?;
  if (code != ApiErrorCode.ok.code) {
    throw ApiException(
      code: ApiErrorCode.fromCode(code),
      message: body['message'] as String? ?? '',
      requestId: requestId,
      // Retry-After 只在 7 个码上存在，缺失时为 null 属正常
      retryAfterSec: _parseRetryAfter(response.headers),
    );
  }
  return body['data'];
}
```

三条易错点：

| 易错点 | 正确做法 |
| --- | --- |
| `data == null` 当成错误 | **不是错误**。`GET /categories/tree` 版本相同时返回 `code=0` + `data=null`（表达 304 语义但走 200） |
| `request_id` 缺失当成错误 | **不是错误**。缓存命中的请求没有经过服务端，天然没有 `request_id` |
| `Retry-After` 按 HTTP-date 解析 | 服务端约定是**整数秒**，不是 HTTP-date。按 `int.tryParse` 解析，失败则回退到 §14 的默认退避 |

### 11.4 UI 报错的唯一回显值

报错弹窗/Toast 展示格式固定为：`{message}（{request_id}）`。`request_id` 是用户能提供给客服、客服能拿去查日志的**唯一线索**。

- `request_id` 为 null（缓存命中或网络层失败根本没到服务端）时，只展示 `message`，**不展示 `interaction_id` 顶替**。`interaction_id` 是客户端生成的，服务端日志里可能压根没有它。

### 11.5 `Accept-Encoding: gzip` 是否需要手动注入 —— 待实测项

`GzipInterceptor` 计划手动注入 `Accept-Encoding: gzip`，但这件事有一个已知风险：Dart 的 `HttpClient` **默认就会**带上 `Accept-Encoding: gzip` 并自动解压；而某些 HTTP 客户端实现遵循「调用方一旦显式设置该头，就视为调用方要自行处理解压」的语义，此时 `response.data` 拿到的会是**未解压的字节流**，`EnvelopeInterceptor` 里 `response.data as Map` 会直接抛类型错误。

因此定为**待实测项**，不在此处下结论。编码期第一件事就是验证：

| 验证步骤 | 判定 |
| --- | --- |
| 不注入该头，请求 `/map/pins`，打印响应头 `content-encoding` 与 `response.data` 的运行时类型 | 若 `content-encoding: gzip` 且 `data` 已是 `Map` → **dio/HttpClient 已自动处理，`GzipInterceptor` 不注入该头**，只保留体积统计职责 |
| 注入该头，同样打印 | 若 `data` 变成 `List<int>` / `Uint8List` → 证实「显式设置即需自行解压」，**必须回退到不注入** |

**默认取值：不手动注入**（依赖 dio 默认行为），实测证明必须手动注入时再改。理由：多余的头带来的收益为零（默认已开压缩），而踩中「自行解压」语义的代价是整条网络层解包崩溃。

压缩体积统计（`t_net_ms` 相关的埋点辅助数据）不依赖这个头，从 `content-length` 响应头与解包后 JSON 长度即可得到，与是否手动注入无关。

#### 实测结论（2026-09-10，U4 第一天双实测）

环境：Windows、Flutter 3.41.9 / Dart 3.11.5、dio 5.11.1（钉版），VM 平台默认 `IOHttpClientAdapter`（与生产同款适配器），服务端为测试脚手架 `MockApiServer`（dart:io `HttpServer` 真栈，真实 gzip 实体压缩，不走外网、不引新依赖）。自动化用例：`test/core/network/gzip_interceptor_test.dart`（8 例全绿）。

**实测一：gzip 行为（本节判定表两行各跑一次）**

| 条件 | 服务端收到的 `Accept-Encoding` | 客户端 `response.data` 运行时类型 | 解压后 `content-encoding` 响应头 | 解压后 `content-length` 响应头 |
| --- | --- | --- | --- | --- |
| A. 拦截器/BaseOptions 不写该头 | `gzip`（dart:io `HttpClient` 自动协商，非应用层写入） | `_Map<String, dynamic>`（已自动解压并 JSON 解码，信封正常拆包，payload 512 字符） | 仍为 `gzip`（头保留） | 仍为压缩态字节数（实测样本 97） |
| B. 经单请求 `Options(headers: {'Accept-Encoding': 'gzip'})` 显式注入 | `gzip`（手工值逐字到达） | `_Map<String, dynamic>`（**仍自动解压**，无异常，payload 512 字符） | 仍为 `gzip`（头保留） | 仍为压缩态字节数 |

结论（二选一裁定落第一行）：

1. 当前钉版组合下「显式设置即需自行解压」的风险**未复现** —— 即便应用层显式设置该头，dart:io `HttpClient.autoUncompress`（默认 true）仍照常自动解压，`data` 不会变成 `List<int>`/`Uint8List`，也不抛解压异常。
2. 两种条件服务端都协商到 gzip、客户端都拿到解码后的 Map，**手动注入零收益**。故裁定 **`GzipInterceptor` 不手动注入 `Accept-Encoding`**，预留注入开关**默认关并固化**（任何注入逻辑须先有新实测结论回写本节才允许添加）。
3. 自动解压后 `content-encoding: gzip` 与压缩态 `content-length` 响应头**仍保留**，故压缩后（线上）字节数可直接读 `content-length`；与「解压后字节数」同口径，体积统计不依赖是否手动注入该头。

**实测二：拦截器三方向执行序（见 §11.1 图注订正）**：dio 5.11.1 三个方向均按 `Interceptors.add` 添加顺序执行（FIFO），并非旧图注所称返回/错误向「自下而上」。该结论决定了 Gzip 在返回向上**先于** Envelope 运行，故其「解压后字节数」量到的是**完整信封**（拆包前）明文。

## 12. 错误码集中枚举与行为映射

### 12.1 枚举（24 个 + `ok`，与后端 §2.3 逐个对齐）

```dart
/// 客户端错误码枚举。
///
/// 与服务端 ErrorCode 枚举一一对应，唯一口径源同为 PRD §12.5。
/// [behavior] 决定拿到这个码之后客户端做什么，是本枚举存在的主要价值 ——
/// 没有它，每个 catch 点都会自己发明一套处理逻辑。
enum ApiErrorCode {
  ok(0, ErrBehavior.none),
  // --- 4xx 确定性失败：提示用户，不重试 ---
  paramInvalid(40001, ErrBehavior.deterministicFail),
  agreementRequired(40002, ErrBehavior.deterministicFail),
  unauthorized(40101, ErrBehavior.refreshToken),       // 走 §13，不走本表其他分支
  loginLocked(40105, ErrBehavior.promptWithRetryAfter),
  detailQuotaUsed(40301, ErrBehavior.deterministicFail),
  qualificationNeeded(40302, ErrBehavior.deterministicFail),
  categoryBanned(40303, ErrBehavior.deterministicFail),
  publishLimit(40304, ErrBehavior.deterministicFail),
  noPermission(40305, ErrBehavior.deterministicFail),  // 后台专用，App 端正常不应收到
  sensitiveWord(40901, ErrBehavior.deterministicFail),
  imageRejected(40902, ErrBehavior.deterministicFail),
  versionConflict(40903, ErrBehavior.forceRefetch),    // 唯一需要强制重取的码
  postGone(41001, ErrBehavior.deterministicFail),
  // --- 429 限流类：不可自动重试，展示剩余秒数 ---
  aiQuotaExceeded(42901, ErrBehavior.promptWithRetryAfter),
  contactLimit(42902, ErrBehavior.promptWithRetryAfter),
  circuitBroken(42903, ErrBehavior.promptWithRetryAfter),
  pushLimit(42904, ErrBehavior.promptWithRetryAfter),
  smsLimit(42905, ErrBehavior.promptWithRetryAfter),
  trackLimit(42906, ErrBehavior.silentRequeue),        // 唯一不向用户呈现的码
  guestDetailLimit(42907, ErrBehavior.promptWithRetryAfter), // 提示须附登录入口
  // --- 5xx 可自动重试 ---
  internalError(50001, ErrBehavior.autoRetry),
  aiUnavailable(50301, ErrBehavior.autoRetry),
  certUnavailable(50302, ErrBehavior.autoRetry),
  geoUnavailable(50303, ErrBehavior.autoRetry),
  // --- 客户端本地码（不来自服务端，不占服务端码段）---
  networkFailure(-1, ErrBehavior.autoRetry),           // 超时 / 连接失败
  parseError(-2, ErrBehavior.deterministicFail);       // 响应不符契约

  const ApiErrorCode(this.code, this.behavior);
  final int code;
  final ErrBehavior behavior;
}
```

**两个本地码用负数**，理由：服务端码段全是正数且前 3 位对齐 HTTP 状态码，负数永远不会与服务端新增码撞车。

### 12.2 五类行为（架构 §6.6 的四分类 + `refreshToken` 单列）

| 行为 | 覆盖码 | 客户端动作 |
| --- | --- | --- |
| `autoRetry` | `50001` `50301` `50302` `50303` `networkFailure` | 按 §14 自动退避重试，**总共 2 次**；仍失败则降级为确定性失败提示 |
| `promptWithRetryAfter` | `40105` `42901`–`42905` `42907` | **不自动重试**。弹提示并展示服务端 `Retry-After` 秒数换算的文案（如「请 58 秒后再试」），由用户显式点击重试。**`42907` 例外之处**：其提示除倒计时外**必须带登录入口**，因为登录就是该限频的唯一解除方式（已登录不受此限，后端 §3.4） |
| `silentRequeue` | `42906` | 埋点事件退回本地队列**头部**，按 `Retry-After` 延后。**全程不打扰用户** |
| `forceRefetch` | `40903` | 必须先 `GET /posts/{id}` 拿新 `version` 与新 `status`，用新状态刷新界面，再由用户决定是否重新提交。**禁止自动带新 version 重发** —— 用户看到的状态可能已经变了 |
| `deterministicFail` | 其余全部 | 展示 `message` + `request_id`，不重试 |
| `refreshToken` | `40101` | 走 §13 单飞续期，**不进入上述任何分支** |

### 12.3 一条容易写错的分支

`40903`（版本冲突）与 `40001`（参数非法）看起来都是「用户改一下再提交」，但处理完全不同：

- `40903` → 重取后再提交**通常会成功**，所以要给「刷新并重试」按钮。
- `40001` → 重试结果**必然相同**，给重试按钮等于骗用户。特别是 `PATCH /posts/{id}/status` 不传 `version` 时服务端返 `40001`（后端 §5.3.3 明确不兜底），这是客户端缺陷，应该在开发期就被测试拦住，而不是给用户一个重试按钮。

## 13. `40101` 单飞续期

### 13.1 时序

```
  请求 A ──┐
  请求 B ──┼── 全部收到 40101（或在续期期间新发起）
  请求 C ──┘
            │
            ▼
   ① 立刻暂停：in-flight 请求与新发请求全部挂起进 _pendingQueue
            │
            ▼
   ② 单飞：只有第一个触发者调 POST /auth/token/refresh
      （_refreshing 标志 + Completer 共享，实际调用次数必须 == 1）
            │
     ┌──────┴──────┐
   成功            失败
     │              │
     ▼              ▼
   ③ 写新 Token   ④ 清会话 + 清挂起队列 + 跳登录页
     重放队列        （不重放，不静默失败）
     （沿用原
      X-Interaction-Id
      与 Idempotency-Key，
      逐字相同）
```

> **编码落地订正注记（2026-09-12，U5 `AuthRefreshInterceptor`）**：上图分支④
> 「失败即无条件清会话」在编码期细化为 **R10 三分流**（弱网不得踢人），判定
> 只引用 `ApiErrorCode` 既有枚举与「码对齐 HTTP（`code ~/ 100`）」不变量：
>
> | 续期失败类别 | 判定 | 会话动作 | 挂起请求结局 |
> | --- | --- | --- | --- |
> | ① 认证类 | refresh 自身再回 `40101` 或 403 段 | leader **唯一一次**清会话（`onSessionCleared`），`writeToken` 0 次 | 不重放，各自保留**原始业务请求的 40101**（不拿 refresh 异常替换） |
> | ② 限流类 | refresh 回 429 段 | **不清会话** | 不重放，以携带 `retryAfterSec`（整数秒 `Retry-After`）的 refresh 异常结束 |
> | ③ 瞬时类 | 网络失败（连接拒绝/超时）/ 5xx / 解析失败等 | **不清会话** | 不重放，异常透传（5xx 与传输错误归一为 `networkFailure(-1)`）；重试是 U6 `RetryInterceptor` 的唯一职责，本拦截器不含任何重试/退避 |
>
> 另有**代次变更（stale）**：续期在途期间会话被登出/换号（`readSessionEpoch`
> 发起取样与写回前比对不一致）或旧 Token 已不存在 → 丢弃新 Token（不
> `writeToken`）、不重放，挂起请求按清会话语义以各自原始 40101 结束。
>
> 落地形态补充（均有真实 HTTP 测试固化）：
> - 单飞字段为共享 `Future<RefreshVerdict>?`，leader 在方法内**全量 catch 把
>   异常收敛为返回值**（`future.ignore()`），挂起分支只 await 同一 Future 后
>   switch，杜绝共享失败 Future 的 unhandled exception；结论落定即清空单飞
>   字段，下一轮 40101 可重新续期；续期期间新到达的 40101 同样挂起共享。
> - 续期请求经**独立 dio**（`buildRefreshDio`，仅挂 Header + Envelope，不挂
>   AuthRefresh/Retry/Gzip），物理隔离防递归续期与嵌套重试。
> - 重放统一经业务 dio 的 `dio.fetch` 重走全链：两键由 HeaderInterceptor
>   「containsKey 才写」逐字保全，`Authorization` 按「每次重写」用新 Token
>   换新，是重放请求**唯一**允许变化的头；extra 置 `auth_refresh_retried`
>   标记，重放仍 40101 时直接失败不二次续期（防循环）。
> - 取消语义：`DioExceptionType.cancel` 裸穿透不触发续期；挂起 follower 在
>   结论落定前被 `CancelToken` 取消不影响共享续期（leader 不中断），该请求
>   不重放，以 cancel 落调用方。

### 13.2 三个必须有测试断言的点

| 断言点 | 断言内容 | 不断言的后果 |
| --- | --- | --- |
| 单飞 | 并发 5 个请求同时收 `40101`，`/auth/token/refresh` 的**实际调用次数 == 1** | 5 个并发续期，服务端旧 Token 可能已失效，后 4 次全失败并把用户踢下线 |
| `X-Interaction-Id` 沿用 | 重放请求头与原请求**逐字相同** | 埋点分母被伪造：一次交互被记成两次 |
| `Idempotency-Key` 沿用 | 重放请求头与原请求**逐字相同** | 续期后重放的写请求变成新请求，可能重复发帖 |

### 13.3 不做本地过期判断

单 Token 模型、有效期 30 天。客户端**不解析 JWT 的 `exp`、不做本地过期预判**，只被动响应 `40101`。理由（架构 §6.7）：客户端时钟可被用户任意修改，本地预判会在时钟被调快时把有效会话误判为过期、把用户无谓踢下线。**以服务端为准是唯一口径。**

## 15. Provider 异步化改造链

### 15.1 现状与目标

现状（[listing_repository.dart](file:///d:/developer/code/aicoding/s2s/lib/features/discovery/listing_repository.dart#L130-L142)）：`allListingsProvider` 是同步 `Provider<List<Listing>>`，返回本地样例或压测数据。整条链 `allListings → filteredListings → sortedListings → listingDetail` 全同步。

**这不是实现细节，是排期风险**（架构 §9.2 原文）：若按「服务端做完客户端接上就行」估工，会在内测包前才发现状态层要整体改写。

| Provider | 现状 | 目标 |
| --- | --- | --- |
| `allListingsProvider` | `Provider<List<Listing>>` | `FutureProvider<List<Listing>>`，内部调 `/posts/search` 或 `/map/pins` |
| `filteredListingsProvider` | `Provider`，本地 `where` | **筛选下推服务端**（分类、供需、半径、关键词均为接口入参），本 Provider 退化为 `AsyncValue` 转发 |
| `sortedListingsProvider` | `Provider`，本地排序 | 排序仍在客户端（服务端不承诺排序），但输入变 `AsyncValue`，需处理 `loading`/`error` |
| `listingDetailProvider` | `Provider.family<ListingDetail?, String>` | `FutureProvider.family`，调 `/posts/{id}`；`40903` 触发 `ref.invalidate` 强制重取 |
| `stressLevelProvider` 分支 | 在 `allListingsProvider` 里切换压测数据 | **保留**。POC-B 要测的是首页完整链路，绕开筛选与信息卡会让数字偏乐观 |

### 15.2 请求竞态：先发后到必须丢弃

架构 §9.2 明确点名的坑：**快速连续切换分类时，先发的响应可能后到，必须丢弃过期响应。**

Riverpod 的 `FutureProvider` 在依赖变化时会自动丢弃旧结果，但**只在依赖真正变化时**。以下两种情况它管不了，必须自己处理：

| 情况 | 处理 |
| --- | --- |
| 同一 Provider 内手动触发多次刷新（下拉刷新连点） | 用 dio `CancelToken`：发新请求前 `cancel()` 上一个。`ref.onDispose(token.cancel)` 保证页面销毁时也取消 |
| 请求已在途，用户切走页面 | 同上。**请求要取消，但埋点事件必须上报**（`result=cancelled`），口径见下 |

**「取消」到底上报什么 —— 消除一处口径矛盾：**

本文档早期版本在此处写「取消的请求不上报埋点」，而 §17.2 写「`cancelled` 会话必须上报」，字面直接冲突。现统一口径如下，**§17.2 的写法为准**：

| 对象 | 处理 | 理由 |
| --- | --- | --- |
| 在途 HTTP 请求 | **取消**（`CancelToken.cancel()`） | 省流量、省渲染、避免旧响应覆盖新结果 |
| `layer_switch` 埋点事件 | **上报**，`result=cancelled`、`fail_reason=cancelled` | 不上报就无法区分「被用户取代」与「客户端崩了压根没上报」。后者是缺陷，前者不是，混在一起等于放弃了这个信号 |
| 该事件是否计入成功率分母 | **不计入**（可观测性 §4.2 轴② 口径） | 用户主动改变意图，不算系统失败 |

所以「不污染 P95」这个目标是通过**分母排除**达成的，不是通过**不上报**达成的。两者的区别很关键：不上报会一并丢掉「取消发生的频率」这个信息 —— 而取消率突然升高，恰恰是「首屏太慢导致用户反复重试」的典型信号。

`duration_ms` 在 `cancelled` 事件里仍然照实记录（从交互起点到取消时刻），四段耗时也照实记录（未开始的段记 0）。它进的是 `cancelled` 这个桶，不进 P95 计算，所以不存在污染。

```dart
/// 按筛选条件拉取信息列表。
///
/// 竞态处理：每次筛选条件变化都会重建本 Provider，旧的 CancelToken 在
/// onDispose 中被取消。若不取消，快速切分类时先发的响应可能后到并覆盖
/// 新分类的结果 —— 表现为「明明选了 A 类目，列表里却是 B 类目的内容」。
final filteredListingsProvider = FutureProvider<List<PostCard>>((ref) async {
  final filter = ref.watch(discoveryFilterProvider);
  final token = CancelToken();
  ref.onDispose(token.cancel);
  return ref.read(postRepositoryProvider).search(filter, cancelToken: token);
});
```

### 15.3 三态在 UI 上的落地

`AsyncValue` 三态必须**逐页**处理，不允许 `.value!` 强解。

| 态 | UI |
| --- | --- |

### 16.3 `grid_id`：Dart 实现必须与 Java / SQL 逐位一致

这是全项目**唯一一处三方（Dart / Java / SQL）必须逐位一致的算法**。不一致的后果不是报错，而是客户端缓存键与服务端缓存键错位、命中率长期偏低且查不出原因。

```dart
/// 计算约 500m 网格的 grid_id（与服务端 GridIdCalculator 逐位一致）。
///
/// 算法四步（顺序不可调换）：
///   1. 先把坐标向下取整到 5 位小数：(deg * 100000).floor()
///   2. 转入【整数微度域】运算，避免浮点累积误差
///   3. 以 450 微度（0.0045°，约 500m）为步长，用向下取整（向负无穷）
///   4. 编码为 "{gx}_{gy}"
///
/// [lng] 经度
/// [lat] 纬度
/// 返回：形如 "12345_6789" 的网格 ID，负数保留减号（正则 ^-?\d+_-?\d+$）
String gridIdOf(double lng, double lat) {
  final int lngMicro = _floorToMicroDegree(lng);
  final int latMicro = _floorToMicroDegree(lat);
  // Dart 的 ~/ 对负数是向零截断，与 Java 的 Math.floorDiv 语义不同，
  // 必须用 (a / b).floor() 才能得到向负无穷取整。
  final int gx = (lngMicro / _stepMicro).floor();
  final int gy = (latMicro / _stepMicro).floor();
  return '${gx}_$gy';
}

/// 将度数向下取整到 5 位小数并转为整数微度（1 微度 = 1e-5 度）。
///
/// 必须用 .floor() 而非 .toInt()：.toInt() 对负数是向零截断，
/// 会让 -0.000015 落到 0 而不是 -1，与测试向量第 9 条冲突。
int _floorToMicroDegree(double deg) => (deg * 100000).floor();
```

**两处 Dart 特有的陷阱**（Java 侧不存在，因此代码不能照抄 Java）：

| 陷阱 | Java 写法 | Dart 正确写法 | 照抄的后果 |
| --- | --- | --- | --- |
| 向下整除 | `Math.floorDiv(a, b)` | `(a / b).floor()` | Dart 的 `a ~/ b` 对负数向零截断，南半球/西半球坐标网格全错 |
| 向下取整转整数 | `(long) Math.floor(x)` | `x.floor()` | `x.toInt()` 是截断，负坐标错一格 |

测试向量与服务端**共用同一份 10 条向量表**（后端 §5.4.1）。其中：

- **第 9 条 `(-0.000015, -0.000015) → "-1_-1"` 是唯一能暴露「用截断代替 floor」的向量**，但它的最终结果偶然正确（截断得中间微度 -1、floor 得 -2，两者除以 450 向下取整后都是 -1）。因此这条向量**必须额外断言中间微度值 == -2**，只断言最终 `grid_id` 等于白测。

```dart
test('向量9：负小坐标，必须额外断言中间微度值', () {
  // 只断言 gridIdOf 结果会漏掉 bug：截断与 floor 在本例最终结果相同
  expect(gridIdOf(-0.000015, -0.000015), '-1_-1');
  // 这一行才是真正的探针
  expect(floorToMicroDegreeForTest(-0.000015), -2);
});
```

### 17.1 `layer_switch` 12 字段（可观测性 §4.1.1 唯一权威定义）

### 17.2 四段计时纪律（最容易实现错的一处）

```
手指离开 Tab ─┬─ t_cache 起 ── 查本地缓存 ── t_cache 止
              │
              ├─ t_net   起 ── /map/pins ─── t_net   止   （缓存命中则为 0，不打点直接置 0）
              │
              ├─ t_agg   起 ── Dart 聚合 ─── t_agg   止   （mode=cluster 则为 0）
              │
              └─ t_render起 ── 首屏绘制 ──── t_render止
   duration_ms 由整段交互的起止时间戳【独立】算得
```

| 纪律 | 内容 | 违反的表现 |
| --- | --- | --- |
| 四段各自独立 `Stopwatch` | **任何一段都不允许由 `duration_ms` 减其他段得到** | 恒等式永远成立但 `t_render_ms` 是无意义余数 —— 校验通过、数据全错 |
| `duration_ms` 也独立测 | 不是四段相加 | 两条路径失去互相校验能力，恒等式没有信息量 |
| 恒等式容差 ±1ms | `abs(四段和 - duration_ms) > 1` 的事件从 P95 分母剔除并告警 | 漏计一段会表现为「P95 突然变好了」，是最难发现的指标错误 |
| `t_net_ms` 与服务端 `rt_ms` 差 ≤50ms | 同 `interaction_id` 交叉核对，由**服务端**执行 | 这条无法被客户端自证，是唯一防篡改校验 |

`cancelled` 单独说明：用户快速连续切分类时，先发起的交互被后一次取代。这类会话**不计入轴② 分母**（不是失败，是用户改变意图），但**必须上报** —— 否则无法区分「被取代」与「客户端崩了没上报」。这与 §15.2 的 `CancelToken` 是同一件事的两面：请求要取消，事件要上报。

| 上报触发 | 满 `NfrApi.trackBatchMaxEvents` 条、或距上次满 30 秒、或应用进入后台，三者任一 |
| 失败退回 | 上报失败（含 `42906`）退回**队列头部**，按 §14 退避延后，**不丢弃**。重发时的幂等键规则见 §17.4.1 —— **这一条搞错会静默丢事件** |
| 回灌限速 | 离线积压恢复联网后按 `NfrApi.trackBatchMaxEvents` 一批、批间 ≥1 秒。否则会自己触发 `42906` |
| 未登录事件 | 本地缓存，**登录后补报**（该接口要求登录态） |

#### 17.4.1 埋点批次重发的幂等键：必须换新 Key（与 §11.1.1 相反）

**这是 P0，症状是「事件静默丢失，而所有日志都显示成功」。**

先看两条规则叠在一起会发生什么：

- §17.4「失败退回队列**头部**」—— 失败的这批事件会被重新组批发送；
- §11.1.1「重试必须沿用原 `Idempotency-Key`」—— 若无脑照搬，重发就带着旧 Key。

而服务端的幂等实现是（后端 §3.3）：Redis 键 `idem:{userId}:{Key}`，命中即**直接返回首次的成功响应 JSON**，业务逻辑一行都不执行。

于是这个链条成立：

```
第 1 次上报 50 条  → 服务端写库成功，缓存 code=0 → 网络在响应回传途中断了
                    ↓ 客户端只看到超时，判为失败
退回队列头部       → 重新组批
第 2 次上报（旧 Key）→ 服务端命中幂等缓存，直接回 code=0
                    ↓ 客户端判为成功，从队列移除这 50 条
结果：数据其实第 1 次就落库了 —— 这种情况下行为正确。
```

上面这种情况是**幂等本该起的作用**，没问题。真正的问题在下一种：

```
第 1 次上报 50 条  → 服务端返 42906（限频），一条未落库
退回队列头部       → 期间又新采集了 20 条
第 2 次组批        → 这批是【前 50 条中的部分 + 新 20 条】，内容已经变了
   若沿用旧 Key    → 服务端命中幂等缓存 → 直接回 code=0
                    ↓ 客户端判为成功，把这 70 条全部从队列移除
结果：70 条事件【一条都没落库】，但客户端与服务端都认为成功。
```

第二种情况的致命之处：**它不产生任何错误日志**。`dropped_count` 也不会 +1（那个计数只统计容量溢出丢弃）。数据就是没了，而所有可观测性指标都是绿的 —— 可观测性系统自己成了盲区，这是最坏的一类缺陷。

> 注意这里还踩了服务端幂等的另一条规则：后端 §3.3 明确「重复 Key 但请求体不同，须返回首次结果」。也就是说服务端**故意不校验请求体差异**（那是幂等的正确语义），所以这个防线只能建在客户端。

**规则：埋点批次每次组批都生成新的 `Idempotency-Key`。**

```dart
/// 组装一个上报批次。
///
/// 幂等键策略与 §11.1.1 的普通写接口【相反】：这里每次组批都生成【新的】Key。
///
/// 理由：普通写接口的重试重发的是【同一笔业务意图】，沿用 Key 才能防重复下单；
/// 而埋点批次退回队列头部后，会与新采集的事件重新组批 —— 内容已经不同，
/// 却复用旧 Key，服务端就会命中幂等缓存直接返回首次的 code=0，
/// 客户端误判成功并把事件从队列移除，导致【静默丢失且无任何错误日志】。
///
/// [events] 本批事件，条数上限 NfrApi.trackBatchMaxEvents
/// [droppedCount] 自上次成功上报以来因容量溢出丢弃的条数
/// 返回：可直接发送的批次对象，含新生成的幂等键
TrackBatch buildBatch(List<TrackEvent> events, int droppedCount) {
  return TrackBatch(
    // 每批一个新 Key。批次是「一次传输动作」，不是「一笔业务意图」
    idempotencyKey: _uuid.v4(),
    interactionId: _batchInteractionId(),   // 见 §17.4.2
    events: events,
    droppedCount: droppedCount,
  );
}
```

**这与 §11.1.1 不矛盾，两者管的是不同的东西：**

| | 普通写接口（发帖、联系） | 埋点批次 |
| --- | --- | --- |
| 幂等键代表 | 一笔**业务意图**（这条帖子只能发一次） | 一次**传输动作** |
| 重发时内容 | 逐字不变 | **可能变**（与新采集事件重新组批） |
| 沿用旧 Key 的后果 | 正确 —— 防止重复创建 | **错误** —— 服务端跳过写入，事件静默丢失 |
| 换新 Key 的后果 | 错误 —— 可能重复创建 | 正确 —— 每批都真正执行一次 |
| 因此 | `containsKey` 判存在，不覆盖 | 每次组批 `uuid.v4()` |

**重复写入风险如何兜住：** 换新 Key 意味着上文第一种情况（响应丢在回程）会导致同一批事件被写两次。这个代价是可接受且可消解的，因为服务端按**事件维度**去重，而不依赖幂等键。**该约束已在 DDL 中固化**（2026-09-06，缺口 #7 已关闭）：

- 埋点库唯一索引 `uk_event_dedup(interaction_id, event_name, user_id, ts)`，见 `V1__init_track_schema.sql` 与《数据库设计文档》§3.16.1；
- 落库语句为 `INSERT ... ON DUPLICATE KEY UPDATE id = id`（**不是** `INSERT IGNORE`）；
- 行为由 `assert_behavior.sh` 的 A8（5 个子断言）守护。

**这给客户端带来三条硬性约束**，因为去重键的四列有三列来自客户端：

| 字段 | 客户端必须保证 | 违反后的表现 |
|---|---|---|
| `interaction_id` | 事件入队时确定，重传**逐字不变** | 每次重传都判为新事件，去重完全失效 |
| `ts` | 取采集时刻、**带毫秒精度**，重传不重新取值 | 只到秒会误丢同秒内的多次同名事件；重新取值则去重失效 |
| `event` | 与契约枚举逐字一致 | 同一事件被记成两种名字，指标分裂 |

最容易犯的错是**在上报前"补全"字段**：例如发现某个事件缺 `ts` 就用当前时间补上、或重传时刷新 `ts`。这类"修复"会让去重键在每次重传时都变化，**索引还在、不报错、只是不再挡住任何东西**。因此纪律是：**事件一旦入队，其去重键三列即冻结**，上报器只做读取和序列化，不做任何加工。

方向上这是刻意的取舍：**宁可重一条，不可丢一条。** 埋点数据重复可以在分析侧去重，丢失则永久不可恢复。反向代价是「同一交互内同毫秒的合法重复事件会被丢弃」，故**新增事件类型时必须先核验它是否可能同毫秒重复触发**（当前五个事件都是用户级离散动作，不满足该条件）。

#### 17.4.2 埋点批次的 `X-Interaction-Id` 从哪来

契约把 `X-Interaction-Id` 定为**全局 required**（`openapi.yaml` → `XInteractionId` parameter），但埋点上报是本系统里唯一没有"交互起点"的调用场景：

| 场景 | 问题 |
| --- | --- |
| 定时触发（距上次 30 秒） | 没有任何用户交互触发它 |
| 进后台触发 | 用户正在离开，不属于任何进行中的交互 |
| 登录后补报 | 事件是登录前采集的，原交互早已结束 |
| 离线回灌 | 一批 50 条可能来自**几十个不同的交互** |

最后一条说明「让批次沿用某一个事件的 `interaction_id`」是错的 —— 挑哪一条都是错的，会把整批的排查线索指向一个无关的交互。

**规则：批次级 `X-Interaction-Id` 由上报器**为每个批次**新生成一个，语义是「这次传输动作」，不是「某个用户交互」。** 事件自身的 `interaction_id` 保留在**事件体内**（`TrackEvent.interaction_id` 字段，契约已有），两者互不覆盖。

| 层级 | 字段位置 | 语义 | 谁生成 |
| --- | --- | --- | --- |
| 批次 | HTTP 头 `X-Interaction-Id` | 这一次上报传输动作 | 上报器，每批新生成 |
| 事件 | 请求体 `events[].interaction_id` | 该事件所属的用户交互 | 交互起点，采集时写入 |

这样契约的 required 得到满足，排查链路也没断：想查某个交互，用事件体里的 `interaction_id`；想查某次上报为什么失败，用批次头上的。

**同时必须明确批次头 `X-Interaction-Id` 不参与重发沿用。** 它和 §17.4.1 的幂等键同步：**每次组批一起换新**。理由一致 —— 它标识的是"这次传输"，重新组批就是一次新传输。

两条与其他章节的耦合：

- `/track/events` 要求登录态，`user_id` **取自登录态而非请求体**（后端 §5.8）。因此未登录期采集的事件在补报时不能自己填 `user_id`。
- 回灌限速与 §14 的重试是**两套独立机制**：限速管的是正常回灌节奏，重试管的是失败后的退避。不要把回灌实现成「靠重试驱动」，那会在离线积压时把 2000 条事件全变成重试。

## 20. 交付物矩阵补项

架构 §9.2 的 10 行矩阵漏了下面两件事，本节补上。§10.4 已覆盖第 12 项，此处只写第 11 项，并附一条与之相关的 UI 文案纪律。

### 20.1 联系外呼与降级（矩阵第 11 项，PRD §7.8）

这是 Batch1 P0 闭环的**最后一步**。链路是：看到帖子 → `GET /posts/{id}/contact` 拿到联系方式 → **实际打出这个电话**。前三步矩阵都覆盖了，第四步没人管 —— 而没有第四步，整个产品的核心价值不成立。

依赖 `url_launcher`（[pubspec.yaml](file:///d:/developer/code/aicoding/s2s/pubspec.yaml) 已在用）。

| 动作 | URI scheme | 降级路径 |
| --- | --- | --- |
| 拨号 | `tel:<号码>` | `canLaunchUrl` 返 false（平板、无 SIM 卡设备）→ **不弹「失败」**，改为「复制号码到剪贴板 + Toast 提示已复制」 |
| 发短信 | `sms:<号码>` | 同上，降级为复制 |
| 唤起导航 | 高德/百度 scheme | iOS 需 `LSApplicationQueriesSchemes` 白名单（§18.1 已登记为缺失项）；未装任何地图 App → 降级为复制地址文本 |

**三条纪律：**

1. **`canLaunchUrl` 的返回值必须判，且判 false 不等于报错。** iOS 上未声明白名单的 scheme 会**恒返 false**（§18.1），这时"打不开"的根因在配置不在设备，弹一个「拨号失败」的错误只会误导用户去检查自己的手机。降级到复制是唯一体面的处理。
2. **联系方式只能来自 `GET /posts/{id}/contact` 的响应，用完即弃。** 不写本地缓存、不写日志、不进埋点属性。它是全系统唯一的联系方式出口（后端 §5.5.1），客户端侧也必须保持这个唯一性 —— 一旦落到本地存储，加解密与 AAD 绑定那一整套服务端防护就被绕过了。
3. **外呼动作本身要埋点，但不带号码。** 事件记录「用户点了拨号」这个行为与是否走了降级分支，属性里**不含**任何联系方式内容。

### 20.2 限频提示文案不得承诺剩余次数

`ContactInfo.remaining_today` 只反映**账号维度**的剩余次数，但服务端限频实际有**四个维度**（账号 / 设备 / IP / 熔断，后端 §3.4）。

于是这个场景成立：

```
UI 显示「今日还可查看 3 次」
用户点第 2 次 → 服务端因【设备维度】超限返 42902
UI 只能说「已达上限」
```

用户看到的是应用先承诺 3 次、然后在第 2 次就自我否定。这不是限频策略的问题（多维限频是必要的风控），而是**UI 把一个维度的数字当成了全局承诺**。

**规则：**

| 做 | 不做 |
| --- | --- |
| 「今日剩余 3 次（以实际请求结果为准）」 | 「今日还可查看 3 次」 |
| 收到 `42902` 时按 `Retry-After` 展示倒计时，文案只说「已达上限，请 X 分钟后再试」 | 追问/解释是哪个维度超限（服务端刻意不区分，风控信息不外泄） |
| 拿到 `42902` 后**立即把本地显示的剩余次数刷成 0** | 继续显示 `remaining_today` 的旧值 |

最后一条尤其重要：如果不刷成 0，用户会看到"还剩 3 次"和"已达上限"同时在屏幕上，这是应用在自相矛盾。

**服务端侧不改。** 让 `remaining_today` 汇总四个维度的最小值在技术上可行，但会把风控阈值直接暴露给客户端（攻击者能反推出设备维度的限额），得不偿失。正确的解法是客户端不把它当承诺。

**`42907` 同样适用本节全部规则，且更严格**（2026-09-06 G2 裁定新增）：未登录详情浏览限频**根本没有任何剩余次数字段**下发到客户端 —— `PostDetail` 不含浏览计数，客户端也不得自行在本地累计次数来「预测」何时会超限。原因与上面同源：设备维和 IP 维的计数在服务端，客户端本地计数永远不等于服务端计数（多设备共享 IP、应用重装、清缓存都会错位），一旦本地预测与服务端判定不一致，就又制造了一次「自相矛盾」。

| 做 | 不做 |
| --- | --- |
| 收到 `42907` 才提示，文案「今日浏览次数较多，登录后可继续查看」+ 登录入口 | 提前提示「今日还可浏览 N 条」 |
| 提示只说「浏览次数较多」 | 说明是设备还是 IP 超限、或透出 30 / 100 这两个阈值 |
| 用户完成登录后**直接重试原请求**（已登录不受此限） | 登录后仍沿用 `Retry-After` 倒计时阻断用户 |
