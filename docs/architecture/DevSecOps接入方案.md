## 3. 门禁总体设计

### 3.1 三层拦截点与职责分工

```
  开发者本地                              发内测包时
┌──────────────┬──────────────────┐   ┌──────────────────┐
│  L1 提交前    │  L2 提交后/本地   │   │  L3 出包门禁      │
│  pre-commit  │  完整校验         │   │  release-gate    │
├──────────────┼──────────────────┤   ├──────────────────┤
│ 秒级         │ 分钟级            │   │ 分钟级 + 产物扫描 │
│ 格式 / lint  │ 全量单测          │   │ 后门剔除验证      │
│ 敏感串扫描   │ 保留键覆盖测试     │   │ 签名验证          │
│ 密钥泄露扫描 │ 红线 grep 审计     │   │ 留证归档          │
├──────────────┴──────────────────┴───┴──────────────────┤
│  失败即 exit 1，不提供 --no-verify 之外的绕过方式        │
└─────────────────────────────────────────────────────────┘
```

**为什么把重活放 L2/L3 而不全塞进 L1**：pre-commit 一旦超过数秒，开发者会开始用 `--no-verify`，门禁形式化。L1 只做「秒级且必然快」的检查。

**为什么不用远端 CI 做主执行体**：已确认本期零自动化，且即便未来引入，Flutter + Java 双工具链在 runner 上每次冷启动的耗时与额度消耗，对单人项目不划算。**门禁的判据定义与执行载体解耦** —— 同一份判据可以由本地脚本执行，也可以将来由 CI 执行，规格不变。

### 3.2 一条贯穿全文的判定原则（引自可观测性 §10）

> **每一道门禁都必须有：执行者、工具与命令、失败判定、留证方式。**四者缺一即视为未定义。

单人项目里判定权与被判定对象是同一个人，所以「留证」不是形式主义，是唯一的约束。本方案每一道门禁都按这四项描述。

### 3.3 明确不引入的工具（避免范围蔓延）

| 不引入 | 理由 |
| --- | --- |
| SonarQube / SonarCloud | 2 核 2G 跑不动；云版免费额度对私有仓有限制；本项目代码量下收益远低于运维成本 |
| Snyk / Dependabot / OWASP Dependency-Check | 依赖数量少（Flutter 12 个运行时依赖）且全为主流包；**改为 §3.4 的人工季度复核** |
| Trivy / 镜像扫描 | 基础镜像为官方 `openjdk` / `mysql` / `redis`，跟随官方 tag 更新即可 |
| DAST / 渗透测试工具 | 无预算；🔴 阻塞项已有明确的手工实测方法（安全方案 §13） |
| 密钥管理服务（KMS / Vault） | 131 元/年预算；架构 §4.4 已定案用 `.env` |

**这是一份主动放弃清单，不是遗漏清单。** 每一项在 Batch2 有收入或有第二个人加入后应重新评估。

### 3.4 依赖安全的替代做法（人工季度复核）

不引入 SCA 平台，改为一条可执行的人工纪律：

| 项 | 规格 |
| --- | --- |
| 频率 | 每季度一次，或发版前一次（取更近者） |
| 客户端 | `flutter pub outdated`，逐个查 changelog 中是否有 security fix |
| 服务端 | `mvn versions:display-dependency-updates` |
| 判定 | 有 security fix 的依赖**必须升**；仅功能更新的不升（版本锁定优先，见 §7） |
| 留证 | 输出写入验收记录 |

## 4. L3 出包门禁（最高优先级，闭合阻塞项 B-1 / B-2）

这是本方案**唯一直接闭合安全漏洞**的门禁，规格来自架构 §9.2.2，本方案将其可执行化。

### 4.1 后门剔除三层判据

| 层 | 检查对象 | 命令（规格） | 通过判据 |
| --- | --- | --- | --- |
| **源码层** | `lib/` 全部 Dart 源码 | `grep -rn "888888" lib/` | 命中行**必须全部位于 `kDebugMode` 分支内**，逐行人工确认；无法确认即失败 |
| **编译期** | release 构建配置 | 代码评审 | 后门代码由 `if (kDebugMode) { ... }` 包裹，使 tree-shaking 可剔除；**禁止用 `assert` 兜底** |
| **产物层** | 构建出的 APK | `strings <apk>` 后分别 `grep -c '888888'` 与 `grep -c 'debugCode'` | **两个计数必须均为 0**，任一非 0 则 `exit 1` |

**产物层是唯一有效的最终判据**，其余两层是辅助。理由：源码层的 grep 只能证明「代码写对了」，产物层的扫描才能证明「编译器真的剔除了」。两者之间存在真实的失效可能 —— 例如后门字符串被放进了某个 `const` 映射表、或被某个非 `kDebugMode` 的调用点间接引用，此时源码看起来合规而产物中字符串仍然存在。

**判定者是脚本本身，不是人工目检**（架构 §9.2.2 原文要求）。

### 4.2 `release-gate.log` 留证规格

| 项 | 规格 |
| --- | --- |
| 路径 | `build/release-gate.log` |
| 生成时机 | 出包脚本执行时**自动**写入，不允许手工编辑 |
| 必含内容 | ① 执行时间戳 ② APK 路径与 SHA-256 ③ `888888` 计数 ④ `debugCode` 计数 ⑤ 签名验证结果（keystore 指纹） ⑥ 最终判定 PASS / FAIL |
| 归档 | **随内测包一起归档**，两者不可分离 |
| 缺失处置 | 该包**不得分发**（详设 §19 已列为前端自检项） |

**为什么日志要包含 APK 的 SHA-256**：否则日志无法与具体某个包绑定 —— 一份 PASS 的日志可以被拿去为另一个未检查的包背书。哈希是把「这份证明」与「这个产物」锁在一起的唯一方式。

### 4.3 签名门禁（闭合 B-2）

| 检查 | 判据 |
| --- | --- |
| release 构建**不得使用 debug 签名** | `apksigner verify --print-certs <apk>` 输出的证书指纹 ≠ debug keystore 指纹；等于则 `exit 1` |
| 签名指纹与 P7 备案材料一致 | 首次备案后把指纹写入脚本常量，此后每次出包比对；不一致则 `exit 1` |
| keystore 与口令的保管 | 等同安全方案 §4.4 的密钥等级：不入 git、权限 600、**独立备份**（丢失即无法覆盖升级，等于产品身份丢失） |

**签名指纹比对是一条容易被认为多余的检查，但它防的是最贵的事故**：换签名等于换应用身份 —— 需重新备案，且**所有老用户无法覆盖安装**。这类错误一旦发生无法回滚。

### 4.4 出包门禁完整检查序列（规格）

```
1. 确认工作区干净（git status 无未提交改动）—— 否则日志无法对应到确定的代码状态
2. 确认当前分支与 commit hash，写入日志
3. 源码层 grep 888888 → 人工确认全部在 kDebugMode 内
4. flutter analyze → 0 error（见 §7.2）
5. flutter test → 全绿
6. flutter build apk --release（含 --dart-define 注入高德 Key）
7. 产物层 strings + grep ×2 → 计数均为 0，否则 exit 1
8. apksigner 验签 → 非 debug 指纹且与备案指纹一致，否则 exit 1
9. 计算 APK SHA-256
10. 写 build/release-gate.log（含上述全部结果 + PASS/FAIL）
11. FAIL 时：删除产物 APK，防止误分发
```

**第 11 步是刻意的**：如果检查失败但产物还在磁盘上，人在赶工期时极可能直接把它发出去。物理删除比警告文案可靠。

**第 1 步同样不可省**：若工作区有未提交改动，日志中记录的 commit hash 与实际打包的代码不一致，整份留证失去意义。

## 5. L2 本地完整校验（服务端 + 客户端）

### 5.1 保留策略键覆盖门禁（`RetentionRuleCoverageTest`，Batch1 R17）

这是**唯一一个已被上游文档明确定义为「构建失败」的门禁**（PRD §13.4）。

| 项 | 规格 |
| --- | --- |
| 比对双方 | `RetentionRuleRegistry` 注册的 key 集合 ⟷ PRD §13.4「保留策略键」列 |
| 判据 | **逐值相等**（不是包含、不是子集） |
| 失败行为 | **构建失败**（普通单测失败即可达成，无需额外机制） |
| 9 个 key | `ocr_image_7d` / `transit_log_30d` / `favorite_deleted_30d` / `publish_memory_180d` / `deactivate_7d` / `post_archived_keep` / `audit_log_180d` / `exif_strip` / `location_no_collect` |

**一个实现上的选择题**：测试如何知道 PRD 里有哪些 key？两种做法 —— ① 在测试里硬编码 9 个 key 的期望集合 ② 写 Markdown 解析器读 PRD 表格。

**选 ①**。理由与 PRD §14.1 对 NFR 常量「本期手写而不上生成脚本」的判断一致：9 个 key 变更频率极低，写解析器不划算，且解析器本身会成为新的故障点。硬编码期望集合的代价是「PRD 改了要同步改测试」，但这**正是门禁想要的效果** —— 强制两处同时改，就是这条门禁的全部目的。

### 5.2 红线 grep 审计（安全方案 §3.2）

| 项 | 规格 |
| --- | --- |
| 审计项 | ① 联系方式出口 ② 身份证存储 |
| 搜索范围 | 见安全方案 §3.2（服务端 `*.java` + mapper XML + `resources/*.yml` + **`logs/` 日志文件** + `application*.yml`） |
| 自动化程度 | **半自动**：grep 可脚本化，但「这处出口是否合规」必须人工逐处判定 |
| 留证 | grep **完整输出（含命中行号）+ 逐处结论**写入验收记录；只写「已确认通过」视为未执行 |
| 时点 | `/contact` 出口审计在发内测包前；身份证审计在 Batch2 `cert` 域交付时 |

**为什么不能全自动**：`phone` 这个字段名出现在代码里不必然是违规 —— `phone_mask`（脱敏形式）是允许的，`phoneHash` 是允许的，`phone` 完整值出现在非 `/contact` 的响应对象里才违规。这个判断需要看上下文，脚本做不到。因此本项门禁的正确形态是「脚本负责穷举候选，人负责判定」，不能宣称全自动。

| `AuditLogWriter` 白名单测试 | 传入含 `phone` 与 `contact_value_enc` 的对象，输出 JSON **不含这两个键** | S8 |
| 审计同事务测试 | 让 `audit_log` 写入抛异常，断言 `/contact` 业务整体回滚（未返回联系方式） | S8 |
| 原图删除同事务测试 | 让原图删除抛异常，断言 `commit` 回滚且 `post_media` 无新行 | S5 |
| 注销完整删除测试 | 同时有 phone 与 wechat 两行 `user_identity` 的用户，到期后**两行都被删** | S9 |
| 启动校验测试 | 缺失 pepper 环境变量时应用**启动失败** | S4 |

**共同特征：它们防的都是「静默降级为不安全状态」** —— 系统看起来正常工作，但安全属性已丢失。人工检查抓不到这类问题（因为没有任何异常现象），只有断言能抓到。这也是这几项与其余自检项的分界线。

### 7.1 锁定口径

| --- | --- | --- |

| 基础镜像 | 明确 tag（如 `mysql:8.4`），**不用 `latest`** | — |

**已知的两处文档与仓库漂移**（须在编码期回写，属文档一致性问题不属门禁）：

| 漂移 | 详情 |
| --- | --- |
| `connectivity_plus` | 技术栈文档写 6.x，[pubspec.yaml](file:///d:/developer/code/aicoding/s2s/pubspec.yaml) 实为 `^7.0.0` |

### 7.2 Lint 强制化（现状最大的低成本收益点）

当前 [analysis_options.yaml](file:///d:/developer/code/aicoding/s2s/analysis_options.yaml) 只有 `include: package:flutter_lints/flutter.yaml`，28 行，无任何强制效力 —— `flutter analyze` 报 warning 不阻断任何流程。

| 建议 | 规格 |
| --- | --- |
| 强制点 | 出包脚本第 4 步：`flutter analyze` 必须 **0 error**（warning 不阻断） |
| 是否加自定义规则 | **本期不加**。理由：一次性引入大批 lint 规则会产出上百条历史违规，在 38 天工期内清不完，结果是规则被 `// ignore:` 淹没，比不加更糟 |
| `analyzer.errors` 升级 | 本期不配。Batch2 代码稳定后，按「一次只升一条规则、清完再升下一条」的方式渐进引入 |

**这是一条克制的建议**：把 lint 从「存在」变成「0 error 才能出包」已经能拦住绝大多数真实问题，而引入自定义规则集在当前工期下是净负收益。

### 7.3 密钥泄露的提交前扫描（L1）

| 项 | 规格 |
| --- | --- |
| 检查 | 提交内容中不得出现 `.env` 文件本身，不得出现 AK/SK 形态字符串、私钥 PEM 头（`-----BEGIN`）、高德 Key 形态 |
| 判据 | 命中即拒绝提交 |
| 兜底 | `.gitignore` 须覆盖 `.env`、keystore、备份目录 |
| 已泄露的补救 | **改密钥，不是删提交**。git 历史中的密钥即使 rebase 掉，也可能已被克隆 |

最后一行是本节唯一真正重要的一条：一旦密钥进了 git 并推送，**唯一有效的处置是作废并更换该密钥**。花时间清理 git 历史而不换密钥，是把精力用在了错误的地方。

## 8. 部署与配置的安全门禁

对应安全方案 §2 / §10，在 Compose 与 Caddy 落地时须验证：

| 检查 | 命令（规格） | 判据 |
| --- | --- | --- |
| 端口不外露 | `docker compose config` | app / mysql / redis 三个服务均**无 `ports:` 段** |
| 镜像不含密钥 | `docker history <镜像>` | 各层无 `COPY .env` 痕迹 |
| `.env` 权限 | 文件权限检查 | 600 |
| Redis 有口令 | 容器内 `redis-cli ping` 无口令时应被拒 | 无口令访问失败 |
| 启动快速失败 | 删除 pepper 环境变量后启动 | 应用**启动失败**（这一项同时是 §5.4 的自动化测试） |
| TLS | `curl -I http://<域名>` | 301 到 `https://` |
| 公网端口 | 云控制台安全组 | 仅 443 开放，22 为白名单 |

**这些检查为什么放在部署门禁而非 CI**：它们校验的是**运行中的环境**，不是代码。CI 里跑不出结果 —— `docker compose config` 在 CI 上读的是仓库里的 compose 文件，而真正要验的是宿主机上实际生效的那份配置。

## 10. 与安全方案自检项的映射

安全方案共 **45 项**自检（S2–S10，2026-09-06 两次裁定后由初版 42 项增至 45 项：G2 裁定新增 2 项在 S6、G3 裁定新增 1 项在 S4）。本方案对每一项给出承载方式：

| 自检组 | 可自动化 | 半自动（脚本穷举 + 人工判定） | 只能人工/实测 |
| --- | --- | --- | --- |
| S2 传输（4） | 1（`docker compose config`） | 1（Caddy 日志检查） | 2（端口扫描、301 验证） |
| S3 接口出口（5） | 2（解密调用点计数、`X-Interaction-Id` 静态扫描） | 1（红线 grep） | 2（异常响应体、抓包验 `Retry-After`） |
| S4 存储密码学（**6**） | **4**（启动失败测试、AAD 测试、git 历史检查、**yml 中 `app.crypto.*` 必为 `${}` 占位 + `.env.example` 变量名对齐**） | 1（身份证正则查询） | 1（OSS 策略 JSON 人工核） |
| S5 媒体（6） | 2（同事务代码断言、失败注入回滚测试） | 0 | 4（EXIF 实测、原图 404 实测、OSS 控制台、pending 清理实测） |
| S6 限频熔断（**7**） | 1（Redis 键存在性） | 0 | **6**（三维打满实测、熔断实测、未登录 `/contact` 实测、响应体无线索、**未登录详情 `42907` 打满实测**、**`42907` 响应体无维度线索**） |
| S7 客户端隐私（6） | 2（静态扫描设备标识、权限声明检查） | 1（`release-gate.log` 计数） | 3（**抓包实测**、`agreedVersion` 实测、release 包输入 888888） |
| S8 权限审计（5） | 3（白名单测试、同事务回滚测试、日志手机号 grep） | 0 | 2（`audit_log` 抽查、轮转实测） |
| S9 数据生命周期（3） | 2（覆盖测试、注销删除测试） | 0 | 1（保留任务实测） |
| S10 部署面（3） | 1（`.gitignore` 检查） | 0 | 2（备份介质分离、演练记录） |
| **合计** | **18** | **4** | **23** |

**一个必须正视的结论：45 项中有 23 项（超过一半）只能靠人工实测，无法自动化。** 其中包括全部 5 项 🔴 阻塞验收中的 4 项（限频熔断实测、地图隐私抓包、EXIF 实测，以及联系方式出口的人工判定部分）。

> **G2 裁定新增两项为何全部落在「只能人工实测」**：`42907` 的正确性判据是「未登录打满 30 次后被拒、而带 Token 的同一请求不被拒」，这需要同时构造两种鉴权状态下的真实请求序列并观察跨请求的计数累积 —— 单元测试可以验证限频器函数，但无法证明**它被正确挂在了未登录分支上**。这恰是本节结论的又一个例证。

> **G3 裁定新增一项为何反而可以自动化**：它的判据是纯静态的文本形态约束（yml 中 `app.crypto.*` 的值必须形如 `${XXX}`、且 `${}` 变量名集合与 `.env.example` 声明的集合相等），不涉及运行时行为，`Grep` 加一段集合比对即可。**这条界线很清楚：判据落在「代码/配置长什么样」的可自动化，落在「系统跑起来行为如何」的基本只能实测。** S4 是 9 个自检组里自动化比例最高的一组，正因为它多数项检的是代码与配置形态。

这意味着**DevSecOps 在本项目中不可能替代人工验收**，它的实际作用是：把那 18 项可自动化的、且失效方式静默的检查固化下来，让人的注意力集中在剩下的 23 项实测上。任何声称「接了 CI 就安全了」的判断在本项目上是错的 —— 尤其是隐私协议顺序这一最高驳回风险项，**只有抓包能证明**，没有任何脚本能替代。
