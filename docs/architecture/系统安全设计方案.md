## 1. 安全目标与威胁模型

### 1.1 本系统的安全特殊性：这不是一个「数据泄露=罚款」的系统

绝大多数 App 的隐私风险终点是「用户信息被卖」。本系统不同 —— 它的核心数据是**发布者的联系方式与发布地点经纬度**，两者一旦被批量抓取并关联，等于对外输出了一份「谁、卖什么、在哪、怎么找到他」的名单。这不是隐私问题，是**人身安全问题**。

因此本方案的优先级排序与通用安全方案不同：

| 优先级 | 保护对象 | 一旦失守的后果 | 对应安全域 |
| --- | --- | --- | --- |
| **P0** | 联系方式的**批量可获取性** | 名单被抓走，用于骚扰、上门推销、诈骗筛选 | §3 联系方式出口 + §6 反爬限频 |
| **P0** | 图片 EXIF 中的 **GPS 原始坐标** | 精确到门牌的住址泄露（用户主观上只想公开「大致位置」） | §5 媒体安全 |
| **P1** | 身份证 / 真实姓名（Batch2） | 身份盗用、合规处罚 | §4 存储加密 |
| **P1** | 隐私同意前的设备标识读取 | 上架驳回 + PIPL 违规 | §7 客户端与隐私合规 |
| **P2** | 后台越权、审计缺失 | 内部滥权无法追溯 | §8 权限与审计 |

**一条判断准则**：当性能、体验、开发成本与「联系方式/坐标的批量可获取性」冲突时，一律牺牲前者。这条准则在架构 §2.1.0（原图删除必须同事务同步完成，明知会拖慢 `commit` 也要做）与详设 §20.2（宁可让 UI 文案变啰嗦，也不把四维限频阈值汇总给客户端）中已经各自体现过一次，本方案将其上升为总则。

### 1.2 威胁模型（STRIDE 裁剪版）

单机单体、无 K8s、无内网横向面（架构 §4.3），因此 STRIDE 中的横向移动与服务间伪造不构成主威胁。实际威胁面收敛为四类：

| 威胁 | 具体攻击路径 | 现有缓解 | 残余风险 |
| --- | --- | --- | --- |
| **T1 爬虫批量拉联系方式** | 注册多账号 / 换设备指纹 / 换 IP，循环调 `GET /posts/{id}/contact` | 三维限频（账号/设备/IP）+ 熔断当日冻结 + 未登录一律拒（PRD §14.3 反爬限频三行） | 设备指纹**明确不可信**（PRD §12.5 设备指纹表），重装即换。账号维是唯一硬边界，故账号注册成本是最终防线 —— Batch1 依赖短信验证码成本，见 §6.4 |
| **T2 GPS 泄露** | 上传原图后，在服务端删除原图前抢先用 `x-oss-process=image/info` 读 EXIF | 原图删除与 `commit` **同事务同步**完成 + 图片域不挂 CDN + 禁「过滤参数」（架构 §2.1.0 七条约束③④） | 若实现时把删除退化为异步任务，漏洞立刻复活。这是本系统**唯一人身安全级实现陷阱**，列为 §5.2 的强制自检项 |
| **T3 密文跨行搬运** | 拿到数据库写权限后，把 A 用户的 `identity_value_enc` 复制到 B 用户行，冒用身份 | AES-GCM 的 **AAD 绑定**（详设 §4.2）：解密时 AAD 不匹配直接失败 | 需 DB 写权限，属已失守后的纵深防御，符合预期 |
| **T4 内部滥权** | 运营/审核账号越权查看用户脱敏信息、批量导出 | RBAC 4 角色最小权限 + `audit_log` 必留 6–7 类操作 + 敏感查看双人复核（PRD §14.5 审计留痕） | 后台越权**无对应错误码**，见 §11 缺口 G1；后台 7 页已移出 Batch1，实际暴露时点为 Batch2 |

**明确不在威胁模型内**（避免过度设计）：DDoS（3M 带宽下由云厂商基础防护承担，应用层不做）、供应链投毒（依赖数量少且全为主流包，Batch1 只做版本锁定不引入 SCA 平台）、物理层攻击。

## 2. 传输安全

### 2.1 规格（归集自 PRD §14.3 传输行 + 架构 §4.3）

| 项 | 规格 | 落点 |
| --- | --- | --- |
| 协议 | 全站 HTTPS，TLS 1.2+，禁明文 | Caddy 2.x 内置 ACME 自动签发与续期 |
| HTTP 跳转 | Caddy 默认 `http://` → `https://` 301，不保留明文可达路径 | Caddyfile |
| 公网端口 | **仅 443**；22 端口限白名单 IP | 安全组 + Compose 不写 `ports:` 映射 |
| 应用/MySQL/Redis 端口 | **不映射到宿主机**，仅走 Compose 内部网络 | `docker-compose.yml` 无 `ports:` 段 |
| Redis | 必设 `requirepass` | `.env` 注入 |

### 2.2 三个容易被忽略的点

1. **不做证书固定（Certificate Pinning）**。理由：Caddy 用 ACME 自动续期，证书 90 天一轮换，客户端固定后每次续期都要发版，运维成本远超收益；且本系统无金融级交易。**这是一个主动放弃的选项，不是遗漏** —— 若后续 Batch 引入支付，须重新评估（届时也会触发 B25 经营许可证红线，见 §12）。
2. **`Authorization` 头不得写入任何日志**。应用日志 8 必备字段中无该字段（可观测性 §3），但 Caddy 的 access log 默认可能记录请求头，须显式关闭或过滤。
3. **明文可达面的真正风险不在 443 而在 22**。单机部署下，SSH 一旦被爆破即等于全盘失守（`.env` 里有全部密钥）。因此 22 端口的白名单 IP 限制与「禁密码登录、仅密钥」是与 TLS 同等级的要求，不是运维细节。

**自检项 S2**
- [ ] `curl -I http://<域名>` 返回 301 且 `Location` 为 `https://`
- [ ] `nmap` 或云控制台确认公网仅 443 开放，22 为白名单
- [ ] `docker compose config` 输出中 app / mysql / redis 三个服务均无 `ports:`
- [ ] Caddy access log 不含 `Authorization` 值

## 3. 接口与出口安全

### 3.1 联系方式唯一出口（P0，🔴 上架阻塞）

这是全系统最重要的一条安全设计，规格来自 PRD §14.3「联系方式出口」行与 §7.7。

| 项 | 规格 |
| --- | --- |
| 唯一出口 | 全系统仅 `GET /posts/{id}/contact` 返回完整联系方式 |
| 未登录 | 一律拒绝，返 `40101`（使换 IP 无法绕过账号维度） |
| 解密入口 | 唯一 `common.crypto.CryptoFacade`；Batch1 唯一调用点 `contact.ContactService#viewContact`（详设 §4.3） |
| 每次解密 | **同步写 `audit_log`**，与业务操作同事务 |
| 客户端侧 | 用完即弃：不写本地缓存、不写日志、不进埋点属性（详设 §20.1 纪律 2） |

**对外视图白名单（详设 §5.1）** —— 白名单而非黑名单，是因为黑名单在新增字段时会静默失守：

| 对象 | 允许出现的字段 | 绝对禁止 |
| --- | --- | --- |
| `user`（他人视角） | `id` / `nickname` / `avatar_url` / `realname_status` / `qualification_badges[]` | `real_name_enc` / `id_card_hash` / `identity_value_enc` / 任何 `_enc` `_hash` 结尾列 |
| `user`（本人视角） | 上述 + `phone_mask` / `default_radius` | 同上 |
| `post` 列表/详情 | 不含 `contact_value` 任何形式 | `contact_value_enc` / 完整 `contact_value` |

### 3.2 出口审计的可执行定义（引自可观测性 §10.1，本方案不改口径）

「全库 grep」四个字无法执行，可观测性 §10.1 已给出可执行定义。本方案完整继承，并强调**判定必须留证**：

| 审计项 | 搜索范围 | 通过判据 |
| --- | --- | --- |
| 联系方式出口 | 服务端全部 `*.java`（controller / service / VO/DTO / MyBatis XML）+ `resources/` 下 `*.xml` `*.yml` | 完整值出口只允许存在于 `/posts/{id}/contact` 的响应对象；发现任何一处非 `/contact` 的完整值出口即失败 |
| 身份证存储 | MySQL 全库 `SHOW CREATE TABLE` + 服务端全部 `*.java` 与 mapper XML | 不存在能容纳 18 位明文的列；正则匹配数须为 0 |

**两点补充（本方案新增，不与可观测性冲突）**：

1. **搜索范围须加上日志与配置产物**。可观测性 §10.1 的范围是源码与数据库，但联系方式还可能从**应用日志**泄出（日志文件被打包给第三方排障、被日志采集 SDK 上传）。因此 grep 范围追加：`logs/` 下全部日志文件、`application*.yml`。这与可观测性 §3「禁止出现完整手机号/身份证/联系方式」是同一条要求的两个执行面。
2. **身份证审计在 Batch1 是真空通过，必须如实标注**。`cert` 域整体在 Batch2，Batch1 库内根本不存在身份证数据。验收记录须写「**Batch1 不适用 / Batch2 验收**」而非「已通过」—— 后者会制造虚假安全感（可观测性 §10 已明确此点）。

### 3.3 幂等与请求标识（归集自详设 §3.3、可观测性 §14.5 链路标识行）

幂等本身是一致性机制，但它在安全上承担两件事：防重放、防限频绕过。

| 项 | 规格 |
| --- | --- |
| `Idempotency-Key` | UUID v4 小写 36 字符，正则 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` |
| 缺失处置 | **返 `40001`，不得放行**（放行等于幂等形同虚设） |
| Redis 键 | `idem:{userId}:{key}`，TTL = `NfrApi.idempotencyWindowHours` |
| 写入时机 | **仅成功响应进缓存**，失败删占位键 |

**两 ID 分工的安全含义（可观测性 §14.5）**：`interaction_id` 由**客户端生成**，因此完全不可信 —— 它只能用于日志串联，**禁用于鉴权、限流、幂等**。任何把 `X-Interaction-Id` 当作限流键或幂等键的实现，都等于把风控开关交给攻击者。`request_id` 由服务端生成，是 UI 报错的唯一回显值。

### 3.4 错误响应的信息泄露控制（引自 PRD §12.5 错误提示口径）

| 规则 | 理由 |
| --- | --- |
| `5xxxx` 统一「服务暂时不可用，请稍后重试」+ `request_id` | 禁止把服务端堆栈或第三方原始报错透传到 UI |
| `42902` 不区分是账号/设备/IP 哪一维超限 | **风控信息不外泄**：区分后攻击者能反推设备维限额（详设 §20.2） |
| `remaining_today` 只反映账号维，客户端不得当作承诺 | 服务端刻意不汇总四维最小值，否则等于把阈值告诉客户端（详设 §20.2 服务端侧不改） |
| 全部 `429` 段 + `40105` 必返 `Retry-After` | 无剩余秒数时用户会反复点击、进一步触发限频（PRD §12.5 `Retry-After` 补充条） |

**自检项 S3**
- [ ] 按 §3.2 两表执行 grep，**完整输出（含命中行号）与逐处结论写入验收记录**；只写「已确认通过」视为未执行
- [ ] `CryptoFacade` 在全仓库的解密调用点数量 == 1（Batch1）
- [ ] 静态检查：无任何代码把 `X-Interaction-Id` 用作限流键或幂等键
- [ ] `GlobalExceptionHandler` 对 `5xxxx` 不输出 `e.getMessage()` 到响应体
- [ ] 抓包确认 `429` 响应含 `Retry-After` 头

## 4. 存储与密码学

### 4.1 双列范式（归集自详设 §4.1、PRD §13.2）

一个敏感字段落库为两列 + 一个版本列。**不是冗余，是两种不同用途的不可合并**：哈希列要能被索引与等值查询，密文列要能被解密展示，同一列做不到两件事。

| 列 | 算法 | 类型 | 用途 |
| --- | --- | --- | --- |
| `xxx_hash` | HMAC-SHA256 + pepper | `BINARY(32)` | 承载**唯一索引**与等值查询（盲索引） |
| `xxx_enc` | AES-GCM-256 + 随机 IV | `VARBINARY` | 仅用于解密展示 |
| `key_version` | — | `TINYINT` | 密钥轮换标识 |

**为什么哈希必须带 pepper 而不能用裸摘要**：手机号与身份证都是**强结构化**数据（手机号 11 位且前 3 位受限、身份证 18 位且前 6 位为行政区划）。裸 SHA-256 的全量彩虹表在普通机器上即可构造完成，等于没加密。pepper 是与数据库分离存放的服务端密钥（在 `.env` 中），使离线穷举失去起点。

**身份证的特殊处置（PRD §14.3 身份证号行）**：`id_card_hash` = HMAC-SHA256 + pepper（`BINARY(32)`）+ `id_card_last4` 明文。**不存完整明文**，`id_card_last4` 是业务展示的唯一明文残留（用于用户确认「是不是我的证件」）。

### 4.2 AAD 绑定：防密文跨行搬运（详设 §4.2）

AES-GCM 的 AAD（Additional Authenticated Data）参与认证标签计算但不被加密。把「这条密文属于谁」写进 AAD，密文被复制到别的行后解密会**直接失败**而非静默返回错误明文。

| 表.列 | AAD 组成 | 防的是什么 |
| --- | --- | --- |
| `user_identity.identity_value_enc` | `user_id` + `identity_type` | 把 A 的微信 openid 密文搬到 B 行冒用登录 |
| `user.real_name_enc` | `user_id` | 姓名密文跨用户搬运 |
| `post.contact_value_enc` | `post_id` | 把高价值帖子的联系方式密文搬到自己的帖子上，绕过限频 |

第三行是最实际的攻击面：若无 AAD，攻击者只要能写自己的 `post` 行，就能把别人的联系方式密文粘过来，然后调**自己帖子**的 `/contact` 接口拿到解密结果 —— 限频、审计全都记在「查看自己的帖子」名下。

### 4.3 解密入口收敛（详设 §4.3）

| 规则 | 说明 |
| --- | --- |
| 全系统唯一解密入口 | `common.crypto.CryptoFacade` |
| 每次解密 | 同步写 `audit_log`，与业务操作**同事务** |
| Batch1 唯一调用点 | `contact.ContactService#viewContact` |

收敛到一个类的价值不在代码整洁，而在**审计的完备性可被证明**：审计写在 Facade 内部，只要调用点唯一，就不存在「解密了但没记录」的路径。反过来，如果解密散落在 5 个 service 里，「每次解密都有审计」这句话就永远无法验证。

### 4.4 密钥管理（归集自架构 §4.4）

| 项 | 规格 |
| --- | --- |
| 存放 | 宿主机 `.env`，权限 **600**，不入 git |
| 注入 | Docker Compose `env_file` 注入容器环境变量 |
| 镜像 | **不 `COPY .env`**（否则密钥随镜像层分发，删了也在历史层里） |
| 文件分离 | `.env`（真实值，`.gitignore`）/ `.env.example`（占位值，入库） |
| 启动校验 | 必需环境变量缺失即**快速失败**，不使用默认值兜底 |
| OSS 凭证 | 子账号，权限「仅限该桶、仅限上传」 |
| 高德 Key | `--dart-define` 构建期注入 + 包名/签名指纹绑定 |

**「启动校验快速失败」为什么是安全条款而非健壮性条款**：如果 pepper 环境变量缺失时代码用了空字符串默认值，系统会**正常启动并正常工作** —— 所有哈希都用空 pepper 计算，等于退化为裸摘要，且这个退化不产生任何错误日志。半年后发现时，库里已有几万条可被彩虹表还原的哈希。这类「静默降级为不安全状态」是密码学实现中最常见的事故形态，必须靠启动即崩来堵。

**密钥轮换在 Batch1 的状态：轮换实现在 Batch2，但三项前置条件本期补齐。** `key_version` 列已预留，回填任务与旧版本下线本期不实现（Batch1 无历史数据、无轮换动机，实现成本与 38 自然日工期不匹配）。**2026-09-06 G3 裁定补齐三项前置条件**（详见 §11.3）：

| # | 前置条件 | 结论 |
| --- | --- | --- |
| ① | 密钥存放方案唯一化 | 以本节 `.env` 为唯一口径源。完整链条：`.env` → Compose `env_file` → 容器环境变量 `HMAC_PEPPERS_JSON` / `AEAD_MASTER_KEYS_JSON` → `application-prod.yml` 的 `${}` 占位 → `CryptoConfig` 配置绑定。**yml 中不得出现任何真实密钥值**；`.env` 不得绕过 yml 直写 `app.crypto.*` 键名 |
| ② | `key_version` 的 `DEFAULT` 语义 | `user` 有 `DEFAULT 0`、`user_identity` 与 `post` **无 DEFAULT**，这个不一致是**刻意的**：后两张表每行必带密文，「忘写 `key_version`」必须在插入时就失败，否则密文与版本号错配将永久损坏该行 |
| ③ | 轮换触发判据 | 五条判据见 §11.3（含最易漏的一条：**接触过生产 `.env` 的人员离场**，须 30 日内换密钥）。**无泄露迹象的定期轮换 Batch1 不做** —— 单人运维下其操作风险高于所防风险 |

**pepper 的保管强度必须高于 AEAD 主密钥**：前者泄露须停写窗口 + 全量重算盲索引，后者泄露只需后台任务逐批重加密、业务无感（《数据库设计文档》§7.1）。保管强度按**处置代价**分级，不按「都是密钥」一视同仁。

## 5. 媒体安全（P0，含唯一人身安全级陷阱）

### 5.1 OSS 直传七条安全约束（引自架构 §2.1.0 R24，逐条不得删减）

| # | 约束 | 防的是什么 |
| --- | --- | --- |
| ① | 客户端**不持长期凭证**，只拿一次性签名 | 反编译 APK 提取 AK/SK 后全桶可写 |
| ② | 桶**不开公共读** | 对象名可枚举时全量下载 |
| ③ | **原图删除必须与 `commit` 同事务同步完成** | 见 §5.2，唯一人身安全级漏洞 |
| ④ | 图片域**不挂 CDN**，禁「过滤参数」 | CDN 缓存住带 EXIF 的原图；`x-oss-process` 被当作参数过滤掉后仍生效 |
| ⑤ | `media_id` 与对象名**服务端生成** | 客户端指定对象名可覆盖他人文件 |
| ⑥ | `content-length-range` + `content-type` 白名单 + `commit` 二次校验 | 传超大文件打满带宽；传伪装成图片的可执行文件 |
| ⑦ | OSS callback 为 `commit` 触发源 + 24h pending 清理 | 客户端不回调即产生永久孤儿对象（内含 EXIF） |

### 5.2 约束③ 的完整说明：为什么不能改成异步删除

这是本方案唯一需要单独一节展开的实现细节，因为它**看起来是性能优化，实际是人身安全漏洞**。

链路：客户端直传原图 → 服务端处理（剥离 EXIF、生成展示图）→ **删除原图** → `commit` 返回。

若把「删除原图」改为异步任务（消息队列 / 定时清理 / `@Async`），就出现一个窗口期：

```
t0  原图上传完成，对象仍在桶中（含 GPS EXIF）
t1  commit 返回成功，客户端拿到 media_id
t2  异步删除任务真正执行（可能延迟数秒到数分钟，任务失败则永不执行）

    在 t0 ~ t2 之间：
    GET https://<桶>/<对象名>?x-oss-process=image/info
    → 返回完整 EXIF，含拍摄地 GPS 经纬度
```

对象名由服务端生成（约束⑤）看似不可猜，但**上传者自己知道对象名** —— 恶意用户可以上传一张图，然后立刻用这个窗口验证 EXIF 是否可读；确认可读后，攻击手法变为「诱导他人上传 + 抢窗口读取」，或在多用户场景下通过其他途径获取对象名。更关键的是：`commit` 已返回成功意味着**业务上已认为图片安全**，而此刻原图还在。

**结论**：删除必须与 `commit` 在同一事务内同步完成。删除失败则 `commit` 失败，图片不入库。宁可让用户重试一次上传，也不能留这个窗口。**明知会拖慢 `commit` 响应时间，仍然这么做** —— 这是 §1.1 判断准则的直接应用。

### 5.3 EXIF 剥离（PRD §13.4 `exif_strip`，🔴 阻塞）

| 项 | 规格 |
| --- | --- |
| 剥离内容 | GPS / 设备信息 / 拍摄时间（PRD §9.6 媒体元数据剥离） |
| 保留期 | **不保留**，服务端强制剥离 |
| OCR 原图 | `ocr_image_7d`，加密存储，7 天到期自动删除（Batch2 `cert` 域） |
| 位置轨迹 | `location_no_collect` —— **不采集**，只存发布时用户主动选择的经纬度点 |

最后一行是常被误读的一条：系统**从不采集用户位置轨迹**。地图页的定位只用于当前视图中心，不落库、不上报。库里唯一的坐标是发布时用户手动确认的那个点。

## 6. 反爬、限频与熔断（P0，🔴 阻塞）

### 6.1 三维限频 + 熔断（PRD §14.3 三行 + §7.7）

| 维度 | 阈值 | 说明 |
| --- | --- | --- |
| 账号 | 每日上限（PRD §14.3 反爬限频行） | **唯一硬边界**，键用 `user_id` |
| 设备 | 每日上限 | 键用 `X-Device-Id`，**明确不可信** |
| IP | 每日上限 | 共享出口 IP 场景下会误伤，故阈值高于前两者 |
| 熔断 | 单账号 1 分钟内 ≥N 次拉取 → **当日冻结** + 进风控待审 | 返 `42903` |

**三维同时生效，任一超限即拒**（返 `42902`）。未登录一律不可拉取完整号码（返 `40101`）—— 这一条是三维限频成立的前提：若允许未登录拉取，账号维度就被完全绕过，剩下设备与 IP 两个都是可低成本更换的维度。

**第四条限频轨：未登录详情浏览（`42907`，2026-09-06 G2 裁定新增）**

| 维度 | 阈值 | 说明 |
| --- | --- | --- |
| 设备 | 每日 ≤ 30 次 | 键用 `X-Device-Id`，**沿用上表设备维阈值，非新造数字** |
| IP | 每日 ≤ 100 次 | 沿用上表 IP 维阈值 |

仅约束**未登录**请求 `GET /posts/{post_id}`；已登录不受此限，因其行为已可按 `user_id` 追溯。任一超限返 `42907` + `Retry-After`，提示附登录入口且**不告知哪个维度超限**。

**为什么这一轨必须存在**：它与上面的联系方式限频保护的是**两份不同的资产**。联系方式限频只挡电话号码，而详情页返回的 `address` 到门牌号（PRD §14.3 已裁定**不做坐标模糊化**，见 §11.2），「精确地址 + 物品」这份清单原本对未登录用户零限频。口径与错误码定案见 PRD §12.3 / §12.5，本节不重抄。

### 6.2 限频键分流原则（详设 §3.4）

| 类型 | 键维度 | 适用 |
| --- | --- | --- |
| 账号级 | 一律 `user_id` | 联系方式查看、AI 配额、举报、熔断 |
| 渠道级 | 保留手机号维 | 短信验证码发送、登录失败计数 |

键名规范以详设 §3.4 表为唯一口径（如 `rl:contact:uid:{userId}:1d`、`fz:contact:{userId}:{date}`），本方案不重抄。

**为什么账号级不用手机号做键**：用户可换绑手机号。若用手机号做键，换绑即重置配额。而 `user_id` 在账号生命周期内不变。反过来，短信验证码必须用手机号做键 —— 因为发送短信时用户还没有 `user_id`。

### 6.3 计数不落库（PRD §13.2 联系限频判定行）

限频计数**走 Redis，不落库**，理由是避免热点行：所有用户的联系行为都会更新同一批计数行，MySQL 行锁会成为瓶颈。`contact_event` 表记录的是**行为事实**（用于北极星指标与反向哨兵），不是限频计数器。

**由此产生一个必须接受的取舍**：Redis 重启（且 AOF 未及时落盘）会丢失当日计数，等于给所有用户重置配额。这个风险被接受，理由是 Redis 配了 AOF everysec，最坏丢 1 秒；且限频的目的是提高爬取成本而非绝对阻断。

### 6.4 账号注册成本是最终防线（本方案补充的分析）

三维限频中只有账号维不可低成本绕过（设备指纹重装即换、IP 可用代理池）。因此**整个反爬体系的强度上限 = 批量注册账号的成本**。

Batch1 的注册成本来源：短信验证码（有真实资费与频控 `42905`）。这意味着：

| 若发生 | 后果 |
| --- | --- |
| 短信验证码频控被绕过 | 批量注册成本趋零 → 三维限频全部失效 |
| 引入「免验证码快速登录」 | 同上 |
| 微信一键登录（Batch2）未做同等频控 | 出现一条低成本注册通道，绕过短信这道成本墙 |

**结论与纪律**：任何新增的注册/登录通道，上线前必须同步评估其批量注册成本，且不得低于短信通道。**这条纪律已于 2026-09-06 经裁定转为可判定的四项硬门禁**（见 §11.4），落点在《系统总体架构设计文档》§5.1.1「Batch2 上线前置检查项」，Batch2 微信/Apple 登录任一项不满足即不得上线。

### 6.5 内容安全（PRD §14.3 内容安全行）

| 项 | 规格 |
| --- | --- |
| 敏感词 | 本地 + 云端双重；命中返 `40901` |
| 图片审核 | 云端审核（涉黄/涉政/广告）；未通过返 `40902`，该图位**仅本人可见** |
| 禁发类目 | 强制拦截，返 `40303`（医疗/金融/武器等） |
| AI 幻觉防御 | Scope 四步管线 + 生成内容与源交叉比对 + 1% 抽审 + SimHash 去重（PRD §5.10） |

`40902` 的「仅本人可见」是一个隐私与体验兼顾的设计：未过审的图不出现在他人视图中，但本人在编辑态与「我的发布」中能看到它并知道原因，否则用户会以为图片丢了。

## 7. 客户端与隐私合规（🔴 上架驳回点密集区）

### 7.1 隐私协议门（`privacy-gate`）—— 顺序错即驳回

规格来自 PRD §14.3 地图合规行与 §6.7。这是**上架驳回率最高**的一项，且验收方法必须是抓包实测而非代码走查。

| 要求 | 说明 |
| --- | --- |
| 时机 | **早于登录**（不是登录后，不是首次用地图时） |
| 形态 | 模态，**不可关闭**（无返回键、无点击遮罩关闭） |
| 落盘 | 同意状态须连 **`agreedVersion`** 一起落盘（政策更新后需重新同意） |
| 顺序 | 同意后才调 `AMapInitializer.updatePrivacyAgree`，未同意**不初始化地图** |
| 未同意期间 | **禁读任何设备标识** |

**为什么必须抓包实测**：代码里 `updatePrivacyAgree` 写在同意回调之后，看起来是对的；但如果地图 SDK 在 `main()` 的某个初始化链里被间接触发（例如某个 provider 的 eager 初始化、某个 widget 的 `initState`），实际网络请求会在同意前就发出。**只有抓包能证明「未同意期间零设备标识外发」**。

### 7.2 设备指纹采集红线（PRD §12.5 设备指纹表）

| 项 | 规格 |
| --- | --- |
| 生成 | 客户端**首次启动**生成 UUID v4，持久化到本地安全存储，此后不变 |
| 传输 | `X-Device-Id` 请求头 |
| 可信度 | **明确标注为不可信** —— 重装或清数据即得新指纹。它只提高刷量成本，**不构成安全边界** |
| 采集红线 | **禁止采集 IMEI、MAC、广告标识符（IDFA/OAID）** —— 属个人信息且需单独授权 |

「不构成安全边界」这句话有具体的设计含义：三维限频中账号维与 IP 维**不可因设备维的存在而放宽**。如果因为「反正有设备指纹兜底」而调高账号维阈值，等于把整个限频体系建在一个可随意更换的标识上。

## 8. 权限与审计

### 8.1 RBAC 四角色（PRD §9.10）

| 角色 | 职责边界 |
| --- | --- |
| 内容审核员 | 内容下架/恢复，不可见用户敏感信息 |
| 运营专员 | 分类与模板变更、定向邀请 |
| 算法运营 | 权重与开关变更 |
| 超级管理员 | 全部 + **唯一可查 `audit_log`**、导出需二次确认 |

三条纪律：**最小权限**、**越权返 403 + `40305`**（G1 裁定，见 §11.1；错误码定案在 PRD §12.5）、**敏感信息查看须双人复核**。

「入口不可见」与「越权返 403」是两道独立防线，不可只做一道：只做前者是前端隐藏（改 JS 即绕过），只做后者会让用户点到一堆报错按钮。**且一切越权必须返同一个码 `40305`**：若按资源类型各返不同码，不同资源间的响应差异本身就成了可枚举的信息通道（论证见 §11.1）。

**Batch1 状态**：运营治理后台 7 页已移出 Batch1（架构 §3），因此 RBAC 在 Batch1 无实际暴露面。但 **P10 安全评估报告需要 RBAC 自证**（见 §12），故本节规格必须先落档。

### 8.2 `audit_log` 规格（可观测性 §5 + DDL）

10 字段：`id` / `operator_id` / `operator_role`(ENUM) / `action` / `target_type` / `target_id` / `before_value`(JSON) / `after_value`(JSON) / `reason` / `created_at`，2 索引。

| 项 | 规格 |
| --- | --- |
| 必留操作 | 认证通过/驳回、内容下架/恢复、分类与模板变更、权重与开关变更、定向邀请、**查看用户脱敏信息**（PRD §14.5） |
| 保留期 | **≥180 天**（`audit_log_180d`） |
| 可见性 | 仅超级管理员可查；导出二次确认；敏感查看双人复核 |
| 写入时机 | **与业务操作同事务** |
| 字段白名单 | `AuditLogWriter` 须剔除 `phone` / `real_name` / `id_card` / `contact_value` 及一切 `_enc` `_hash` 结尾列 |

**「同事务」是审计可信的前提**：若审计走异步或独立事务，就存在「业务成功但审计失败」的路径 —— 而这条路径恰好是滥权者最想要的。同事务意味着审计写失败则业务回滚，代价是审计成为业务的可用性依赖，这个代价被接受。

**字段白名单是一个反直觉但必要的设计**：审计要记录「改了什么」，最自然的实现是把变更前后的整行序列化进 `before_value`/`after_value`。但这样一来，`audit_log` 里就有了明文手机号与联系方式 —— 而 `audit_log` 保留 180 天、可被超管导出，等于开了一条绕过 §3.1 唯一出口的旁路。因此白名单不是可选优化，是硬要求。

### 8.3 `audit_log` 与 `contact_event` 不可互替（可观测性 §5）

这是一个命名相近导致的高风险陷阱：

| 对象 | 位置 | 保留期 | 能否用于合规举证 |
| --- | --- | --- | --- |
| `event_name='contact_event'` | 埋点库 `track_event_YYYYMM` | 90 天 | **不能** |
| `audit_log` | 业务库 | ≥180 天 | **是唯一举证来源** |

两者不可合并互替。若因为「反正埋点里也记了联系行为」而省掉 `audit_log` 写入，结果是：保留期从 180 天缩到 90 天（违反 PRD §13.4）、数据在独立库无法与业务同事务、且埋点数据本身允许丢弃（有 `dropped_count`）。

### 8.4 应用日志的脱敏要求（可观测性 §3）

JSON 单行，8 必备字段：`ts` / `level` / `request_id` / `interaction_id` / `user_id` / `path` / `code` / `rt_ms`。

| 规则 | 说明 |
| --- | --- |
| 禁止出现 | 完整手机号 / 身份证 / 联系方式 |
| grep 范围 | **日志文件本身也纳入 §3.2 的审计范围** |
| 轮转 | 必须配置（2 核 2G / 40G 盘，日志打满盘会导致 MySQL 写失败） |

### 9.1 九条保留策略键（PRD §13.4，为 CI 门禁比对键）

`ocr_image_7d` / `transit_log_30d` / `favorite_deleted_30d` / `publish_memory_180d` / `deactivate_7d` / `post_archived_keep` / `audit_log_180d` / `exif_strip` / `location_no_collect`。

### 9.2 注销的完整删除（PRD §13.4 `deactivate_7d` + §9.7）

| 项 | 规格 |
| --- | --- |
| 冷静期 | 7 天，期内可撤回，撤回后数据**原封不动** |
| 到期处置 | 按 `user_id` 删除**全部** `user_identity` 行 |

**「全部」三个字是一个具体的事故防范**：`user_identity` 表按身份类型多行存储（手机号一行、微信 openid 一行）。若删除时只按 `identity_type='phone'` 过滤，微信身份行会残留 —— 用户下次用微信登录时，`identity_value_hash` 命中残留行，**直接复活一个已注销账号**，且该账号的 `user` 主行状态可能已是「已注销」，导致数据状态自相矛盾。

### 9.3 已下架/过期内容不物理删除

`post_archived_keep`：`status` 置位，**不物理删除**。理由是收藏与申诉需可追溯。这与「用户注销即删除全部身份」并不矛盾：前者是内容，后者是身份标识 —— 内容脱离身份后不再是个人信息。

## 10. 运行时与部署面安全

### 10.1 暴露面（架构 §4.3）

| 组件 | 公网可达 | 说明 |
| --- | --- | --- |
| Caddy | ✅ 443 | 唯一入口，TLS 终止 |
| SSH | ⚠️ 22 白名单 IP | 仅密钥登录，禁密码 |
| 应用（Spring Boot） | ❌ | Compose 内部网络，无 `ports:` |
| MySQL | ❌ | 同上 |
| Redis | ❌ | 同上，且必设 `requirepass` |

**「Redis 不映射端口了为什么还要 `requirepass`」** —— 因为端口不映射防的是外部直连，`requirepass` 防的是同一 Compose 网络内其它容器的横向访问，以及未来某次为了排障临时加 `ports:` 后忘记撤销。纵深防御在单机场景下依然成立：这两道防线的失效原因完全不同（一个是网络配置错误，一个是凭证泄露），不构成冗余。

### 10.2 单机架构的安全含义（本方案补充）

单机单体在安全上有两面：

| 优势 | 劣势 |
| --- | --- |
| 无服务间通信 → 无内部 API 伪造面 | **单点全失守**：SSH 沦陷 = 数据库 + 密钥 + 应用全部沦陷 |
| 无服务注册/配置中心 → 无这类组件的未授权访问 CVE | 无网络分区隔离，应用漏洞可直接读 `.env` |
| 攻击面小、可完整枚举 | 无独立审计主机，日志与被审计对象同机（攻击者可篡改日志） |

**结论与本期取舍**：日志与审计同机的问题在 Batch1 **接受不处理**（无独立日志主机预算，131 元/年约束）。但 `audit_log` 在 MySQL 中而非文件中，其篡改门槛高于文本日志，这是选择把审计放 MySQL 而非日志文件的一个额外理由（原始理由是要与业务同事务，见 §8.2）。

### 10.3 备份与恢复的安全维度（架构 §4.5）

备份文件本身是**完整的敏感数据副本**，其安全等级须等同生产库：

| 项 | 要求 |
| --- | --- |
| 备份文件权限 | 600，与 `.env` 同级别 |
| 不入 git | `.gitignore` 须覆盖备份目录 |
| 恢复演练 | 演练用的恢复数据须与生产隔离，演练后**删除** |
| pepper 与备份分离 | 若 pepper 随备份一起丢失，`xxx_hash` 全部失去可比性（登录直接不可用）；若 pepper 与备份一起泄露，加密全部失效。**两者必须分开存放** |

最后一行是一个容易两头都做错的点：把 pepper 和备份放一起 → 一次泄露全丢；完全不备份 pepper → pepper 丢失后所有用户无法登录（`phone_hash` 算不出来）。正确做法是 pepper 独立备份到另一个介质。

**自检项 S10**
- [ ] 备份文件权限为 600 且路径在 `.gitignore` 中
- [ ] pepper 的备份介质与数据库备份**物理分离**，且有恢复演练记录
- [ ] 演练环境数据已删除

### 11.1 G1 裁定：后台 RBAC 越权错误码定为 `40305`

**取证结论**：PRD §9.10.1 后台验收只写「越权入口不可见且接口返回 403」，无错误码；`403` 段已占 `40301`–`40304` 且全为业务语义；**全仓 Grep 确认 `40305` 未被任何文档或代码占用**。

**裁定**：在 PRD §12.5 补 `40305` = 「无权限访问该资源」，语义通用于一切后台 RBAC 越权（含读与写），**不按资源类型拆分多个码**。

| 判断项 | 结论 |
| --- | --- |
| 为何不留到 Batch2 补 | 现在补号只改 PRD 一处；Batch2 补要同时改 PRD + 后台契约 + 客户端码表 + 已在写的代码。原建议「Batch2 后台开发前」恰是成本最高的时点 |
| 与「入口不可见」是否冲突 | 不冲突。PRD 原文用「且」连接，前者是 UI 层、后者是接口层，本就是两道独立防线（见 §8.1） |
| **为何单一码本身就是防枚举手段** | 反直觉但关键：若不定统一码，实现者会各自用 `404` / `40301` / 裸 `403`，**不同资源返回不同响应，反而制造出可枚举的信息差**。统一返 `40305` 才消除了这个差异 |
| 是否用 `404` 掩盖资源存在性 | **不做**。后台威胁模型是 T4 内部滥权，内部人员本就知道资源存在，防线是 `audit_log`（§8.2）而非信息隐藏；上这层只增排障成本、收益为零 |

**落点**：[PRD.md](file:///d:/developer/code/aicoding/s2s/docs/PRD.md) §12.5 错误码表新增 `40305` 行、§9.10.1 权限隔离验收行补「+ `40305`」；[openapi.yaml](file:///d:/developer/code/aicoding/s2s/docs/api/openapi.yaml) `responses.Forbidden` 描述补 `40305` 并注明「后台专用，App 端接口不返回此码」。

### 11.2 G2 裁定：明确不做坐标模糊化，改以知情告知 + 未登录详情限频承接

**取证推翻了原本的问题设定。** 实读 PRD §6.4.3 确认全文只有列表页顶部/筛选/卡片规格，**无任何隐私表述** —— 引用确实悬空。但更重要的是第二个发现：**§12.1 那句括注的手段与目的完全不匹配**。

| 精度 | 实际距离 | 能隐藏到什么 |
| --- | --- | --- |
| 6 位小数（详情/发布） | ≈ 0.11 m | 门牌级 |
| **5 位小数（`/map/pins` 现口径）** | **≈ 1 m** | **仍是门牌级** |
| 4 位小数 | ≈ 11 m | 仍可定位到楼栋单元 |
| 3 位小数 | ≈ 110 m | 才开始隐藏具体住户 |

**从 6 位降到 5 位不是模糊化，是压缩响应体积**，离真正的模糊化差两到三个数量级。这比单纯的悬空引用更危险：它把一个**性能优化**冒充成**隐私措施**，会让后续评审看到「已经模糊化了」而跳过这个议题。

**产品侧已作出相反且强激励的选择**：🟢 完整档要求「位置到门牌号」并享 **×2 优先展示**（PRD §9.8）；发布后主动引导「还差 2 张图 + 门牌号就能让附近更多人看到」；`address` 为明文 `varchar(120)` 到门牌号、`PostDetail` 直接返回。

**裁定：不做坐标模糊化。这不是妥协，而是唯一自洽的选择** —— 因为 `address` 明文到门牌号照原样返回，坐标即使模糊到 500m 也挡不住任何人。**半吊子模糊化是最坏结果：产品价值受损，隐私一点没保护。**

保护手段改为两条派生措施，均已落盘：

| # | 措施 | 落点 |
| --- | --- | --- |
| **①** | **位置知情告知**（PIPL 告知同意在位置数据上的唯一落点）：地图选点页与完整度引导文案须写明「门牌号将对所有看到这条信息的人可见」，**不得只写「附近更多人看到」**；隐私政策（P6）须列明「精确位置（含门牌号）会向其他用户公开展示」 | PRD §14.3 新增「位置知情告知」行 |
| **②** | **未登录详情浏览限频 `42907`**：设备维每日 ≤30 次、IP 维每日 ≤100 次（**沿用 §7.7 联系方式的设备/IP 维阈值，不新造数字**），任一超限即拒 + `Retry-After`；提示附登录入口且不告知哪个维度超限 | PRD §12.3 + §12.5 `42907`；openapi `TooManyRequests` 6→7 码、`/posts/{post_id}` 补 `429` |

**措施 ② 补的是一处此前完全未识别的防线不对称**：联系方式有三维限频 + 熔断，**而「精确地址 + 门牌号 + 物品」这份清单对未登录用户完全开放、零限频**。攻击者要的未必是电话号码 —— 「哪里有人在出租房 / 卖车」加精确地址本身就是成品目标清单，这正是 §1.1 定义的 P0 保护对象，却原本完全在防线之外。

**顺带裁定一处口径冲突**：PRD §12.3 写「未登录可只读查看详情」，而 openapi `/posts/{post_id}` 原先**无 `security: []`**（即需鉴权）。经用户裁定**以 PRD 为准**：该接口未登录可访问，openapi 已补 `security: []` 并显式注明「与 `/posts/{id}/contact` 的未登录一律 `40101` 不同，二者不可混同」。

### 11.3 G3 裁定：轮换仍在 Batch2，但本期必须补齐三项前置条件

**取证结论：G3 的问题设定不准确。** 实读《数据库设计文档》§7.1 确认，密钥泄露的处置流程**已完整成文**（两类密钥的影响面、处置步骤、是否需停写、pepper 须停写的原因、Batch1 无在线吊销能力），并非「无平滑更换手段」。真正缺的不是流程文本，而是**流程能否被执行的三项前置条件**。

**裁定：轮换的实现（回填任务、旧版本下线）维持在 Batch2，但下列三项本期补齐** —— 它们的共同特征是「等到真要轮换时才发现缺，就已经来不及了」：

| # | 前置条件 | 本期动作 | 若不补，Batch2 会怎样 |
| --- | --- | --- | --- |
| **①** | **密钥存放方案唯一化** | 见下方冲突裁定 | 两套配置并存，轮换时不知道该改哪里，改一处另一处覆盖回旧值 |
| **②** | `key_version` 三张表的 `DEFAULT` 语义统一 | 见下方 DEFAULT 裁定 | 新增版本号时三张表行为不一致，回填任务要写三套分支 |
| **③** | 轮换的**触发判据**写明 | 见下方触发判据 | 「怀疑泄露」无定义，实际结果是永远不轮换 |

**冲突裁定（①）：密钥存放以《系统安全设计方案》§4.4 的 `.env` 为唯一口径源。**

这是本次取证发现的一处**从未合并的双方案并存**：

| 出处 | 方案 |
| --- | --- |
| 本方案 §4.4 / 架构 §4.4 | 宿主机 `.env`（权限 600、`env_file` 注入、不 `COPY` 进镜像） |
| `docs/plans/2026-09-04-1630-refactor-batch1-data-model-corrections-plan.md` KTD5 | Spring `application-{env}.yml`，生产用 `HMAC_PEPPERS_JSON` / `AEAD_MASTER_KEYS_JSON` 环境变量覆盖 |

二者**并非对立，而是同一条链的两段被当成了两个方案**：`.env` 决定密钥值以什么形式到达容器（环境变量），`application-{env}.yml` 决定 Spring 以什么形式读取它（`app.crypto.*` 配置绑定）。裁定后的完整链条只有一条：

`.env`（真实值，600，不入 git） → Docker Compose `env_file` → 容器环境变量 `HMAC_PEPPERS_JSON` / `AEAD_MASTER_KEYS_JSON` → `application-prod.yml` 中 `app.crypto.hmac-peppers: ${HMAC_PEPPERS_JSON}` → `CryptoConfig` 的 `@ConfigurationProperties`

**由此明确两条禁令**：yml 文件中**不得出现任何真实密钥值**（包括开发环境；开发环境同样走 `.env`，值可以是弱值但形式必须一致，否则生产是唯一没被验证过的路径）；`.env` 中**不得直接写 `app.crypto.hmac-peppers`** 这类带点号的键名试图绕过 yml —— 配置绑定的唯一入口是 yml，`.env` 只负责提供 `${}` 占位符的值。

**为什么必须现在裁定而不能留到 Batch2**：KTD5 定的 `hmac-peppers` / `aead-master-keys` 是**列表**（按 `key_version` 索引），这个数据结构本身就是为轮换准备的 —— 它是 Batch1 就要落地的代码结构（`CryptoConfig`、`HmacHasher.hash(plaintext, keyVersion)`、`AeadCipher.encrypt/decrypt(bytes, keyVersion)`）。如果 Batch1 按「单个密钥值」实现，Batch2 轮换的第一步就是改这三个类的签名并回归所有加解密调用点。**列表结构是 Batch1 的唯一正确实现，即使列表当前只有一个元素。**

**DEFAULT 裁定（②）：`user_identity.key_version` 与 `post.key_version` 的「无 DEFAULT」是刻意的，不是遗漏。**

实测 DDL 三处定义不一致：

| 表 | 定义 | 裁定 |
| --- | --- | --- |
| `user` | `TINYINT NOT NULL DEFAULT 0` | 保留 DEFAULT。`user` 行可能在尚无任何加密列值时先建（注册事务内先建 `user` 再写身份行，见架构 §5.1.1），此时 `key_version` 需有兜底值 |
| `user_identity` | `TINYINT NOT NULL`（无 DEFAULT） | **保持无 DEFAULT**。该表**每一行都必然带加密列**（`identity_hash` 与 `identity_value_enc` 均 `NOT NULL`），写入方必须显式声明用了哪个版本的密钥 |
| `post` | `TINYINT NOT NULL`（无 DEFAULT） | **保持无 DEFAULT**，同理（`contact_value_enc` 随发布必写） |

**这个不一致是对的，因为它编码了一条真实的语义差异**：有 DEFAULT 意味着「不写也能插入成功」，而对于必然携带密文的行，「不写 `key_version`」是一个**必须在插入时就失败**的错误 —— 否则密文用 v1 密钥加密、`key_version` 记为 0，解密时取错密钥，AEAD 直接抛异常且无法从数据本身判断真实版本，这行密文实际上永久损坏。**用数据库约束把「忘记声明密钥版本」变成插入失败，比任何代码 review 都可靠。** 本次动作只是把这条语义写进文档，DDL 不改。

**触发判据（③）：什么情况下必须启动轮换。**

| 触发条件 | 处置密钥 | 是否可延后 |
| --- | --- | --- |
| `.env` 文件曾被提交到 git（哪怕已 `git rm`） | 两类密钥全换 | **不可延后**。git 历史层与远端克隆都留有副本，删提交不等于删密钥（《DevSecOps 接入方案》§7.3「已泄露的补救 = 改密钥，不是删提交」） |
| 数据库备份文件与 pepper 曾同介质存放或同时外传 | 两类密钥全换 | 不可延后（§10 备份纪律的反面） |
| 宿主机被判定失陷（未授权登录、可疑进程） | 两类密钥全换 | 不可延后 |
| 接触过生产 `.env` 的人员离场 | 两类密钥全换 | 可排期，但须在离场后 30 日内完成 |
| 无任何泄露迹象的定期轮换 | — | **Batch1 不做**。无 KMS、单人运维，定期轮换的操作风险（停写窗口、重算出错）高于它防的风险 |

**倒数第二行是最容易被漏掉的一条**：前三行都是「出事了」，只有人员离场是**没有任何异常信号的常规事件**，因而不会触发任何人的警觉。而它恰恰是密钥泄露最常见的现实路径。

**pepper 与 AEAD 主密钥的保管强度必须不同**：AEAD 主密钥泄露只导致密文可解、索引不受影响、可在线逐批重加密、**业务无感**；pepper 泄露导致全部盲索引列失效、须全量重算 `identity_hash` / `id_card_hash` 并重建 `uk_type_hash`、**须停写窗口**（《数据库设计文档》§7.1）。同样是一次泄露，一个是后台任务，一个是停服维护 —— **保管强度应当按处置代价分级，而不是按「都是密钥」一视同仁**。

**落点**：本方案 §4.4 密钥轮换段补前置条件索引；《数据库设计文档》§7.1 补触发判据与 DEFAULT 语义说明；《技术栈选型说明》不涉及。

### 11.4 G4 裁定：注册成本纪律转为四项可判定的 Batch2 硬门禁

**原缺口的实质问题不是「没写纪律」，而是纪律不可执行。** §6.4 原文「上线前必须同步评估其批量注册成本，且不得低于短信通道」只有「必须评估」四个字 —— 没有判据（怎么算「不低于」）、没有卡点（谁在什么节点检查）、没有失败后果（评估结论是「偏低」时上不上）。这种写法在 Batch2 排期压力下必然被解释为「已经评估过了，微信也有频控」而通过。

**裁定：转为四条逐项打勾的硬门禁，任一不满足即不得上线**，全文见《系统总体架构设计文档》§5.1.1「Batch2 上线前置检查项」。要点：

| # | 门禁 | 沿用的既有口径 |
| --- | --- | --- |
| ① | 微信注册接口有设备维 + IP 维限频，阈值不高于短信 IP 维 20/h | `42905` + §6.2 短信阈值，**不新造码、不新造数字** |
| ② | 微信首次注册**必须绑手机号**才具备发布与联系权限 | §6.4 成本墙论证 |
| ③ | 账号级风控与配额在微信会话下仍以 `user_id` 为键 | PRD §3.4.1 第②条硬约束 |
| ④ | 注销按 `user_id` 删**全部** `user_identity` 行 | PRD §3.4.1 第③条硬约束、§9.2 |

**②是这四项中唯一会被「体验优化」掉的，也是唯一真正承载成本的一项。** ①只限制注册速率，攻击者可用时间换量；③④防的是权限与残留，不是成本。只有②让每个具备发布能力的账号都对应一个真实手机号，把成本从零抬到「一条短信资费 + 一个可接码的号」。**若把②改成「手机号绑定可选」，①③④全部形同虚设** —— 攻击者要的不是账号，是账号附带的发布与联系能力。

**为什么落点选架构 §5.1.1 而不是本方案**：Batch2 微信登录的排期与待做项清单在那一节，检查表必须与它**物理相邻**才会在排期时被读到。放在安全方案 §11 里，等于放在一份「缺口登记」章节中，Batch2 开工时没人会翻。

**③④与 Batch1 已交付内容的关系**：Batch1 已把风控键改成 `user_id`、注销改成按 `user_id` 删全部身份行（架构 §5.1.1「Batch1 实际交付」），这份改造的**全部收益都在微信上线这一刻兑现**，③④正是验收它是否真的到账。

### 11.5 G5 裁定：非安全侧缺口，确认已在可观测性方案闭环，本方案关闭

**取证结论：该项在可观测性方案中已有完整闭环，不是悬空。** 实读《可观测性架构方案》§6.3 确认三点：告警通道在单机形态下就是日志扫描加通知，明确不引入 Prometheus / Grafana（2G 内存约束）；「通知」的承载组件本期不定，**定案时点已绑定** —— 与 SLS 迁移绑定，迁移后用 SLS 自带告警能力，不另选组件；**且在此之前有替代保障** —— 「有没有人真的去看那个日志」由 §9.1 的周巡检任务承担，不靠通知。

**裁定：本方案对 G5 无任何动作，标记关闭。** 理由：

| 判断项 | 结论 |
| --- | --- |
| 是否安全议题 | **不是**。`P95>300ms` 是性能指标，其告警不可达影响的是性能回归的发现速度，不构成任何安全风险敞口。本方案 §1.1 的保护对象（个人信息、位置、联系方式）与此无交集 |
| 「无接收端等于告警不可达」是否成立 | **不成立**。有落盘日志 + 周巡检就是一条可达路径，只是延迟从「分钟级」变成「周级」。对内测阶段唯一开发者而言，这个延迟是可接受的 |
| 本方案是否应重复登记 | **不应**。同一议题在两份文档各登记一次，会产生「两处待办、各自以为对方在跟」的落空。**唯一口径源原则同样适用于待办项，不只适用于数字** |
| 安全告警是否受影响 | **不受**。本方案的安全侧留痕靠 `audit_log`（§8.2，保留 ≥180 天）与 `security_event` 日志，走的是审计而非告警通道，不依赖 G5 的通知组件 |

**最后一行是这项裁定的关键**：如果安全事件也依赖「通知」才能被发现，那 G5 就是安全缺口而非性能缺口。之所以不是，是因为 §8.2 的设计从一开始就选了**留痕 + 事后可查**而非**实时告警**这条路 —— 这在单人运维、无 7×24 值守的形态下是正确取舍：一个没人接的告警和一条没人看的日志，价值完全相同，但后者不需要额外组件。

### 11.6 G6 裁定：服务端构建工具定为 Maven

**裁定：Maven。** 完整判据与命令口径落在《技术栈选型说明》§3.1（该节为构建工具的**唯一口径源**，此前该文档对构建工具零提及），并已并入其 §2 选型总表。

| 判断项 | 结论 |
| --- | --- |
| 生态匹配 | Spring Boot 官方文档与 start.spring.io 默认 Maven。1 人 38 天工期下「抄得到的样例最多」本身是首要指标 |
| AI 辅助准确率 | `pom.xml` 是纯声明式 XML；Gradle 的 `build.gradle(.kts)` 是可执行脚本，易混用 Groovy / Kotlin DSL 两套语法，排错成本落在唯一的开发者身上 |
| Gradle 的长处在本项目为零 | 其优势在多模块并行与增量构建，本项目单体单进程、单模块、无自定义构建逻辑（架构 §4 已否掉微服务） |
| 内存 | 宿主机直接 build（无独立 CI runner），Gradle Daemon 会与 JVM 750MB 争抢同一份 2G |

**这不是「哪个工具更好」，而是「哪个工具在本项目约束下不产生额外工作」。** Gradle 的收益需要一个本项目不存在的前提（模块数 > 1），而它的成本（DSL 歧义、Daemon 内存）是立即发生的。

**为何不留到「编码期 Day 1」**：原时点定为 Day 1 看似合理，但《DevSecOps 接入方案》§5 的全部服务端门禁命令、§3 的依赖锁定规格都以此为前置 —— 不定案，那些规格只能写成带条件前缀的半成品（实测原文中有三处「D-1 定案后」的条件写法）。**现在定案改的是三份文档的文字；Day 1 定案改的是已经写好的门禁脚本。**

**落点**：《技术栈选型说明》§3.1（新增，含五条命令口径与版本号纪律）+ §2 选型总表新增行；《DevSecOps 接入方案》六处（§1 现状表、§2 D-1 行与纪律段、§4 巡检命令、§7 版本锁定表、§9 待办第 1 项、§11 问题登记 D-1 行）。**D-2（测试执行时机）不在 G6 范围** —— 它的口径源不是《技术栈选型说明》而是《DevSecOps 接入方案》§5.3，故不能随 G6 一并裁定；已于同日在该方案内就地定案（单测每次提交前，集成测试仅出包前）。

**执行者一律为开发者本人（单人团队），因此判定必须留证**：每项的完整命令输出、抓包文件、SQL 结果须写入验收记录。只写「已确认通过」而无输出留存的，**视为未执行**。这一条是防自证条款，不是形式主义 —— 单人项目里判定权与被判定对象是同一个人，唯一的约束只能是留证。
