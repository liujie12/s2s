| --- | --- | --- |

## 1. 分支模型：条目即分支

### 1.1 必须回应的技能契约

`agent/skills/ce-commit/SKILL.md:32` 原文：

> **Branch first** — if detached HEAD, or on the default branch (main / master / the bare default name above), create a feature branch from the change content (`git checkout -b <name>`)... Do not ask — commit-only still must not leave work only on a detached HEAD or the default branch.

本仓库 HEAD 恒为 `main`。**每调用一次 `ce-commit`，技能契约就与仓库现实冲突一次** —— 这是本规范存在的直接触发原因，也是判断本规范是否落地的最直观信号：如果调用 `ce-commit` 时它还在提示「你在默认分支上」，说明规范只写在纸上。

### 1.2 分支命名

| 类型 | 格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 条目分支 | `item/<条目号>-<短描述>` | `item/113-branch-tag-spec` | 条目号取说明文档的方括号编号，去掉方括号；带后缀的条目保留后缀（`[47-b]` → `item/47-b-xxx`） |
| 修复分支 | `fix/<短描述>` | `fix/g2-false-negative` | 用于没有条目号的即时修复（一般是当轮条目内的子问题，不另编号） |
| 里程碑集成分支 | `milestone/<里程碑>` | `milestone/M4` | **可选**，仅当一个里程碑要横跨多个条目且需要独立集成时才开；本期 1 人团队大概率不需要 |

**短描述用小写 ASCII + 连字符**，理由是分支名会出现在 shell 命令、日志、`--no-ff` 合并信息里，中文在 Windows/WSL 混合环境下的编码问题已在本项目踩过（`1c82e7d` 修的就是中文用户名致 Kotlin 路径转义丢失）。

### 1.3 生命周期

```
main ──────●───────────────────●──────────────────●──▶
            \                 /                  /
             ● ● ● ●  ───────●  (--no-ff)       /
             item/113                          /
                          ● ● ●  ─────────────●  (--no-ff)
                          item/114
```

1. **开分支**：`git checkout -b item/<n>-<desc>`，起点是当前 `main`
2. **分支活着时允许脏、允许堆积** —— 这是刻意的。堆积发生在**可丢弃的分支**上，而不是 `main` 上。中间可以有跑不通的提交、可以有半成品，反正合并时会留下一个 merge 节点做边界
3. **验收后并回**：`git checkout main && git merge --no-ff item/<n>-<desc>`
4. **删分支**：`git branch -d item/<n>-<desc>`（合并后本地分支已无信息量，merge 节点才是记录）

### 1.3a 三泳道并行（solo 模式，2026-09-09 用户裁定）

条目即分支默认**串行**（同一时刻一条 item 分支活着）。solo 模式（多 agent 并行）下放宽为**泳道级并行**：固定三条常驻泳道，每条泳道内部仍严格串行，**禁止同泳道内并开两条分支**。

| 泳道 | 分支前缀 | 职责 | 并行边界 |
| --- | --- | --- | --- |
| A 后端主线 | `item/<n>-backend-<域>` | `[121]→[129]` Java 实现 | 关键路径，决定总工期；不可与同泳道并行 |
| B 前端骨架线 | `item/<n>-frontend-<域>` | `lib/core` + 各域 UI 骨架（内存 mock 先行） | 可与 A 并行推进；**「接线」动作必须等 A 对应接口就绪** |
| C 测试线 | `item/<n>-test-<域>` | 条目级单测/门禁测试骨架 | 可与 A/B 并行写；**跑测须等 A 接口就绪** |

**四条硬约束**：
1. 每条泳道在**独立 git worktree**（`wt-backend`/`wt-frontend`/`wt-test`）中推进，互不共享工作区，杜绝并发改同一文件。
2. 跨泳道的「接线/跑测」是**同步点**，不是并行：A 接口就绪 → B 接线、C 跑测，各自验收后**各自 `--no-ff` 并回 main**（三条泳道各自留 merge 节点，`git log --merges` 仍是条目清单）。
3. 每条分支严格按流程链推进：`ce-plan → ce-worktree → ce-work ⇄ ce-debug → ce-simplify-code → ce-code-review → ce-commit → ce-commit-push-pr → ce-resolve-pr-feedback → 合并(--no-ff) → ce-compound + 更新说明文档`。
4. 行政阻塞项（高德 Key、泄露 key 作废、随机密钥）不占泳道编号，由用户侧并行推进，到点未备则对应条目「验证环节」硬阻塞。

### 1.4 为什么必须 `--no-ff`

`--no-ff` 强制生成一个 merge 提交，于是：

```bash
git log --merges --oneline
```

**恰好就是条目清单**。这是整个分支模型唯一的收益点 —— 如果用 fast-forward，条目边界就消失了，`git log` 退化成一串扁平提交，与现状无异。

回退粒度也因此从「最近一次提交」变成「一整个已验收条目」：

```bash
git revert -m 1 <merge-hash>   # 一次性撤掉整个条目
```

### 1.5 `main` 的状态约定

| 约定 | 强制状态 |
| --- | --- |
| `main` 上每个 merge 节点都应是「已验收的条目」 | ⚪ 无强制（靠自律） |
| 不直接在 `main` 上提交业务改动 | ⚪ 无强制 |
| 允许在 `main` 上直接提交的例外：纯文档的错别字修正、`.gitignore` 补条目 | —— |

> **本项目当前不设 branch-gate.sh、不设 pre-commit 钩子**（条目 [113] 明确的范围边界）。
> 这意味着 §1.5 全部条款是**约定而非闸门**。按 `CONCEPTS.md`「闸门」词条的口径：**没有机器校验的规则不是闸门，正向遵守若干次也不构成它会被持续遵守的证据**。此处如实记录为 ⚪，不粉饰成「已规范」。

## 2. 提交信息约定

### 2.1 现状：惯例用了一半就没收口

近 40 条提交的实测分布：

| 形态 | 条数 |
| --- | --- |
| Conventional Commits 前缀（`feat:` / `fix:` / `docs:` / `chore:` / `refactor:` / `perf:` / `style:` / `design:`） | 15 |
| 自由文本（无前缀，直接写中文） | 6 |
| 其余 | 混合 |

典型对照（同一天的两条提交）：

- `dd54faa I2 落地：Token 的 Dart 单向出口 + 一致性断言` —— 无前缀
- `598e864 feat: Design Token 落地，17 项数值升为 Figma Variables` —— 有前缀

### 2.2 约定

沿用 `ce-commit/SKILL.md:34` 的规则（「match project commit conventions already in context; else conventional commits」）——本项目已有一半在用 Conventional Commits，故**收口到 Conventional Commits**：

```
<type>(<scope>): <中文描述>

[可选正文：为什么这么改，而不是改了什么]

[可选 trailer]
```

| type | 用于 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 只改文档 |
| `refactor` | 不改行为的结构调整 |
| `perf` | 性能改进（须附数据，参照 `5819f2e` 的「2483.9ms → 126.9ms」） |
| `test` | 只改测试与探针 |
| `chore` | 构建/配置/依赖 |
| `style` | 只改格式与视觉，不改逻辑 |
| `design` | Figma 稿层面的改动（本项目特有，已在用） |

**描述用中文**（与项目全部文档一致），**type 与 scope 用 ASCII**。

### 2.3 建议项：`Fixes: <hash>` 反向引用

当本次提交修的是某个**已入库提交**引入的缺陷时，在正文末加：

```
Fixes: 3ec783b
```

**为什么是建议项而不是硬约定**：构想文档否决清单已把它降级 —— 它的收益是让「同一个坑第二次踩」在 `git log --grep` 里可见，但代价是每次修 bug 都要去翻是哪个提交引入的，在多数情况下这个考古成本高于收益。**只在「这个坑明显是二次踩」时用**，例如 `c1ce9aa`（privacy-gate 缺稿）与 `f330f7a`（同一条盲区换了一条边再犯）之间就该有这条引用。

### 2.4 已否决：提交 trailer 里嵌验证数

构想文档否决清单原列「提交 trailer 嵌 `Verified: n/m` 验证数」，判定为**推迟**。理由：验证数的真源是探针脚本的运行输出，写进 trailer 就产生了一份人工抄写的副本 —— 而本项目在「源-派生副本」这件事上已经踩过多次（`0ca37b6` 就是把手写副本改为运行时自报）。验证数应该走 §3.3 的 `checkpoint/*` tag message，而不是每个提交都抄一遍。

## 3. 两类 tag 命名空间

刻意分两个命名空间，因为两者的**生命周期与消费者完全不同**：`rel/*` 被部署与回滚消费、有工具读；`checkpoint/*` 被人消费、用来回答「那一刻的状态是什么」。混在一个命名空间里，`git tag --list` 会变成一锅粥。

### 3.1 `rel/<env>/<APP_VERSION>` —— 发版锚点

| 项 | 规格 |
| --- | --- |
| 格式 | `rel/<env>/<APP_VERSION>`，`env` ∈ `dev` / `staging` / `prod` |
| `APP_VERSION` 口径 | **与 `deploy/scripts/deploy.sh:300` 的 `export APP_VERSION="${TIMESTAMP}"` 同一个值**，即 `YYYYmmdd-HHMMSS` |
| 示例 | `rel/prod/20260930-142530` |
| 类型 | 附注 tag（`git tag -a`） |
| message 必含 | ① 镜像 tag（= `APP_VERSION`）② 门禁结论（PASS 项数 / SKIP 项数）③ 若有 `--gate-allow-skip` 放行则写明理由 |
| 打 tag 时机 | 部署成功后，**不是部署前** —— 打在前面等于给未验证的东西背书 |

**为什么 tag 名要与 `APP_VERSION` 严格同值**：`部署架构设计文档.md:487` 已定「发版镜像 tag 为发版时间戳（`APP_VERSION=YYYYmmdd-HHMMSS`），这是 §9.4 方案 B 能按 tag 回滚的前提」。若 git tag 用另一套编号，回滚时就要做一次「git tag ↔ 镜像 tag」的映射查找 —— 而这个映射没有任何地方存着，只存在于当时那个人的记忆里。同值即免映射。

回滚时的用法：

```bash
git checkout rel/prod/20260929-101500      # 取到当时的源码
APP_VERSION=20260929-101500 S2S_ENV=prod docker compose ...   # 取到当时的镜像
```

两者用同一个字符串，这是这条规格的全部意义。

### 3.2 与出包门禁的衔接（尚未闭合）

`DevSecOps接入方案.md` §4.4 的 L3 出包门禁 11 步中，第 2 步是「确认当前分支与 commit hash 写入日志」。**本规范给这一步提供了可写的内容**：分支名（`item/<n>-*` 或 `main`）与最近的 `checkpoint/*` tag。

反向的欠账也要如实记：

- `release-gate.log` 当前住在 `build/` 目录下，而 `build/` 既被 `.gitignore` 忽略、又是 `flutter clean` 的删除对象 —— **它无法用 git tag 锚定**。这是构想文档 S9 待办项，本轮不做
- L3 出包门禁脚本本身尚不存在（`DevSecOps接入方案.md` §7 待办表第 3 项，🔴 发内测包前）。所以 §3.1 的 `rel/*` tag 目前**只有手工执行路径**，没有脚本自动打

### 3.3 `checkpoint/<里程碑>` —— 状态快照锚点

| 项 | 规格 |
| --- | --- |
| 格式 | `checkpoint/<里程碑标识>`，标识取说明文档 §1.3 里程碑表的编号（`M1` / `M2.5` / `M3` / `M3.1`…） |
| 类型 | **必须是附注 tag**（`git tag -a`），因为轻量 tag 存不了 message |
| message 必含 | ① 里程碑名 ② 实际完成日期 ③ **当时的验证数**（探针项数、框数、测试项数等可核对的数字）④ 若无 git 锚点则写明 |
| 唯一来源 | `说明文档.md` §1.3 里程碑表 —— **不允许自行发明里程碑** |

**为什么 message 里要写验证数**：这是 `checkpoint/*` 与「随便找个 hash 打个标记」的分界。`git show checkpoint/M3` 应当能直接回答「M3 验收时到底验了什么」，而不需要再去翻说明文档。验证数是那一刻的可核对事实，日期不是（日期只说明「什么时候」，不说明「达到了什么」）。

### 3.5 「无 git 锚点」的处置：不强行找近似提交

M1 / M2 / M2.5 / M2.6 / M3.1 五个里程碑**不打 tag**。

这是刻意的，而不是遗漏。可以强行给 M1 打在 `2320ca8`（首个提交）、给 M2 打在 `b65542e`（三件套入库），但那样做的后果是：

`git show checkpoint/M2` 会显示 2026-08-25 的一个提交，而说明文档写 M2 完成于 2026-08-10 —— **tag 与真源矛盾**。下一个人（或半年后的自己）会花时间去搞清哪个对，而正确答案是「两个都对，只是 tag 打错了对象」。

这正是项目反复强调的判定原则在文档层的应用（`CONCEPTS.md`「闸门」词条 / `DevSecOps接入方案.md` §3.2）：

> **判不了就不要报通过。**

「M2 在 git 里没有锚点」是一个**准确的事实**，比「M2 的 tag 指向一个语义错误的提交」更有价值。故本节把它写下来，而不是用一个近似 tag 把它盖掉。

若将来需要为这些里程碑留 git 锚点，正确做法是**在当时就打 tag**，而不是事后考古。

### 4.1 tag 的推送

tag 默认**不随 `git push` 推送**。需要显式推：

```bash
git push origin checkpoint/M3
```

当前本地领先 `origin/main` 64 个提交且尚未 push，故 tag 也未推远端。**tag 不推远端就仍然是宿主机本地状态**，与 §0.1 批评的「随宿主机重建消失的锚点」同类。push 时机由后续条目决定。

## 5. 与现有门禁的分界

| 层 | 归属文档 | 本文档的关系 |
| --- | --- | --- |
| L1 pre-commit | `DevSecOps接入方案.md` §3.1 / §7.3 | **本文档不定义**，且本轮明确不做 |
| L2 本地全量门禁（`deploy/scripts/gate-check.sh` 13 项） | `deploy/docs/部署架构设计文档.md` §14.5 | 无交集。门禁判的是代码与环境，本文档管的是 Git 拓扑 |
| L3 出包门禁 | `DevSecOps接入方案.md` §4.4 | 单向依赖：L3 第 2 步需要「分支与 commit hash」，本文档提供其口径（§3.2） |

**为什么分支规范不做成门禁**：条目 [113] 用户明确定为「仅规范文档 + 回填 tag，不加强制拦截」。补充理由是 —— 分支规范的违反是**可见的**（`git branch --show-current` 一眼看出在不在 main 上，`git log --merges` 一眼看出有没有条目边界），而门禁真正要防的是**不可见的失效**（如 `gate-lib.sh` 的 SKIP 档被改成 0 却仍打印绿色结论）。把稀缺的门禁工程量花在可见问题上，不划算。

## 6. 强制状态清单（本文档最需要如实维护的部分）

| 条款 | 位置 | 强制状态 |
| --- | --- | --- |
| 分支命名格式 | §1.2 | ⚪ 无强制 |
| 条目分支生命周期（开→脏→`--no-ff` 并回→删） | §1.3 | ⚪ 无强制 |
| `--no-ff` 不得省略 | §1.4 | ⚪ 无强制（省了不会报错，只会让条目边界消失） |
| 不在 `main` 上直接提交业务改动 | §1.5 | ⚪ 无强制 |
| Conventional Commits 前缀 | §2.2 | ⚪ 无强制（无 commit-msg 钩子） |
| `Fixes: <hash>` 反向引用 | §2.3 | ⚪ 建议项，本就不强制 |
| `rel/*` tag 与 `APP_VERSION` 同值 | §3.1 | ⚪ 无强制（L3 出包脚本尚不存在，见 §3.2） |
| `checkpoint/*` 必须是附注 tag 且 message 含验证数 | §3.3 | ⚪ 无强制 |
| 里程碑标识只能取自说明文档 §1.3 | §3.3 | ⚪ 无强制 |

**全部 9 条均为 ⚪ 无强制。** 这张表现在没有一个绿灯，是本轮范围的真实反映，不是笔误。

按项目已沉淀的判据（`docs/solutions/workflow-issues/verification-code-fails-silently-as-pass.md:167`「失效的门禁比没有门禁更糟」）—— 一份没有强制的规范至少还诚实：它不会让人误以为有东西在把关。真正危险的是写了 `branch-gate.sh` 却因为某个 `|| true` 而从不拦截。

若将来要给某条加强制，应同时在本表把 ⚪ 改成对应状态，**并写明校验它的脚本路径与判据**（照 `DevSecOps接入方案.md` §3.2 四要素：执行者、工具与命令、失败判定、留证方式）。
