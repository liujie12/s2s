## 1. 怎么读这份文档

上一份文档回答「系统由哪些部分组成」，这一份回答「为什么是这些部分」。每一项选型按同一个结构写：

- 结论与批次
- 被否掉的替代方案，以及否掉的具体理由
- 什么条件下这个选择应当被推翻（退出条件）

读完这份文档，一个没参与讨论的人应当能复述出每项被否方案的理由，而不只是记住结论。

### 1.1 压缩了全部选择空间的三条约束

在看任何一项选型之前，先看这三条。它们不是「偏好」，而是让绝大多数常规方案根本跑不完的硬边界：

| 约束 | 数值 | 出处 |
|---|---|---|
| 人力 | Batch1 为 1 人加 AI 辅助 | `docs/BRD.md:298` |
| 工期 | 38 自然日 / 28 工作日，明确「高强度满负荷，无缓冲」 | `说明文档.md:185-202` |
| 成本 | 域名加服务器合计约 131 元/年 | `docs/上架前置工作指导手册.md:94` |

一台 2 核 2G 的机器、一个人、38 天。任何需要额外中间件进程、需要 GPU、或需要按技术层横向拆多模块的方案，不是「重一点」，是**做不完**。后面每一处「否掉」，基本都能追到这三条中的某一条。

## 3. 语言与框架：Java 21 加 Spring Boot 3

**结论**：服务端用 Java 21 加 Spring Boot 3。批次 Batch1。依据 R1。

**这是用户直接指定的选择**（session-settled: user-directed），不是权衡后的推荐。记录被否方案是为了让后来者知道当时看过什么：

| 方案 | 否掉的理由 |
|---|---|
| Go | 生态里现成的东西少，短工期内每个能力都要自己搭，1 人加 38 天撑不起 |
| Node.js | 单进程 CPU 密集场景（聚合计算、加解密）表现弱，且类型安全需额外引入 TypeScript 工具链 |
| Python | 同样的内存预算下并发承载能力最差，2G 机器上尤其吃紧 |

选 Java 也有明确代价，必须提前承认：**JVM 是内存预算里最贵的一项**。唯一权威数值在《系统总体架构设计文档》§4.1 的内存预算表：JVM 整体 750MB（含堆外与元空间），其中 `-Xmx600m` 是堆的硬上限而不是建议值。Go 在这台机器上能省出约 500MB。这个代价是为生态成熟度付的钱。

（本节曾写「800MB / `-Xmx640m`」，那是 Caddy 未承担 TLS 终止时的旧口径，已废弃。任何一处出现 640m 或 800MB 均以 §4.1 表为准。）

**Java 21 而不是 17**：2026-09-04 用户指令升级。但**虚拟线程不开启** —— 本项目瓶颈在内存不在线程数（2 核 2G、并发 20），CPU 密集场景虚拟线程无收益；且 Java 21 的 `synchronized` 会导致载体线程 pinning（MyBatis-Plus / HikariCP 链路上 `synchronized` 块不少），Spring Boot 4.1 官方文档明确「for the best experience, Java 24 or later is strongly recommended」。

**虚拟线程退出条件**：升到 Java 24 或 Batch1 压测证明 I/O 阻塞是瓶颈时再开。

**换语言退出条件**：内存成为主要瓶颈且已无法通过调参解决时，才考虑换语言 —— 但那时更合理的动作是加机器规格，不是重写。

### 3.1 构建工具：Maven（2026-09-06 定案）

**结论**：服务端构建工具用 **Maven**，不用 Gradle。批次 Batch1。本节是构建工具的**唯一口径源**（此前本文档对构建工具零提及，《DevSecOps 接入方案》D-1 与《系统安全设计方案》缺口 G6 均指向此处待定）。

| 判断项 | 结论 |
| --- | --- |
| 生态匹配 | Spring Boot 官方文档与绝大多数示例以 Maven 为默认，start.spring.io 生成的工程首选 Maven。1 人 38 天工期下，"抄得到的样例最多"本身就是首要指标 |
| AI 辅助准确率 | `pom.xml` 是纯声明式 XML、无 DSL 逻辑分支；Gradle 的 `build.gradle(.kts)` 是可执行脚本，AI 生成时容易混用 Groovy / Kotlin DSL 两套语法，排错成本落在唯一的开发者身上 |
| 本项目用不上 Gradle 的长处 | Gradle 的优势在多模块并行构建与增量编译。本项目**单体单进程、单模块、无自定义构建逻辑**（§4），这些优势全部为零 |
| 内存预算 | 2 核 2G 机器上 Gradle Daemon 常驻内存是实打实的负担。虽然构建通常在开发机而非 ECS 上执行，但本项目**部署形态为宿主机直接 build**（§10 Docker Compose 无独立 CI runner），Daemon 会与 JVM 750MB（《系统总体架构设计文档》§4.1）争抢同一份 2G |

**这个决定不是"哪个工具更好"，而是"哪个工具在本项目的约束下不会产生额外工作"。** Gradle 在多模块大型工程上确实更快，但那个收益需要一个本项目不存在的前提：模块数大于 1。而它的成本（DSL 语法歧义、Daemon 内存）在本项目是立即发生的。选型只看约束内的净值。

**由此确定的依赖锁定与门禁命令口径**（《DevSecOps 接入方案》§3 依赖锁定、§5 全部服务端命令据此展开）：

| 用途 | 命令 |
| --- | --- |
| 依赖树审查 | `mvn dependency:tree` |
| 可升级依赖巡检 | `mvn versions:display-dependency-updates` |
| 单元测试 | `mvn test` |
| 集成测试 | `mvn verify` |
| 出包 | `mvn -DskipTests package` |

**版本号纪律**：`pom.xml` 中一切依赖写**显式版本号**，禁止 `LATEST` / `RELEASE` / 版本范围写法。Spring Boot 的 `spring-boot-starter-parent` 负责统一托管版本，不在子依赖上另写版本覆盖，除非有明确的安全补丁理由并在 `pom.xml` 就地注释说明。

**退出条件**：若后续拆出多模块（当前架构 §4 明确否掉微服务，此条实际不会在 Batch1/Batch2 触发），再重评 Gradle。

## 4. 架构形态：单体单进程

**结论**：全部功能域跑在同一个 JVM 进程内，不拆微服务。批次 Batch1。依据 R1。

| 方案 | 否掉的理由 |
|---|---|
| 微服务 | 2G 内存放不下多个 JVM。每个 Spring Boot 进程基础开销就有 200MB 以上，拆三个就把内存吃光了，还没算注册中心与网关 |
| 模块化单体（多 module 编译） | 对 1 人团队没有收益 —— 模块边界的价值在于隔离多人协作，而当期靠目录约定（R9）已经够了 |

单体的代价是无法独立扩缩容与独立发布。当期无所谓：单机部署本来就没有扩缩容，发版就是重启。

**退出条件**：出现两个负载特征差异极大、必须独立扩容的功能域时（最可能是 `ai` 与 `map`）。在此之前，垂直切分的目录结构已经为将来拆分留好了缝 —— 每个功能域自带完整的 controller 到 mapper，拆的时候是整目录搬走。

## 5. 持久化：MySQL 8.4 LTS

**结论**：MySQL 8.4 LTS 作为唯一持久化，承载业务、埋点、审计三类数据。向量检索推到 Batch3。批次 Batch1。依据 R2。

**为什么是 8.4 而不是 9.x**：8.4 是 LTS，9.x 是创新版本（发布周期短、支持窗口窄）。生产环境不用创新版本。

**关于向量检索，这里值得写清楚，因为容易被误解为「MySQL 做不了向量」**。实际查证结果是三条路径都存在，但三条都不匹配当期条件：

| 路径 | 实际情况 | 为什么不用 |
|---|---|---|
| MySQL 9.x 原生 | 有 `VECTOR` 类型和 `DISTANCE()` 函数，但**没有 ANN 索引** | 只能全表暴力比对，数据量一上来就退化成全表扫描 |
| MyVector 社区插件 | 提供 HNSW 索引 | 需要自行编译，且不支持 Windows 构建 —— 而开发环境是 Windows（`说明文档.md` 环境约定），本地跑不起来的东西不能上生产 |
| 云厂商增强版（如 PolarDB） | 功能完整可用 | 需要购买托管实例，与 131 元/年的成本量级不在一个数量级 |

所以结论不是「MySQL 不能做向量」，而是「三条能做的路各有一个当期迈不过去的门槛」。当期匹配只有规则排序与 GBDT 两条路（详见第 8 节）。

**为什么埋点也放 MySQL**：这是用户明确的选择，附带条件是「需要做好后期日志暴涨迁移的准备」。完整的量级测算、三条防线、迁移触发阈值都在《可观测性架构方案》里。

**退出条件**：语义召回成为匹配效果的主要瓶颈，且样本量已足以验证向量方案确实优于 GBDT 时（Batch3）。届时优先考虑独立向量库而不是给 MySQL 装插件。

## 6. 缓存：Caffeine 加 Redis 两层

**结论**：进程内 Caffeine 承载极少变更的热数据，Redis 7 承载跨请求共享状态。批次 Batch1。依据 R3。

**这是用户在三个选项中直接指定的两层方案**（session-settled: user-directed）。

两层的分工是硬边界，不是「都可以放哪层随意」：

| 数据 | 放哪层 | 为什么不能放另一层 |
|---|---|---|
| 三级分类树、模板 Schema | Caffeine | 每个请求都要读，走网络到 Redis 是纯浪费；且它极少变更，用版本号失效就够了 |
| 会话与 Token | Redis | 重启不能丢，Caffeine 是进程内的 |
| 限流计数（联系限频三维、AI 配额） | Redis | 计数必须是全局唯一的一份，放 Caffeine 会导致计数分裂、限频失效 |
| 远景聚合结果 | Redis | 计算代价高、可跨请求复用，但体积不小，占进程内存不合适 |

| 方案 | 否掉的理由 |
|---|---|
| 只用 Redis | 分类树这种每请求必读的数据白付一次网络往返，直接侵蚀 P95 ≤150ms 的预算 |
| 只用 Caffeine | 限流计数放进程内在单实例下"能用"，但一旦上第二个实例就静默失效 —— 这是会埋雷的省事 |

Redis 的 `maxmemory` 定为 128MB（进程预算 150MB）。这里有一个必须显式定死的参数，否则默认值会造成静默故障：

| 参数 | 取值 | 为什么不能用默认值 |
|---|---|---|
| `maxmemory-policy` | `volatile-lru` | 默认 `noeviction` 在内存打满时会让写命令直接报错，等于登录与限流全挂。而 `allkeys-lru` 又会淘汰没设过期时间的键 —— 选 `volatile-lru` 意味着只淘汰设过 TTL 的键 |
| 持久化 | 开 AOF，`appendfsync everysec` | 只开 RDB 时重启会丢最后一个快照点之后的全部会话，用户被无故登出 |

由此产生一条编码纪律：**会话、Token、幂等键这三类不可重建的数据必须显式设置 TTL**，这样它们才处于 `volatile-lru` 的候选集中被有序淘汰，而不是在 `allkeys` 模式下被随机清掉；同时**不能把它们当作唯一存储** —— 幂等键丢失时的兜底是数据库唯一约束，不是 Redis。

**已知延后项**：多实例时 Caffeine 需要跨实例失效通知，单机单实例下不构成问题，已登记为延后项。

**退出条件**：无。两层缓存是长期形态。

## 7. 数据访问：MyBatis-Plus

**结论**：数据访问统一走 MyBatis-Plus。简单 CRUD 用自动能力，性能敏感语句写 XML 并附 `EXPLAIN` 结论。批次 Batch1。依据 R10。

| 方案 | 否掉的理由 |
|---|---|
| Spring Data JPA | `docs/PRD.md:2376` 要求手写网格 `IN` 集合查询并用 `EXPLAIN` 验收索引命中。JPA 自动生成的 SQL 不好控，为了控它要写大量 native query，反而比 MyBatis 更绕 |
| 原生 MyBatis | 简单 CRUD 也要手写 XML，1 人 38 天的工期下这是纯粹的时间损耗 |
| JDBC Template | 抽象层级太低，实体映射全靠手写 |

MyBatis-Plus 正好落在中间：14 张表的基础 CRUD 靠自动能力免写，而地图取 Pin 这类必须逐字控制 SQL 的地方允许写 XML。

**配套纪律**：任何写在 XML 里的查询都要附一条 `EXPLAIN` 结论作为注释，说明它走了哪个索引。这不是文档要求而是代码要求 —— `docs/PRD.md:2367-2387` 给的是验收标准（无全表扫描、P95 ≤150ms），具体列序要实测定，实测结论必须留在代码里。

**退出条件**：无。

## 8. AI 能力：两件不同的事，两个不同的答案

这一节是全文最容易做错决策的地方，因为「AI 能力」实际是两件独立的事，它们的最优解相反。

### 8.1 排序模型：只能自训，成本几乎为零

**结论**：GBDT 用 LightGBM 在本地离线训练，模型文件随应用发布，线上只推理不训练。批次 Batch2 起。依据 R4。

这件事没有「买」的选项 —— 排序模型的特征是本项目独有的（分类、距离、完整度、认证状态、行为标签），不存在通用现成模型。所以只能自训。

好消息是自训成本几乎为零：

| 项 | 成本 |
|---|---|
| 训练算力 | 0（LightGBM 在开发机 CPU 上跑，几万条样本是分钟级） |
| 标注 | 0（标签来自 `contact_event` 的客观行为，不需要人工标注） |
| 线上推理 | 0（模型文件几 MB，CPU 推理，不需要 GPU） |

真正的瓶颈不是算力也不是钱，是**样本量**。启用是分阶段的：

| 线上累计样本 | 排序方式 |
|---|---|
| 不足 1 万条 | 只跑规则排序，不加载模型 |
| 达 1 万条 | 启用 LR |
| 达 10 万条且单类目不少于 2000 条 | 启用 GBDT |

`docs/BRD.md:280` 的 18 条冷启动种子远不够训练，`docs/BRD.md:289` 也已记录 R10 样本量不足风险。因此 GBDT 的实际启用时点由真实用户行为量决定，不能排进工期。这一点必须写在文档里，否则会被当成排期任务承诺出去。

`docs/BRD.md:59` 与 `docs/BRD.md:243` 的绿清单允许 LR 加 GBDT，本选择在合规边界内。

### 8.2 文本解析：调 API，自训比买贵十倍

**结论**：发布文本的结构化解析调用外部大模型 API，不自建也不自训语言模型。批次 Batch2。依据 R5。

这件事和排序模型相反 —— 通用现成能力已经很成熟，自训是在重复造轮子，而且造得更差。

成本实算（100 用户 × 5 次/日 = 1.5 万次/月 × 约 350 token）：

| 方案 | 一次性投入 | 月度运行 | 实现复杂度 | 卡点 |
|---|---|---|---|---|
| **调外部 API** | 0 | 10 至 30 元 | 低（一个 HTTP 客户端加 prompt 模板） | 无 |
| 自训 3B 小模型 | 需标注 2000 至 5000 条语料 + 租 GPU 训练 | 推理需 GPU 云实例，量级在百元以上 | 高 | **鸡生蛋问题**：语料要从真实发布数据里来，但真实数据要等产品上线才有 |
| 端侧 3B 离线 | 模型转换与端侧适配 | 0 | 很高 | `docs/BRD.md:374` 列为黄清单待验证，且低端机内存与包体都成问题 |

「鸡生蛋问题」是决定性的：自训需要的语料只能从上线后的真实发布数据里积累，而发布功能又需要解析能力才好用。所以自训在 Batch2 这个时点物理上不可行，不是「更贵」而是「做不了」。

`docs/BRD.md:59` 的红清单禁止 70B 端到端，本选择用的是通用 API 而非端到端大模型驱动业务决策，在边界内。

**成本假设的脆弱处**：10 至 30 元是按 100 用户与 `docs/PRD.md:958` 的配额分层算的。用户量或配额上调会**线性放大**这个数字。上量前必须重算，不能沿用。

**退出条件**：真实发布数据积累到 5000 条以上且 API 月度成本超过 GPU 实例成本时，才重新评估自训。

## 9. 云资源：ECS 经济型 e 加 OSS

**结论**：一台阿里云 ECS 经济型 e（2 核 2G、40G ESSD、3M 带宽），图片与媒体存 OSS。批次 Batch1。依据 R6。

| 方案 | 实价 | 否掉的理由 |
|---|---|---|
| **ECS 经济型 e 2 核 2G** | 99 元/年，99 计划新老同享、续费同价 | 选中 |
| 阿里云轻量应用服务器 | 38 至 68 元/年 | 更便宜，但带宽与磁盘弹性不足，且升配路径受限 |
| 腾讯云轻量 | 68 至 99 元/年 | 同上，且与 OSS 不同厂会让图片直传的内网流量假设失效 |
| 更高规格 ECS | 数百元起 | 超出 131 元/年的成本量级 |

**2 核 2G 是能贴住内存预算的下限，不是宽裕选择**。五项进程合计约 2000MB（MySQL 450 + Redis 150 + JVM 750 + Caddy 50 + 系统 600），必须配 swap 兜底。降到 1 核 1G 则 MySQL 与 JVM 二者只能活一个。明细见《系统总体架构设计文档》§4.1。

**经济型 e 的 CPU 是共享型，阿里云不提供性能 SLA**，这是一条必须登记的假设而不是可忽略的细节：

- 同物理机上其他实例的负载会通过 CPU steal 影响本实例，`docs/PRD.md:2415-2426` 的 P95 数字在这种机型上**不是可稳定复现的承诺**。
- 因此 P95 复测时必须同时记录 CPU steal（`top` 的 `st` 列或 `vmstat` 的 `st`）。**steal 全程均值超过 10% 时的实测结果不算有效数据**，要换时段重跑 —— 但重跑有上限，终止规则与留存要求见《系统总体架构设计文档》§10.3.4（最多 3 次，3 次全废即判机型不满足 SLA 进入升配评估，不得记作「待复测」）。
- 若排除 steal 后 P95 仍跑不过，才是实现问题；若只在 steal 高的时段跑不过，则升配到独享型是唯一解，需重估成本。

**为什么图片必须走 OSS 直传**：只有 3M 带宽。如果图片经过 ECS 转发，几个用户同时上传就能把带宽打满，连带把 `/map/pins` 的 P95 ≤300ms 一起拖垮。这是必要条件而不是优化。

**成本假设的脆弱处**：99 元续费同价是阿里云的促销政策（99 计划标注新老同享），不是合同承诺。若续费涨价，`docs/上架前置工作指导手册.md:94` 的 131 元/年量级需重算。

**退出条件**：内存预算调无可调、或 40G 磁盘被埋点数据挤占（后者的判据在《可观测性架构方案》的迁移阈值里）。

## 10. 编排：Docker Compose

**结论**：MySQL、Redis、应用三个进程由 Docker Compose 编排。批次 Batch1。依据 R7。

| 方案 | 否掉的理由 |
|---|---|
| Kubernetes | 单机上 K8s 自身的控制面就要吃掉几百 MB 内存，是纯开销。2G 机器上装 K8s 相当于把一半内存交给调度器 |
| 裸机直装 | 环境不可复现，开发机（Windows）与生产（Linux）差异无法收敛 |
| 单个大镜像塞三个进程 | 违反容器单进程原则，任一进程崩溃会带走全部 |

Compose 的代价是没有自愈、没有滚动发布。内测阶段接受：单机本来就没有滚动发布的余地。

**退出条件**：出现第二台机器时。

## 11. 日志归档：阿里云 SLS（预置未启用）

**结论**：埋点事件与审计事件先落 MySQL，应用日志以 JSON 单行格式落盘（三类数据三套规则，见《可观测性架构方案》第 2 节）；SLS 作为预先指定的迁移目标，阈值命中后启用。批次为阈值命中后。依据 R13、R16。

现在不上 SLS 的理由很简单：内测 100 DAU 约 45MB/月，MySQL 完全吃得下，提前上是无谓的复杂度与成本。

**这里的关键不是「先用 MySQL」，而是「迁移目标和触发条件今天就定死」**。历史上这类决策出问题都不是因为选了便宜方案，而是因为便宜方案撞墙时没人知道该往哪走，于是选择了加机器 —— 那条路在 40G 盘上是走不通的。完整的量级测算与三条阈值在《可观测性架构方案》。

## 12. 客户端依赖选型

前 11 节全是服务端选型。但客户端目前只有 6 个功能性运行时依赖（`flutter_riverpod`、`go_router`、`amap_map`、`x_amap_base`、`shared_preferences`、`url_launcher`；`cupertino_icons` 是图标字体资源不计入），**其中没有一个能发 HTTP 请求**。这意味着接服务端所需的依赖一个都还没选，而选型漏了的直接后果是：写代码时随手 `import` 一个，不同模块用不同库，最后有两套网络栈和两套序列化风格。

因此在此把 Batch1 必需的客户端依赖定死。判据统一是「够用即可、依赖数量最小、都是 pub.dev 一线包」——1 人加 AI 辅助的人力约束下，每引入一个库都要付学习与排障成本。

| 用途 | 选定 | 否掉的 | 理由 |
|---|---|---|---|
| HTTP 客户端 | `dio` | `http` | `http` 太薄：拦截器、超时分离配置、请求取消都要自己写。而《系统总体架构设计文档》§6.5 的单飞续期、§6.6 的退避重试、§9.2 的请求竞态取消**全部依赖拦截器与取消能力**。用 `http` 等于自己实现半个 `dio` |
| JSON 序列化 | 手写 `fromJson` / `toJson` | `json_serializable`、`freezed` | `lib/domain/` 下 7 个纯模型共 1424 行已经是手写风格，引入代码生成要改全部模型并加 `build_runner` 到构建链。**Batch1 只需接 20 个接口**（全量 39 个中的当期子集，见《系统总体架构设计文档》§9），手写成本低于改造成本。**这是刻意接受的技术债**：模型超过 20 个、或 Batch2 全量 39 个接口全部接入时应重新评估 |
| UUID 生成 | `uuid` | 手写随机数 | `Idempotency-Key` 与 `X-Interaction-Id` 都要 UUID v4（§6.3 已定格式），手写容易出版本位与变体位错误，而服务端会按正则拒收 |
| 网络类型探测 | `connectivity_plus` | 平台通道自写 | `network_type` 是《可观测性架构方案》§4.5 的必采项，也是 P95 弱网排除的唯一判据。自写平台通道要维护两端原生代码 |
| 本地持久化 | `shared_preferences`（已有） | `sqflite`、`hive` | 需要持久化的只有三类：会话 Token、设备指纹、埋点队列（上限 2000 条）。前两类是键值，第三类用 JSON 字符串列表足够。引数据库为 2000 条记录不值得 |
| 图片选择 | `image_picker` | — | 发布流程必需，无替代方案 |
| 图片缓存 | `cached_network_image` | Flutter 自带 `Image.network` | 列表页与地图页会反复加载同一批图，自带的内存缓存没有磁盘层，滚动回来就重新下载。3M 带宽下这是实打实的体验损失 |
| 定位 | `amap_map` 自带（已有） | `geolocator` | 高德 SDK 自带定位，再引一个定位库会有两套权限请求逻辑与两套坐标系（GCJ-02 与 WGS-84）转换问题 |
| 设备信息 | 不引 | `device_info_plus` | 设备指纹已定为客户端自生成 UUID（《可观测性架构方案》§4.5），不采集任何真实硬件标识，因此不需要这个库 |

新增依赖数：`dio`、`uuid`、`connectivity_plus`、`image_picker`、`cached_network_image` 五个，客户端运行时依赖从 6 个增至 11 个。

三条纪律：

- **不引第二个 HTTP 客户端。** 任何模块都必须走统一封装的 `dio` 实例，不允许直接 `HttpClient` 或 `http.get`。
- **`mem_peak_mb` 不引库。** 它由 Android 侧平台通道采集（《可观测性架构方案》§4.5），iOS 侧 Batch1 上报空值。为一个指标引一个跨端性能监控库不划算。
- **依赖版本锁定在 `pubspec.lock`。** 内测期不做依赖升级，任何升级都要重跑一遍五大 P0 闭环。
