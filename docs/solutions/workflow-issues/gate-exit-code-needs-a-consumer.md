# 门禁的退出码必须有消费方：判据严谨度乘以零仍是零

## Context

一轮门禁建设跨了三个工作条目：前两轮逐条修复判据缺陷，累计修掉七处「什么都没校验就报合格」的伪 PASS —— 其中五处是无条件报合格，两处是判定对象缺失却落入合格分支；第三轮才把门禁的退出码接进部署脚本。

复盘时才看清一件事：**在第三轮之前，那七处修与不修，对发版流程的实际影响完全相同。** 部署脚本当时调用门禁的写法是「执行并把输出送进日志」，退出码在传递过程中被吞掉，没有任何分支读它。门禁每次都跑、每次都正确打印 `[FAIL]`，然后发版照常继续。

这与「[校验代码自身失效时会输出 PASS](file:///d:/developer/code/aicoding/s2s/docs/solutions/workflow-issues/verification-code-fails-silently-as-pass.md)」是两个不同的失效层：那一篇讲**门禁内部**算错了；这一篇讲**门禁算对了，但结论没有出口**。后者更难发现，因为现场毫无异常——脚本正常执行、结论正常打印、日志正常落盘，唯一的差别是那个数字没人读，它不产生告警，也不出现在任何报表里。

## Guidance

### 1. 门禁有效性 = 判据严谨度 × 是否有调用方消费退出码

后一项为零时，乘积为零。落地阶段的第一个问题不是「判据够不够严」，而是：

> **哪一行代码读了它的退出码？**

答不出具体位置，就视为这道门禁**未落地**，不计入已完成。

排查时逐项过三关：

| 检查点 | 危险形态 | 后果 |
|---|---|---|
| 调用写法 | `执行门禁 \| 送进日志函数`，返回值随传递被吞 | 上游全部判据同时失效 |
| 容错兜底 | 调用链上任意一处把非零码归零（尾随的「忽略失败」惯用语、包裹的容错分支） | 只要有一处，其上游全部判据同时失效 |
| 管道尾巴 | 管道末位是 `tee` 之类恒 0 的命令，用 `$?` 取码 | 恒取到 0；须读管道首位的退出码 |

第三条有个具体陷阱：为了让门禁输出同时进日志而写 `门禁 | tee -a 日志`，此时 `$?` 是 `tee` 的退出码。改用保存各段退出码的数组取首位即可，但**不能用「忽略失败」惯用语去压 `set -e`**——那个惯用语会把该数组整体覆盖成 `(0)`，门禁彻底失效。正确顺序是：临时关闭 pipefail → 跑管道 → 读数组首位 → 恢复 pipefail。

### 2. 门禁定义的要素清单须含第五项「消费方」

常见的四要素是**执行者、工具与命令、失败判定、留证方式**。这四项只规定了门禁自己怎么算，**没有规定有没有人读结果**：

- 「失败判定」回答的是「门禁如何得出不合格」
- 「消费方」回答的是「得出不合格之后，谁会因此停下」

前者齐备而后者缺失，正是上面描述的静默失效。故门禁清单加第五列，填具体到脚本名与函数名（或 CI 作业的依赖关系）；该列为空即视为未落地。**这一列要在评审门禁方案时作为必填项检查，而不是落地后回补。**

### 3. 退出码分三档，且带理由放行只对「不知道」生效

两档（0/1）表达不了「不知道」。「判不了」既不是合格也不是不合格，归入任一档都会造成错误决策：归 0 是放过未知风险，归 1 是让正常缺件的环境永久无法通行。

放行开关三条约束：

| 约束 | 违反后果 |
|---|---|
| 只对「判不了」生效，对「不合格」无效 | 放行退化为无条件跳过门禁 |
| 理由必须随开关附带（开关值即理由文本，不接受裸开关） | 放行记录里只有「放行了」，无法事后审计 |
| 理由须写入调用方的留证日志 | 下次无人知道当时为何放行 |

### 4. 判定结果四态，「判不了」与「不适用」不能合并

第三态「跳过」还需再拆一次：

| 态 | 含义 | 对退出码 |
|---|---|---|
| 合格 | 已判定，符合要求 | 无影响 |
| 不合格 | 已判定，不符合要求 | 失败档 |
| 判不了 | **本项应当被判定**，但前置条件缺失 | 「不知道」档 |
| 不适用 | **本项按当前环境设计就不存在判定对象** | 无影响 |

**分界线是「有没有可判定的对象」**，不是「有没有判成功」。合并的后果可以直接推算：若某环境下必然存在若干「按设计不存在」的项，把它们计入「判不了」，则该环境每次运行都必然「判不了 ≥ 1」、退出码恒为「不知道」档。**恒定报警等于没有报警**——规则会在第一天被「忽略失败」惯用语绕过。

### 5. 建设顺序：先接链路，再精修判据

接通「退出码 → 调用方」的工作量，通常远小于逐条精修判据，但它决定精修是否产生任何效果：

| 顺序 | 前期收益 | 风险暴露 |
|---|---|---|
| 先精修判据、后接链路 | 零（成果无人消费） | 期间自认为已受保护，实际完全裸奔 |
| 先接链路、后精修判据 | 立即生效（哪怕判据只有一条） | 逐轮递减 |

判定动作：每轮结束时问一句——**这一轮的产出，在当前状态下已经能改变交付流程的行为了吗？** 答「还不能，要等后面某一步」的，说明顺序排错了。阶段划分以「链路是否已通」为界，而非以「判据完成了几条」为界。

## Why This Matters

这条失效的隐蔽性高于绝大多数门禁缺陷，原因是它**没有任何观测面**。判据算错至少还能通过负向输入构造出来；退出码无人消费不产生任何可观测差异——同一份日志、同一组绿字、同一个耗时，唯一区别在一个没被读取的整数上。

代价则是叠加的：整个未接通期间，团队获得的是「门禁已经在保护交付」的错觉，而这段时间恰好是最需要保护的施工期。更糟的是，一旦有人后来发现，之前所有「门禁通过」的记录都要重新判定为无效证据——包括那些确实合格的。

顺序错误的成本在这里被放大：把最便宜的一步放在最后，等于让前面每一轮的产出都在零收益状态下等待。这不是「效率低」，而是「期间的风险敞口按未受保护计算」。

## When to Apply

- 门禁从方案进入代码实现的那一刻——**第一个动作就是接链路**，而不是写第一条判据
- 门禁脚本已存在但从未拦住过任何一次发版时，先查有没有消费方，再查判据
- 评审门禁方案时，把「消费方」当作与「失败判定」同级的必填项
- 新增门禁层级（如从部署面扩到出包面）时，确认新层级的退出码也有各自的消费方
- 任何「先有规格、后建门禁」的场景：规格越完备，越容易一头扎进判据细节，把「谁来读结论」当收尾工作

## Examples

**反例：返回值被吞**

```bash
# 门禁每次都跑、都正确打印 FAIL，然后发版照常继续
run_gate_check() {
  log "$(bash "${gate_script}" "${ENV_NAME}")"   # 退出码随命令替换消失
}
run_gate_check
deploy_containers                                 # 无条件执行
```

**反例：管道尾巴 + 忽略失败**

```bash
bash gate-check.sh "${ENV_NAME}" | tee -a "${LOG_FILE}" || true
gate_rc="${PIPESTATUS[0]}"   # 恒为 0：|| true 已把 PIPESTATUS 覆盖成 (0)
```

**正例：三档逐档处置**

```bash
local gate_rc=0
set +o pipefail                                   # 关闭后取末位 tee 的码（恒 0），-e 不触发；门禁真实码改由 PIPESTATUS[0] 取出后分档处置
bash "${gate_script}" "${ENV_NAME}" 2>&1 | tee -a "${LOG_FILE}"
gate_rc="${PIPESTATUS[0]}"                        # 取首位，不用 $?
set -o pipefail

case "${gate_rc}" in
  0) log "[OK] 门禁全部通过（无不合格、无未判定项）" ;;
  2) if [[ "${GATE_ALLOW_SKIP}" -eq 1 ]]; then
       log "[WARN] 存在未判定项，已按显式放行继续；理由：${GATE_ALLOW_SKIP_REASON}"
     else
       die "发版中止：有判据未能判定，结论是「不知道」，不是「合格」。"
     fi ;;
  *) die "发版中止：存在不合格项。放行开关只对未判定项生效，不能绕过不合格。" ;;
esac
```

三档实现（摘要打印与退出码结算拆开，供需要「先留证再退出」的调用方单独取码）见 [gate-lib.sh](file:///d:/developer/code/aicoding/s2s/deploy/scripts/gate-lib.sh#L117-L159)；逐档处置见 [deploy.sh](file:///d:/developer/code/aicoding/s2s/deploy/scripts/deploy.sh#L248-L280)。

**放行开关的参数形态**

```bash
# 裸开关直接拒绝，强制附带理由
--gate-allow-skip)   die "必须以 = 附带理由，不接受裸开关形式" ;;
--gate-allow-skip=*) GATE_ALLOW_SKIP_REASON="${1#--gate-allow-skip=}"
                     [[ -n "${GATE_ALLOW_SKIP_REASON}" ]] || die "理由不能为空" ;;
```
