# 造数保真度：性能与容量结论的有效性前提

## Context

数据库设计阶段要给两类数字：`/map/pins` 的 P95 耗时（验收线 150ms）、以及 40G 盘能装多少数据。两类都需要造数实测，不能靠推算。

同一批造数先后被用于两个目的，各错了一次，错法不同：

| 轮次 | 造数写法 | 用途 | 结论 |
|---|---|---|---|
| 1 | `grid_id = CONCAT(n%1000,'_',n%997)` | EXPLAIN 性能 | **无效**——热点组合只有 1 行 |
| 2 | 同上（`desc` 仅 4 字节） | 容量估算 | **反向错误**——得出「索引≈数据」 |

两次都不是代码写错，SQL 全部正常执行、EXPLAIN 也确实命中了覆盖索引。错的是造出来的数据不像真实数据。

## Guidance

**造数前先写下这批数据要回答什么问题，再据此确定哪些维度必须保真。** 不同问题对保真度的要求落在不同维度上，一批数据通常只能服务一个问题。

| 要回答的问题 | 必须保真的维度 | 可以随意的维度 |
|---|---|---|
| 索引选择、扫描行数、P95 | **键的分布**（长尾、热点集中度） | 字段内容长度 |
| 行宽、表体积、容量上限 | **字段内容长度**（按真实语义填） | 键的分布 |
| 并发冲突、锁等待 | **键的重合度** | 前两者 |

**在测量前加一条前置断言，让不真实的数据自己报错。** 这是把「事后发现结论无效」变成「事前拒绝出结论」的唯一办法：

```bash
MATCHED=$(qv "SELECT COUNT(*) FROM post WHERE $WHERE;" | tail -1)
if [ "${MATCHED:-0}" -lt 100 ]; then
  echo "### FAIL：命中行数 < 100，分布仍不真实，EXPLAIN 结论无效"
  exit 1
fi
```

断言的阈值来自「这个数字要用来做什么」——若要支撑 P95，扫描行数必须达到百行量级，`rows=1` 的耗时没有统计意义。

**测量目标不能拿臆造的参数去查。** 第一轮直接写死 `grid_id='500_497'` 跑 EXPLAIN，返回 `COUNT(*)=0`；空结果集上的执行计划不代表任何东西。正确做法是先从表里取实际热点，再拿它当查询条件：

```sql
SELECT CONCAT(grid_id,'|',leaf_category_id,'|',type) FROM post
WHERE status='active' AND expire_at > NOW()
GROUP BY grid_id, leaf_category_id, type ORDER BY COUNT(*) DESC LIMIT 1;
```

**换目的就要重造，不要复用。** 容量测算另起了独立测算库、按 PRD 字段语义填内容（`title` 20 汉字、`desc` 100 汉字、`template_values` 5 个键值对、`contact_value_enc` 40 字节密文），用完即删，不污染主库。

## Why This Matters

**分布不真实，性能数字无效；内容长度不真实，比例关系会反向。** 后者比前者危险得多。

第一轮的错误至少表现为「`rows=1`，这个耗时说明不了什么」——数字可疑，人会警觉。第二轮的错误表现为一个看起来完全合理、可以直接写进文档的观察：

> 索引体积 96.8MB ≈ 数据体积 95.6MB，后续新增索引须评估写放大

这句话已经写进了设计文档和项目说明文档两处。它读起来专业、有数据、有行动建议，没有任何一处触发怀疑。但它是错的：那批数据 `desc` 只有 4 字节，行宽约 190 字节，把数据体积的分母压小了。按真实行宽重测，二级索引占数据体积 **30%**，`idx_pins_cover` 单独占 12%，完全正常。

一个反向的结论比一个可疑的结论危害更大，因为它会真的被采纳。「索引与数据等大」会导向「削减索引」的决策，而真实数据支持的恰恰相反——`/map/pins` 必须走覆盖索引，因为 100 万行时数据页达 824MB，远超 256MB 的 `innodb_buffer_pool_size`，一旦回表必然引发磁盘随机读。按错误结论砍掉覆盖索引，等于砍掉这条查询的生存条件。

**静态审查抓不到这类缺陷。** 造数脚本本身没有语法错误、没有逻辑错误、跑得也很顺；错误只存在于「造出来的数据」与「真实数据」之间的差异里，只有把测出来的数字与业务语义对照才能发现。这轮的两个缺陷都是在实测之后、且是在换用途重测时才暴露的。

## When to Apply

任何时候造数的产物是**要写进文档的数字**，而不只是「让代码跑起来」的填充物。

判据是问一句：这个数字如果错了，会导致什么决策？

- 「跑通就行」的冒烟数据 → 不适用，随便填
- 「支撑索引取舍、容量规划、验收结论」的数据 → 适用，必须按上表确定保真维度并加前置断言

反过来也成立：如果说不清这批数据要回答什么问题，就还不到造数的时候。

## Examples

**分布：从均匀散开改为长尾集中**

```sql
-- 错：n%1000 × n%997 ≈ 100 万种组合承载 50 万行，单组合最多 1 行
grid_id = CONCAT(n % 1000, '_', n % 997)

-- 对：70% 的帖子落进 5 个热点网格，单组合达到 2322 行
--     此时 EXPLAIN ANALYZE 才有意义
```

改后取得的证据：

```
Covering index range scan on post using idx_pins_cover
(cost=475 rows=2322) (actual time=0.0526..0.831 rows=2322 loops=1)
```

p95 = 1.37ms，对照组 `SELECT *` 显示 `Using index condition`（回表），覆盖索引成立。

> **2026-09-06 补记——同一批造数还藏着第三个保真维度：SELECT 列表。** 上述证据首次取得时用的是 `SELECT id, user_id, completeness_level`，而 `/map/pins` 的响应契约必须返回 `lng`/`lat`。分布对了、内容长度对了，但**查询本身不是线上那条查询**，测出的 index-only scan 依然是假象。改用响应契约的真实六列复测（并给索引补上坐标列）后数字才成立。这印证了本文的核心论点：保真维度由测量目的决定，而「测量目的」必须回溯到线上契约，不能凭对查询的印象。

**内容长度：从占位符改为按字段语义填**

```sql
-- 错：desc 4 字节，行宽约 190B
'test'

-- 对：按 PRD §13.2 的字段语义取中位长度，行宽 1072B
REPEAT('这是一段接近真实长度的描述正文用于容量测算', 5)
```

两种填法测出的结论：

| | 错误造数 | 真实行宽造数 |
|---|---|---|
| `post` 行宽 | ~190B | **1072B**（824 数据 + 248 索引） |
| 索引 vs 数据 | 96.8MB ≈ 95.6MB（假象） | 二级索引占数据 **30%** |
| 导向的决策 | 「索引太重，考虑削减」 | 「覆盖索引必须保留」 |
