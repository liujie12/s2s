# 设计阶段的验证越界：为了验证而搭的工程会替下一阶段做决策

## Context

数据库设计阶段要交付设计文档、ER 图、数据字典和建表脚本。为了不让 DDL 停留在"纸面正确"，我做了实测——建库、执行 DDL、跑行为断言、EXPLAIN 实测覆盖索引。实测抓出了静态分析发现不了的缺陷（列注释里的 4 字节字符导致 `Error 1300`，注释落库变成乱码），价值确凿。

但为了跑 Flyway 迁移，我顺手做了两件事（以下两个路径**均已在本次收尾时删除**，仓库中不再存在）：

1. 建了 `server/pom.xml` —— 一个最小 Maven 工程
2. 把 DDL 从 `docs/database/` 移到 `server/src/main/resources/db/migration/`

两件事都有正当的直接理由（Flyway 需要工程和扫描路径），且都成功了。用户的反应是一句质问：

> 现在是数据库设计阶段，你是在开发代码吗？

我没写一行 Java。但 `pom.xml` 里写死了 groupId、artifactId、Java 版本、目录结构——**这些是后端工程搭建阶段的决策，被我用"验证需要"的名义提前定死了**。移动 DDL 同理：它替一个尚不存在的工程规定了资源布局。

## Guidance

**验证手段可以借用下一阶段的工具，但不能产出下一阶段的决策。** 两者的分界是：产物里有没有需要拍板的选择。

| 产物 | 有无决策 | 判定 |
|---|---|---|
| 一次性 shell 脚本，连库执行 SQL 后断言 | 无——换个人写也差不多 | 合规 |
| 构建配置（groupId、语言版本、目录结构） | **有**——每一项都是要拍板的 | 越界 |
| 目录布局（把产物挪进未来工程的路径） | **有**——规定了别人的家该怎么摆 | 越界 |

**优先选择不留下决策痕迹的验证路径。** 我要验的是"DDL 能否在真实 MySQL 上建出符合设计的表"，`docker exec mysql < ddl.sql` 就够了。选 Flyway 是因为它顺带验证了迁移工具的兼容性——但那个附加收益需要一整个 Maven 工程做代价，不划算。

**本阶段的全部产物集中在本阶段的目录下。** 设计阶段结束时，交付物应当能用一个目录树讲清楚：

```
docs/database/
├── 数据库设计文档.md          ER 图 + 数据字典 + 索引 + 容量估算
├── ddl/                        建表脚本
└── scripts/                    验证脚本（过程工具，非交付件）
```

跨阶段的路径要求（比如 Flyway 的 `classpath:db/migration`）用**文件命名**而非**物理位置**来预留。DDL 沿用 `V1__init_schema.sql` 的 Flyway 命名，放在 `docs/database/ddl/`，工程搭建时直接移入扫描路径，不用改名也不用改内容。命名是零成本的兼容，移动位置则是提前占位。

**验证产生的结论与产生结论的工具，寿命不同。** 工具删除不使结论失效。删掉 Maven 工程后，"Flyway 可执行性已验证"这个结论仍然成立，只需在文档里注明结论的来源和工具已移除的事实。

## Why This Matters

**越界不是靠"我没写业务代码"来判断的。** 我当时的自我辩护正是这句——一行 Java 都没有，怎么算编码？但阶段边界划的是**决策归属**，不是文件后缀。`pom.xml` 是 XML，`build.gradle` 是 Groovy，都不是业务代码，却都在替后端工程定架构。

**越界产物会伪装成资产被继承。** 如果没有被叫停，那个 `pom.xml` 会一直留在仓库里。下一个搭后端工程的人看到它，最可能的行为是在此基础上扩展——于是我在数据库设计阶段随手填的 Java 版本、依赖版本、目录结构，就成了既成事实。它从来没有被评审过，因为它当时只是"为了跑个验证"。

**这类越界最容易发生在验证环节，因为验证有正当性。** 写业务代码越界很容易自觉（"这明显不是设计阶段该做的"），但"为了验证设计正确性而搭建必要的环境"听起来无可指摘。判据不在动机，而在产物：**这个产物删掉之后，结论还在不在？** 在，说明它是工具；不在，说明它已经成了交付的一部分——那就要问它属不属于本阶段。

**散落的交付物会让阶段完成度无法核对。** 归拢之前，数据库设计的产物分散在 `docs/database/`（设计文档）和那个 Maven 工程目录（DDL 与验证脚本）两处。要回答"设计完成了吗"，得同时看两个目录，还得判断工程目录里哪些是设计产物、哪些是工程骨架。归拢到一处并在文档里放一份目录树之后，这个问题变成看一眼就能回答。

## When to Apply

任何"为了验证 A 而需要先搭建 B"的场景，且 B 属于尚未启动的阶段。

自查三问：

1. **这个产物里有没有需要拍板的选择？** 有 → 它是决策，不是工具
2. **删掉它，验证结论还成立吗？** 成立 → 它是工具，可以删；不成立 → 它已是交付物，要归位
3. **下一个人看到它，会不会以为它是经过评审的？** 会 → 要么删除，要么明确标注来历

不适用的情形：验证脚本、临时测试库、一次性造数——它们不含决策，也不会被误当作资产继承。

## Examples

**收尾时的处理**

```
删除：
  server/pom.xml            越界：定死了 groupId / Java 版本 / 目录结构
  server/target/            构建产物
  verify_flyway.sh          依赖已删的 pom，留着是死脚本
  explain_pins_index.sh     造数分布错误，结论已被 explain_pins_real.sh 取代

归拢：
  DDL       → docs/database/ddl/        （保留 Flyway 的 V1__ 命名）
  验证脚本  → docs/database/scripts/
```

**文档里的结论保留方式**

删掉工具后，结论不能跟着消失，也不能假装工具还在。原文改为脚注：

> 曾另建最小 Maven 工程实测 `mvn flyway:migrate`，两库均迁移成功且与手工执行 DDL 的结果列定义、索引差集为空。该工程属工程搭建阶段产物，已在数据库设计阶段收尾时删除，故上表口径改回手工执行。**Flyway 可执行性已获验证这一结论仍然成立**，后端工程搭建时按 §1.4 的路径与库名配置双 datasource 即可。

**计划文档里的跨阶段路径**

实施计划里写的是工程搭建后的目标路径，与当前存放位置不同。两者都要保留，用注记区分，而不是改掉其中一个：

> - `db/migration/V1__init_schema.sql`（新建，Flyway 默认路径……）
>
> **落地进展**：DDL 已在数据库设计阶段写就并实测通过，当前存放于 `docs/database/ddl/`。后端工程搭建时移入上述扫描路径即可，脚本内容无需改写。
