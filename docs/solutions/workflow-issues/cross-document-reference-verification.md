# 跨文档引用与口径搬运的核验约定：语义级错引比死链更危险

## Context

项目需要补齐 SRS（软件需求规格说明书）缺失的工程侧三章。核查结论是：需求侧（范围、用户故事、信息架构、界面 Token）已覆盖约 60%，但**接口契约、数据字典、非功能需求三章完全缺失**，直接拿 PRD 交研发必然联调返工。

决策是**不在 docs 下新建独立的 SRS 文档**，而是在 [PRD.md](file:///d:/developer/code/aicoding/s2s/docs/PRD.md) 内追加「第十部分：工程契约」（§12 接口 / §13 数据 / §14 非功能，约 420 行）。理由是独立 SRS 与 PRD 大面积重叠，每次改需求要两处同步，失同步风险远高于收益 —— **PRD 保持唯一权威源**。

为保证新章节不夹带私自新增的产品需求，给每一条契约都标注了「来源章节」。正是这个溯源动作暴露出两类问题，写完自检时共修出 **12 处引用错误 + 2 处口径冲突**：

| 类别 | 数量 | 危险程度 |
|---|---|---|
| 章节号不存在（死引用） | 1 | 低 —— 评审一眼看出 |
| **章节号存在但讲的是另一件事** | 4 | **高 —— 评审不报错，研发照做才踩坑** |
| 行号式引用（`§9 L1530`） | 5 | 中 —— 文档增删后静默失效 |
| 分段规则自相矛盾 / 表格列错位 / 伪造来源 | 3 | 中 |
| **从别处搬来的废弃口径** | 2 | **高 —— 差一步把已淘汰算法写进数据字典** |

## Guidance

### 一、被引章节必须逐条核实「存在 + 语义对得上」

死链会被评审发现，**语义级错引不会**。本轮 4 处错引全部是「章节号在 PRD 里真实存在，但内容完全是另一件事」：

| 我写的 | PRD 该章节实际内容 | 我的本意 | 修正为 |
|---|---|---|---|
| `§2.7`（2 处） | 用户旅程 | **说明文档** §2.7 内测包裁剪 | `**说明文档 §2.7** 定为本期不做` |
| `§9.4`（2 处） | 用户旅程 | 设置项 | `§9.3 设置页` |
| `§2.5`（2 处） | 资源态 vs 需求态 | **说明文档** §2.5 技术建议 | `§7.4.2 触达埋点` / `§5.10 严格 Scope 四步管线` |
| `§12.6` | 不存在 | 可观测性 | `§14.5 可观测性` |

根因是**两份文档共用相似的章节编号体系**（PRD 与 `说明文档.md` 都有 §2.5 / §2.7 / §9.x），凭记忆写就会串。

核验手段是把章节标题批量拉出来比对，而不是逐段读：

```
Grep pattern: "^### (2\.[5-9]|8\.6|9\.[1-9]|9\.10)" 于 docs/PRD.md，带 -n
```

一次输出全部真实标题，逐条对照自己写的引用。**跨文档引用必须写明文档名**（`说明文档 §2.7`），只写 `§2.7` 默认指向当前文档。

### 二、从别处搬来的规格，必须与权威源同主题章节逐条对账

草稿里两处规格是从 `说明文档.md` 的「技术建议」段搬来的，而那是**早期口径**，PRD 后来已经改过：

**① 完整度算法**

```markdown
改前（说明文档 §2.5 旧口径，加权分）：
| `completeness_score` | tinyint | 0-100 | 规则引擎得分（必填 50% + 位置 30% + 类目 20%） | §9.8 |

改后（PRD §9.8 现行口径，三条件达成计数）：
| `completeness_conditions` | json | — | 三条件各自达成态（`required_full` / `address_precise` /
`leaf_matched`），**档位＝三者达成计数**（3 个＝🟢 / 2 个＝🟡 / ≤1 个＝🔴），落库存条件而非加权分，
便于「还差哪几项」逐项回显 | §9.8 唯一判定口径 |
```

PRD §9.8 的表格明确写「🟡 半完整 = 三条件只满足 2 个 / 🔴 待补 = 三条件只满足 ≤1 个」，是计数不是加权。若照加权分落库，字段类型都是错的（`tinyint` vs `json`），且发布完成页「还差哪几项」根本无法回显。

**② 状态机枚举**

```markdown
改前（按常见写法凭感觉写）：
| `status` | enum | draft/online/offline/hidden/removed | … |

改后（对齐 PRD §8.6 状态机）：
| `status` | enum | draft/active/archived/hidden | 取值须与 §8.6 状态机严格一致；
`hidden`＝24h 未实名自动隐藏（**不删除**，实名后可一键恢复） | §8.6 状态机 / §3.7 |
```

PRD §8.6 的状态机是 `草稿 draft → 在架 active → 自动下架 archived`，`archived → 重发 → 克隆新 draft`。这条改完还要连带同步接口行为与 `expire_at` 说明，否则接口层与数据层枚举不一致。

**对账动作**：每写一条涉及枚举 / 阈值 / 算法的字段，先 `Grep` 权威源里同主题章节的标题定位，再 `Read` 那一段，确认现行取值后才落笔。凭会话记忆或另一份文档的印象写，就是把废弃口径固化进数据字典。

### 三、只引章节号，绝不引行号

草稿里有 5 处写成 `§9 L1530` / `§9 L1521-1523` / `§8 L1392`。行号会随任何一次文档增删全部漂移，且**漂移后不报错**。全部改为 `§9.10.1` / `§8.6` 这类规范章节号。

自查：

```
Grep pattern: "L1[0-9]{3}" 于 docs/PRD.md   → 期望 No matches
```

### 四、新章节章首必须声明定位、口径原则与不覆盖范围

三行声明把「这部分不是新需求」写成规则，避免后续评审把工程契约当产品变更来审：

```markdown
> **本部分定位**：§1–§11 定义「产品要什么」，本部分定义「系统按什么契约实现」…
> **口径原则**：本部分**不新增任何产品需求**，全部条款均由 §1–§9 既有规格推导而来，
> 每条注明来源章节；若与前文冲突，**以前文为准并须回改本部分**。
> **不覆盖范围**：运营治理后台 7 页的接口与表结构（**说明文档 §2.7** 定为本期不做）…
```

文末结语同步声明同一条冲突处置规则，保证读者从任一端进入都看到。

### 五、无法溯源的条款要诚实标注新增，不要伪造来源

草稿把传输层的 `Idempotency-Key` 约定标成来源 `§5.8 发布防重`，但 §5.8 并无此条 —— 这是为凑齐「每条都有来源」而编的。改为：

```markdown
| `Idempotency-Key` | … | 本节新增的传输层约定（不改 §5 任何发布规则） |
```

宁可显式标「本节新增」并说明它不改动哪些既有规则，也不要编一个看起来合规的来源。伪造来源会让下一个读者顺着去查、查不到，然后开始怀疑整章的可信度。

## Why This Matters

- **语义级错引是静默失效**。死链在评审时会被指出，`§9.4` 这种「号对内容不对」的引用能顺利通过评审，直到研发按着 §9.4（用户旅程）去找设置项规格、找不到才发现 —— 此时返工成本已经落在联调阶段。
- **废弃口径固化进数据字典的代价是迁移**。完整度若按加权分建表（`tinyint`），改回三条件（`json`）就是一次数据迁移 + 接口出参变更 + 前端回显逻辑重写，而写的时候只差一次 `Read`。
- **溯源标注本身是审计闸门**。要求「每条注明来源章节」的价值不在于读者会去查，而在于**写的人被迫逐条确认自己没有夹带私自新增的需求** —— 本轮 2 处口径冲突正是在补标注时暴露的。
- **唯一权威源优于文档齐全**。新建独立 SRS 能让文档清单看起来更完整，但代价是每次需求变更要两处同步；把工程契约并进 PRD 是用「一处冲突声明」替代「长期双向同步」。

## When to Apply

- 在既有权威文档内追加新部分，且新部分需大量回引前文章节
- 项目内存在多份文档、章节编号体系相似（如都有 §2.x / §9.x）
- 规格草稿的来源不是权威文档本身（技术建议、会议纪要、历史会话记忆）
- 补写数据字典或接口契约 —— 这两类一旦落地就绑定表结构与出入参，改动成本最高
- 判断「是否该新建一份文档」时：先算清同步成本，而非只看文档清单完整度

## Examples

**反例（本轮踩到的）**：

```
1. 凭会话记忆写 §12–§14 共 420 行，每条随手标来源章节
2. 完整度算法从「说明文档技术建议」搬加权分
3. status 枚举按常见写法写 draft/online/offline
4. 自检 → 12 处引用错误 + 2 处口径冲突
   ✗ 其中 4 处是「章节号存在但讲的是另一件事」，评审阶段不会报错
```

**正例**：

```
1. 先 Grep 权威源章节标题（^### N\.M）建立真实章节索引
2. 每条契约落笔前 Read 被引章节，确认语义对得上
3. 涉及枚举/阈值/算法的字段，与权威源同主题章节逐条对账现行取值
4. 跨文档引用一律带文档名；行号式引用一律改章节号
5. 无法溯源的条款标「本节新增」并说明不改动哪些既有规则
6. 章首 + 文末双端声明冲突处置规则
7. Grep "L1[0-9]{3}|§2\.5|§9\.4 |§12\.6" → No matches；GetDiagnostics → 零诊断
   ✓ 可复现的核验闸门
```

**Grep 正则的一个坑**：想排除 `§9.4x` 只留 `§9.4` 时写了否定预查 `§9\.4(?!\d)`，ripgrep 报 `regex parse error: look-around … is not supported`。改用带尾空格的 `§9\.4 ` 达到同样效果。
