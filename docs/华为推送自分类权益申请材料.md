## 2. 拟申请类别（第一优先 · 可立即报，无解释空间）

| 拟申请类别 | category 取值 | 对应本项目通知 | 官方场景依据（原文） |
| --- | --- | --- | --- |
| **工作事项提醒** | `WORK` | ① 实名认证审核结果 ② 资质认证审核结果 | 「待处理业务流程，推送对象为服务提供方：**审核进度提醒、认证状态流程提醒**、工单处理…」 |
| **账号动态** | `ACCOUNT` | 认证状态变更 | 「用户账号和账号下资源资产的动态信息…**账号信息认证**等」 |

> 两者同属「**服务与通讯类 → 服务提醒**」，提醒方式默认 锁屏 + 铃声 + 振动，**推送数量不受限**。

## 4. 场景说明（申请页可填，可照抄）

> 本应用为本地供需信息共享平台。用户在应用内**主动提交**实名认证与资质认证后，处于等待审核结果的状态；审核结果（通过 / 需补充材料 / 不通过）产生时，通过推送即时告知用户。
> 该通知对应**用户主动发起并等待结果的业务动作**，用户对接收此类消息有明确预期，属服务提醒类消息，非运营推广内容。

**官方「订阅流程要点」**（申请时须提供满足要求的**应用内订阅流程示意图**）：

| 要点 | 本项目现状 |
| --- | --- |

| 推送的**标题或正文须含**「订阅 / 预约 / 关注 / 好友 / 粉丝」等字样 | ⚠️ **产品当前无「关注/订阅」关系**，文案难自然满足 ⇒ 需产品改造，否则有被判错类风险 |
| 订阅消息范围不得过于宽泛（错误示例：订阅资讯、兴趣标签） | ⚠️ 若做「订阅分类」需具体化 |

> 社交动态类可覆盖的场景含「**被收藏**、留言、评论」；本项目「有人收藏 / 联系你的信息」在场景上可对应，但**流程要点②**（文案字样）对不上，故列为备选。

## 7. 申请通过后的实现衔接（给编码侧的接口）

- 服务端下发通知时须携带 `category` 字段（取值 = `WORK` / `ACCOUNT`，**全大写**）；`category` 为空或无效值 ⇒ **不会加快发送**
- 本项目下发管道现状：`PushDispatchService`（站内必写 → 筛可下发目标 → 占配额 → 逐设备下发）+ `PushSender` 按 `device.push_platform` 选通道
- ⇒ **实现要求**：`PushMessage` / 华为 `PushSender` 需支持**按通知类型映射 `category`**；映射关系待申请通过后按获批类别确定，**不得自创**（编码规范红线）
