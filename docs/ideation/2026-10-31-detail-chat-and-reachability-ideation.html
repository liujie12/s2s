Ideation

详情页发起聊天与消息触达

「能不能在详情页直接聊」这个问题，真正难的不是聊天框，而是三件现有系统里根本没有的东西：一个不越权的会话锚点、一个只有单一作者的未读数、一条能关得掉又关不死的推送链路。以下是入选的七个方向。

现状

Codebase Context

「S2S / 找呀找」是 Flutter 前端（lib/，Riverpod + go_router）配 Spring Boot 3 后端（src/main/java/com/s2s/server，MySQL + Flyway + Redis）。用户发布 post，用 supply_demand 二态区分「资源」与「需求」，两态共用同一个详情页。今天唯一的联系路径是：详情页底栏「联系 TA」/「响应需求」→ /contact/:id 中转页 → 拉取完整手机号 / 微信号。也就是说，全产品的「往来」到中转页就结束了。

下面的事实均已逐条核对到 file:line，它们决定了七个方向里哪些能落地、哪些只是在讲故事。

没有 IM，且是十处明文

  • 无 message / conversation 表；pom.xml:59-175 无 websocket / netty / MQ 客户端（全仓 grep 长连接的 16 行命中全是 Dart CustomPaint 子串误报）；openapi.yaml 无 /messages、/conversations；app_router.dart 路由表无任何消息 / 会话路由。
  • PRD 109 / 1765 / 1813-1819 / 1841-1844 / 1972 / 2196 / 3006 与 BRD 353(D6) / 117 / 397 均明文禁 IM。其中 PRD.md:1844 原文「『回复』在本产品内无处发生」；PRD.md:2196 把「消息列表页、聊天详情页」逐字列进「明确不做的页面」。
  • 原始论据（ideation/找丫找v2-需求深度还原-ideation-20260819.html:312）：IM 内容审核成本 / 条是中转的 5.6 倍，触达率反而低 12%。
  • 反向风险已登记：BRD R4「砍掉 IM 后联系效率下降｜中」。

推送链路：写好了，没人调

  • PushDispatchService.dispatch()（notify/PushDispatchService.java:84-113）已实现「写站内通知 → 筛可下发设备 → 占当日配额 → 发送」，但 src/main 零业务调用方（仅 PushDispatchServiceTest 5 处）。
  • 配额按消息而非设备（:32-34），NfrPush.DAILY_LIMIT 为 10 —— 一轮 10 条对话会烧光当日全部额度。
  • notify_enabled / notify_system / notify_interaction / notify_cert 四列已存在（V6__user_setting.sql:21-24），auth/SettingService.java:59-66,102-137 读写，但下发链路从不读取。
  • 前端 settings_screen.dart:110-114 只有一行总开关，settings_provider.dart:51-56 只有 setNotifyEnabled；settings_repository.dart:52-66 契约已支持三元组却无 UI。

未读与角标：两个消费者，零个桌面落点

  • 唯一真源是 GET /notifications 的 unread_count，跨三 Tab 不收窄（NotifyService.java:83-85；NotificationMapper.xml:65-71 按行 COUNT(*)）。
  • 两个消费者互不共享、互不失效：notification_provider.dart:92-183 与 profile_provider.dart:96-110（后者另发一次 fetchNotifications(pageSize:1)）。无轮询、无 AppLifecycleState 回调。
  • 桌面角标双端零落点：Android 全量 grep badge|shortcut|ShortcutBadger|setNumber 无命中；ios/Runner/AppDelegate.swift 全文 16 行无 applicationIconBadgeNumber。
  • Tab 数字角标是刻意不做：PRD.md:1148「红点（8px），不用数字气泡｜导航栏仅剩 24px 见方，双位数气泡会溢出压到搜索框」。

推送通道的现实

  • 仅小米有原生 receiver；华为有服务端 sender 无客户端桥；iOS APNs 未接入（push_service.dart:68-69）。
  • AndroidManifest.xml:5-11 连 POST_NOTIFICATIONS 都未声明；推送点击深链未实现。
  • 当前唯一的权限申请点是发布成功页（publish_success_screen.dart:55）。

信任机制

  • ContactService.viewContact 九步链：登录 40101 → 绑手机号 40302 → 冻结 42903 → 三维日限 30/30/100 → 突发 → 可见性 41001 → CryptoFacade.decrypt 唯一解密 → 写 contact_event → 同事务写 audit_log。
  • ContactService.java:140-142 明确「配额先于可见性判定……否则按 id 遍历探测可绕过限频」。
  • 举报需已实名（40305，不新增码）。ReportRiskScore：fraud 50 / false_info 20 / wrong_category 20 / harassment 10 / other 5，企业 ×1.5，≥60 自动下架。
  • CryptoFacadeCallSiteTest 守门调用点 == 1。

结构与口径约束

  • 横切链顺序固定：RequestIdFilter → AuthInterceptor → RateLimitInterceptor → IdempotencyInterceptor → Controller；限流必先于幂等。
  • RateLimitTrack 17 行且 notify 域明确拒绝新增轨道；错误码固定 24+0；幂等 idem: 前缀、24h 窗口、按登录 / 设备 / 匿名分维度。
  • 分页只有 offset（LIMIT #{offset}, #{limit}，page_size 上限 50）；NotificationMapper.xml:17-18 已记录 created_at 秒精度需 id DESC 兜底防翻页重复；全仓无 API 级游标。
  • NfrRetention 有埋点 90d / audit 180d / contact_event 30d，唯独没有 notification 的保留期条目。
  • TaskSchedulingConfig.java:16「单实例…无需分布式锁」，11 个 @Scheduled 依赖这一前提；OssClient.java:40 与 MediaService.java:88 两处明令禁 @Async。

历史经验（docs/solutions/）

  • ① 延期功能要延期逻辑、不延期数据模型：会话 / 成员 / 消息 / 未读游标 / 偏好字段必须在第一版迁移里预留。
  • ② 选型必须当场落进唯一口径源，不能留到编码期。
  • ③ 模板 Caffeine 缓存随 provider 存活且不自动刷新，开关照抄会「重启才生效」。
  • ④ 角标数必须与它汇总的列表同源 —— 本仓已出现过「角标 2 / 列表 1」类缺陷。

外部参照

  • 闲鱼「我想要」开 1:1 会话替代暴露手机号、聊天内拦号、「叮一下」二次推送；小红书陌生人回复前限 1-3 条 + 每日发起上限；BOSS 直聘强制招呼模板且只预览前 17 字；OfferUp 的出价以消息形式进会话；Craigslist 每帖一个中继别名。
  • iOS 角标由 APNs 绝对值驱动（0 清除）；Android 8+ 标准是通知圆点，setNumber() 不保证。
  • 推送授权中位数 iOS 48.85% / Android 53.3%；每周 2-5 条推送即让 46% 用户关闭通知；78% 客户向第一个回应者下单、1 分钟内响应转化 +391%。
三条硬约束，任何方向都绕不过去。 横切链顺序不可调换、notify 域不新增限流轨道、错误码不新增（唯一口径源是 PRD §12.5 的 24 码 + 0）；解密只有 CryptoFacade 一个入口且必须同事务写 audit_log；设计文档未覆盖的口径先问，禁在业务代码里自创。另有一条判断会影响全部七条：PRD.md:1972「不做站内 IM」与 contact_screen.dart:8-11「不做站内文本聊天」是能力级禁令，「只禁两个页面」是对 PRD 的选择性引用 —— 所以下面凡是碰会话的构想，都要求一次正式的 PRD / BRD 口径变更，且变更先于实现。变更清单：PRD.md:2196（撤销「消息列表页、聊天详情页」两行）、1972、1765、1844、BRD 353 五处实质改写，另需为底部 Tab 数字角标与桌面角标各新增一条口径。

分解

Topic Axes

把「详情页发起聊天 + 触达」拆成五条互不重叠的面，发散时每条轴都被迫产出至少一条：

轴名称这条轴在问什么
A会话入口与开场对话从详情页的哪一下开始，第一条消息以什么形态出现，会话挂在谁身上。

消息中心：独立会话列表 + 会话详情，第四 Tab（对齐闲鱼）

1轴 · 会话入口与开场
描述
把会话列表与会话详情做成独立的消息中心，挂在底部导航第 4 个 Tab 上（今天是丫圈 / 发布 / 我的：两个持久分支加一个 push 型中键）。列表行结构对齐参考图：头像（未读时右上红点）· 昵称 + 状态标 · 最后一条消息预览（或未读前缀「[N 条]」）· 时间 · 右侧关联帖子封面缩略图；按时间分组（今天 / 一周内 / 「1 个月以前的消息」）；顶部给搜索与管理入口；系统与认证类通知作为「服务号」置顶一行，与用户会话分开。会话内顶部固定一张关联帖子卡片，帖子下架（41001）即置灰并停止发送。详情页底栏仍是唯一入口 —— 点进来直接进入这条会话，不新开一条。会话唯一键仍是 (post_id, visitor_id)。首版迁移一次建三张表：conversation（post_id + visitor_id 唯一）、conversation_member（last_read_message_id 水位线）、message（sender_id / seq / body / created_at，(sender_id, interaction_id) 唯一键）。chat.enabled 关闭时存量会话转只读 + 顶部横幅，不隐藏。
依据
direct:home_shell.dart:9-11「本壳只承载两个持久分支（丫圈…我的），中间的『发布』键…onPressed 是 push('/publish') 而非 goBranch」—— 加「消息」Tab 要动这个壳；PRD.md:2196「明确不做的页面…消息列表页、聊天详情页」正是这一形态要撤销的两行；PRD.md:1148 的「红点（8px），不用数字气泡」约束对象是首页顶部导航栏（旁边挤着搜索框），底部 Tab 是新面，需要为它单独补一条口径而不是改 1148；V1__init_schema.sql:333-345 的 notification.type 三分类已能承载「服务号」置顶行；contact_screen.dart:3-6「让『拉取完整值』成为一个可限频、可埋点、可熔断的独立动作」。 external:闲鱼消息中心的行结构（头像红点 / 昵称 / 预览或条数 / 时间 / 商品缩略图 / 「1 个月以前的消息」分组 / Tab 数字角标）；小红书与 BOSS 直聘同样用独立消息 Tab 承载会话。
为什么重要
参考图把问题从「要不要建收件箱」直接推进到「收件箱长什么样」—— 用户要的不是在详情页里聊两句，而是一个能承载 N 条会话、能一眼看出谁在等你的消息入口。这一形态同时给未读、角标、推送三件事提供了统一落点：会话行红点、Tab 数字、桌面图标都从同一份会话未读派生。代价是 PRD 的实质改写从三条扩到五条（2196 的两个页面、1972、1765、1844，加 BRD 353），并新增一条底部 Tab 角标口径。
代价与风险
要改 home_shell.dart 新增持久分支，影响所有 Tab 下标与深链；「所有对话」入口出现后，跨帖的会话检索、排序、分页都要定口径；列表缩略图要求会话关联 post_id 并 join 封面；搜索一旦上线就是新的索引与审核面；PRD / BRD 实质改写从三条增到五条，公告面明显变宽。

密封投标：需求帖的开场是「应标—开标」，不是聊天

2轴 · 会话入口与开场
描述
需求态（supply_demand=demand）的「我能帮忙」不再跳 /publish，而是提交一张结构化应标单（能提供什么／交付时间／一句留言）。投标人之间互不可见，发布者看不到对方联系方式；发布者看到的是「投标列表」与待开标角标，点「开标」才解锁那一条并生成会话，开标动作计一次 contact_event，沿用既有三维配额。
依据
direct:detail_screen.dart:775 按钮文案是「我能帮忙」，而 PRD.md:1881 要求「我有资源 / 能帮忙 · 一键发布对应资源（跳发布页，预填对应分类）」—— 入口存在但语义已漂移；PRD.md:1977「你的『需求』被人发布了对应资源」是已定义却无承载物的互动通知。
为什么重要
需求侧天然一对多，直接套一对一会话会立刻变成骚扰池；一个「开标」状态机把 N 个应标者压成 1 个被选中的人，同时把已经写好却悬空的那条互动通知变成有内容、可点击、可回应的东西。
代价与风险
引入开标状态机（新状态 + 新表），已超出「加个聊天」的范围；发布者长期不开标会让应标方僵死，需要超时规则。

传呼台：不做长连接，推送唤醒 + after_id 增量

3轴 · 消息读写与实时性
描述
把实时性明确建模成寻呼台而非在线聊天。POST 消息同步落库即返回「已发呼」；服务端走既有 dispatch() 发一条「请回呼」推送；客户端只在进入前台、打开会话、下拉刷新三处按 after_id 拉增量；离线草稿进本地发件箱，联网后带同一 Idempotency-Key 重发，服务端以 containsKey 幂等去重。「已送达」由对方游标越过该条时写回，「已读」由对方显式打开会话写回。
依据
direct:pom.xml:59-175 依赖清单无 websocket / netty / MQ；TaskSchedulingConfig.java:16「单实例……无需分布式锁」；NotificationMapper.xml:17-18「created_at 为 DATETIME（秒精度），同一秒多条时若无 id 兜底，翻页会出现重复 / 漏行」；OssClient.java:40 与 MediaService.java:88 两处明令禁 @Async；notification_provider.dart:92-183 全文无 Timer、无 Stream。
为什么重要
这是「加聊天」最容易失控的工程决策 —— 一旦引入 WebSocket，单实例假设、11 个 @Scheduled 的无锁前提、以及「扩多实例必须同时加分布式锁」的既有约束会同时被打破。用推送触发拉取，等于把实时性外包给已有链路，后端只多一张表和两个端点。
代价与风险
对方在线时消息也最多延迟到一个推送或一次前台切换；after_id 是全仓第一个 API 级游标，破了「只有 offset」的既有约定，需要一次架构记档；首屏会变成两段式（先拉页、再补增量）。

一个读水位：未读三处同源 + 已读回执

4轴 · 未读与角标
描述
整件事只由一个水位线驱动：conversation_member.last_read_message_id。未读的计数单位从「未读消息条数」改成「有待处理消息的会话数」—— 一个会话无论堆 12 条还是 1 条，最多计 1，直到你打开它。这个绝对值喂给三处：底部「消息」Tab 的数字角标、会话行头像右上角的红点（只给红点不给数字）、桌面图标角标（iOS 走 APNs badge、Android 走厂商参数）。已读回执是同一个水位的反方向：我的消息 seq ≤ 对方的 last_read_message_id 即「已读」，否则「未读」；消息列表接口多返回一个整数 peer_last_read_id，客户端自行比较即可，不需要逐条 read_at、不需要新表、不需要新接口。标签只挂在「我发的最后一条」下面，避免每行都出现两个字。已读只更新水位，不产生推送；发送方在下次拉取（打开会话、回到前台）时看到状态变化。这个值随响应信封返回、或至少收敛成唯一 provider；失败重试一律以服务端绝对值覆盖以修复漂移；同时删掉「我的」页那第二路独立请求。
依据
direct:PRD.md:1148「红点（8px），不用数字气泡｜导航栏仅剩 24px 见方，双位数气泡会溢出压到搜索框」—— 反对数字的真实理由是空间；NotifyService.java:83-85 与 NotificationMapper.xml:65-71 现口径按行 COUNT(*)；profile_provider.dart:96-110 用 fetchNotifications(pageSize:1) 独立再发一次且与 notificationsProvider 无共享状态；Android / iOS 角标 grep 均为空。 external:iOS badge 是绝对值、0 清除；Android 8+ 标准是通知圆点，setNumber() 不保证；行业共识是服务端绝对值为唯一真源、重试用绝对值修漂移。
为什么重要
引入三者等于引入三个未读消费者；不先立「唯一作者」，就是把已知的「角标 2 而列表 1」缺陷复制三遍。计数单位换成会话后，双位数几乎不可能发生，Tab 数字角标重新变得可用 —— 这是用语义选择解决 PRD 的视觉红线，而不是视觉妥协。另需注意：PRD.md:1148 那条约束的是首页顶部导航栏（旁边有搜索框），底部 Tab 是全新面，应新增一条口径而非沿用或推翻 1148。已读回执几乎零成本：它复用的正是为未读本来就要建的水位线，一个字段同时回答「我有几条没看」与「对方读没读」，不必为回执再开一套表。
代价与风险
ResponseBodyWrapper.java:103-110 目前只是把 DTO 套壳，没有按请求追加字段的钩子，「单点追加」低估了改动；会话计数会让「12 条未读」显示为 1，用户可能低估紧急度；底部 Tab 数字角标与桌面角标都是新面，需要在 PRD 里各补一条口径；iOS 本期没有 APNs 落点，桌面角标只有 Android 一半。已读回执另有三个副作用：一是「已读不回」在 C2C 议价场景里是真实的社交压力，需要产品决定是否允许关闭（微信无开关、WhatsApp 有、闲鱼无）；二是已读事件不实时，发送方要等下一次拉取才看到状态变化，容易被误读为「对方没看」；三是对已删除 / 已拉黑的会话，状态会停在水位线最后一格，需要一句代替文案而不是一直显示「未读」。

打扰预算：档位三选一 + 会话聚合 + 权限时机后移

5轴 · 推送触达与打扰控制
描述
把「关掉通知」从关断改成降档，三选一：实时（每条进通知栏）／摘要（每天固定窗口汇总）／仅角标（只更新应用内与桌面角标）。发送侧统一走一个预算组件，读既有四列开关 + 档位 + NfrPush.DAILY_LIMIT。同一会话在窗口内只下发 1 条「{昵称} 给你发了 N 条消息」，第二条起只更新那条站内通知的摘要、不占新配额。系统权限申请点从「发布成功页」后移到「用户第一次收到回复」。
依据
direct:dispatch() 在 src/main 零业务调用方；SettingService.java:59-66,102-137 写了四列但 PushDispatchService / PushQuotaGate / 各 sender 均未读取；settings_screen.dart:110-114 只有一行总开关；publish_success_screen.dart:55 是当前唯一的权限申请点；AndroidManifest.xml:5-11 未声明 POST_NOTIFICATIONS；PushDispatchService.java:32-34「配额按消息而非设备」—— 一轮 10 条对话会烧光当日全部额度；NfrPush.java:31 DAILY_LIMIT=10。 external:Localytics「每周 2-5 条推送已让 46% 用户关闭通知」；Airship 2025 授权中位 iOS 48.85% / Android 53.3%。
为什么重要
用户说的「可以关闭通知」如果只做成一个总开关，实际结果是关掉后再也不知道有人找，聊天功能直接失效。不聚合的话，聊天一上线就会把 10 条/天烧满，等于用聊天杀死系统通知。这条也是让那四列死开关第一次拥有真实语义的地方。
代价与风险
档位是新产品概念，要动 user_setting 结构与 PATCH /notifications/settings（现标 Batch2 占位）；「首次收到回复才要权限」会让第一条消息完全静默，可能伤到响应速度；聚合窗口按「会话」还是按「接收者」需要定口径。

信任阶梯：额度分账 + 模板卡准入 + 号码只在卡片

6轴 · 信任与反骚扰
描述
三道闸合成一条可见的阶梯。未实名 → 只能发服务端下发的模板卡（按分类：还在吗／价格能谈吗／位置在哪／今天能看吗）；已实名 → 可发自由文本；有过成功往来 → 会话内出现「获取联系方式」卡片，点击调用的仍是今天那个 GET /posts/{id}/contact，九步链路一行不改。额度分账：看号保留 CONTACT_UID/DEV/IP/BURST 四轨 30/日不动，绝不与消息互相挤占；消息侧限的是「每日主动开新会话数」与「每会话未回复前条数」，两个值都落 Nfr 常量，用数据库计数而非 Redis 新轨，超限复用既有 42902，未绑手机号仍 40302。聊天内畅聊不受条数限制，但任何「一对多」广播式用法在第一道闸被卡住。聊天正文结构上不承载号码，卡片是唯一出口。
依据
direct:RateLimitTrack.java:66-68,74-76,82-84,97-100 是 CONTACT_UID/DEV/IP/BURST 四轨且 notify 域明确拒绝新增轨道；ContactService.java:160 配额先于可见性；ContactService.java:226-230「用既有码 40305（无权限）—— 不新增错误码（红线）」；CryptoFacadeCallSiteTest 守门调用点 == 1；contact_screen.dart:3-6。 external:小红书回复前限 1-3 条、每日主动私信 5-20 人；BOSS 直聘限主动开聊额度并可付费提额；闲鱼聊天内拦微信号 / 手机号、拿到联系方式是会话内后置步骤 —— 三家限的都是「主动发起的人数」，不是「消息条数」。
为什么重要
这是唯一「零新码、零新轨、零新解密入口」就能给聊天上风控的形状。它同时正面回答 PRD 拒绝 IM 的第三条论据（「不接 IM SDK = 不产生聊天内容存储 / 审核合规风险」）—— 本设计下聊天内容在结构上就不含合规敏感项，所以「存了聊天记录」的风险等级与「存了一条『还在吗』」相同。分账而非共用，是因为群发的成本来自「给很多人各发一条」，不是「给一个人发很多条」；限主动开场人数既能挡住群发，又不动「看号」这条核心转化路径的稀缺性。
代价与风险
比共用多一套计数逻辑（按 `(sender_id, 自然日)` 与 `(conversation_id, sender_id)` 各一次计数）；两个阈值都要新定并写进 Nfr 常量，属于设计文档未覆盖的口径（按红线必须先问）；模板卡准入对未实名用户是硬墙，会压低会话量；「有过成功往来」的判定口径要新定。

举报带证据：审核成本从「全量」收窄到「被举报的那几屏」

7轴 · 信任与反骚扰
描述
举报弹窗自动携带 thread_post_id 与命中的消息 id 列表，服务端把摘要写进既有的 report.evidence JSON 列，风险分从「原因估值」变成「原因 + 证据条数」。运营侧只给一个「被举报会话」的只读窄视图（不是聊天后台，只审被举报的那几屏），同时给被误判的用户一个可见的申诉面（能看到自己哪条触发了拦截）。
依据
direct:ReportRiskScore.java AUTO_OFFLINE_THRESHOLD=60，基础分 fraud 50 / false_info 20 / wrong_category 20 / harassment 10 / other 5；contact_screen.dart:745-847 举报面板只有原因选择与备注，无任何证据入口；report.evidence 列在服务端存在且 ReportRequest.evidence 是 List<String>，只差前端入口。 reasoned:运营最担心的「聊天审核成本按条计」，可以被收窄成「只审被举报的那几条」—— 这是对 PRD 那条 5.6 倍成本论据最直接的正面回应。
为什么重要
举报没有证据就无法判定，而聊天正好生成证据。它把「做聊天」的成本叙事从「全面审核」改成「抽样审核」，是能让评审点头的那句话；也让 harness 基础分 10 这个拍出来的数字第一次有可核对象。
代价与风险
需要一条运营侧窄视图（新后台页面）；消息保留期必须补进 NfrRetention（当前连 notification 都没有条目）；客服能否查看被举报会话正文是合规决策，不是工程决策。

2「我能帮忙」变资源卡开场（预填分类 + 两帖互链）依据真实但动作未落地：/publish 仍是占位屏、预填分类未实现，两帖互链没有数据路径（已并入第 2 条）。
