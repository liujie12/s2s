Grounding Context

Codebase Context. 产品是 5 公里生活圈双向供需 App，地图优先；北极星为「AI 匹配召回率 × 图层加载成功率（P95≤300ms）× 🟢完整发布率」。本次范围限定在首页地图的搜索：用户说一句自然语言，系统解析出类目、供需方向、半径、地点锚点与类目专属信息，用户不离开地图，地图按半径收窄。

仓库现状里，这些候选所依据的关键事实是：

  • 搜索框是 AppBar 内 32px 的 TextField，逐字符写筛选态，无提交、无防抖、无清空、无麦克风；lib/features/map/map_screen.dart:513-549。
  • PinsQuery 只有类目、供需、半径、网格、版本号、lng/lat/zoom，没有 keyword；docs/api/openapi.yaml 的 /map/pins 同样没有 keyword。地图上的搜索目前对 Pin 不生效。
  • 半径是离散档位 1/3/5/10/city；服务端按约 500m 网格 ceil 扩圈，不做 Haversine 距离裁剪；src/main/java/com/s2s/server/map/MapService.java:338-354。
  • 半径圆的直径只被用于计算缩放，从未画给用户看过；仓库内无 Circle/Polygon 覆盖物。已有同构的「视野外还有 N 条」角标。map_screen.dart:288-303, 952-996。
  • PRD 的 S2 动态蜂窝半径（按密度自动扩圈 + 30 秒分层兜底）未实现，推迟理由明写为「做半套会让用户看到范围莫名其妙变了却没有任何解释」；lib/features/discovery/list_screen.dart:536-540。
  • 类目叶子已编码「合租/整租」：20101 主卧出租、20102 次卧出租、20103 整租出租，20201 个人求租；src/main/resources/db/migration/V3__seed_category.sql:97-102。这是口语到类目的事实底座。
  • 同义词与拼音在 PRD 有规格（613/624/1150），代码零实现，且注明「同义词表属运营配置」；lib/features/publish/category_selector_screen.dart:11-12。
  • 地址只有逆地理（坐标→地址、展示用），没有正向 POI/地理编码；lib/features/location/reverse_geocode.dart:6-10。
  • 唯一「一句话→结构化字段」的实现是发布域的严格 Scope 管线：逐字段溯源，越界字段进 unresolved_fields，服务端不猜；src/main/java/com/s2s/server/ai/AiParseService.java:192-197, 428-444。
  • 语音链路：录音 AAC-LC/m4a，60s 是实现护栏；录完上传音频得到 voice_media_id，再由服务端 ASR；客户端解析读超时 5s，后端上游 10s。lib/features/publish/ai_entry_sheet.dart:569-596、NfrAi.java:43-50。
  • 隐私门告知清单只有位置、手机号、发布内容、高德 SDK，没有麦克风、录音、AI；隐私政策只覆盖「语音转写文本」，没有原始音频留存/删除条款；lib/features/privacy/privacy_gate_screen.dart:111-118、docs/legal/隐私政策（草稿）.md。

外部参照包括：高德车机「语言大脑 + 空间大脑」的意图/事实分离；百度 POI 的时空上下文排序；58/赶集按 10km 圈选的 Query 理解；Yelp 的六类 query 分段；Amazon AsK 三档澄清与 LLM 的 under-clarification 偏差；微软语音的 time-to-first-audio 与「键盘输入即停收音」；ASR 2-pass 与流式 600ms 分片；雷达/声呐的由粗到细；eBay 的零结果改写（>25% 可救回）。

Topic Axes

  • 语音入口与转写体验 —— 怎么开始说、说到一半能不能改、说完多久有反馈。
  • 一句话到筛选条件 —— 类目、供需方向、半径、地点、价格与类目专属信息如何被解析、澄清与纠正。
  • 地图收窄与半径交互 —— 收窄如何被看见、如何撤销、半径是承诺还是参数。
  • 性能预算与失败降级 —— ASR → 解析 → POI → Pin 的逐段预算，失败时保留什么。
  • 亮点时刻与信任边界 —— 用户如何感知「过滤掉了不相关」，以及语音/音频的隐私承诺。

Ranked Ideas

1. 可见的一次性搜索圈 2. 确定性短路 + 一份运营词表 3. 按住地图说话 4. 解析过程可见且可反驳 5. 两段式交付 6. 自证台账 7. SemanticQuery 语义快照

I1.可见的一次性搜索圈

Axis地图收窄与半径交互

Description解析出半径后，不把它写进用户的持久筛选，而是在地图上叠一个一次性搜索圈：圈内正常显示，圈边挂「1km · 37 条」，圈外命中压成「还有 45 条 · 放宽到 3km」，并提供一次性撤销回到上一档。零结果时，圈上直接长出三张改写牌（扩到 3km / 换成求租方向 / 放宽类目），每张写明「因为你点了…」。圈的几何用解析出的真实米数（800m、1200m）绘制，查询仍走既有档位，客户端按真实米数对返回点做 Haversine 精裁后再上图。

direct半径圆直径今天只被用于缩放计算，从未绘制给用户看（map_screen.dart:952-996，仓库无 Circle/Polygon 覆盖物）；「视野外还有 N 条」角标已存在，可同构复用（map_screen.dart:288-303）；S2 被推迟的理由正是「范围变了没有解释」（list_screen.dart:536-540）；服务端只按 500m 网格扩圈、不做距离裁剪（MapService.java:338-354）。

Rationale用户原话是「留在原地图、根据半径收窄地图」。收窄若没有形态，用户只看到 Pin 变少，第一反应是「图坏了」而不是「筛掉了」。圈把技术妥协（网格近似）从隐患变成公开的诚实，同时把 PRD 推迟 S2 的理由反转成设计约束：只要变化可见、可撤销、有解释，就不需要自动扩圈。

Downsides

  • 服务端网格扩圈是方形，圈是圆形；「圈内计数」必须在服务端按真实距离算，或明确标注为近似，否则数字会撒谎。
  • cluster 模式下没有单点可裁，圆与聚合点会打架，需要定义聚合态下的表现。
  • 一次性圈与持久筛选并存，状态归属要写清楚，否则会出现「上次的圈还在」。
  • 「圈外还有 N 条」与零结果改写都需要服务端返回对照计数，是新契约与额外查询成本。

I2.确定性短路 + 一份运营词表，三个消费方

Axis一句话到筛选条件

Description把搜索槽位固定成一张卡（供需方向 / 类目 / 半径 / 位置锚点 / 预算 / 时间），然后先用确定性规则填卡：半径词映射到既有档位；供需意图词决定看资源还是需求；类目名、别名、首拼与「合租→20101/20102、整租→20103」走词表。命中即不出网、不扣 AI 配额、同一句话永远同一结果。只有剩余的自由文本（如「离地铁近点」）才进严格 Scope 的模型兜底。词表只维护一份，被三处同时消费：地图搜索、发布页类目推荐、筛选面板。

direct半径是五档枚举，注释明确「允许任意值会让摘要需要处理 4.7km 这种不该存在的输入」（discovery_filter.dart:19-28）；合租/整租已在类目叶子里（V3__seed_category.sql:97-100）；同义词表 PRD 有规格、代码未做且注明属运营配置（PRD.md:613,624,1150；category_selector_screen.dart:11-12）；严格 Scope 的逐字段溯源已有可复用范式（AiParseService.java:428-444）。

Rationale这是成本、时延、可解释性同时改善的一层：语音搜索的量一旦起来，每次都说给模型听会把 20/10/3 的配额和费用上限先打穿；而规则层让「解析对不对」从概率问题变成可单测的问题。词表的三消费方是复利最强的一处——一次运营配置同时让三个界面变准。

Downsides

  • 词表冷启动需要人工投入；方言、简称、错别字会持续产生长尾。
  • 「不合租」「不要中介」这类否定表达容易误命中，需要否定窗口与优先级。
  • 规则与模型双通道必须定死冲突时的优先级，否则同一句话两个答案。
  • 槽位卡里的「预算/时间」在现有 /map/pins 没有落点，地图侧只能先展示、不能过滤。

I3.按住地图任意点说话

Axis语音入口与转写体验

Description不新增一个孤立的麦克风按钮：长按地图任意点开始收音，按压点同时就是空间锚点；松手后半径圈从该点长出，Pin 分批落位。顶栏文字框保留，但一检测到键盘输入就立即停麦。这样「我在某某小区」不再需要 ASR 去猜地名——手指已经指定了位置，语音只负责补「要租房、合租、两千以内」。

direct搜索框是 AppBar 内一个 32px 的 TextField，地图本身几乎不参与输入（map_screen.dart:513-552）；仓库只有逆地理、没有正向 POI，文本里的地名无法解析（reverse_geocode.dart:6-10）。external对讲机 PTT 的「按住即传输、松键即结束」；微软语音的「检测到键盘输入即停收音」；百度 POI 的时空上下文排序（同一前缀因位置不同需要不同结果）。

Rationale语音的入口摩擦不是点击次数，而是「用户得先知道有这个功能」。把入口绑在地图手势上，语音成为地图交互的一部分，而不是挂在顶部的输入法；同时它绕开了整条缺失的正向地理编码链路，让「某某小区」这个最容易被说出口、系统却最接不住的输入有了确定答案。

Downsides

  • 长按与地图拖动手势冲突，需要明确按压阈值与取消手势。
  • 没有麦克风权限时，用户会先长按才发现；需要在按压动画里提前露出权限提示。
  • 「按住」对运动障碍用户不友好，必须保留点按、文字与手动选点三种替代。
  • 地图上需要持续可见的「按住说话」提示，否则功能不可发现。

I4.解析过程可见且可反驳

Axis一句话到筛选条件

Description三段可见：边说边出——流式转写驱动本地词表先匹配，每识别出一个约束就在搜索框下出现一枚可删的 chip；说完复诵——执行前先给一行「找：1km · 合租（主卧/次卧）· 只看房源」，点「改」只问最容易错的那一维；越界可见——模型返回了 scope 之外或未命中的词，不静默丢弃，而是灰/黄标成「没敢用」，点它可手动绑定或强制生效。每次纠正都沉淀成（原话、原解析、正确解析）三元组，脱敏后进入运营的未命中榜。

direct录音停止后才上传与解析，整个窗口里用户看不到任何一行字（ai_entry_sheet.dart:569-596）；越界字段已算进 unresolved_fields，但只留在响应里，界面没有承载位（AiParseService.java:192-197, 428-444；map_screen.dart:520-549）；零结果已有运营入队队列可作为未命中榜底座（MapService.java:213-220）。

Rationale语音搜索的可信度不由识别准确率决定，而由「错了之后用户还能不能救」决定。ASR 有错误率、模型有保守性，把这两者变成界面上可点掉的灰块，比任何准确率宣传都更能留住用户；同时它把每次纠错变成词典的确定性供给。

Downsides

  • 流式 ASR + 增量解析需要新的契约与状态机，工程量最大。
  • chip 会遮挡地图，收起与展开的时机需要真实用户验证。
  • 边说边出可能让用户误以为「已经搜完了」，复诵与结果态必须区分清楚。
  • 纠错数据涉及用户原话，必须脱敏并受 AI 改进开关约束。

I5.两段式交付：先给可感知结果，再做精算

Axis性能预算与失败降级

Description说话结束后的第一个可感知结果不等解析完成：先把转写文本落在搜索框里（可读、可编辑），或用当前条件先发一次粗查询（cluster 级）。解析到达后 diff 出条件变化，只有差异非空才发第二次请求并静默替换。解析失败或超时，保留第一段结果，给一个「重新解析」按钮——只重跑解析，不重录、不重传音频；失败与超时不扣 AI 配额。

direct录音停止后必须先上传拿到 voice_media_id，整个可感知窗口里没有任何一行字（ai_entry_sheet.dart:569-596）；客户端解析读超时 5s（nfr_constants.dart:258-271），后端上游 10s（NfrAi.java:43-50），语音路径还是转写 + 生成串行。external微软语音的 time-to-first-audio；ASR 的流式出字 + 句末离线重转；雷达/声呐的宽扫再窄扫。

Rationale用户已经等了一次「说话」，不能再等一次白屏。把首帧压到一帧内，准确率交给第二帧，是把「听得见的慢」变成「看得见的快」；超时保留前一段，则让失败不再是全损。

Downsides

  • 同一句话可能发两次请求，幂等键与配额口径要重新定义。
  • 两段结果不一致时会出现「先给后又收回」，需要视觉上的替换而非闪烁。
  • 粗查询与精查询共用缓存键还是分键，会直接影响命中率。
  • 「失败不扣配额」需要先确认服务端实际扣减点，不能凭口号实现。

I6.自证台账：把不可见的减法变成可查、可逆

Axis亮点时刻与信任边界

Description收窄完成后给一张可停留的回执，只说三件可证的事：听懂了什么（条件 chips）、替你排除了多少（同半径、无语义条件下的基线计数，例如「同范围共 82 条，当前 37 条」，基线由服务端返回，不写死）、被排除的是什么类别（「已排除 45 条 · 家政/宠物」，可展开恢复某一类，不展示被排除条目正文）。隐私部分不写「音频未保存」这类无法证实的话，只陈述真实链路（音频会上传用于转写、留存策略是什么），并把「隐私门缺麦克风/录音/AI 告知」与「政策缺原始音频留存条款」作为上线前置修复。

direct隐私门告知清单只有位置/手机号/发布内容/高德，没有麦克风、录音、AI（privacy_gate_screen.dart:111-118）；隐私政策只覆盖转写文本，没有原始音频留存条款；而代码确实会先上传音频再送 ASR（ai_entry_sheet.dart:583-594）。地图侧目前只有 L2 类目硬过滤，任何语义收窄都是新增的、用户看不见的减法（NfrMatch.hardFilterCategoryLevel=2；/map/pins 无 keyword）。

Rationale用户要的是「过滤不相关」，但过滤的对称风险是「过滤掉相关」，而后者不会报错。一行台账把不可见的减法变成可逆出口，同时给北极星里的「匹配召回率」补上可直接观测的误杀分母——否则召回率永远只能靠离线评测说话。隐私承诺只有建立在真实链路上才叫承诺，否则是负债。

Downsides

  • 需要服务端返回按原因分组的排除计数与基线计数，是新契约，且对照查询有性能成本。
  • 「恢复某一类」会改变当前结果集，需要与一次性搜索圈的状态协调。
  • 隐私文案必须由法务确认，工程不得自拟「未保存」这类承诺。
  • 排除类别过细会变成第二个筛选面板；建议只按 L1/L2 聚合。

I7.SemanticQuery 语义快照

Axis性能预算与失败降级

Description不引入一个裸 keyword，而是把一次语音查询固化成可哈希对象：原话、归一化文本、叶子类目集、供需方向、半径档、解析器版本、置信度；实现值相等，并进入 Pin 缓存键。同一句话第二次说，直接命中缓存，不重复付 ASR 与模型费用；同一对象可以生成分享深链、可以存成评测 golden set、可以回放做 A/B。

directPinsQuery 已经是值相等对象，字段与 ==/hashCode 齐全（discovery_providers.dart:26-85）；Pin 缓存是五要素键 + LRU 50 + TTL 60s（pin_cache_key.dart:49-57）；AI 配额 20/10/3、费用日 1 元/月 10 元（NfrAi.java:61-76）。

Rationale它同时解决三件通常要三套系统解决的事：成本（缓存挡住重复 ASR + 解析）、可复现（评测集天然产生）、可分发性（一句话变成链接）。二序效应最狠：一旦解析产物是对象，共享与传播才有可能，否则「核心亮点」会被自己的账单先关掉。

Downsides

  • /map/pins 没有语义参数，快照要么降维成「类目 + 供需 + 半径」，要么扩契约并把缓存键扩为六要素，前后端必须同构改。
  • 分享深链需要落地页与权限策略，超出「地图内搜索」一小步。
  • 解析器版本进入键会让每次模型/词表升级造成一次全量缓存失效，需要评估。
