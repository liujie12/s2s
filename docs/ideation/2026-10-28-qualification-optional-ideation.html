Grounding Context

代码库上下文与外部信号，全部候选在此之上被资格化与筛选。

一、产品与红线

找呀找（s2s）是 Flutter + Spring Boot 的本地生活分类信息产品。信任体系代号 T4，只有三件套：实名标、资质标、信息完整度三档。 三条红线写进了产品文档与代码注释：不做统一信誉分、不做信誉徽章/评价历史、不做负面背书标 （docs/PRD.md:640,646,1029,1679；lib/domain/listing_detail.dart:85-86； lib/features/detail/detail_screen.dart:583-584）。

二、现状的五个断点

  • 强制是一条硬拦截，不是建议。 category.need_cert（V1__init_schema.sql:80-87）驱动服务端 40302（PostValidator.java:85-88）， 客户端每个叶子类目还硬编码了 requiredCert（lib/domain/category_tree.dart:197-517）； 发布页在提交前拦下并跳转认证浮层，注释写得很直白：「无论用户选哪个都不放行」（lib/features/publish/publish_screen.dart:322-334）。
  • 「资质」与「一条信息」之间没有数据关系。 post 表没有任何 cert 列（V1:152-198），发布 payload 没有资质字段（lib/features/publish/publish_form_state.dart:372-397）， PostCreateRequest 的 required 里也没有（docs/api/openapi.yaml:4782-4790）。资质只挂在用户身上。
  • 详情页的资质展示是断的。 PostQueryService.java:132-138 把 qualification_badges 硬编码成 List.of()； post_detail_provider.dart:90-92 取首项；detail_screen.dart:583-595 用单行 _TrustLine(Icons.workspace_premium) 渲染。领域模型 Publisher 只有单个 label，没有签发方、没有有效期。
  • 人工审核写进了契约，但从未兑现。 /cert/qualification 只落 pending 并返回 2 小时 SLA，「人工审核留 B2-5 运营后台」（openapi.yaml:2053-2062）； /cert/status 的资质列表「本轮恒空」（:2092-2100）。而隐私政策写的是「资质证照仅用于人工审核，7 天内自动删除」。
  • 有效期是空字段。 expire_at 在 DDL、DTO、PRD 里都有，但代码里没有赋值、没有 expired 写入、没有定时任务，NfrCert 里也没有对应常量。

三、已经可以复用的东西

  • 快照先例：post.contact_mask 在发布时算好落库，读路径「不触调解密」 （V9__post_contact_mask.sql、PostService.java:325-330、PostQueryService.java:157-159）。
  • 迁移纪律：最新是 V21，已应用的迁移不可改，新改动必须新开 V22； docs/solutions/workflow-issues/data-model-reservation-for-deferred-features.md 主张「延期的是逻辑，不是数据」，预留可空列优于 NOT NULL 或唯一键。
  • 审计：AuditLogWriter 是 audit_log 唯一写入口（刻意不加 @Transactional，保留 180 天，白名单剔除 id_card/real_name/*_enc）。
  • 设计语言：B 族静态标记（内边距 2/4、圆角 4、caption、accent 填充 + surface 文字）最接近「资质徽章」； 状态一律「矢量色点 + 文字档名」，禁 emoji（PRD.md:815）；信任卡在浅青底上文字取 primary-dark（6.7:1）。

四、外部信号

  • 没有主流平台把资质审核直接取消。 它们把审核对象从「人」换成「件/交易」，把展示拆成等级：闲鱼 2025-09 卖家协议把「经营资质核验」与「个人声明」并列可选； Thumbtack 全员强制背调 + 可选 Licensed pro；Upwork 强制身份核验 + 可选 Identity Verified + 约 1% Expert-Vetted； Amazon 强制 KYB + 可选第三方证书；Airbnb 双向强制证件但从不展示证件。
  • 监管在收紧，而不是放松。 SAMR 2026-04 以「一店一罚」对 6 家平台罚 35.97 亿元，罪名即未尽资质审查义务；2026-09 两高典型案例涉伪造证件 3961 张； 抖音 2025-08 处置 6.2 万资质造假商家。电商法 38 条是连带责任，「形式审核不算尽责」。医疗须在显著位置公示电子证照； 家政有「家政信用查 / 电子居家上门服务证」；便民劳务允许自我声明，但必须明示。
  • 机审不是万能。 企业信用公示系统、学信网在线验证报告、医师电子证照都没有面向任意第三方的公开查询 API，需要机构合作才能接。
  • 可借的结构。 Sigstore/Rekor 透明日志只证明「未被篡改」，不证明「内容可信」；SLSA 2026-05 的教训是「provenance 有效 ≠ 内容可信，徽章必须写清证明了什么」； 餐厅 A/B/C 分级优于「有证/无证」二元；arXiv 靠可追溯与撤稿水印建立信任而非准入门槛。

Topic Axes

四个正交切面，用来防止六副镜头都落在同一个解读上。

  • A信任信号的陈列与分级 —— 详情页/发布者卡/列表显示什么、单张还是多张、已核验与自声明如何并存、签发方与有效期怎么露出。
  • B发布侧引导与关联 —— 发布流哪里引导而不拦截、一条信息挂一张的模型与选择器、跳过路径、成功页与草稿编辑。
  • C资质数据与生命周期 —— cert 与 post 的关系、审核取消后的状态语义、过期与撤销、快照还是读时关联、审计留痕。
  • D无人审下的风控与合规 —— 假证、分级分类、机审能力边界、抽检与举报、法律责任、拦截降级。

01

发布关联快照：一帖一证，冻结在发布那一刻

Description
新开 V22 迁移，建 post_cert_link：post_id、cert_id（可空）、投放时冻结的 snapshot、 declared_at、version。发布或补录时，把展示所需字段一次性算好写进快照；详情页读快照，不 join cert、 不读原图、不解密，也不随用户后续认证状态漂移。用户换证后给一个显式的「更新为最新」动作生成新版本，历史版本原地保留。
Axis
C 资质数据与生命周期
Basis
directV1:152-198 post 表无任何 cert 列； directpublish_form_state.dart:372-397 payload 无资质字段； directPostService.java:325-330 + PostQueryService.java:157-159 的 contact_mask 先例「读取它不触调解密」； direct迁移纪律：最新 V21、新改动必须 V22； reasoned资质是账号的易变状态，帖子是可被外部引用的历史陈述，把两者直接 join 会让一条三个月前的帖子在无人操作时「变差」。
Rationale
用户要的是「资质属于用户信息、每次发布可以关联某个资质证书」。这句话在数据模型上的正解是「引用 + 冻结」，不是外键指针。 这条也是其余五条的地基：没有关联层，详情页永远只能从作者聚合态猜，任何展示、引导、过期逻辑都没有落点。
Downsides
快照会让「发布时是什么」与「现在还有效吗」分叉，因此必须同时保留一个实时有效性判定，否则撤证或过期后详情页仍会显示「已核验」； JSON 快照需要版本号支撑字段演进；写入口有三处（发布、补录、换证），不收敛就会口径漂移。

02

资质元数据档案与详情页证据行

Description
cert 从「只存原图引用」升级为「结构化元数据 + 原图」：补签发方、脱敏证号、核验来源、核验时间、有效期、图像哈希六个字段。 原图仍按隐私政策窗口清理，元数据与哈希长期保留。详情页把现在的单行 _TrustLine(Icons.workspace_premium) 换成「证据行」：证名 · 签发方 · 有效期至 · 平台做了什么核验；没有关联资质时整块不渲染。点证据行进入只读资质档案页， 列出该用户全部资质，页面上不放评分、评价、发布次数。
Axis
A 信任信号的陈列与分级
Basis
directV1:299-322 cert 表无 issuer、无证书编号、无核验来源列； directdetail_screen.dart:583-595 只有单个 qualificationLabel， 且同处注释已确立「没有认证就不展示，不做负面背书」； directdocs/legal/隐私政策（草稿）.md:38,44-49「资质证照仅用于人工审核」「核验完成后 7 天内自动删除」—— 这条目的限定正是「只存原图」方案的天花板； externalSLSA 2026-05 的教训：徽章必须写清「证明了什么」，而不是「可不可信」； external餐厅 A/B/C 分级之所以有效，是因为它公示可核对的检查事实，而不是给一个总评。
Rationale
用户说「详情可以看到资质信息，这样可以提升资源的可信度」。现在详情页拿到的是一个恒定空列表。 把档案主体从图像换成元数据，同时解决两件事：7 天删图不再等于「无证可展示」，以及平台终于能只陈述自己做过什么、不替用户下结论。
Downsides
必须先改隐私政策的目的限定（从「仅用于人工审核」扩到「用于展示资质摘要」），否则这条与现行政策直接冲突——这是本条的硬前置，不是工程细节； 六个列属于 V22 里的实质变更；签发方要么用户填、要么 OCR 提取，录入成本上升； 「平台做了什么核验」写错一个字就是虚假陈述，文案需要法务逐条过。

类目资质要求三档化，只删「建议档」的硬拦截

Description
把类目的资质要求从「有无强制」升级为三档：none / suggest / require-by-law。 suggest 档只产出一条非阻断提示（「此类目关联资质后，对方更容易联系你」+ 可跳过的「去关联」）， 不调用认证浮层、不阻断提交、不产生 precheck 码；require-by-law 档保留既有 40302 与拦截浮层。 40302 的语义与号段一律不动。客户端 category_tree.dart 的硬编码 requiredCert 改为读服务端下发的档位，消掉双源。
Axis
B 发布侧引导与关联
Basis
directpublish_screen.dart:322-334「无论用户选哪个都不放行」； directPostValidator.java:85-88 产 40302，category_tree.dart:197-517 逐叶子硬编码； direct「哪些类目必须认证」同时写在用户协议 7.3/8.1 与 PRD §4.3，是法务承诺而非 UX 选项，所以只能按档降级、不能整体删除； external闲鱼 2025-09 卖家协议把「经营资质核验」与「个人声明」并列可选，而不是取消强制项。
Rationale
这是让「可选」在代码层成立的方式：不是把 if 改成 false，而是让「强制」从布尔位变成档位， suggest 档彻底不进入拦截链路，同时给法务留一个明确出口。只改条件判断会留下一个「实名即资质」的隐形闸门 （PostValidator.java:141-143 现在拿实名状态当资质代理）。
Downsides
「哪些类目属于 require-by-law」是一次法务盘点，不是工程决定；医疗类目当前由 40303 禁发兜底，不能直接当样板； 改客户端读服务端档位会牵动 category_tree 的本地兜底与既有测试；降档后若某类目纠纷率上升，回滚成本在数据侧而不在代码侧。

发布后补挂：把引导从摩擦点挪到意愿峰值

Description
发布表单里的资质区块默认折叠、可跳过、不参与 canSubmit；发布成功页与「我的发布」各加一张「给这条加一份资质」卡片， 点开只列档案里未过期的证书，选中后原地预览它出现在详情页的样子。补挂与发布走同一个快照写入口，补挂率作为可观测指标。
Axis
B 发布侧引导与关联
Basis
directpublish_success_screen.dart 目前只有「首页 / 我的发布 / 回去补齐」三个出口，没有任何资质引导； directpublish_screen.dart:933-937 现在是在分类行先用 _HintText 预告「该分类发布前需完成…认证」， 把提示做成了事前压力； reasoned用户在发布成功获得正反馈时上传意愿最高，在被表单拦住时最低——引导应该放在意愿峰值，而不是摩擦峰值。

取消全量前置人审，改为核验强度声明 + 抽样后置

Description
/cert/qualification 不再以「pending 等 2 小时人审」为默认路径：提交后按实际能做到的核验方式落一条 verify_source（用户声明 / 材料已留档 / 平台比对项 / 人工抽检），展示层只陈述「平台做了什么」，不说「已认证」。 同时保留常量比例的随机抽检与举报触发的后置复核；复核不通过只解除该次关联，并复用既有下架与处置链路，不新增错误码。 连带改写 PRD §4.3/§4.5、隐私政策、用户协议 8.1 里「人工审核」的表述。
Axis
D 无人审下的风控与合规
Basis

Rationale
用户明确说「可以不审核」。能站住的形态不是静默关掉开关，而是把承诺口径从「这条资质是真的」改成「我们做了哪几项核验、事后能怎么处置」， 同时把成本结构从 O(提交量) 改成 O(抽样率 + 举报量)。SLSA 的教训正好适用：把流程证明包装成内容结论，就是虚假背书。
Downsides
这是一次跨文档改写（PRD、隐私政策、用户协议、openapi、上架自评材料），不是纯代码变更，落地前必须过法务； 「用证书编号自动比对官方库」目前走不通——企业信用公示、学信网、医师电子证照都没有面向任意第三方的公开 API，需要机构合作， 因此不能作为主路径写进方案；抽检比例若落到 0，约束只剩举报，需要先确认举报入口与响应时限已在现有口径内。

06

有效期是日历事件，不是一次状态跃迁

Description
expire_at 在证书写入时落库；展示层按当前日期比较决定是否陈列该条资质——到期即静默不显示，不写 expired、 不跑批、不显示「已失效」红标，续期后自动恢复可见。到期前提醒窗口收敛到 NfrCert 常量，供通知与「我的」页复用； 完整度「待补」仍由既有三档规则产生，不为资质另造负面标。
Axis
C 资质数据与生命周期
Basis
directexpire_at 在 DDL、DTO、PRD 里都有，但代码无赋值、无 expired 写入、 无定时任务，NfrCert 也无对应常量； directPRD.md:856「年审到期前 30 天提醒，超期自动打『待补』标，不可继续发高敏类目」； directdetail_screen.dart:583-584「不做负面背书」； reasoned「有效期至 YYYY-MM」是用户可以自己判断的事实，而「已过期」是平台对该用户下的判断。
Rationale
少一个状态值、少一个定时任务、少一类客服工单；同时天然满足「不做负面背书」——过期表现为消失，而不是变红。 这也补上了现在最荒谬的一处：expire_at 有列没人写，等于资质永远有效。
Downsides
PRD:856 明确要求「超期打待补标、不可继续发高敏类目」，静默不陈列与该条冲突，必须先改 PRD 或把「待补」明确限定在完整度上而不作用于资质行； 「不跑批」与到期提醒的通知投递需要惰性写入或查询兜底，否则提醒永远发不出去；读时比较的成本要在列表与详情两处各评一次。
