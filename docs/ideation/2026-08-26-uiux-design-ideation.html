SEC-GROUNDING依据现状

这一轮不是从零构想界面，而是回答一个交棒问题：08-28 要冻结的东西，怎样才能让设计师接得住、并且改完之后我们还认得出红线在不在。

原型侧的事实：prototype-figma/code.js 约 3400 行，生成 42 个画框（18 个主态 + 23 个变体 + 1 个组件页）、20 个 Component master、21 个 COLOR 变量、23 条原型跳转、35 张画布标注卡。PRD v2.1 是唯一权威源，规定了 16 个语义色 + 5 个分类色、6 阶字号、6 阶间距、5 阶圆角、六件基础组件、S2 四档聚合、空态六时点、T3 弹层三退出口。

缺口集中在四个地方，且都不是「画得不够好看」，而是规格没有可交付的载体：字号 / 间距 / 圆角 / 阴影四类共 17 项仍是 JS 字面量，Figma 侧只有颜色进了变量；20 个 master 互相之间没有任何关系表达，全文没有 createComponentSet；35 张标注卡对被标注对象零引用，纯粹漂在画布上；生成器的操作界面上有四处计数已经和实现脱节。

本轮的红线（项目原则 ⑳）：视觉精修与动效实现是设计师的本职，我们做了她也会推翻重做。凡属「替设计师决定颜色好不好看、动画怎么弹」的想法一律不算机会。但「不做实现 ≠ 不交规格」——规格必须以可读回的形式交出去。六条存活想法全部落在这条线的内侧。
取证遗留：本轮环境无联网工具。地图 UI 的外部先例（bottom sheet 分档惯例、marker 聚合视觉惯例、图层面板形态谱、地图与列表联动模式等 6 类）本轮无法取证，需在有联网的会话补齐。所有 external 依据均取自本机已安装的 130 个 Figma MCP 工具 schema 原文，未编造任何 URL。

SEC-AXES主题的四条轴

从缺口反推，「怎么把原型推成设计稿」这个问题实际被四条互不重叠的轴切开。四条轴与 08-24 那份「生成器如何升级」的四条轴完全不同。

A1 · 规格的承载体

35 张画布标注卡，和「绑在节点上、能读回、进 Dev Mode」的规格，是两种东西。前者评审时好用，交棒后就是噪音；后者才能在设计师改稿之后仍然可查。

A2 · Token 的完备度与出口

21 个颜色变量之外的字号、间距、圆角、阴影；以及 Token 从 Figma 流向 Flutter 时的口径——用什么单位、谁是权威源、冲突时谁让路。

A3 · 组件之间的关系

20 个散装 master 之间的关系没有被表达；PRD §1.7 的六件基础组件只做了一件。组件库的价值在结构，不在数量。

A4 · 交棒契约与离场对账

设计师拿到文件后从哪儿起手、哪些不许改、改完之后凭什么证明红线还在。这一轴决定的是交付是否可复现（项目原则 ㉔）。

I1

规格从画布卡迁到节点上：改一个函数体，35 张卡整体换承载体

轴 A1 规格的承载体 信心 82% 复杂度 Medium 推荐 Top pick

今天的 35 张标注卡，是一个函数生出来的：annotation(title, lines) 全身只有一个浅色框、一个标题、一个循环打印的条目列表——对被它标注的对象一无所知。它不知道自己在说哪个按钮，卡片和对象之间只有「挨得近」这一层关系。设计师一旦挪动布局，这层关系就断了。

关键杠杆在于：所有 35 处规格都从这一个函数流出。换掉函数体，等于一次性把 35 处规格从「画布上的浅色框」搬到「绑在节点上、Dev Mode 能读回」的 annotation 上，而不需要逐个调用点改写。

搬过去之后还能顺手做两件今天做不到的事。一是分级：现在 35 张卡视觉完全同构，「主色对比度不得低于 4.5:1」和「这里建议留点呼吸感」长得一模一样，设计师无从判断哪条是红线；annotation 支持分类，红线与提示可以从此分开。二是分通道：人要读的理由写进 labelMarkdown，机器要核的数值挂进 properties[]，不再让一句话里既有理由又有数字。

最后这件事才是它真正的价值：设计师改完稿之后，我们可以把全部 annotation 读回来逐条对账。今天做不到——今天只能靠人肉看图找那 35 张浅色框还在不在。

依据
  • directcode.js:1170-1180 —— annotation() 函数体仅 box('_annotation/'+title, 'VERTICAL', {w:260, fill:'color/primary-light', stroke:'color/border'}) + 标题 text + 循环 text，无 severity 维度、对被标注对象零引用
  • direct全文 23 处静态调用点，运行时展开为 35 张卡（含 3+6+3+4+1 的循环体）
  • externalfigma_set_annotations schema —— 支持 labelMarkdown、properties[]（可 pin 33 项）、categoryId
  • externalfigma_get_annotations schema —— 支持 include_children 与 depth，构成离场对账的读回通道
为何重要
它把「规格」从评审期的一次性道具，变成贯穿交棒全程的可查资产。项目原则 ㉔ 说「审批的载体决定交付可复现性」——这条正是换载体。
风险
  • Desktop Bridge plugin 是二元前置。不通则这条为零，因此第一步应是一次独立的连通性验证，不要和迁移混在一起做。
  • 画布卡在评审场景仍然有用（投屏时一眼能看见）。迁移不等于删除，需要决定是否保留双投影。
  • 「哪条是红线」这个分级判断本身需要过一遍 PRD，不是纯机械改造。
I2

Token 的权威源既不在 Figma 也不在 code.js，而在 DTCG；出口按 dp 直连 Flutter

轴 A2 Token 完备度与出口 信心 76% 复杂度 Medium

今天的 Token 状态是不对称的：颜色进了 Figma 变量（16 语义 + 5 分类，共 21 个），而字号 6 阶、间距 6 阶、圆角 5 阶——共 17 项——仍然是 code.js 里的 JS 字面量，注释回标 PRD 章节号，但 Figma 侧完全看不见。后果是设计师在 Figma 里改不动它们：她想把卡片圆角从 12 调到 16，只能改一个画布上的具体矩形，改不了「圆角 lg」这个概念。

补齐本身不难，难的是补齐之后谁是权威源。如果 Figma 有一份、code.js 有一份，就回到了「多格式交付件一致性」那个已经吃过教训的坑里。所以这条想法的重点不是「导入变量」，而是把权威源移出两边，落在一份 DTCG 格式的 Token 文件上，Figma 变量和 code.js 常量都降格为它的投影。这类似于千克原器在 2019 年被普朗克常数取代——去掉实物基准，任何一方损坏都可以从定义重建。

出口上有一个恰好的便利：项目的画布宽高 390×844 在注释里就写明「与 Flutter 逻辑像素一致」，而导出工具支持 sizeUnit: 'dp'。选 dp，Token 从 Figma 到 Flutter 之间不需要任何换算，也就少了一个漂移点。

还有两个细节值得一并决定。导入冲突时的行为默认是「问」——一字不写、等人确认，这天然就是「设计参数复核闸门」那条沉淀想要的东西，不用另建流程。另一头则要留神：版本 diff 工具明确不追踪变量值的变更，也就是说有人把主色从 #0B7C8C 调深一档，diff 里看不出来——而主色对比度实测 4.91:1，红线 4.5:1，余量只有 0.41。Token 值这条腿必须单独记一本账，不能指望版本对比替你看住。

依据
  • directcode.js:57-71 —— TYPE_SCALE(6 阶) / SPACING(6 阶) / RADIUS(5 阶) 为纯 JS 字面量，注释只回标 PRD §1.4.4/§1.4.5，无任何 figma.variables 调用
  • directcode.js:260 —— ensureVariables() 只查 getLocalVariablesAsync('COLOR')，非颜色类型从未纳入
  • directcode.js:74 —— CANVAS = {w:390, h:844}，注释原文「与 Flutter 逻辑像素一致」
  • directPRD:201 —— 主色对比度实测 4.91:1，红线 4.5:1，余量 0.41
  • externalfigma_setup_design_tokens schema —— DTCG 花括号别名，上限 modes≤4 / tokens≤100（现存 21 + 新增 17 = 38，远未触顶）
  • externalfigma_export_tokens schema —— 10 种格式、sizeUnit: px/rem/pt/dp、dry-run、$extensions 存 variable ID 保 round-trip
  • externalfigma_diff_versions schema —— 明确声明不追踪变量值变更
为何重要
M3 的验收项里「Design Token 落地」是硬指标。今天落地率是 21/38，而且缺的正好是设计师最常调的字号与间距。
风险
  • 阴影一类的实际数量需要重新点算——原始候选里写的「13 处 DROP_SHADOW」经核实实为 8 处，说明这类计数不能凭印象。
  • DTCG 作权威源意味着多一个需要维护的文件与一条同步纪律；如果没人真的按它走，反而多一份漂移源。
  • 动效类 Token 走不通这条路（见 I5）。
I3

20 个平行 master 合成变体集，SLOT 承载结构差异变体——被否过的想法，前置条件变了

轴 A3 组件之间的关系 信心 71% 复杂度 High

组件页上有 20 个 Component master：6 个按钮（primary / secondary / ghost / default / hover / disabled 六个平行名字）+ 10 个 pin + 若干其他。全文没有一处 createComponentSet、没有 combineAsVariants、没有 componentPropertyDefinitions。它们是 20 个孤岛，彼此之间的关系全靠命名暗示。

这带来两个具体损失。一是那六个按钮名字其实混了两个正交维度——primary/secondary/ghost 是样式，hover/disabled 是状态，把它们并列成六个名字是范畴错误，也意味着「secondary 的 disabled 态」这一格根本不存在、而且没人看得出它缺了。变体矩阵的价值恰在于缺格会自己显形。二是没有变体集就没有「状态覆盖度」这个概念，可访问性审计工具无从下手——比如全套组件是否都有 focus 态，今天没法回答。

更值得注意的是一条被否想法的复活。08-24 那轮曾提出把 pin 做成变体，被否的理由很硬：Instance 禁止增删子节点，而 pin 的选中态（48×48 带阴影）与角标态是结构差异，不是属性差异，所以代码里一律回退到原生构造 pinRaw，留下一份重复实现。现在有了 SLOT——schema 原文说它「比 INSTANCE_SWAP 更灵活」，SlotNode 会自动创建同名 SLOT 属性，正是「结构可换」的官方出口。项目原则 ⑱ 要求被拒想法随前置条件复评，这条到点了。

合并的时机风险也比想象小：create_component_set 会保留 base 的 node ID、已有 instance 不断链。42 框已经成型的情况下仍然可以无损合并，不必推倒重来。

依据
  • directcode.js:1330-1356 —— registerComponents() 六次 toComponent('ui/button/'+variants[v]) + 双层循环注册十个 pin，合计 20 个平行 master；全文检索 combineAsVariants|createComponentSet|componentPropertyDefinitions 零命中
  • directcode.js:1290-1322 —— pin() 注释明确「选中态（48×48+阴影）与角标态属结构差异，一律回退原生构造」，并在 1313 行落地回退
  • directcode.js:1201-1206 —— toComponent() 只设 name 并入缓存，20 个 master 全无 description
  • externalfigma_create_component_set schema —— base 保留 node ID、instance 不断链、上限 100 变体
  • externalfigma_create_slot schema —— SlotNode 自动创建同名 SLOT 属性，原文「more flexible than INSTANCE_SWAP」
  • externalfigma_audit_component_accessibility schema —— 状态覆盖度 + annotation 完整度 + 色盲模拟
  • direct项目原则 ⑱（说明文档:941）—— 被拒想法须随前置条件复评
为何重要
组件库交付给设计师，交的是结构而非数量。变体矩阵一旦成立，缺口自己会说话，审计也才有落点。
风险
  • 复杂度是这六条里最高的，且 PRD §1.7 六件基础组件补齐所需的工作量此前被显著低估——核实后，标签 / 空状态 / 骨架屏三件全无对应函数，需要从零写，不是「包一层」。建议先只做按钮与 pin 的合并，其余三件单独排。
  • SLOT 的实际行为未在本项目验证过，schema 说明与真实表现可能有差距，需要一次小样验证。
  • 同样依赖 Desktop Bridge。
I4

交棒第一屏做成可信入口：计数运行时自报，契约随组件走

轴 A4 交棒契约 信心 88% 复杂度 Low 性价比 最高

设计师接手时看到的第一个界面是生成器的操作面板 ui.html。上面有四个数字，四个全错：写「14 页 + 3 模态」，实际 18 个主态；写「语义色 13」，实际 16；写「等 13 页」，实际 14；写「22 条跳转」，实际 23。这些不是笔误，是手写副本随实现漂移的必然结果——「跨文档引用核验」那条沉淀讲的就是这件事。

问题的根不在数字，在撰写权。只要这些数字由人手打，它们就会再次过期。做法应当是取消人工撰写权：让计数在运行时由生成器自报，界面只负责显示。这样「交棒界面上的数字说谎」这种事，从此在结构上不可能发生。

同一屏还缺第二样东西：契约。20 个 master 全部没有 description，设计师打开组件页看到 20 个孤立框，不知道该从哪个起手、哪些是不许动的。把「从哪起手 / 哪些不许改」写进每个组件的 description，契约就和文件同生共死，不会像一份单独的交接文档那样被遗忘在某个目录里。

加上 I1 提供的读回通道，这一屏就构成完整闭环：数字自报、契约随组件、红线可读回。三件事各自都很小，凑在一起是「交付可复现」的最小实现。

依据
  • directui.html:24「14 页 + 3 模态」实为 18 主态（screen() 去重后 18 个 pageId）
  • directui.html:30「语义色 13」实为 16（SEMANTIC_COLORS 16 键）
  • directui.html:42「等 13 页」实为 14（code.js:3289-3291 列 14 个 build*）
  • directui.html:54「22 条跳转」实为 23（code.js:3576-3601 计 23 行）
  • directcode.js:1201-1206 —— toComponent() 从不写 description
  • directdocs/solutions/workflow-issues/cross-document-reference-verification.md
  • externalfigma_set_description 与 figma_generate_component_doc
为何重要
四个错误数字出现在交棒动线的第一个触点上。第一屏不可信，后面所有规格的可信度都要打折。而修它的成本在六条里最低。
风险
  • 计数自报需要生成器在跑完之后回填界面，涉及一次消息通道改动——小，但不是零。
  • description 写什么需要人来定，不能自动生成；写得太细会变成第二份 PRD。
I5

动效规格改走 annotation：记「♩=120」，不记弓法

轴 A1 / A2 交界 信心 64% 复杂度 Low

23 条原型跳转共用同一段硬编码 transition：SMART_ANIMATE / EASE_OUT / 0.3s，而 link() 的函数签名里根本没有 duration 参数——就算想给某条跳转单独设时长，今天也传不进去。于是搜索框展开、弹层升起、整页切换这三种语义完全不同的转场，动起来一模一样。

本来的自然想法是把时长和曲线做成 Token，跟着 I2 一起进变量。但这条路是堵死的：动效类 Token（TIMING / EASING）无法经 Plugin API 创建为变量。这不是懒得做，是能力边界。既然 Token 层承载不了，动效规格就只能落到 annotation 上——正好和 I1 是同一个承载体。

更要紧的是划清交什么、不交什么。乐谱记 ♩=120，不记弓法：时长与曲线是规格（必须交），运镜与弹性是表演（留给设计师）。按这把刀切，我们该交的是「弹层升起 250ms / ease-out，页面切换 300ms / ease-in-out」这类可核对的量，不该交的是「这里应该有一点回弹感」。后者属于原则 ⑳ 明确要避开的区域——我们做了她也会重做。

可以顺手做的一件事是让 23 条跳转按语义分档，这样设计师在 Present 模式里能直接体感差异，而不必读文档去想象。但要注意这一步很容易越线：分档的依据必须是已有的语义分类，不能变成我们在替设计师调手感。这也是这条信心只有 64% 的原因。

依据
  • directcode.js:3706-3721 —— transition 为硬编码字面量 {type:'SMART_ANIMATE', easing:{type:'EASE_OUT'}, duration:0.3}，签名 link(node, target, trigger) 无 duration 参数
  • directcode.js:3570-3602 —— FLOW_LINKS 实为 23 条，全部共用上述字面量
  • externalfigma_import_tokens schema —— 明确声明 TIMING / EASING 无法经 Plugin API 创建
  • reasoned记谱法的规格 / 演绎分界：定量参数入谱，表现手法留给演奏者
为何重要
动效是 14 页视觉稿之外最容易在交棒时丢失的一类规格，因为它不在静态画面上。而它恰好又是 Token 层唯一承载不了的一类，必须显式安排去处。
风险
  • 最贴近原则 ⑳ 红线的一条。「按语义分档」与「替设计师调手感」之间只有一层，需要在动手前明确写下判据。
  • Present 模式的体感差异是否真的比文档有效，未验证。
I6

08-28 冻结的对象，从像素翻转为契约

轴 A4 交棒契约 信心 69% 复杂度 Low 类型 范围决策

M3 的里程碑写的是 2026-08-28 冻结 14 页视觉稿、Design Token 落地。但如果承认原则 ⑳——视觉精修由设计师主导、我们做的视觉稿大概率会被推翻——那么「冻结 14 页视觉稿」这个目标本身就有内在矛盾：冻结一件注定要被重做的东西，冻结动作没有承载价值。
