SEC-GROUNDING依据现状

这一轮的起点不是「架构该长什么样」，而是一个更难堪的事实：PRD 已经把目标态写到了接口级与数据字典级，而代码侧的后端一行都没有。两侧之间没有任何自动对账通路，所以每一处不一致都要等到联调那天才会现身。

代码侧的硬事实：全库检索 http / dio / HttpClient / retrofit / freezed / json_serializable 零命中——不存在网络层，也不存在序列化代码生成。四个 Repository（auth / listing / contact / publish）全部是假实现，内含 7 处 TODO(接后端)。request_id 在 lib/** 与 test/** 均为 0 命中。PRD §6.10 规定的三级缓存、三档 TTL、50 键 LRU，以及 §14 要求的 layer_switch 埋点，一处实现都没有。

PRD 侧的硬事实：§12 接口契约、§13 数据字典、§14 非功能需求已作为 SRS 三章并入，共 192913 B。北极星在 PRD:32 直接写定 0.6 × 0.6 × 0.6 = 0.216（三轴等权硬线）。§14.1 给出七个数字：图层切换 P95 ≤ 300ms、读接口 P95 ≤ 150ms、帧渲染 ≤ 16ms、单次取数 ≤ 10KB、渲染上限 500 Pin、推送 1min 触达 Top20/Top30。

已经落地的三块地基虽小但方向明确，且都在为架构决策提供先例：lib/features/map/clustering/grid_cluster.dart 刻意不 import Flutter（:6-8 原文「聚合是纯计算，不碰 UI。好处是 POC-A 能在 Dart VM 里直接跑基准」）；lib/features/perf/frame_metrics.dart 已经实现了一套完整的分位与直方图口径（:129 桶边界 [8,16,32,50,100]）；lib/features/map/map_screen.dart:206-217 的 canRenderRealMap 双分支同结果，实际上已经是「能力降级注册表」的第一个实例。

取证时抓出的九条 PRD↔代码冲突（C1–C9），其中最硬的是 C6，量纲级冲突：map_screen.dart:40 的 _kClusterGridSize = 60（像素）× :46 的 _kInitialMetersPerPixel = 12 ≈ 720m，而 PRD:1354 写「约 500m 网格取整」。两侧不只是数值不同，量纲都不是同一个——一边是屏幕像素，一边是地理米。这条冲突后来成了存活想法 A2 的全部动力。
取证缺口，须先声明：web research 子代理连续两次空返回，已按降级路径改用 3 次直接检索（OTel Dart 生态现状 / 空间检索方案对比 / 模块化单体趋势），均成功。但下列外部数字独立核验环节无法证实，因此依赖它们的候选（R15 模块边界 CI 门禁、R09 三通道分层）一律未进存活集：Shopify Packwerk 的 68% / 55%、CNCF Q1 2026 的 42% 微服务回并率、Workiva OTel Dart v0.18.x「logs 未实现」。

独立核验推翻的一处自造事实：发散阶段有三路想法共同建立在「22 个错误码 ↔ 22 个失败枚举值」这个漂亮对称上。逐行点算后，PRD §12.5 错误码表实为 20 行 / 19 个非零码，客户端侧 AuthFailure 8 个 + ContactFailure 5 个 = 13 个。22 ↔ 22 是编造的。据此 X1 整条前提崩塌被驳倒，R02 降级。

引文精度扣分项：PRD §12 及其之后的引文存在系统性 +1 行偏移（如实际 2057 被引为 2058）。逐字内容全部真实，故只扣分不判否；而 §6.10、§9.10、§13、§14.5 段的行号完全精确。

SEC-AXES主题的五条轴

「目标态架构」这个题目太大，无法整体思考。从上面的缺口反推，它实际被五条互不重叠的轴切开——每一条都能独立决策，且每一条上都存在真取舍而非单一正确答案。

轴 1 · 后端服务形态与分层接缝

后端从零开始，这是一次性的自由。单体还是拆分、按什么维度切、客户端与服务端之间那条缝由谁定义、谁是契约的真源。这一轴决定另外四轴的落点。

轴 2 · 数据模型与空间检索

C1–C9 九条冲突全部落在这一轴。空间检索选型（PostGIS / MySQL SPATIAL / Redis GEO）只是表象，底下的问题是空间量纲由谁定义、两侧命名要不要统一。

轴 3 · 300ms 四段预算的算力归属

缓存查找 + 网络 + Dart 聚合 + Pin 渲染四段，总预算 300ms。真问题不是「怎么更快」，而是每一段的算力放在哪一侧、新鲜度的权威归谁。聚合实测仅占 1.6%，说明瓶颈不在算得快慢上。

轴 4 · 可观测性链路的贯通

trace / metrics / logs / 审计四类信号，PRD 分散在 §14.4、§9.10、§12.1 三处规定。这一轴的核心矛盾是度量主权在客户端还是服务端，而 PRD 目前两边都写了一点。

轴 5 · AI 能力的部署与降级路径

LR + GBDT 与 3B 模型放在读路径上还是写路径上、降级有几档、降级态算不算一种要验收的产品形态。这一轴上的候选最少，说明它被想得最浅。

SEC-IDEAS存活想法（7 条，按推荐度排序）

  • A1 · 按「可预计算性」划分架构，不按端点划分
  • A2 · grid_id 升为唯一空间量纲
  • A3 · 先定新鲜度权威在哪一侧，再定缓存实现
  • A4 · 客户端是唯一能算出真实 P95 分母的地方
  • A5 · 契约即代码：PRD §12/§13 升为机器可读真源
  • A6 · 0.216 反解为三份 error budget
  • A7 · AI 移出读路径，在线只取物化结果
A1

先按「数据的可预计算性」画一条分割线，再谈服务形态——语言与框架选型会自动退化为次要决策

轴 轴 1 服务形态与分层接缝 信心 84% 复杂度 Medium 推荐 Top pick

《技术栈选型说明》最自然的写法是从「后端用什么语言」起手。这条想法主张那是第二个问题。第一个问题是：这个系统里哪些数据能在请求到来之前就算好，哪些必须在请求当时才能算。

之所以说这条线本来就存在，是因为 PRD 自己已经画了一半、只是没给它起名字。PRD:2274 规定「计数走缓存不落库，避免热点行」——这是承认某类数据不需要在线一致性；PRD:2221 规定「落库存条件而非加权分」——这是承认另一类数据必须是已落库的事实而不能是请求时的推导结果。两条相邻的规定，方向相反，各自都对，但没人说过它们合起来是一条架构分割线。

把这条线明确画出来之后，在线面剩下的东西非常少：/contact 的手机号解密、三维限频判定（PRD:2151 的账号 / 设备 / IP 任一）、配额扣减、幂等去重。其余全部可以是预计算面。这个划分的价值在于它把「性能」这个模糊要求变成了归属问题——300ms 里的每一段都能问一句「你在线上算这个是必须的吗」。

更关键的连带效果是：一旦分割线成立，三个看起来在互相竞争的方案其实是同一条光谱上的三点。静态化 CDN 快照、瓦片化 z/x/y、网格位图——差别只在固化粒度（快照 / 瓦片 / 位图）与固化时机（版本变更 / 烘焙周期 / 请求时），而它们的取舍完全一致：都是用新鲜度换确定性。所以架构文档里应该写的不是「我们选了瓦片」，而是这条固化程度轴，以及我们在轴上选了哪个点、为什么。

最后一层：这条线也顺手解决了 300ms 该怎么用的问题。PRD:2306 留了一条后路——「POC 不通过则下调 Pin 上限并按实测改写 SLA」。那条后路正是「先做出来再优化」的产物。反过来用，300ms 应当是方案的准入筛选器：一个方案如果只能靠调优才勉强够，它在分割线上的位置就是错的。

依据
  • directPRD:2274「计数走缓存不落库，避免热点行」 vs PRD:2221「落库存条件而非加权分」——分割线的两个雏形，相邻但未被命名
  • directPRD:2151 42901 限频维度「账号 / 设备 / IP 任一」——典型的必须在线判定项，客户端无法自行区分
  • directPRD:2270「空间条件必须先行否则退化全表」——查询计划已被钉死，不留在线插入推理的余量
  • directPRD:2306「POC 不通过则下调 Pin 上限并按实测改写 SLA」——这条后路的存在本身，证明 300ms 目前不是筛选器
  • directtool/poc_b_paint_benchmark.dart:10-11「开发机绝对毫秒不得写入 SLA」+ :16-18 形状判据——项目已有「用形状而非绝对值判定」的先例
  • direct说明文档:1959 原则 74
为何重要
它是七条里唯一会改变其余六条形态的想法：分割线一旦落定，A3 的缓存权威、A7 的 AI 归属、以及技术栈选型的自由度全部随之收窄。因此它应该最先被拍。

  • 分割线画错的代价不对称：若把配额扣减误划到预计算侧，直接后果是超发——这是钱和信任的损失，不是性能问题。在线面宁可画大不可画小。
  • 作为准入筛选器使用时，需要在没有真机数据的阶段用推算淘汰方案，而推算本身可能错。
  • 若落到 CI 门禁上，容差定紧则天天红灯没人信，定松则抓不住回归。这一层建议后置，不与分割线本身混做。
A2

grid_id 升为系统唯一的空间量纲，屏幕像素网格退回纯渲染去重——C6 不是数值不符，是两个量纲在打架

轴 轴 2 数据模型与空间检索 信心 88% 复杂度 Low 性价比 最高

C6 通常被记成「代码 720m，PRD 500m，数值不符」。但把两侧引文并排看，会发现问题深一层。grid_cluster.dart:13 的注释原文是：「用屏幕像素坐标而非经纬度：聚合阈值按 PRD §6.15 定义在屏幕像素网格上」。而 PRD:1354 写的是「约 500m 网格取整」。一边的单位是像素，一边的单位是米。720 与 500 的差距只是这件事在当前缩放级别下的投影。

算术是这样来的：map_screen.dart:40 的 _kClusterGridSize = 60（像素）乘以 :46 的 _kInitialMetersPerPixel = 12，得 720m。但这个乘积会随缩放变化——也就是说今天代码里的「网格」在不同缩放级别下代表不同的地理范围，而 PRD 的「500m 网格」是一个固定的地理单位。两者不是可以通过调参数对上的关系。

所以收口方向应当是单向的：地理量纲的 grid_id 是唯一权威，它同时是空间检索的索引键、预聚合的分组键、缓存键的一个要素、以及埋点的一个维度。而像素网格降格为渲染层的一个局部实现细节——它只负责「屏幕上这两个 Pin 挨得太近，画一个就够了」，不再承担任何数据含义。

之所以说这条性价比最高，是因为它成本极低而影响面极大。它顺带消解了 C1 / C2 / C4 那组「两侧命名要不要统一」的争论：一旦承认存在一个明确的权威量纲，剩下的命名差异就是投影关系而不是冲突，用不着为它建一整套双向映射层。同一个代码库里其实已经两种策略并存 —— listing.dart:48 遇到 decimal→double 精度问题时只留了注释，而 listing_detail.dart:7 明写「列名直接作为字段名，不做重命名」。这不是不一致，这是不同层次该有不同待遇。

还有一个隐藏收益值得单独说。grid_cluster.dart:6-8 刻意不 import Flutter，理由是「聚合是纯计算，不碰 UI」，好处是能在 Dart VM 里直接跑基准——正因如此我们才拿到了「5 万点聚合仅 4.73ms，占 300ms 预算的 1.6%」这个数字。把 grid_id 定为地理量纲，等于把这个纯度从一个文件的局部选择升格为分层约束：网格 ID 计算、缓存键规范化、完整度判定、编解码都属于同一类无设备依赖的纯逻辑。

依据

  • directPRD:1354「约 500m 网格取整」+ PRD:2063 服务端预聚合口径
  • directmap_screen.dart:40 _kClusterGridSize = 60 × :46 _kInitialMetersPerPixel = 12 ≈ 720m，且乘积随缩放浮动
  • directgrid_cluster.dart:102 final String key = '$gx:$gy:${p.categoryId}';——聚合键当前由像素坐标构成
  • directlisting.dart:48-49（留注释）vs listing_detail.dart:7-9（明写不重命名）——同库两种命名策略并存，证明层次差异是刻意的
  • direct说明文档:1908「5 万点聚合仅 4.73ms，占 300ms 预算的 1.6%」+ grid_cluster.dart:6-8 不 import Flutter 的自陈理由
  • directcategory_tree.dart:22 TODO(M5)——数据字典派生尚未接通
为何重要
C6 是九条冲突里唯一的量纲级冲突，也是唯一一条「联调时会表现为数据看起来对但聚不到一起」的隐蔽故障。收口成本是改几个常量与一处注释，不收口的成本是每次讨论聚合都要先对一遍单位。
风险
  • 反过来要求 PRD §6.15 的聚合阈值重新定义：现在那句话在「屏幕上几条聚成一个」和「500m 内几条聚成一个」之间是含混的，收口意味着必须选一个，而这是产品口径而非技术口径。
  • 阈值本身还带分类差异化（工作 3 / 房屋 5 / 生活 8）× 供需态 × 完整度，量纲切换后这几个数字都要复核一遍。
  • marker_builder.dart:75 已警告：若用簇中心当单点位置，同格两条会精确重叠，第二个 Pin 永远点不到。地理网格化后这个风险不降反升。
A3

先回答「新鲜度的权威在客户端还是服务端」，缓存实现是这个答案的推论——不是反过来

轴 轴 3 300ms 预算的算力归属 信心 82% 复杂度 Medium 属性 真两难，无优解

PRD §6.10 已经把缓存写得很具体：三级、三档 TTL（1h / 15min / 5min）、50 键 LRU、五要素缓存键。代码侧的实现情况是零——检索 lib/ 内无三级缓存、无 TTL、无 LRU，三处出现「缓存」字样的地方经核实均不是 §6.10 所指的第 3 层。

但这条想法的重点不是「去把它实现出来」。重点是 PRD 里有两处规定在权威归属上互相拉扯，而实现之前必须先解开：

  • PRD:1347 / :1357 / :1358 描述的是客户端持有权威的形态：本地命中就直接读，不发请求（这也是 cache_hit 埋点存在的前提）
  • PRD:1355「运营改配置即全量失效」+ PRD:2025「3 秒内清三级缓存」描述的是服务端持有权威的形态：服务端一变，客户端必须在 3 秒内知道

这两者不能同时成立，因为客户端本地缓存没有推送通道。要在 3 秒内让所有客户端丢弃本地缓存，只有两条路：主动推送（而推送受 42904 的「≤10 条 / 日」限制，配额上根本不够用），或者每次读之前先问一次服务端（那就等于放弃了「直接读本地不发请求」，cache_hit 的语义随之改变，300ms 的第一段预算也从「0」变成「一次往返」）。

把权威问题解开之后，缓存的失效机制才有意义可谈。而一旦选了服务端权威，一个连带推论会自然出现：时间维的 TTL 就不再是正确工具。三档 TTL 本质上是「不知道什么时候变，所以定期重问」，而 PRD:1355 恰恰说明我们知道什么时候变（运营改配置那一刻）。此时更贴合的是版本号或标签化失效——但这需要服务端为每个网格维护版本号，会引入新的热点风险，且 PRD:2022 已有的 304 语义要如何与之共存也要一并想清楚。这些都是权威归属的下游问题，先答上游再谈。

顺带一提：PRD:2139 把「缓存键要素不全」专门编成了错误码 40001。一个专用错误码的存在，说明设计时已经预见到缓存键会被写错——而缓存键的五个要素里就含坐标网格，也就是说 A2 的量纲收口是这条想法的前置条件。

依据
  • directPRD:1347 / :1357 / :1358——三级缓存、TTL 三档、50 键 LRU 的原文规定
  • directPRD:1355「运营改配置即全量失效」+ PRD:2025「3 秒内清三级缓存」——服务端权威侧的规定
  • direct取证档案第十二节：lib/ 内无三级缓存 / TTL / LRU 实现，三处「缓存」字样均非 §6.10 第 3 层
  • directPRD:2139 专设 40001「缓存键要素不全」——设计时已预见此处易错
  • directPRD:42904 推送 ≤10 条 / 日 的配额限制——决定了主动推送失效在配额上不可行
  • directPRD:2022 已定义 304 语义——与版本化失效存在语义重叠，需一并处理
为何重要
缓存是 300ms 四段里的第一段，也是唯一一段可以为 0 的。这一段的归属决定其余三段的预算余量。且这条决策一旦实现落地就很难反转——本地缓存的语义会渗进埋点口径与 SLA 定义里。
风险
  • 这条想法本身不给答案，只强制排序。如果决策者希望文档给出「就用三级缓存」这种确定结论，这条会让人失望。
  • 权威放客户端 = 运营改配置后最长 1h 旧世界，而这个代价 PRD 从未定义可接受性——「Pin 的新鲜度 SLA」至今是空白。
  • 权威放服务端 = 每次切图层至少一次往返，直接与「图层切换 P95 ≤ 300ms」抢预算，且 cache_hit 这个已定的埋点字段含义要重新定义。
A4

客户端是唯一能算出真实 P95 分母的地方——这个事实应当决定整份《可观测性架构方案》的组织方式

轴 轴 4 可观测性链路 信心 80% 复杂度 Medium

《可观测性架构方案》的默认写法是「客户端埋点上报 → 服务端聚合计算 → 看板与告警」。这条想法主张那个组织方式在本项目里是错的，理由是三条互相独立的证据指向同一个结论。

第一条：计时的两端都在客户端。PRD:2129 把图层切换的计时定义得非常明确——起点是「手指离开分类 Tab」，终点是「Pin 首屏绘制完成」。这两个时刻服务端一个都看不见。服务端能看见的只有中间那一段网络往返，而 PRD:2124 已经把 net_rt_ms 单列成一个字段——说明「四段各自计时」这个念头 PRD 里本来就有，只是没被组织成一条 trace。

第二条：服务端的样本天生有偏。如果缓存命中就不发请求（A3 的左侧方案），那么服务端 trace 里出现的永远只是那些没命中缓存的慢样本。用这批样本算出来的 P95 不是 P95，是「未命中集合的 P95」——数值会系统性偏高，而且偏多少无法从服务端侧知道。同理，PRD:2130 规定「2G / 3G / 断网会话不计入 P95 分母」，而「当前是什么网络」这个信息也只有客户端知道。分母的两次修正都发生在客户端。

第三条：服务端判定这条路本期没有执行通路。PRD:2358 规定「P95 > 300ms 自动告警」，PRD:1403-1404 规定「连续 3 次帧渲染 > 16ms 或 P95 > 800ms 触发降级」。但 PRD:2379 明写「降级开关本期不实施」——也就是说服务端即使判定出该降级，本期也没有下发通路。

三条合起来的结论是：可观测性的重心必须在客户端，服务端是佐证方与长期存储方，而不是计算方。这个结论会连带改变两件具体的事。一是告警与降级判定必须分离——告警在服务端按群体样本聚合（含弱网剔除），降级在客户端按本机短窗自判，两者不共用判定逻辑也不共用阈值，因为它们要回答的是不同问题（「系统是不是坏了」vs「我这台机器现在是不是该退让」）。二是 layer_switch 应当做成一条本地 trace（四个 span + 一个 root，环形缓冲平时只留不传，超 300ms 或用户报错时才上报），而不是一条打平的埋点事件。

依据
  • directPRD:2129「计时起点 = 手指离开分类 Tab，终点 = Pin 首屏绘制完成」——两端均在客户端
  • directPRD:2130「2G / 3G / 断网会话不计入 P95 分母」——分母修正所需信息只有客户端持有
  • directPRD:2124 net_rt_ms 已被单列为独立字段——分段计时的念头已存在于契约中
  • directPRD:2379「降级开关本期不实施」——服务端判定本期无下发通路
  • directPRD:2358「P95 > 300ms 自动告警」 vs PRD:1403-1404 客户端降级判据——两套判据用途不同却常被混谈
  • direct取证档案第九节：lib/ 内无 layer_switch 埋点、切换入口无 Stopwatch
  • directframe_metrics.dart capacity 2000（60fps 下约 33 秒）——现有客户端窗口长度
  • externalW3C Trace Context 的 traceparent 头规范；Last9 的 Approach A（拦截器注入而非全量 SDK）
为何重要
它决定《可观测性架构方案》的章节骨架。按「上报后计算」组织，方案会长成一套 APM 接入指南；按「客户端为度量主权方」组织，方案的第一章会变成分位口径与窗口设计——而后者才是 0.216 能不能被真实测出来的关键。
风险
  • SLA 数字由不可信端产出，对外承诺的可审计性下降。若将来需要向第三方证明性能，客户端自报的数字说服力不足。
  • frame_metrics 现有的 33 秒窗口远不足以支撑分位统计——33 秒样本的 P95 统计意义薄弱，且会把弱网误判成性能问题。窗口设计要重做，这是这条想法的必要前置工作。
  • PRD:1998 明写 trace 起点由服务端生成，与 W3C Trace Context 的方向相反；采纳本条意味着要反向修改已定契约。
  • 在 grid_cluster 里插桩会污染它「不 import Flutter」的纯度（见 A2），需要设计一个不依赖 UI 的计时注入方式。
A5

PRD §12 / §13 升为机器可读的单一真源，两侧代码从它派生——顺带消解「删不删 Repository」这场争论

轴 轴 1 服务形态与分层接缝 信心 78% 复杂度 High

PRD §12 已经把接口写到了逐字段级，§13 已经把数据字典写到了列级。但它们是散文——没有任何一处代码拿它们跟自己比过。最能说明问题的证据在 test/category_tree_test.dart:5：那份测试安静地躺过了一整个里程碑，因为没有任何一处代码拿它跟真源比过。

把 §12 / §13 转成机器可读格式（OpenAPI 或等价物）之后，能派生的东西超出直觉：Dart 侧的数据模型、后端的接口骨架、Mock server、契约测试，甚至埋点字段的校验——因为 §14 的必埋事件字段和 §12 的接口字段本质上是同一批名字。

但真正让这条想法值得进存活集的，不是 codegen 本身，而是它消解了轴 1 上一场看起来无解的争论。发散阶段产生了两个直接对立的候选：

  • 一边主张删掉 Repository 抽象层：listing_repository.dart:3 和 contact_repository.dart:8 给出的存在理由只有「可替换」一条，而 Riverpod 已经是注入接缝了，所以这一层只做同义转发，还是命名漂移的产地（C2 就是在这一层产生的）
  • 另一边主张双实现长期保留：那 7 处 TODO(接后端) 不是「填个 URL」而是「删除本地逻辑」。auth_repository.dart:211 写的是「删除本地生成」，publish_screen.dart:129 写的是「一律视为未持有」——这些业务判定要等到上线那天才第一次被真正执行，所以 fake 实现必须留着当契约测试基座

两边都对。而如果 Mock 是从契约生成的而不是手写的，两边的矛盾就消失了：手写搬运层的批评不再成立（因为那层是生成物，不会漂移），而「无 Key / 无网环境的开发通路」与「假实现里藏着的业务判定需要提前被测试」这两个价值仍然保留。这三个决策应当作为一个包裹评估，不是三个独立选项。

还有一处约束值得在这里点出，因为它直接影响生成物的形状。PRD §14.1 写了单次取数 ≤ 10KB，同时写了渲染上限 500 Pin。10KB ÷ 500 ≈ 20 字节 / Pin，而 §12 的 /map/pins 出参每个 Pin 有 6 个字段。20 字节装 6 个字段，JSON 在数学上就不可能——连字段名都放不下。这不是优化问题，这是选型问题：要么改协议（定点量化坐标 + 位打包 + 定长二进制或列式），要么改数字。一次除法就能推翻默认选型，而这个除法在 PRD 定稿至今没人做过。

依据
  • directtest/category_tree_test.dart:5-6——测试「安静躺了一个里程碑，因为没有任何一处代码拿它跟真源比过」
  • directPRD §12 /map/pins 入参已逐字包含五要素、出参含 6 字段与 clusters[]；/posts/search 出参含 items[] 与 has_more——契约精度已足以支撑生成
  • directPRD §14.1 单次取数 ≤ 10KB + 渲染上限 500 Pin → 20 字节 / Pin；PRD:1983「超出须减字段或提高聚合粒度」
  • directlisting_repository.dart:3-5 + contact_repository.dart:8——Repository 自陈存在理由只有「可替换」一条
  • directauth_repository.dart:211「删除本地生成」+ publish_screen.dart:129「一律视为未持有」——业务判定藏在 fake 实现里，上线那天才首次执行

  • direct全库 freezed / json_serializable 零命中——尚无既有生成体系需要迁移，是一次性窗口
为何重要
九条 PRD↔代码冲突全部是「人工搬运」的产物。冲突在 CI 暴露还是在联调暴露，成本差一个数量级。而后端零遗产 + 契约已冻结，是这条想法唯一的可行窗口——有了第一版手写实现之后，迁移成本会陡增。
风险
  • 会出现第二个真源，与「PRD 是唯一权威」这条项目宪法直接冲突。必须先决定：机器可读文件是 PRD 的投影（PRD 改了它跟着改），还是它取代 PRD 成为接口章的正文。这个决定不做，两份东西必然分叉。
  • 生成物膨胀是真实代价——检索到的一份 Dart OTel 实现被批评生成了 75 个以上 .pb.dart 文件。需要预先决定生成物是否入库。
  • 把三个决策捆成一个包会放大失败的连带面：若 codegen 路线走不通，「删 Repository」与「Mock 先行」会一起落空。
  • 二进制协议的代价是调试性——curl 看不懂响应。这一项与 A4 的客户端插桩需求存在张力。
  • 先写契约测试与 Mock 意味着「为还不存在的东西写测试」，短期产出观感差，首次赶工时必然是第一个被砍的。
A6

0.216 = 0.6³ 反解为三份独立的 error budget：每一轴都必须有被设计过、被埋点过、被 UI 承认的失败路径

轴 轴 4 可观测性链路 信心 76% 复杂度 Low

PRD:32 把北极星写成 0.6 × 0.6 × 0.6 = 0.216（三轴等权硬线）。这个式子通常被当成一个目标值读。反过来读一次，它说的是另一件事：每一轴都被允许失败 40%。

40% 不是一个可以靠「尽量别出错」应付的数字。它意味着失败是常态路径而不是异常路径，因此每一轴都必须有三样东西：被设计过的失败路径（用户看到什么）、被埋点过的失败原因（我们知道为什么）、被 UI 承认的失败状态（不是白屏也不是 toast 一闪）。

而现在的埋点口径与这个要求是错位的。PRD:2124-2127 规定的必埋事件记录的是发生量——duration_ms、cache_hit、rank。失败原因的枚举位是缺失的。换句话说，今天的埋点能告诉我们「成功了多少次」，但不能告诉我们「那 40% 是怎么没的」。而对一个允许 40% 失败的系统，后者才是第一需求。

还有一处需要在文档里明写，因为它会让按独立性做的规划系统性偏乐观：三轴不独立。乘法形式借来的是可用性串联模型，而那个模型假设各环节故障独立。本项目里不成立——图层加载失败会同时打掉「资源详情点击」（轴①的分子）和发布入口（轴③），同一个根因被惩罚三次。所以按独立性算出来的容量与冗余规划一定偏乐观。

反过来这也是一条正面情报：修好图层能同时抬三轴。三轴不独立意味着投入不是均摊的，而是有杠杆点的——这直接决定优先级排序，而不只是一个统计学注脚。

依据
  • directPRD:32 0.6 × 0.6 × 0.6 = 0.216（三轴等权硬线）——式子原文，逐字确证
  • directPRD:2360「三轴各自可独立采集并计算乘积」——但未给出每轴各自的目标值
  • directPRD:2124-2127 必埋事件字段为 duration_ms / cache_hit / rank——记发生量，失败原因枚举位缺失
  • externalGoogle SRE 的串联可用性与 error budget 模型——乘法形式与其假设的独立性前提
  • directframe_metrics.dart:111-112 final int rank = (percentile / 100 * sorted.length).ceil(); + :129 桶边界 [8,16,32,50,100]——已有一套可复用的分位与直方图口径
  • directtest/frame_metrics_test.dart:3-5「分位算错的表现是 P95 看起来达标，没有任何异常现象提示它错了」
为何重要
它把北极星从一个季度看板数字变成一份对埋点字段的硬要求，而且要求很具体：每一轴加一个失败原因枚举位。这条改动的实施成本在七条里最低，但它决定了 0.216 达不到时我们能不能说出原因。
风险
  • PRD 至今未定义「超 300ms 但最终成功」算不算轴②成功。这个定义不明，轴②的 error budget 就没有分母，本条无法落地。这是必须先补的空白。
  • 把三轴的失败原因都枚举出来会显著扩大埋点维度基数，需要评估上报量与存储成本。
  • 实施前提是分位口径统一。现有 frame_metrics 每次读都执行 sorted()（:107），多指标高频复用时会成为新的性能源——需要在「精确排序」与 t-digest / HDR 之间做一次取舍。
  • 承认三轴不独立之后，「三轴等权」这条硬线本身的合理性会被质疑，而它是 PRD 明写的产品口径。
A7

AI 整体移出读路径：3B 在写路径抽特征，GBDT 批式预计算并物化，在线只做「取 + 过滤 + 截断」

轴 轴 5 AI 部署与降级 信心 72% 复杂度 High 属性 轴 5 唯一存活

读接口的 P95 预算是 150ms，而且这 150ms 本身是 300ms 里的一段。PRD:2270 已经把查询计划钉死到「空间条件必须先行否则退化全表」的程度——这个计划里没有留出插入模型推理的余量。也就是说「AI 在请求内推理」这个方案从预算上就不成立，不需要等到实测。

更值得注意的是 PRD 自己已经给出了一条不需要在线推理的采集路径。PRD:2275 规定召回率的采集口径是「demand_push_sent 与 resource_detail_click 按 post_id 关联 5min 窗口」——这个口径完全不要求推理发生在请求内。而 PRD:2304 给推送留的时限是 1 分钟，比 150ms 宽 400 倍。两条合起来说明：AI 的产出在时间上有巨大的腾挪空间，是我们自己把它想成了在线组件。

所以形态应当是：3B 模型在写路径（发布时）抽特征并落库；GBDT 按 grid_id × 叶类目 × 供需态 批式预计算并把结果物化；在线请求只做三件不含推理的事——取物化结果、按当前条件过滤、截断到上限。配额扣减仍留在服务端在线面（ai_confirm_screen.dart:167 已明确「配额扣减必须在服务端」），这与 A1 的分割线一致。

这条想法必须连带承认一件事，因为它是对核心心智的让步：新鲜度受批次周期限制，新发布的内容在进入名单之前有一段可见的空窗。而「双向撮合」是产品的核心卖点，空窗直接削弱它。这个代价必须被显式接受，不能悄悄产生。

还有一个更根本的限制，它不是这条想法引入的，而是被这条想法暴露的：PRD:2236 明写禁止增加 contacted_success / deal_done 等字段。这意味着系统里没有成交回报——一个撮合引擎最重要的反馈信号在契约层面被禁掉了。后果是召回率只能用「5min 内 Top20 是否被点击」来近似，而点击不等于撮合成功。这不是可以靠架构解决的问题，只能在文档里如实写明，并说清它对模型迭代能力的限制。

依据
  • directPRD:2300 读接口 P95 ≤ 150ms，且是 300ms 四段中的一段
  • directPRD:2270「空间条件必须先行否则退化全表」——查询计划已钉死，不留在线推理余量
  • directPRD:2275「demand_push_sent 与 resource_detail_click 按 post_id 关联 5min 窗口」——召回率采集不要求推理在请求内
  • directPRD:2304 推送 1min 触达 Top20 / Top30——比 150ms 宽 400 倍
  • directPRD:2155 已定义 50301 AI 降级错误码——降级契约位已存在
  • directai_confirm_screen.dart:167「配额扣减必须在服务端」
  • directPRD:2236 禁止增加 contacted_success / deal_done 字段——无成交回报，反馈闭环在契约层被禁
为何重要
轴 5 上唯一存活的一条，也是唯一一条会改变数据流形状（而非仅改变部署位置）的想法。它同时把「AI 是在线依赖」这个隐含假设摆到桌面上——若不摆，150ms 预算会在联调时被推理时间悄悄吃掉。
风险
  • 新鲜度空窗是对核心心智的直接让步，且空窗长度等于批次周期，无法通过优化消除，只能通过缩短周期缓解（而缩短周期会推高预计算成本）。
  • 无成交回报导致反馈闭环原理上搬不过来——召回率的近似口径（点击代替成交）会让模型朝「更容易被点」而非「更容易成交」的方向优化，这个偏差随时间累积。
  • 批式物化的存储量随 grid_id × 叶类目 × 供需态 的组合数增长，需要在选型阶段估一遍量级，否则会在轴 2 的空间检索选型上产生反向约束。
  • 降级面（AI 不可用时给什么）在本条中只留了接缝未定策略。PRD:2379 写「降级开关本期不实施」，所以降级形态的产品定义仍是空白。
