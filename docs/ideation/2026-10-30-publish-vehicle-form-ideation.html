现状

发布页有 8 段表单，其中 7 段是硬编码的，「分类专属信息」这一段是唯一由模板驱动的（publish_screen.dart:695-721）。拼车模板的四个字段定义在 publish_template.dart:209-246：route（起点 → 终点，文本，必填）、depart_time（出发时间，文本，必填）、seats（空座数，数字，必填）、car_model（车型，文本，选填）。服务端可以覆盖这份定义，同名 seed 在 V4__seed_template.sql:23-24。

控件能力

  • 模板字段的渲染只有两种：select 走 ChoiceChip，其余一律 TextField（publish_screen.dart:1176-1266）
  • 数字只加了 digitsOnly 键盘，全仓没有任何时间、日期、步进器控件
  • 本地枚举只有 4 型；契约已有 date、multi_select，到客户端被静默降级成文本框与单选（publish_template_provider.dart:71-77）

数据形状

  • 所有附加字段都是 String，塞进同一张 Map<String,String>（publish_form_state.dart:174-175）
  • 数据库只有 post.template_values 一个 JSON 列，没有路线、时间、座位、品牌、车牌的结构化列
  • 草稿恢复只认 String，非字符串值被静默丢弃（draft_store.dart:115-121）

地点能力

  • 地图选点已经真接上了，但只有单点：MapPickResult{lat,lng,doorNumber,address,radius}
  • POI 搜索只在发现侧（POST /search/resolve），发布侧没有复用
  • 「起点 → 终点」靠 placeholder「如：回龙观 → 中关村」教用户写

减负现状

  • 草稿是单份本地快照，3 秒防抖，提交成功即清空
  • 模板记忆（user_id + leaf_category_id）在 PRD 里有定义，但代码里是演示值
  • 屏幕上的「示例：回龙观 → 中关村」对每个人都是同一句假话（publish_template.dart:80-85）
三条硬约束，任何方向都绕不过去。 字段清单必须由服务端模板下发（PRD :955 / :2314），前端不得自造字段或校验口径；必填集合与完整度三档（🟢🟡🔴，权重 2/1/0.5）直接耦合（PRD :2084-2096）；设计文档没覆盖的口径先问，不在业务代码里自创。用户点名的五个方向里，有四个需要先动模板 schema 才可能合法落地。

起终点：两个地点对象 + 双针选点 + 就地交换

1C · 地点输入路径
描述
「起点 → 终点」从一个自由文本框升成两个地点对象：每个对象带 name、lat、lng、city_code。选点页内是 A/B 两个槽位，起点默认用当前定位，终点在地图上落针；两点都确认后回填两组坐标，卡片上直接显示「约 18km · 预计 8:38 到」。两侧各留一个可点区域，中间一个「⇄ 交换」就地翻转并重算距离，不需要重新进地图。
依据
directmap_selector_screen.dart:62-85：MapPickResult{lat,lng,doorNumber,address,radius} 只有一组坐标，:121-122 是 late LatLng _selected;——一次选点只能拿回一个点。
directpublish_form_state.dart:409-410：if (hasLocation) 'lng': lng, if (hasLocation) 'lat': lat,——全帖只有一对坐标，终点没有承载位。
external滴滴把「目的地」与「推荐下车点」分成两个图形（橙大头针 / 小橙点），默认给一个推荐点让用户确认，而不是让人从零拖准星。
为什么重要
车主在停车场选完起点、再进一次地图选终点，中间没有任何东西告诉他这两个点凑起来是不是一条顺路的线——而这正是他决定发不发这条帖的全部依据。距离与到点时间把「填表」换成「确认一条我认识的路线」，也顺手回答了搭车人最先问的那句「几点能到」。填反方向是这类帖最常见的错误，而现在的模型里每次选点都是一次全屏 push–pop，纠错只能整段重来。
代价
两个点串行选、各进出一次全屏地图页，用户中途接个电话回来上下文就丢了；逆地理 Key 缺失时 _refreshAddress 返回空串（reverse_geocode.dart:37-41），终点只剩一个准星。数据侧意味着要在 JSON 或新列里装两个点，与「发现侧与发布侧选点必须收敛成同一份交互」那条既有决议必须一起解决，否则会出现两个准星页。

出发时间：默认下一整点 + 三枚快捷 chip + 滚轮

2A · 控件选型
描述
字段进页面就带一个默认值（当天下一个整半点，跨夜则落到次日早间档），呈现为一行可点的值加三枚快捷 chip：「现在出发 / 1 小时后 / 明早 8:00」。点值才展开时间滚轮。上送统一成 ISO 时刻，而不是「工作日 8:00」这类自由文本。
依据
directpublish_template.dart:223-230：depart_time 是 type: text，placeholder「如：工作日 8:00」；publish_template_provider.dart:71-77 契约的 date 被降级成 text。
directPRD :878：「模板决定字段清单、字段标签、默认值、必填校验」——默认时间属于模板的 default，不该由发布页硬编码。
external哈啰开放平台 planDepartureTime 不传即「立即出发」、waitMinutes 默认 10 最大 180，双模与弹性窗口在接口层已经固化；医院挂号的「号源时段」同构——时间是离散刻度，客户端只做选择不做输入。
为什么重要
出发时间是拼车的成交前提，也是发现侧唯一能做的硬过滤。文本态下它既不能排序、也不能提醒、也不能筛选，用户还得自己记「工作日」还是「周一」。默认值加三枚 chip 让多数人零键盘完成，同时给「一小时内出发」这类排序留了可比较的字段。
代价
预填的整点算不算用户已确认——算，则有人没看时间就发了；不算，则「出发时间」的必填判定要另立一条口径，牵动 blocker 文案与完整度。固定网格会让「时间灵活」的用户无处安放，必须留出口。设备时间不准时预填值是错的，而用户不展开滚轮根本发现不了。

人数：一行 1/2/3/4+ 大按钮，不弹键盘

3A · 控件选型
描述
标签从「空座数」改成「还能带几人」，控件从数字输入框换成一行四个大按钮（1 / 2 / 3 / 4+），点一下完成，全程不弹数字键盘。默认值与上限由模板的 default / options 下发，hint 补一句「儿童也计入人数」。
依据
directpublish_template.dart:231-237：label: '空座数'、type: number、placeholder: '1-6'；publish_screen.dart:1241-1256 的 number 只有 TextInputType.number + digitsOnly。
external哈啰口径「儿童/婴幼儿一律计入乘车人数」——人数不是自然数，需要一句说明；Poparide 新司机默认 3 座并提示「后排最多 2 人可提升 50% 预订」，用默认值加一句引导替代解释。
为什么重要
数字键盘是整个「分类专属信息」里唯一必须切换输入法的地方：点一下、弹键盘、输数字、收键盘，四步才得到一个 1–6 的整数，而键盘一弹还盖住下一段「车型」。一次点按把它压成一步。默认值同时把「空」变成「已填」，直接消掉一次「模板必填项未填完」的拦截。
代价
不能在前端把 number 擅自渲染成按钮——那是改写字段语义，必须先由服务端下发 options 或新类型。默认值会让「必填项 100%」在用户零输入时也成立，等于悄悄放松 🟢 的第一条件，这一点要在完整度口径里说清。四枚按钮在 44×44 触控口径下容易误触，需要真机验证。

车型：品牌可搜索 + 颜色色块

4A · 控件选型
描述
打开先看到 8–10 个颜色格子加一个品牌搜索框：点颜色即完成颜色（一次点按），品牌输两个字命中，车系可留空。选项全部由模板下发，客户端只负责最近使用与常见度排序。
依据
directpublish_template.dart:238-244：car_model 是 type: text、连 required 都没有，placeholder「如：轩逸（白色）」——一个框同时要求品牌、车系、颜色，还要用户自己决定用不用全角括号。
external汽车之家口径 149 品牌、车系约 1700，必须带搜索、最近使用、按常见度排序；瓜子与懂车帝用 VIN 扫码带出全车参数，说明「强标识符替代手填字段」是行业共识。
为什么重要
中文输入法下打「轩逸」要选字，「白色」和「白」是两种写法，全角括号大部分人不会打——最终落库的是「轩逸」「白色轩逸」「轩逸 白」三种互不相干的字符串，对搭车人和任何按车型筛选都是废数据。它同时是模板里唯一「不填也能发」的字段，把高价值可选项做成了高成本空白项。颜色先于品牌还有一个现实理由：车主对「我车是白的」比对「我这车属于哪个品牌层级」确定得多。
代价
级联选择天然比文本框多一跳，单手操作路径反而变长。品牌枚举一旦下发就不能前端硬编码，谁维护、多久更新要在模板编辑器里说清；纯靠 options 装不下 1700 个车系，「字典」这个概念 PRD :2314 的 fields[] 里并不存在，落地等于先改契约。旧客户端遇到新类型会静默降级成一个裸输入框，用户不知道这是降级而不是设计。
置信度 / 复杂度
68% · 中

车牌：专用键盘是主路径，拍照是加速器

5E · 信任·合规·转化
描述
车牌不设计成「拍照 → 成功」或「失败 → 空框」，而是：拍照得到整牌候选，结果逐位可点改、低置信位高亮；认不出时保留已识别的部分，直接落省简称加字母数字的专用键盘（排除 I / O，覆盖 7 位燃油与 8 位新能源）。字段保持选填，不因新增车牌而增加必填项数量；他人视角展示打码（如「京A·***45」），完整值只回给本人。
依据
directPRD :855：「OCR 识别失败 | 证名留空并提示手动填写，不阻断提交」；cert_repository.dart:88-107 的抽取失败仍返回 200 / code=0、结果为 null。
directmedia_section.dart:200-226：相机打不开只有一句固定文案加「从相册选」，现有媒体链路没有「拍完立刻识别并回填」的位置。
external整牌一次全对率按 85–93% 预估（腾讯云官方 98%+、ML Kit 端侧字符级 96.5%、HyperLPR 卡口 95–97%）；GA36-2018 规定新能源 8 位、序号不含 I/O、省简称 30 个。
为什么重要
车牌是唯一「用户必须走到车尾才能填」的字段，也是唯一字符集受限、却要给中文输入法的字段。识别成功的那 85% 不决定成败，失败的 15% 才决定用户觉得「还行」还是「算了」。允许失败，产品才敢把拍照放在入口；专用键盘让失败成本从「蹲在车后打八个字」降到一个字符。
代价
专用键盘是全仓没有的新控件（现在只有 TextField 与 ChoiceChip），要处理 44×44 触控、30 个省简称的分组与最近使用，复杂度接近一个小型选择器。复用资质域的 POST /cert/ocr 会把「失败也 200」的语义带进发布页，前端必须自己判 null。车牌照片若进 media_ids 会占掉「最多 9 张」的一张。车牌属个人信息，能否公开、公开成什么样，PRD 目前没有条款，属于「口径未覆盖先问」。

attributes 值类型升级 + 模板版本快照

6B · 模板与契约
描述
值从「一律 String」升级成按字段类型序列化：标量仍平铺（seats: "3"），成组值收进对象（route: {from:{lat,lng,name}, to:{…}}、car: {brand, color}），时间存 ISO。前端 templateValues 放宽为 Map<String, Object?>，草稿、重发、AI 确认页三处读写同批改；帖子落库带 template_version，老帖按老规则渲染。
依据
directpublish_form_state.dart:174-175 Map<String,String> templateValues，:401-405 上送时逐字段 trim()；draft_store.dart:115-121 恢复只收 entry.value is String。
directPostValidator.java:148-159：value == null || (value instanceof String s && s.isBlank()) 即判未填——非 String 一律当作已填，一个空对象也能过，这是改结构时必须同批修的坑。
reasoned前六条方向里有四条（双点、时间、人数、品牌颜色）都卡在「值往哪放」。不先解决这个，每个新控件都会在提交那一步卡住，而且草稿恢复会把坐标和时刻悄悄清空，用户看到的是「我明明填了」。
为什么重要
这是复利最大的一处，也是唯一「现在不做、以后一定重做」的地方。值类型一旦升级，按出发时间排序、按人数筛选、按起终点算距离、按字段权重算完整度、重发原样回填、AI 合并结构化猜测，全部自动成立；不升级，每一个下游能力都要在字符串上做一次脆弱切分，而且脏字符串无法索引、无法比较、无法迁移。
代价
数据模型迁移是成本最高、风险最大的变更类型：必填判定、完整度、草稿容错、重发反序列化、AI 合并五处必须同批改，否则会出现「发布页按对象写、服务端按 String 判空」的半新半旧。契约的 attributes 是 additionalProperties: true，值语义没有约束，改之前要先补契约描述与 PRD。DB 仍是单 JSON 列，结构化值仍无法直接走索引。

模板记忆接真：第二次发布只改时间

7D · 复用与减负
描述
把 PRD 里已定义、代码里还是演示值的记忆机制接真：按 user_id + category_leaf_id 存最近一次发布值（本地加云端），字段上方一键带入；超过 30 天保留但加提示，超过 180 天清空。时间型字段特殊处理——带入的是上次的时刻，若已过去则顺延到下一个同类时点，而不是把「昨天 8:00」原样填进去。最近几条同路线沉淀成线路卡，点一下两端一起回填。
依据
directpublish_screen.dart:1257-1261：_HintText('示例：${spec.memoryHint}')，注释写明「只显示模板给的示例值，不自称记忆带入：真记忆需云端」；publish_template.dart:80-85「本轮是演示值而非真记忆」。
directPRD :956「记忆机制：按 user_id + category_leaf_id 维度存最近一次发布值，写入本地缓存 + 云端」；:969 30 天提示 / 180 天清空。
external嘀嗒车主「常用路线」最多 8 条，可设自动抢单、途经点与频次——路线是复用单位，不是一次性的字符串。
为什么重要
拼车是典型高频同构发布：同一条路、同一个时间、同一辆车。第二次发布的手指次数从几十次降到两三次，这是唯一能让第 N 次成本低于第 1 次的机制，而且版面位已经留好了，接真不需要重排版式。现在的屏幕上写着「示例：回龙观 → 中关村」，对每个人都是同一句假话，还会误导用户以为系统记住了。
代价
记忆是「N 份」，草稿是「单份」，恢复优先级必须先定，否则进页面同时弹草稿恢复与记忆带入会互相覆盖。记忆会制造「看起来已经填好了」的陷阱：用户改了时间却忘了改人数，发出一条错误信息，比空白表单更危险。云端存起终点加时间属敏感信息，留存期限与删除路径要同步写进安全方案。30 / 180 天阈值必须走常量，不能写字面量。

#候选否决原因
1type→控件注册表实现手段而非产品改进；其收益已被候选 6 与控件选型三条覆盖。
2结构化短码输入原语（车牌/VIN/门牌通用）被候选 5 的车牌专用键盘吸收；过早抽象，第二个使用方还不存在。

5模板下发 presets[] 常用组合卡契约无此概念（openapi :4684-4716），且与候选 7 的记忆能力重复。
6品牌/颜色改为模板字典PRD :2314 的 fields[] 没有字典概念；先做候选 4 的选项集更务实。
7粘贴一段话 / 说一句，AI 填多字段潜力高但依赖解析质量，PRD :1000 要求不猜；留作候选 7 之后的增量。
8「起点→终点」升为两个地点对象已是候选 1 的核心机制，重复。
9起点默认定位、终点点开是候选列表被候选 1（默认定位）与候选 7（线路卡）分别吸收。
10线路是一等对象超范围：等于重构发布数据模型，其价值由候选 1 + 7 部分实现。
11「我的车」用户级车辆档案跨分类用户级存储无 PRD 依据；先做候选 7 的 user×leaf。
12整单「再来一单」与候选 7 的记忆机制重复，且「沿用旧值在新模板下怎么渲染」未定。
13草稿恢复送回断点（还差 N 项 + 跳转）价值真实但低于候选 7，且需先把两套「还差几项」口径桥接起来。
14拍行驶证一次回填品牌+颜色+车牌依据被推翻：CertOcrResult 只有 certName，PRD :781 把行驶证 OCR 限定在车辆认证用途。
15字段级 sensitivity 元数据超出 PRD 的模板口径；合规策略应由服务端定，不能进运营可编辑的模板。
16渐进披露三段折叠与「blocker 一次只报一条」正面冲突；折叠里的必填项会造成二次拦截。
17分类专属信息不阻断发布（先发后补）依据被推翻：PRD :1000「必填项未补齐时确认发布保持禁用」，allowIncomplete 仅限抢发模式。
18负向复利清单不是方案，是取舍标尺；已作为候选 4 / 6 / 7 的代价论证使用。
19「一条线路」成为发布一等对象与第 10 条同源，超范围。
20模板即表单契约一次补齐六项过度打包：六项依赖不同前置（有的要改 PRD，有的要改 DB），捆一起无法启动。
21降级必须可见（旧客户端提示「需更新 App」）作为候选 4 与 6 的实施要求保留，不单独成项。
22发布漏斗埋点与字段级耗时可观测性基础设施，不是录入改进本身；但缺它，「效率变好」无法验证。
