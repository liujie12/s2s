## 二、存活想法（7 主 + 2 顺手）

### S1 · 条目即分支 + 两类 tag 命名空间 —— 对"分支规范"的正面回答
**轴**：branch-topology

项目已有一套比 Git 更强的工作单元编号（说明文档的 `[47]`/`[47-b]`/`[48]` 条目），但完全没有映射到 Git 拓扑上。做法：每个条目开一次性分支，验收后 `--no-ff` 并回 main，于是 `git log --merges --oneline` 恰好是条目清单，回退粒度从"最近一次提交"变成"一整个已验收条目"。分支活着时允许脏、允许堆积——堆积发生在可丢弃的分支上而不是 main 上。同时定两类 tag：`rel/<env>/<APP_VERSION>`（发版锚点）与 `checkpoint/<里程碑>`（附注 tag，message 写当时的验证数）。

**依据**（direct）：`agent/skills/ce-commit/SKILL.md:32` 明文禁止"把工作只留在默认分支"，而当前 HEAD 恒为 `main` —— **每调用一次 ce-commit，技能契约就与仓库现实冲突一次**。[说明文档.md:1207](file:///d:/developer/code/aicoding/s2s/说明文档.md#L1207) 记录了代价："14 个文件横跨条目 [47]/[47-b]/[48]/[49] 四轮全部未提交……最近可回退点是四轮之前"。而回滚锚点现状是：方案 A 需人工去阿里云控制台点快照，方案 B 依赖"镜像仍在本机"（[部署架构设计文档.md:502-503](file:///d:/developer/code/aicoding/s2s/deploy/docs/部署架构设计文档.md#L502-L503)）—— 两个锚点都会随宿主机重建消失，而 git tag 免费、可推远端、不随宿主机状态消失。

**为何重要**：这是用户所要的"分支规范"里唯一有本项目特异性的答案——不是照抄 trunk-based，而是把已有的条目编号变成 Git 一等公民。
**会议测试**：我们已经在文档里给每轮工作编了号，为什么 Git 里看不见这些号？

### S2 · 不可逆标识冻结闸门 —— 出包前扫"必须已定型的东西"
**轴**：gate-criteria

现有出包门禁规格扫的全是**不该存在的东西**（`888888`、`debugCode` 计数为 0），但另有三个值属于**必须已经定型**：包名、签名指纹、版本号格式。三者目前全处于开发期临时值，且没有任何载体在包离开本机前拦一次。加一条闸门：APK 分发/送备案前断言 `applicationId` 无 `.dev` 后缀、签名指纹 ≠ debug 指纹、版本号匹配全项目统一口径，任一不符即删产物。

**依据**（direct）：三处临时值逐字在库——`android/app/build.gradle.kts:26` `applicationId = "com.s2s.zhaoyazhao.dev"`、`:39` `signingConfig = signingConfigs.getByName("debug")`、`pubspec.yaml:19` `version: 1.0.0+1`。三处不可逆性同样逐字在库——`docs/上架前置工作指导手册.md:349`「包名与签名证书须是正式发布用的那一套，之后不能换」、`:368`「备案用的签名证书与最终上架包不是同一套 → **必须重新备案**」、`:129`「版本号格式全项目统一为 `V1.0`……禁止混用 `1.0.0` 等形状」——`pubspec.yaml:19` 的 `1.0.0+1` 正是这条禁令点名的形状。

**为何重要**：这是全清单里唯一**出错代价不可逆**的一条。其余门禁失效意味着返工，这条失效意味着备案重做。
**会议测试**：如果今天为了备案出一个签名包，包名会是 `.dev` 吗？

### S3 · SKIP 补成真计数器 + 抽出 `gate-lib.sh` 外壳
**轴**：gate-criteria

项目自己的 learning 写死了「SKIP 必须是与 PASS/FAIL 并列的第三态，门禁汇总里 SKIP 计数不为零本身就是需要被看见的信号」（`verification-code-fails-silently-as-pass.md:76`），`CONCEPTS.md:42` 也固化了同一句。而代码只兑现了前半句（不复用 PASS 分支），没兑现后半句（计数被看见）。补 `skip()` + `SKIP_COUNT`，汇总行改三列，退出码引入第三态（`SKIP>0 → exit 2`，语义为"未判定"）。同时把三态记账/汇总/退出码/留证写盘抽成 `deploy/scripts/gate-lib.sh` —— 即将要写的出包门禁 11 步序列里，第 1/2/10/11 步全是外壳职责而非判据职责。

**依据**（direct）：见第一节实测行号。方法论侧支撑：`AI工程化方法论.md §7.5:2024`「判据定义与执行载体要解耦……把判据和某个具体工具的配置文件写在一起，会导致换工具时判据一起丢失」。

**为何重要**：SKIP 计数改动量约 10 行，是全清单性价比最高的一项；外壳抽取则让此后每道新门禁只写判据函数，且留证格式天然唯一。
**会议测试**：我们自己写的《SKIP 必须是第三态》那篇，我们自己的门禁脚本没照做。

### S4 · 门禁结论写进 git 对象，`deploy.sh` 开跑前先查
**轴**：gate-criteria / enforcement

"门禁通过"现在是一次脚本运行的瞬时事实，通过后代码可以继续变。方案已意识到这个缺陷，于是要求日志里记 commit hash 和 APK 的 SHA-256 —— 把这个原则前推一层：用 `git notes`（或 `refs/gates/<sha>`）把"该 commit 已过某道门禁"写成 git 对象，`deploy.sh` 拉取后先查 HEAD 是否持有该记录，无记录直接拒绝发版。判据不变，只是把留证从"一份可挪用的日志文件"换成"绑在 commit 上、随 push 同步的引用"。

**依据**（direct）：`DevSecOps接入方案.md:153`「为什么日志要包含 APK 的 SHA-256：否则一份 PASS 的日志可以被拿去为另一个未经检查的包背书」；`部署架构设计文档.md:543`「发版前执行该脚本即可」—— 但 `deploy.sh` 不校验，"执行过"只存在于终端里。`说明文档.md:4123` 已判定这类形态零效力：「一条纪律若没有判据、卡点、失败后果三件套，实际效力为零 —— 因为『评估过了』永远可以被声称」。
（external：Gerrit 用 `refs/notes/review` 存审核元数据；`git notes` 是 Git 原生机制，零新增依赖。）

**为何重要**：它把"发版前记得跑 gate-check"从一句纪律变成 `deploy.sh` 里一次 `git notes show` 的 exit code。
**会议测试**：gate-check 通过了哪个 commit，现在只有我的终端知道，deploy.sh 不知道也不问。

### S5 · lint 从"不加规则"改成"锁住数字/锁住文件面"
**轴**：enforcement

`DevSecOps §7.2:305` 决定"本期不加自定义规则"，理由是上百条历史违规 38 天清不完、规则会被 `// ignore:` 淹没 —— 这个理由完全成立，但它只否掉了"加规则"，没否掉另外两条路：

- **棘轮**：把 `flutter analyze` 当前违规计数快照成入库的基线数字，判据是"不得高于基线"，基线只许下调。`analysis_options.yaml` 一个字不改，历史违规一条不清，从今天起获得"新代码不许新增违规"的硬拦截。
- **切文件面**：规则开到严格档，同时用 analyzer 原生 `exclude:` 做一次历史违规文件快照。历史文件永久豁免（零噪音），所有新文件自动受严格约束；清单只允许删行、不允许加行。

**依据**（direct）：`analysis_options.yaml` 全 28 行实测无 `exclude`、无 `analyzer.errors`（`:23-25` 的 `rules:` 下两行全是注释）；`DevSecOps接入方案.md:35`「静态检查存在但不强制」、`:304` 唯一强制点是出包时 `flutter analyze` 0 error（**warning 从今天到出包之日可无上限增长**）。
（external：Android Lint `lint-baseline.xml`、ESLint `--max-warnings <n>`、TS 渐进严格化迁移，均为成熟先例。）

**为何重要**：绕开了"上百条历史违规"这个唯一阻塞理由，且完全用现有工具实现。服务端代码尚未开工，越早切面收益越大。
**会议测试**：不清一条历史违规、不改一行配置，今天就能拦住新违规——为什么要等 Batch2？

### S6 · CI 不是自动化，是外部证人 —— "⚪ 可不做"值得翻案
**轴**：enforcement

`DevSecOps §9:357` 把 GitHub Actions 判为「⚪ 可不做」，理由写的是"无（本地已可判定）"。但同一份文档 `:99` 承认「单人项目里判定权与被判定对象是同一个人，所以留证是唯一的约束」。**可判定性与不可串通性是两件事**：本地留证由被判定者生成、存在被判定者的磁盘上、可被事后编辑。最小 CI 的价值不是新增任何检查，而是让同一份判据在一台我无法编辑其输出的机器上重跑一次。工作量是把已有 `gate-check.sh` 装进一个 20 行 workflow —— 方案自己 `:93` 已备好这次移植的接口（判据与执行载体解耦）。

**佐证**：45 个入库 `.sh` 全部 `100644` 无执行位，这个缺陷在 Windows 本机永远不可见，只在 Linux ECS 上暴露 —— 正是"本地已可判定"这句话的反例。
（external：SLSA Level 2 的核心要求正是"provenance 必须由托管构建服务签发，而非开发者本地生成"，理由完全同构。private 仓 Actions 每月 2000 分钟免费，不占 2 核 2G。）

**为何重要**：这一条决定要不要翻案，直接影响 S3/S4/S5 的落点是本地脚本还是 CI。
**会议测试**：本地能判定，但本地的 PASS 是我自己签给自己的——CI 唯一不可替代的是它签的名我改不了。

### S7 · 未跟踪项白名单（新增 G12）—— 把"记得改 .gitignore"换成机器点名
**轴**：repo-hygiene

`.gitignore` 已忽略 `.pylibs/`、`.pptx_lib/`，却漏掉同族的 `.pydeps/`（1863 文件 / 183MB）—— 这不是判断失误，是"新目录出现时没人想起来"。黑名单要求穷举所有该忽略的东西，而这是开放集合。改为正向判据：`git status --porcelain` 的 `??` 行必须全部命中一份显式白名单，否则 FAIL 并要求当场裁决"入库 / 忽略 / 删除"，FAIL 文案直接给出待粘贴的 `.gitignore` 行。

**依据**（direct）：项目自己的原则已写死 —— `verification-code-fails-silently-as-pass.md:101`「黑名单的问题是它要求穷举所有错误形态，而错误形态是开放集合。白名单只需定义唯一正确形态」。现有 G3b 正是黑名单（只认 `deploy/env/.env.*` 一种通配，[gate-check.sh:222-231](file:///d:/developer/code/aicoding/s2s/deploy/scripts/gate-check.sh#L222-L231)），而密钥可以出现在任何新目录里；`系统安全设计方案.md:694`「`.env` 曾被提交到 git（哪怕已 `git rm`）→ 两类密钥全换，**不可延后**」。

**为何重要**：一条判据同时覆盖 183MB 误入库、未来任意新增密钥路径、`git add .` 手滑三件事。
**会议测试**：`.pylibs` 我们记得忽略，`.pydeps` 我们忘了——下一个我们也会忘。

### 顺手做（成本极低，不占决策位）

**S8 · `agent/` 与 `.agents/` 双份技能包收口**（repo-hygiene）
实测 397 条同名路径中 **34 条 blob 已不一致**，`.agents/` 独有 9 条（含 `.openspec-target`，暗示它是某工具的写入目标 → 漂移会继续扩大）。这不是冗余，是**已经发生且单向扩大的规范分叉**：`说明文档.md:1716` 已警告「就成了与 PRD 相矛盾的第二个口径」。定一侧为真源，另一侧删除或降级为生成物；若两侧都要留，加一条闸门：同名路径 blob 必须全等。803 个跟踪文件的搜索噪音是每次 grep 都要付的税。
**会议测试**：刚才那条技能规则，是 `agent/` 里的那份还是 `.agents/` 里的那份在生效？

**S9 · `release-gate.log` 搬出 `build/`**（repo-hygiene）

## 三、被否决的候选（附理由）

| 候选 | 否决理由 |
|---|---|
| gate-selftest 常驻负向实测套件 | 方向正确且证据充分（`CONCEPTS.md:42`「正向跑通不构成证据」），但它是 S3 外壳抽取完成后的自然产物，现在单独立项会与 S3 抢同一段代码。**并入 S3 的后续，不占独立决策位** |
| 提交 trailer 嵌 `Verified: n/m` 验证数 | 依据硬（`说明文档.md:3771` 凭印象说 36 次被实测改成 31 次），但收益是复盘便利，不是拦截能力；且需要先有稳定的验证数来源。**推迟到 S1 分支规范落地后** |
| 提交信息 `Fixes: <hash>` 反向引用 | 46% 返工率是最硬的数字，但反向引用只产生可查询性，不产生约束力；单人项目里"忘了写 Fixes"没有任何拦截点。**降级为 S1 分支规范里的一条建议项** |
| 评审冷却期（时间隔离代替空间隔离） | 想法本身很强（Linux stable 的 48 小时静置同构），但与"绝不允许项目延期 + 38 天工期"直接冲突——强制静置 N 小时在赶工期时必然被豁免，豁免一次即失效 |
| 跳过评审需命中白名单 | 保留价值，但当前评审本身尚无稳定载体（`说明文档.md:775` 那次跳过是唯一记录）。**先要有评审流程，才谈得上豁免白名单** |
| 评审裁定台账（已驳回 finding 不许重提） | 19% 误判率是实测数字，但台账的维护成本对 1 人项目偏高，且收益随评审轮数才显现。38 天内评审轮数不足以摊平 |
| 环境即工作树（`git worktree` 绑三环境） | 设计优雅，直击 `.current-env` 记账文件这个"关于状态的第二份陈述"，但 2 核 2G 上三份工作树 + Maven 构建产物的磁盘与内存代价未经核算，且改动面涉及 deploy.sh/env-up.sh/backup-mysql.sh 三处拦截逻辑 |
| 零构建宿主机（`docker save`/`load` 搬运同一产物） | 论证成立（staging 通过的与 prod 跑的目前是两个不同二进制），但它是部署架构变更，超出"分支规范/门禁/仓库规范"这次要建的范围。**建议单独立项** |
| 陌生人零上下文发版演练 | 有价值（`deploy.sh:199` 的 `S2S_ENV` 默契、`说明文档.md:1883` 的 flutter 升级禁令都只活在注释里），但它是文档质量测试，不是规范条目 |
| 门禁三级裁剪档（1天/1周/完整） | 前瞻性好，但在门禁实物本身尚未落地时先定裁剪档，等于先设计豁免路径。**门禁落地后再做** |
| APP_VERSION 加 commit hash | 已被 S4（git notes 绑定）覆盖——S4 解决的是同一问题的更强形式 |
| 路径类别声明表（产品码/文档/工具链/一次性器材） | 与 S7 白名单是同一动作的两面，白名单落地时顺带产生分类，不需独立立项 |
| 可判定天花板预告（跑前宣告本平台能判几项） | 被 S3 的 SKIP 三态计数覆盖大半，剩余增量不足以独立成条 |
