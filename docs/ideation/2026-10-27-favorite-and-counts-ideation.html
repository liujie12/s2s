Grounding Context 仓库现状与被核实的原文

需求落点与既有实现

  • 收藏域已完整存在：POST/DELETE /posts/{post_id}/favorite、GET /favorites；前端四件套在 lib/features/favorite/。缺的只是详情页的入口。
  • 详情页 lib/features/detail/detail_screen.dart 的 AppBar 无 actions（:56-68），底部 _ContactBar 是单个 FilledButton 占满整行（:427-483），没有次要动作位。
  • 「在架」是「我的发布」的四页签之一（全部／在架／已下架／草稿），卡片副标题 _subtitle() 是**唯一**计数出口（my_publish_screen.dart:1098-1111），且未设 maxLines。

计数目前没有数据源

  • view_count 后端硬编码 null：PostQueryService.java:207-208，注释写明「Batch1 无数据源」。
  • MyPostItem 无 favorite_count；PostDetail 无 favorited、无任何计数；PostCard 无计数（openapi.yaml:4856-4982）。
  • 埋点这条路在本期走不通：5 个事件里没有浏览事件（track_event.dart:23-37）、月表无 post_id 列（V1__init_track_schema.sql:33-51）、/track/events 强制登录（TrackController.java:55-79）、表注释写明「90 天、允许丢、不可用于合规举证」。
  • 可复用的现成范式：contact_count 的整页批量聚合 IN + GROUP BY（PostQueryMapper.xml:91-98）。

一处关键纠正（推翻了初判）

已核实 后端收藏前置校验 countPostById 是 SELECT COUNT(*) FROM post WHERE id=#{postId}，不带 status 条件；同文件注释写明「post 无软删列，下架帖仍在库里可被收藏」（FavoriteMapper.xml:7-11、36-38）。 因此 PRD 的「已下架时收藏保留」在服务端本来就成立——砸掉它的是前端 detail_screen.dart:105 把 41001 整页替换成 _NotFoundScreen。

空间预算

卡片宽 358，扣 1px 描边 ×2 与内边距 16×2 后为 324；再扣色条 4 + 间距 12 + 缩略图 44 + 间距 12 = 72，剩 252；再扣状态标前 8 与状态标本体（在架 38 / 契约外取值 60），主体只剩 206 / 184。而「浏览 12｜收藏 3｜3 天前发布」在 caption 11 下约 143px、在 small 12 下约 156px。

Topic Axes

  • A1 收藏动作的落点与状态 —— 详情页放哪、什么形态，未登录／自己的帖子／已下架／网络失败各走哪条路。
  • A2 在架卡片的信息密度与计数呈现 —— 槽位、文案格式、零值、大数、溢出与卡高。
  • A3 计数口径与可信度 —— 数据从哪来、是否含自己、怎么聚合、是否模糊化。
  • A4 激励与边界 —— 谁看得见、是否进排序／通知，以及契约形状怎么把边界钉死。

Ranked Ideas

1 收藏不能只活在 data 态：让星标跨五种屏存活

A1 动作落点 Confidence 88% 复杂度 中
Description
把 Scaffold／AppBar 提到 detailAsync.when 之外，星标固定在 appBar.actions，body 内部再分流 loading／error／41001／40301。41001 不再是「另一个页面」，而是同一壳的降级态：顶部红条 + 正文 Opacity 60% + 联系按钮禁用 + 星标仍在。设计交付物应是一张「5 屏 × 星标（可见・可用・实心）」矩阵，而不是一屏稿加一句说明。
Basis
direct: detail_screen.dart:45-49 是 when(loading/error/data)，只有 data 分支内部建 Scaffold（:54），loading 与 error 各建独立屏；:102-113 三路整页替换；_NotFoundScreen:615-651 只有图标与「这条信息已下架或不存在」；PRD.md:1891 与 :2449 两处都写「联系按钮禁用，收藏保留」；后端 FavoriteMapper.xml:7-11、36-38 证实下架帖仍可收藏。
Rationale
宿主留在 data 态，「收藏保留」就永远落不了地；而用户从「我的收藏」点进一条已下架信息想取消收藏，会走进一条死路——这恰好是收藏最该发挥作用的时刻（「我想留住这条」）。四个错误屏各加一次星标还会产生四份重复实现。
Downsides
41001 时拿不到详情 DTO，星标的初始「是否已收藏」没有来源，只能靠收藏列表索引或契约补字段（见方向 2）；错误屏与正常屏共用 AppBar 后，标题文案与返回行为的差异要在矩阵里写清，否则会退化成「什么都保留了」。

2 星标是三态，不是布尔：未知态与「登录后自动补收藏」

A1 动作落点 Confidence 80% 复杂度 中
Description
星标至少有三种视觉与行为：已收藏（实心）／未收藏（空心）／未知（详情未加载、游客、请求失败）。未知态不允许被画成空心——那是在替用户断言「你没收藏过」。点击时若未登录，走 push<bool>(AppRoutes.login)，ok == true 后自动补执行这次收藏，而不是要求用户回来再点一次。前端需要一个按 postId 索引的收藏态来源（来自详情字段或批量状态查询），不能靠比较 author.id:int 与 AuthSession.userId:String。
Basis
direct: contact_screen.dart:209-217 已有范式 final ok = await GoRouter.of(context).push<bool>(AppRoutes.login); if (!mounted || ok != true) return; await _reveal();；login_screen.dart:243-253 注释「登录多半是从收藏/联系按钮弹上来的」；api_error_code.dart:71 unauthorized(40101, ErrBehavior.refreshToken) 只续期、不弹登录；detail_screen.dart 全文无 isLoggedInProvider 消费；PostDetailDto 无 favorited／isOwner（post_dto.dart:218-237）。
Rationale
现状是「未登录点星标 → 一次静默的 40101 → 用户看到错误而不是登录页」。同一类账号依赖动作，联系入口有前置判断、收藏没有，说明缺的不是能力而是落点。把「未知」做成一等状态，也顺手解决了「详情加载失败时星标该显示什么」这个最容易糊过去的问题。
Downsides
「登录后自动补收藏」意味着平台替用户完成了一次写操作，需要明确的口头确认（星标立刻实心 + 一条可撤销提示，见方向 3）。若收藏态改由服务端新字段承载，要同步 openapi 的 required 与 Dart 可空性（规范 :196 禁 ?? 掩盖可空），并决定游客场景该字段是「缺失」还是「false」。

3 收藏是一次本地翻转，不是一次整页重拉：乐观写 + 3 秒撤销

A1 动作落点 Confidence 82% 复杂度 中
Description
点击后本地立即翻转图标并计入待提交队列，失败回滚；成功给一条 3 秒撤销提示。撤销有两种实现：延迟提交（3 秒内再点一次即取消、零请求）或提交后反向提交。无论哪种，收藏状态必须是「按 postId 的单一事实源」，让详情页星标、我的收藏页星标、未来发现页星标读同一处；refresh() 退化为对账手段，不再是交互路径。
Basis
direct: favorite_provider.dart:138-142 refresh() 先把 state 置 AsyncValue.loading()；:161-169 remove() 仅 removeFavorite + refresh()，无乐观、无回滚；favorite_screen.dart:78-87 失败只弹 SnackBar，无撤销；PRD.md:1979 明确要求「取消后 3 秒内显示"撤销"浮条」；全库仅 media_section.dart:374 一处 SnackBarAction。
Rationale
现在的写法在物理上让「撤销条」无处可挂：取消收藏会触发整页骨架，页面正在转圈，没有稳定 UI 承载浮条。把收藏改成乐观写，撤销条才有落点，收藏页取消也不再整页闪一下。这是一次结构性修改，会让三处星标共用一套并发控制。
Downsides
同一帖子在多处并发点击需要 pending 去重，否则后到的响应会覆盖先前的翻转；延迟提交要求离开页面／切后台时立刻落地，否则撤销会吞掉用户的操作；失败回滚需要本地状态，而当前没有任何回滚通道。

4 先拆掉不合规的状态胶囊，再谈两个数字怎么排

A2 卡片密度 Confidence 78% 复杂度 低
Description
状态标目前是 Container + 12% 底色 + 横向 8 内边距的胶囊，而规范要求这类元数据「纯文本、无容器无底色」。还原成纯文本后主体宽度从 206／184 回到 222／200，恒定 +16px。加上 maxLines: 1 与一套降级序列（三段全出 → 只出收藏 + 时间 → 只出时间），并规定整页统一取同一档，避免逐卡自适应导致卡高参差。
Basis
direct: 设计系统与组件规范.md:213「纯文本、无容器无底色」；:190 摘要用 small 12；实现却是 my_publish_screen.dart:669-677 的 Container + alpha 0.12 + 横 8，且副标题 :601-607 未设 maxLines／overflow。reasoned: 先修一处既有偏离（胶囊违规）正好付得起另一处（小字号 caption 11 而非 small 12）的账——宽度问题不是被计数吃掉的，是被不合规容器吃掉的。
Rationale
开发者现在没有任何宽度预算可依，加一个字就换行；逐卡换行会让列表从「等高卡」退化为「自然流」，卡高漂移比字挤更早被用户感知。先把不该占的 16px 要回来，能让「要不要缩字号／要不要砍一个数」这类牺牲式讨论直接取消。
Downsides
纯文本化会同时降低「在架」状态的视觉权重，需要确认产品是否接受；16px 之外仍需真机验证（现有 206/184 是按代码常量推算，未在 360dp 小屏实测）；如果「全部」页签里状态标必须突出，就得给组件加显隐开关而不是一刀切。

5 零值分三种，不能共用一个「0」

A2 卡片密度 Confidence 65% 复杂度 低
Description
「没有数字」要拆成三种语义分别处理：①无数据源（整段不显示，沿用现状）；②真实 0（有口径但确实没人收藏，需要一句不伤人的话术，具体文案待产品裁定）；③刚发布（还没进入统计窗口，用「刚发布」而不是 0）。三态共用一套判定函数，时间窗落 NfrXxx 常量，不在 UI 里写魔法数。
Basis
reasoned: 现有注释拒绝的是归因错误——「把『没有数据源』说成『没人看过』，会把发布者劝退」（my_publish_screen.dart:1100-1102）。真实 0 不存在归因错误，但仍有情绪问题；这两者必须分开处理，而不能把该注释直接外推成「0 一律不显示」。direct: PRD.md:2805-2807 要求 NFR 数字集中落 lib/nfr_constants.dart 并回改 PRD。external: eBay 浏览数对卖家可见但对 bot 两阶段过滤、YouTube 明示指标可延迟／冻结／下调，两者做法都是「不保证即时精确」而非「藏掉」。eBay 官方帮助页「Viewing page views」。
Rationale
收藏数一上线会立刻捅破现有那条只覆盖 null 的口径；而新发布、最需要鼓励的那张卡恰恰是 0/0。三态分开后，绝大多数「为什么我的数不动」的客服问题在界面上就被消化掉。
Downsides
真实 0 的文案是产品判断，工程不能自拟（项目红线：设计未覆盖的口径先问）；三种状态叠加会让副标题逻辑变厚，需要单测固定；如果「刚发布」按信息类型给不同窗口，常量就不再是单值。

6 浏览数本期不交；收藏数一次把口径定死

A3 计数口径 Confidence 85% 复杂度 中
Description
设计稿上写清楚两栏：「本期可上线」= 收藏数；「依赖后续批次」= 浏览数。收藏数只走业务表聚合：补 favorite(post_id, deleted_at) 索引，照抄 contact_count 的整页 IN + GROUP BY，一次查询覆盖整页，聚合时排除帖主自己。同时显式拒绝「收藏率／热度分」——收藏按人去重是人头，浏览被实名额度与游客限频裁剪过是通过闸门的次数，两者不同质；文案用量词承载（「3 人收藏」）。
Basis
direct: view_count 硬编码 null（PostQueryService.java:207-208）；5 个埋点事件无浏览（track_event.dart:23-37）；月表无 post_id 列（V1__init_track_schema.sql:33-51）；TrackController.java:55-79 强制登录；表注释「允许丢、不可用于合规举证」。收藏侧：FavoriteService.java:75-81 只校验帖子存在、不拦自收藏；V1__init_schema.sql:286-296 uk_user_post(user_id, post_id) 无 post_id 独立索引；PostQueryMapper.xml:91-98 是成熟批量聚合范式。
Rationale
这是本刀唯一能让工期翻倍的隐藏坑：稿上三个数字，编码时两个是空的。一个只有作者看得见、作者自己还能刷的数字，连「参考」都算不上。contact_event 的批量聚合证明这条路在本仓是现成的，不需要为了一个卡片数字去改埋点表、放开游客上报、再建读路径。
Downsides
拿不到「曝光 → 收藏」漏斗与长期趋势；排除自收藏意味着作者自己的收藏不计入，日后若把收藏当书签需要重新定义口径；补索引会随软删行膨胀，需与 30 天物删任务一起看。

7 用契约形状钉死可见性：数字只进「我的发布」

A4 激励边界 Confidence 85% 复杂度 低
Description
favorite_count 只加在 MyPostItem；PostCard（发现页卡片）与 PostDetail（他人视角）都不加，sort 枚举不新增任何计数项，并在字段 description 里写死「仅帖主可见、不对外展示、不参与排序」。互动通知仍只有「被联系 × 次」，不扩成「被收藏 × 次」。
Basis
direct: openapi.yaml:4939-4961 MyPostItem 已有 view_count／contact_count；:4963-4982 PostCard 无任何计数；:4856-4922 PostDetail 无计数、无 favorited；:1795-1817 sort 六项无计数，composite = 时效 40% + 距离 40% + 完整度档 20%。PRD.md:640 不做信誉徽章／评价历史；:745 无商业化分级；:1678 完整度角标「不卖、不含等级」；:2046-2050 完整度三档是唯一曝光杠杆（×2／×1／×0.5）。
Rationale
收藏数一旦出现在他人可见的卡片上，它事实上就变成了跨用户的信任信号，直接撞上「信任信号只由实名／资质 + 完整度构成」的口径。把它钉在 MyPostItem 一个 schema 里，后续所有「帖主反馈」类需求都在对内一侧，不必每次重开可见性讨论。
Downsides
契约里的 description 不是运行时约束，仍要靠评审守；如果未来真要做「热门」，必须重开契约并过红线评审；「仅帖主可见」这条结论目前只能从 PRD 的相邻条款推出，PRD 本身没有逐字条文，需要产品在评审时确认。
