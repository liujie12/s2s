代码库上下文

基于 找鸭找 项目现有约束进行构思：

  • 技术栈：Flutter 客户端 + Spring Boot 3 单体后端 + MySQL 8.4 LTS（唯一持久化） + Redis 7 + Caffeine + 阿里云 OSS + 高德地图 SDK（GCJ-02）
  • 基础设施预算：131 元/年 · ECS 经济型 e（2 核 2G） · 内存：MySQL 450M / Redis 150M / JVM -Xmx600m
  • 排期：38 自然日，无缓冲
  • 14 张业务表（三批次）：user · user_identity · post · contact_event · publish_memory · category · report · audit_log · system_config · scheduled_task · task_log · notification · notification_template · file_metadata
  • 数据模型核心机制：grid_id ~500m 网格冗余列 · l2_category_id 二级类目冗余列 · version 乐观锁（40903） · user_identity 身份归一化（双唯一索引） · 分类树三级编号规则
  • 5 条已知口径冲突（原型代码遗留）：完整度计数 · 分类树编号 · 网格边界 · 状态流转 · 敏感字段
  • 11 条保留策略：含 90 天埋点整表 drop · 180 天 audit_log · 7 天冷静期 · 通知 30 天等
  • Past Learning 判据：延期的是逻辑，不是数据 —— 延后后是否需要在有真实数据的库上改表结构

来源

direct PRD.md:2354-2357 identity_value varbinary 加密存储 + uk_type_value 唯一索引 → AEAD 随机 IV 下唯一约束与等值查密码学上不可用

direct PRD.md:2339-2340 id_card_hash char(64) "只存不可逆哈希" 与 id_card_last4 明文并存 → 18 位强结构化 + 后 4 位明文 → 候选空间可 GPU 穷举
direct 可观测性:437 出包门禁只查明文列不查是否加盐，缺口真实
reasoned 无 key_version 列则密钥轮换必须停机全表重写

落地形态：

  • identity_hash char(64)（HMAC-SHA256 + pepper）— 承载唯一索引与等值查
  • identity_value_enc varbinary(1024)（AEAD 密文）— 仅解密展示
  • key_version tinyint — 支持可灰度密钥轮换
  • user.phone 拆为 phone_mask varchar(20)（明文掩码，仅展示）与归一化到 user_identity 的加密原文
  • id_card_hash 改 HMAC + pepper

不可逆性：事后修改必须在有真实密文的库上重写全表并重算全部唯一索引。

权衡：增加一列存储开销；key_version 引入密钥管理复杂度；phone_mask 与 identity_value 的展示一致性需业务层保障。

落地形态：

  • post 增 status_reason tinyint（枚举：1=主动下架 · 2=到期 · 3=审核下架 · 4=成交）
  • post 增 status_changed_at datetime（非空，每次 status 变更同步更新）

不可逆性：唯一「今天不做则永久缺失」项——90 天窗口内未采到的维度不可追补，非 active 状态事后不可区分。

权衡：post 表增两列增加存储；status_changed_at 需在每次 status 变更时同步更新（增加写路径复杂度）；埋点快照增加单行写入体积。

④ 生命周期、状态与保留
来源
A4-1 · A4-6
direct 架构:325 三条并发写路径；架构:339 40903 不允许自动重试；架构:602 §8 定时任务表
direct 架构:814 已有「定时任务与手动下架相撞」验收项，却未定守卫口径

落地形态：

  • 用户意图写 → WHERE version = ? 版本守卫（冲突返回 40903）
  • 系统派生写 → WHERE status IN (合法前驱集) 状态守卫（定时任务永不产生 40903）
  • 两者在同一 UPDATE 的 WHERE 中组合
权衡：增加了状态流转矩阵的维护成本（需明确定义每个状态所有合法前驱）；系统派生写失去版本乐观锁的冲突检测能力。

网格计算改整数微度域

轴
① 空间读路径的数据组织
来源
A1-1
direct PRD.md:2371 步长 0.0045° + floor 运算
reasoned 0.0045 在 IEEE-754 下不可精确表示，floor(lng / 0.0045) 在网格边界附近会跳格；10 条测试向量全绿不能证明线上正确。lng_e6 DIV 4500 使运算全整数域，不改变编码结果

落地形态：grid_id 生成算法在服务端与客户端统一改为整数微度运算（先 round(deg * 1e6) 再整除 4500），编码格式与既有定案不变。

权衡：需同步修改客户端与服务端两处实现并在分界点确认一致；round 的精度边界需与测试向量对齐。
