# 整体测试方案（功能 / 集成 / 性能）

> 版本：v1.0（2026-11-03）
> 定位：第一阶段功能已交付、微信登录与部分行政工作等待 ICP 备案期间的**整体测试执行口径**。本文只做测试编排与用例清单，判定口径一律引用《编码规范》《完成定义DoD》《前端详细设计文档》《后端详细设计文档》，不复制其条文。
> 适用对象：Flutter 客户端（`lib/`）、Java 后端（`src/`）、管理端接口（`/admin/*`）、部署与真机侧。

## 0. 结论先行

用例总数 **66 条**（功能 34 + 集成 16 + 性能 16），按执行方式分布如下：

| 执行方式 | 数量 | 说明 |
| --- | --- | --- |
| 全自动 | 49 条 | CI 或一条命令可判定，无需人眼 |
| 半自动（脚本执行 + 人工判读） | 11 条 | adb 编舞、golden 比对、压测出数 |
| 必须人工 | 4 条 | 微信授权、定位权限、弱网手感、外部凭据链路 |
| 分模式 | 2 条 | OSS/媒体上传：桩模式自动、真桶人工（FT-22、IT-08） |
| 人工专项 | 13 项 | M-01 ~ M-13，不属于用例表，但必须排期 |

三条硬结论：

1. **单元测试已经不是瓶颈，缺的是“真装配”和“真链路”。** 现有 734 个后端 `@Test` 全是 hermetic，全库无 `@SpringBootTest`；前端 1153 条用例默认全部跑在 mock 上，真后端模式（`S2S_API_BASE_URL`）至今没有消费方。
2. **能自动化的部分比想象的多，但前提是先补一条“真底座”。** 没有 `application-test.yml`、没有容器化 DB/Redis，任何集成与性能测试都只能靠人手起环境，自动化无从谈起。
3. **必须人工的部分集中在四类**：真机观感与手感、真实外部凭据（微信/推送/OSS 真桶）、真实设备能力（相机/定位/后台唤醒）、合规与上架判断。这四类**不可用 mock 结论替代**。

## 1. 判定规则：一条用例能不能自动化

不按“感觉”分，按五条判据分。五条全过才是**可自动化**：

| # | 判据 | 反例（因此必须人工） |
| --- | --- | --- |
| J1 | **可重复**：任意人在任意时间用同一命令得到同一结论 | 依赖“当前这台手机恰好连着”、“今天推送恰好通了” |
| J2 | **可断言**：期望值能写成机器判定（状态码、字段、计数、阈值、像素差） | “看起来顺不顺”、“文案读起来别不别扭” |
| J3 | **可隔离**：不依赖不可控外部状态（第三方审核、厂商通道、真实运营商） | 微信 code→openid、厂商推送到达、实名核验 |
| J4 | **可归因**：失败时能定位到具体模块/断言，而不是“整机卡了一下” | 弱网手感、滚动掉帧的主观体感 |
| J5 | **有明确期望值**：设计文档或契约里写死了口径 | “启动要快”但没有阈值 |

**半自动**的判定：执行可脚本化（J1 过），但结论需要人看一眼（J2 不过）。典型是 adb 编舞取数与 golden 截图比对。

**明确不作为自动化处理的三件事**：

- 用 mock 结果代替真实外部链路结论（微信、推送、实名、OSS 真桶）。
- 用单台设备的点估计代替机型结论（见 `Batch1-进度记录.md:5656`「样本不足时一律不得下达标判定」）。
- 用“跑绿了”代替“证明会红”（见 `docs/solutions/workflow-issues/fail-closed-gate-judgments-with-mutation-self-checks.md:29`）。

## 1.5 测试环境基线（2026-11-03 裁定：后端用正式环境）

**后端一律使用正式环境 `https://s2s.build110.com`，不搭建本地容器化真底座。**

裁定理由：本机 Windows 无 `docker` CLI（WSL 内有 Docker 28.1.1，但需额外桥接）；项目已有可用正式环境，当前处于内测期。

由此产生的口径变化：

| 原计划 | 正式环境下的处理 |
| --- | --- |
| 本地容器起 MySQL/Redis + 跑 V1–V33 迁移 | **不执行**（正式环境不重启、不重建库） |
| 一条 `@SpringBootTest` 首启 smoke | **不执行**，记 N/A；改由部署后冒烟（MC-11）覆盖 |
| DB 级断言（审计同事务、定时任务、埋点落库） | **无法验证**，只验接口可观察部分，其余记 SKIP |
| 契约真模式 | **可执行**（只读端点） |
| 登录、限流、幂等、敏感字段扫描 | **可执行**（仅测试账号） |
| 并发 20 × 5 分钟压测 | **需显式批准**；未批准前只做低并发只读基线 |
| 删除 / 注销 / 解绑等破坏性操作 | 仅在专用测试账号执行，且逐个确认 |

### 正式环境事实（2026-11-03 实测）

- `/actuator/health` 返回 `{"status":"UP"}`。
- 根路径无反代前缀：`/categories/tree` 返回 `code:0`；带 `/api/v1` 会 404。
- 短信仍是 dev 桩（验证码固定 `888888`），生产白名单非空。
- 微信、推送、OSS 真桶、实名核验凭据状态不变（见第 10 节）。

### 正式环境测试八条保护措施

| # | 约束 |
| --- | --- |
| G1 | 只用测试账号，禁止使用真实用户账号做写操作 |
| G2 | 测试数据标题统一前缀 `[测试]`，测完立即下架或删除 |
| G3 | 不修改他人数据，不删除非本次创建的数据 |
| G4 | 压测需显式批准；先只读、低并发、低峰；禁止无批准打满并发 |
| G5 | 注销、解绑、删除对象等破坏性用例只在专用测试账号执行 |
| G6 | 证据与日志脱敏：手机号、身份证、`Authorization` 一律不入档 |
| G7 | 发现线上缺陷先记录证据再复现，不在正式环境反复试错 |
| G8 | 每批测试结束复核测试数据残留，并在进度记录写明清理结果 |

## 2. 三层测试的定义与现状

| 层 | 目的 | 现有资产 | 缺口 | 主要工具 |
| --- | --- | --- | --- | --- |
| 功能测试 | 每个用户可见路径按规格工作 | 前端 1153 条 widget/单元用例、后端 734 条单测 | 无端到端功能验收；无真机功能清单 | `flutter test`、`mvn test`、adb 编舞 |
| 集成测试 | 组件之间、服务之间、外部依赖边界正确 | 契约套件（MockApiServer）、横切链 standalone 测试、G1–G11 部署门禁 | 无真装配（`@SpringBootTest`）、无真后端契约、无容器化 DB/Redis、无实时通道端到端 | Testcontainers、k6、真模式契约 |
| 性能测试 | 关键路径达到 SLA | 压测口径（并发 20 / 5 分钟 / 弃前 30 秒 / 异机 / `rt_ms`）、`seed-perf.sql` 15 万行造数、POC 基准脚本 | 无常态化的接口压测流水；无真机性能回归资产 | k6 或 JMeter、adb 编舞、`frame_metrics` |

口径来源：读接口 P95 ≤ `NfrPerf.readApiRtP95Ms`（150ms）、图层切换 P95 ≤ `NfrPerf.layerSwitchP95Ms`（300ms）、帧预算 `NfrPerf.frameBudgetMs`（16ms）、`/map/pins` 读取超时 `NfrPerf.mapPinsReadTimeoutSec`（3s）、慢触发 `NfrPerf.p95TriggerMs`（800ms）。代码侧只引用常量名，不写字面量。
