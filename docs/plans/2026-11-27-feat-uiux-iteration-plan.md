## 0. 五条硬规则

1. **无设计稿不编码**：任何迭代在 Gate D（设计定稿）签字前，不得创建改 `lib/` 的分支。
2. **每片可独立上线**：迭代之间不共享未完成状态；不允许「先上线一半，等下一迭代补齐」。
3. **不改口径**：五类分类、供需双态、完整度三档、零商业化等既有口径不动；不新增品类、不新增错误码、阈值只引用 Token 名与 `NfrXxx`。
4. **只用能力库**：所有迭代的设计、评审、验收必须走设计能力库（见 §0a）；未运行或库未覆盖的项必须显式登记，不得自创判据、不得手写图标/插画/色值。
5. **不出「并列大厂」结论**：本方案只输出 G1～G6 的达标 / 不达标二分；「未验证」视同未达标。竞品只作差距参照，不做分数估算，不在任何验收文件里写「追平 / 并列」。

## 0a. 设计能力库使用规范（强制，适用于所有迭代）

> 依据：设计能力库 0.2.0（`ds.js`）。设计、评审、验收只用库里的方法与判据，**不自行发明标准**。

### A. 四道库门禁（每迭代必跑）

| 时点 | 必跑命令 | 产物 | 失败处理 |
| --- | --- | --- | --- |
| **D0 开工前** | `doctor` → `bench` → `scan-dart` | 环境自检、能力对标、硬编码基线（初始 164 处：color 100 / spacing 47 / font-size 14 / credential 3；2026-11-28 修复凭证日志后 **161，credential 0**） | 环境不过不得开工；`scan-dart` 作为只减不增的基线 |
| **D1 设计稿** | 按迭代类型调用：`visual palette` / `visual rhythm`（视觉）、`icon_*` MCP（图标）、`visual illustrate` 或 `hero`（插画）、`photos`（授权图） | 设计稿 + 生成 manifest + 校验报告 | 生成物 `passed=false` 不得进入评审 |
| **D2 评审** | `check` / `visual audit` / `icon_review` / `icon_set_report` / `illustrate-verify` / `content-audit` / `a11y-audit` / `state-check` | 报告文件 + 逐条判据号 | 任一硬违规即不通过；不能跑的写「未运行 + 原因」，不得写「通过」 |
| **D4 验收** | `scan-dart` + 可跑的 `check` / `gate` + 真机截图 | 前后对比、退出码 | 硬编码增量 >0 或 `check` 回退即验收不通过 |

### B. 六条「不许自行发散」

1. **结论必须落到判据**：每条结论 = 页面 + J 号（J1–J49）或库脚本输出；库没覆盖 → 按库 §7 回流，不得自创判据。
2. **图标不手写**：必须走 `icon_generate → icon_validate → icon_render → icon_review → icon_set_report`；`validation.ok=false` 最多回填重生成 2 次，仍失败就停并报告（库 §4.5）。
3. **插画不新画风**：必须走 `visual illustrate` / `visual hero`，由 `scenes.json` 与风格板派生出图（库 §4.10 / §4.11）。
4. **色值 / 字阶 / 间距不手挑**：视觉稿由 `visual palette` → `visual rhythm` 生成；组件层禁止字面色值（库 §5）。
5. **照片必须可核验**：过 `photos verify`（许可 / 署名 / 哈希），页面每张内容图带 `data-photo-id`（库 §4.9）。
6. **评审不得只写感受**：结论必须是「页面 + 判据号 + 可观察证据」，禁用「整体感觉不错」（库 §3.4）。

## 2. 「完整交付」的 7 条定义

一个迭代只有同时满足以下 7 条，才算完成：

1. 用户可在真机上看到本迭代承诺的**可见变化**；
2. 不存在依赖下一次迭代才完整的「半成品态」；
3. 有明确回滚边界（组件或开关），可单独回退；
4. `flutter analyze` 0 issue、`flutter test` 全绿；
5. 真机截图与评审通过的设计稿逐屏一致（差异需登记并复评）；
6. 能力库证据齐备：D0/D2/D4 的命令、退出码、报告路径可追溯；未运行项已登记；
7. D5 回填完成。

> **I0 例外**：I0 不产出代码，它的「完整交付」按 I0 卡的交付判据执行（方向签字 + 竞品采样 3/3 + G5 面积预演结论），第 1、4 条不适用。

## 3. 四条泳道与顺序

| 泳道 | 顺序 | 为什么这样排 |
| --- | --- | --- |
| **基座泳道** | I0 → I2a | I0 用同一组数据定唯一方向与基线（含 G5 面积预演）；I2a 把 U-20 的字阶 / 字体栈 / 光影 / 主色面积规格落进真源，后面所有切片共用 |
| **图形泳道** | I1 → I1b → I5 | I1 建立资产接入机制（SVG 或 CustomPaint 二选一），I1b 补齐三级叶子，I5 的插画与彩色锚点直接复用该通道 |
| **结构泳道** | I2 → I3 → I7 | I2a 先落 Token，I2 再定图片位与卡片骨架，I3 接真图；I7 收口「我的 / 详情」的同类问题 |
| **反馈泳道** | I4 → I6 | I4 先产出 `AppMotion` 六档，I6 的地图过渡直接引用，不写字面量 |

执行顺序：**I0 → I1 → I1b → I2a → I2 → I3 → I4 → I5 → I6 → I7**。I1 与 I2a 可并行做设计稿；I3 的后端封面链路（U-00）可在 I0 阶段并行启动，但 I3 编码必须等 U-00 可联调。

#### I1 的范围说明：三级分类怎么算

| 层级 | 规模 | 在 I1 的处理 | 出现在哪 |
| --- | --- | --- | --- |
| 一级 | 5 | 重绘 | 底栏分类入口、筛选大类、详情面包屑、地图图例 |
| 二级 | 25 | 重绘 | 列表 44 徽标、地图 Pin、筛选 chip、详情面包屑 |
| 三级（叶子） | 123（122 个图标名） | 28 个已引用自绘**收敛**到同网格同母题；其余 94 个**回落所属二级字形** | 仅发布页三列选择器的叶子列（18px） |

结论：**三级需要重绘，但要分两片。** I1 先保证全树不出现 Material（28 枚自绘收敛 + 94 枚回落二级）；I1b 再逐叶派生，做到「同二级可辨、语义准确」。不逐枚自由创作，是因为 18px 下 94 个独立造型必然失控（现有代码已有 0.9–1.4 半径细部在 22px 糊成噪点的证据）；做法是「25 个二级母题 + 每叶 1 个差异元素」，车辆族现有 `车 + 楼/环/飞机/人/日历` 已验证 18px 可辨。
