## 1. 前置条件

### 1.1 硬件与系统

| 项 | 最低要求 | 推荐配置 | 依据 |
|---|---|---|---|
| CPU | 2 核 | 2 核 vCPU | [部署架构设计文档 §1.1](./部署架构设计文档.md#11-物理拓扑) |
| 内存 | 2 GB | 2 GB | [部署架构设计文档 §3.1](./部署架构设计文档.md#31-预算分配表)（合计 1414MB） |
| 系统盘 | 40 GB SSD | 40 GB ESSD | [部署架构设计文档 §4.1](./部署架构设计文档.md#41-40g-essd-分配表) |
| 带宽 | 3 Mbps | 3 Mbps | 架构 R6 |
| 操作系统 | CentOS 7+ / Ubuntu 20.04+ / Debian 11+ | Ubuntu 22.04 LTS | 官方镜像均可 |

> ⚠ 2 核 2G 是**严格预算**，四个容器（Caddy + app + MySQL + Redis）加起来内存预算 1414MB，留给系统和内核的只有约 600MB。
> 不满足不要勉强扩容，而是先查 §3.1 预算表找出哪一项超了。

### 1.2 软件依赖

- **Docker** ≥ 24.0（带 compose plugin，即 `docker compose` 子命令可用，非旧版 `docker-compose` 二进制）
- **Git** ≥ 2.30
- **OpenSSL**（生成密钥用）
- **curl**（健康检查用）

检查命令：

```bash
docker --version          # 期望 Docker version 24.x.x
docker compose version    # 期望 Docker Compose version v2.x.x
git --version
openssl version
curl --version | head -1
```

### 1.3 域名与 DNS

- 一个已备案的域名（如 `example.com` 或二级域名 `api.example.com`）
- 域名 A 记录指向本服务器公网 IP
- 一个可用邮箱，用于 Let's Encrypt 证书到期提醒

> 国内服务器必须完成 ICP 备案才能对外提供服务，否则 80/443 端口会被阻断。

### 1.4 凭证与密钥（提前准备）

| 凭证 | 用途 | 哪里来 |
|---|---|---|
| OSS AccessKey / SecretKey | 媒体存储与备份上传 | 阿里云 RAM 控制台，新建子账号，仅授予指定桶权限 |
| OSS Bucket 名称与 Endpoint | 同上 | 阿里云 OSS 控制台 |
| 数据库 root 口令 / 业务库口令 | MySQL 初始化 | 自己生成，见 §4.2 |
| Redis 口令 | Redis 鉴权 | 自己生成，见 §4.2 |
| AEAD 主密钥（32 字节） | 列加密（手机号/实名等） | `openssl rand -base64 32` |
| HMAC pepper（32 字节） | 盲索引（手机号等） | `openssl rand -base64 32` |
| JWT 签名密钥（32 字节） | 登录 Token 签发 | `openssl rand -hex 32` |
| 大模型 API Key（可选） | AI 辅助发布（Batch3） | LLM 服务商控制台 |

> 🔴 **安全红线**：以上所有密钥**一律不准提交到 git**、不准写进文档、不准发到聊天工具。
> 只出现在两个地方：服务器上的 `deploy/env/.env.prod`（权限 600）和你的密码管理器。

## 2. 服务器初始化

> 以下命令默认以 `root` 执行。非 root 用户请加 `sudo`。

### 2.1 系统更新与基础工具

```bash
# Ubuntu/Debian
apt update && apt upgrade -y
apt install -y curl wget git vim unzip openssl

# CentOS/RHEL
yum update -y
yum install -y curl wget git vim unzip openssl
```

### 2.2 配置 swap（2 GB）

2G 内存无 swap，MySQL + Java 极易触发 OOM。按 [部署架构设计文档 §4.3](./部署架构设计文档.md#43-swap-配置) 配置 2GB swap：

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 降低 swappiness（减少主动换出，避免性能抖动）
sysctl vm.swappiness=10
echo 'vm.swappiness=10' >> /etc/sysctl.conf

# 验证
free -h
```

预期看到 Swap 行显示约 2.0Gi。

### 2.3 安装 Docker

**Ubuntu：**

```bash
# 安装依赖
apt install -y ca-certificates curl gnupg lsb-release

# 添加 Docker 官方 GPG key
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
chmod a+r /etc/apt/keyrings/docker.gpg

# 添加仓库
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" \
  | tee /etc/apt/sources.list.d/docker.list > /dev/null

# 安装
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

# 验证
docker --version
docker compose version
```

**CentOS：** 参考 Docker 官方文档，流程类似，改用 yum。

### 2.4 防火墙

只放行 22（SSH）、80（HTTP，用于 ACME 挑战）、443（HTTPS）。数据面端口（3306/6379/8080）**绝不对外**。

```bash
# Ubuntu (ufw)
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
ufw status

# CentOS (firewalld)
firewall-cmd --permanent --add-service=ssh
firewall-cmd --permanent --add-service=http
firewall-cmd --permanent --add-service=https
firewall-cmd --reload
firewall-cmd --list-all
```

> 📌 如果你在云厂商（阿里云/腾讯云等）上，记得在控制台的**安全组**里也做同样的放行规则——两者是双层防护，缺一个都不通。

### 2.5 时区与时间同步

```bash
timedatectl set-timezone Asia/Shanghai
timedatectl set-ntp true
date
```

确认时间正确。容器内 TZ 变量已在 compose 中统一设为 `Asia/Shanghai`。

## 3. 代码拉取与目录结构

### 3.1 拉取代码

选一个部署目录，比如 `/opt/s2s`：

```bash
mkdir -p /opt
cd /opt
git clone <你的代码仓库地址> s2s
cd s2s
```

> 首次上线建议切到 `main` 分支的**最新稳定 tag**（如 `rel/prod/20260930-150000`），而不是直接用 `main` 头。
> 参考 [分支与版本标记规范](../../docs/architecture/分支与版本标记规范.md)。

### 3.2 熟悉目录结构

`deploy/` 是部署相关所有资产的根目录：

```
deploy/
├── docker-compose.yml              # base：环境无关骨架
├── Dockerfile                      # 应用镜像构建
├── images.lock                     # 镜像基线台账（tag + digest）
├── compose/
│   ├── docker-compose.dev.yml      # dev 环境 override
│   ├── docker-compose.staging.yml  # staging 环境 override
│   └── docker-compose.prod.yml     # prod 环境 override
├── config/
│   ├── Caddyfile.prod              # Caddy 生产配置
│   ├── my.cnf                      # MySQL 配置
│   ├── redis.conf                  # Redis 配置
│   ├── logback-spring.xml          # 日志配置
│   └── app/
│       ├── application-dev.yml
│       ├── application-staging.yml
│       └── application-prod.yml    # 应用外部化配置（不含密钥）
├── env/
│   ├── .env.prod.example           # 密钥模板（入 git）
│   └── .env.prod                   # 真实密钥（不入 git，手动建）
├── initdb.d/
│   └── 01-init-databases.sh        # MySQL 首启建库授权（只建库不建表）
├── scripts/
│   ├── env-up.sh                   # 统一启动/停止入口
│   ├── deploy.sh                   # 一键发版
│   ├── gate-check.sh               # 部署面安全门禁
│   ├── gate-lib.sh                 # 门禁外壳库
│   ├── backup-mysql.sh             # 数据库备份
│   ├── image-baseline.sh           # 镜像基线校验/刷新
│   └── setup-swap.sh               # swap 配置脚本
└── docs/
    ├── 部署架构设计文档.md
    └── 部署操作手册.md              # 本文档
```

> 记忆口诀：**base 是骨架，override 穿衣服，env 给钥匙，scripts 是总开关。**
> 启动时四件套必须配套：`base + override + env_file + S2S_ENV`，缺一个都不会报错、只会静默起出一套错配的。

## 4. 密钥与配置

### 4.1 生成密钥文件

```bash
cd /opt/s2s

# 从模板复制
cp deploy/env/.env.prod.example deploy/env/.env.prod

# 严格设为 600（只有 owner 可读写）
chmod 600 deploy/env/.env.prod

# 确认未被 git 跟踪（输出应为 fatal 或 untracked，绝不能是 tracked）
git status deploy/env/.env.prod
```

如果 `git status` 显示 `modified:` 或 `new file:`，**立刻停止**，说明 `.gitignore` 没配好或你动错了文件。
正常应为 `Untracked files` 或未出现。

### 4.2 逐项填写 .env.prod

打开编辑：

```bash
vim deploy/env/.env.prod
```

逐项说明：

#### 站点基础

| 变量 | 说明 | 示例 |
|---|---|---|
| `SITE_DOMAIN` | 站点域名，Caddy 用它申请证书和反向代理 | `api.example.com` |
| `ACME_EMAIL` | 证书到期提醒邮箱 | `admin@example.com` |
| `APP_VERSION` | 应用版本号，发版时由 `deploy.sh` 注入时间戳，这里填占位即可 | `1.0.0` |

#### MySQL

| 变量 | 说明 | 生成方法 |
|---|---|---|
| `MYSQL_ROOT_PASSWORD` | root 口令，仅初始化用 | `openssl rand -base64 18` |
| `MYSQL_DATABASE` | 业务库名，默认 `s2s` 即可 | `s2s` |
| `MYSQL_USER` | 业务账号名 | `s2s` |
| `MYSQL_PASSWORD` | 业务账号口令 | `openssl rand -base64 18` |
| `MYSQL_TRACK_DATABASE` | 埋点独立库名 | `s2s_track` |

#### Redis

| 变量 | 说明 | 生成方法 |
|---|---|---|
| `REDIS_PASSWORD` | Redis 口令，**必填**，空口令会导致健康检查失败 | `openssl rand -base64 18` |

#### 密钥类（三巨头）

| 变量 | 说明 | 生成方法 |
|---|---|---|
| `AEAD_MASTER_KEYS_JSON` | 列加密主密钥，JSON 数组，支持多密钥轮换 | `openssl rand -base64 32`，包成 `[{"id":"k1","key":"<结果>"}]` |
| `HMAC_PEPPERS_JSON` | 盲索引 pepper，JSON 数组，泄露代价高于 AEAD | `openssl rand -base64 32`，包成 `[{"id":"p1","key":"<结果>"}]` |
| `JWT_SECRET` | JWT HS256 签名密钥 | `openssl rand -hex 32` |

> 🔴 **三个密钥千万别搞混**：AEAD 是加密用的（可解密还原）、HMAC 是哈希用的（不可逆，用于盲查）、JWT 是签名用的（防篡改）。
> 泄露代价排序：HMAC > AEAD > JWT。HMAC 泄露要停写+全量重算盲索引（见 [DevSecOps 接入方案 §2.2](../../docs/architecture/DevSecOps接入方案.md#22-两处未闭合的阻塞项)）。

#### OSS

| 变量 | 说明 |
|---|---|
| `OSS_ENDPOINT` | 如 `https://oss-cn-hangzhou.aliyuncs.com` |
| `OSS_ACCESS_KEY_ID` | RAM 子账号 AK |
| `OSS_ACCESS_KEY_SECRET` | RAM 子账号 SK |
| `OSS_BUCKET_NAME` | 桶名，如 `s2s-media` |

> RAM 子账号**只授目标桶的读写权限**，不要给管理员权限。

#### LLM（可选，Batch3 用）

| 变量 | 说明 |
|---|---|
| `LLM_API_KEY` | 大模型 API Key |
| `LLM_API_BASE_URL` | API 基址 |

Batch1/Batch2 可暂时留占位值，不影响启动。

#### SLS（可选，可观测迁移目标）

留空即可，命中迁移阈值后再填。

### 4.3 复核

```bash
# 权限必须是 600
stat -c %a deploy/env/.env.prod

# 文件中不应出现 example / change_me / placeholder 等占位词
grep -nE 'example|change_me|placeholder|YOUR_' deploy/env/.env.prod
# 预期输出：无匹配。有匹配说明漏填了。

# 密钥长度粗检（AEAD/HMAC 应为 32 字节 base64 约 44 字符；JWT hex 64 字符）
wc -c deploy/env/.env.prod
```

## 5. 首次启动

> ⚠ 首次启动前，请确认 §2–§4 全部完成。尤其是：swap 已配、Docker 正常、`.env.prod` 已填好且权限 600。

### 5.1 预热：刷新镜像基线

`images.lock` 里的 digest 都是 `PENDING`（首次使用），先拉一次并填充基线：

```bash
cd /opt/s2s
bash deploy/scripts/image-baseline.sh --refresh
```

预期：pull 五个镜像（caddy / mysql / redis / maven / eclipse-temurin），然后回写 `images.lock`。

> 如果服务器无法联网拉镜像，需要在能联网的机器上 `docker save` 打包后 scp 过来 `docker load`。基线 digest 以实际拉到的为准。

### 5.2 启动

用统一入口脚本启动 prod 环境：

```bash
sudo bash deploy/scripts/env-up.sh prod
```

脚本内部做的事：
1. 校验环境名合法、当前没有别的环境在跑
2. 校验 `docker-compose.yml` + override + env 文件三件套存在
3. 执行 `docker compose up -d --wait`
4. 写入 `deploy/.current-env` 记账文件

### 5.3 观察启动过程

启动需要时间：MySQL 首启要初始化数据目录（约 1-2 分钟）、应用首启要跑 Flyway 迁移。

```bash
# 查看所有容器状态
docker ps

# 实时看应用日志
docker logs -f --tail 100 s2s-app

# 看 MySQL 日志
docker logs -f --tail 50 s2s-mysql

# 看 Redis
docker logs -f --tail 30 s2s-redis

# 看 Caddy
docker logs -f --tail 30 s2s-caddy
```

### 5.4 启动成功的标志

按顺序出现以下现象，说明启动成功：

1. `docker ps` 四个容器（caddy / app / mysql / redis）全部 `Up`，且 STATUS 列显示 `healthy`
2. `s2s-app` 日志出现 `Started S2sServerApplication in X.XXX seconds`
3. `s2s-app` 日志无 ERROR，Flyway 迁移成功（`Successfully applied X migrations`）
4. `s2s-caddy` 日志无报错，证书申请成功（可看到 `obtain certificate` 或 `certificate obtained`）

如果启动失败，先看 §10 排错。

## 6. 部署验证

### 6.1 健康检查（容器内）

```bash
# 应用健康
docker exec s2s-app curl -sf http://localhost:8080/actuator/health
# 期望：{"status":"UP"}

# MySQL 健康
docker exec s2s-mysql mysqladmin ping -u root -p$(grep MYSQL_ROOT_PASSWORD deploy/env/.env.prod | cut -d= -f2) --silent
# 期望：mysqld is alive

# Redis 健康
docker exec s2s-redis redis-cli -a $(grep REDIS_PASSWORD deploy/env/.env.prod | cut -d= -f2) ping
# 期望：PONG
```

### 6.2 外网访问验证

在你本地电脑上（不是服务器上）执行：

```bash
# HTTPS 通
curl -I https://<你的域名>/actuator/health
# 期望：HTTP/2 200，证书有效

# HTTP 自动跳 HTTPS
curl -I http://<你的域名>/
# 期望：HTTP/1.1 301，Location 指向 https://...
```

如果 80/443 不通，先查防火墙（§2.4）和云厂商安全组。

### 6.3 关键接口冒烟

挑几个读接口验证数据面工作正常：

```bash
BASE="https://<你的域名>"

# 分类树
curl -s "$BASE/api/v1/categories/tree" | head -c 500

# 地图 Pin（空数据也应该返回 200 + 空列表）
curl -s "$BASE/api/v1/map/pins?category_id=10100&radius=5&lat=30.2741&lng=120.1551" | head -c 300

# 帖子搜索
curl -s "$BASE/api/v1/posts/search?page=1&page_size=10" | head -c 300
```

都返回 `code:0` 或结构正确的 JSON，说明数据链路通了。

### 6.4 证书验证

```bash
curl -vI https://<你的域名> 2>&1 | grep -E 'subject:|issuer:|expire date:'
# 期望：issuer 是 Let's Encrypt，有效期约 90 天，自动续期
```

### 6.5 门禁自检

跑一次完整部署面安全门禁：

```bash
sudo bash deploy/scripts/gate-check.sh prod
```

> 首次跑大概率会有 SKIP（G5 密钥缺失启动失败 / G7 安全组 等人工项）。
> 人工确认过的项通过环境变量声明：
>
> ```bash
> sudo GATE_MANUAL_CONFIRMED="G5,G7" bash deploy/scripts/gate-check.sh prod
> ```

门禁四态语义（必须理解，不能只看绿）：

| 状态 | 含义 | 退出码 |
|---|---|---|
| PASS | 查过了，合格 | 0 |
| FAIL | 查过了，不合格，**必须修** | 1 |
| SKIP | 没查到（缺前置条件），**不等于合格** | 2 |
| N/A | 按环境设计就没有这一项 | 不影响 |

### 6.6 日志脱敏抽查

拿最新的应用日志扫一眼有没有手机号等明文：

```bash
# 扫 11 位连续数字（可能是手机号的模式，会有误报，人工筛）
docker exec s2s-app grep -E '[^0-9]1[3-9][0-9]{9}[^0-9]' /var/log/app/*.log | head -20
```

有命中就人工确认是不是真的明文手机号。真有 = 严重事故，立刻查代码。

## 7. 日常发版

### 7.1 标准发版流程（推荐）

用 `deploy.sh` 一键发版，它做 6 件事：拉代码 → Maven 构建 → 构建镜像 → **门禁自查** → 备份数据库 → 滚动重启 app。

```bash
cd /opt/s2s
sudo bash deploy/scripts/deploy.sh prod
```

> 🔴 **门禁是硬卡点**：FAIL 直接中止，没有绕过开关；SKIP 默认也中止，除非你带 `--gate-allow-skip="理由"` 显式放行。

发版成功后，会打印版本号（时间戳，如 `20260930-150000`）和日志路径。

### 7.2 常用变体

```bash
# 跳过 git pull（比如你手动切了分支或 cherry-pick 了 patch）
sudo bash deploy/scripts/deploy.sh prod --skip-pull

# 声明人工确认项已验证
```

## 8. 回滚与应急

三种回滚方案，按代价从小到大：

### 方案 A：仅回滚应用镜像（最快）

适用：代码 bug、新功能异常、**数据结构未变更**。

```bash
# 1. 查看可用镜像 tag（保留时间取决于你保留了多少份）
docker images s2s-app --format '{{.Tag}}  {{.CreatedAt}}' | sort -r

# 2. 选一个确认过的旧版本号，替换到下面命令

cd /opt/s2s
sudo APP_VERSION="$OLD_VERSION" S2S_ENV=prod docker compose \
  -f deploy/docker-compose.yml \
  -f deploy/compose/docker-compose.prod.yml \
  --env-file deploy/env/.env.prod \
  up -d --no-deps --wait app
```

> 前提：旧镜像还在本机上。镜像被清掉了就只能重 build（回到对应 git commit 再跑一次 deploy.sh）。

### 方案 B：整机回滚（系统盘快照）

适用：数据结构变更出问题、配置大面积改错、不确定回滚到哪一版。

**步骤（在云厂商控制台操作）**：

1. 阿里云控制台 → 云服务器 ECS → 本实例 → 云盘
2. 找到系统盘 → 回滚云盘 → 选择发版前的快照 `s2s-pre-rollback-YYYYMMDD`
3. 确认回滚，实例会重启
4. 重启后验证服务恢复

> ⚠ 回滚快照 = 盘上所有数据（包括数据库）回到快照时点。
> 快照之后的新数据（用户发的帖、新注册用户）**全部丢失**。只在万不得已时用。

### 方案 C：数据回滚（MySQL 备份恢复）

适用：只有数据错了（如误删、脏数据），代码不需要回滚。

```bash

# 2. 恢复到新实例或临时库核对，确认正确后再切换
# （具体操作按备份脚本 README 执行；严禁直接覆盖生产库）
```

## 10. 常见问题与排错

### 10.1 容器一直 Restarting / unhealthy

先看日志：

```bash
docker logs --tail 100 s2s-app
docker logs --tail 100 s2s-mysql
```

**最常见原因：**

1. **env 文件有变量没填** → 应用启动失败（缺失必填环境变量会快速失败）
   - 检查：`grep 'change_me\|example\|placeholder' deploy/env/.env.prod`
   - 修复：补全后 `bash deploy/scripts/env-up.sh prod` 重启

2. **MySQL 连不上** → 应用健康检查不过
   - 检查：`docker logs s2s-mysql | tail -50`
   - 常见：配置文件权限不对（`my.cnf` 必须 ≤ 644，否则被 mysqld 忽略）

3. **Redis 无口令** → 健康检查失败
   - 检查：`grep REDIS_PASSWORD deploy/env/.env.prod`，值非空

### 10.2 Caddy 证书申请失败

**常见原因：**

- 域名 A 记录没生效 → 先 `dig <域名>` 确认指向本服务器公网 IP
- 80 端口不通 → ACME HTTP 挑战需要 80 端口，检查防火墙和云安全组
- 申请太频繁触发限流 → 换个域名（或等一小时），Let's Encrypt 有限速

验证：

```bash
# 80 端口从外部可达？
curl -I http://<你的域名>/

# Caddy 日志
docker logs s2s-caddy 2>&1 | grep -iE 'cert|tls|acme|error'
```

### 10.3 应用启动报 "Public Key Retrieval is not allowed"

MySQL 驱动在非 TLS 连接下默认禁止索取 RSA 公钥。
**解决：** 配置中已经用 `sslMode=REQUIRED` 走 TLS 了，如果你改了连接串导致 TLS 失效就会出这个问题。
**不要**加 `allowPublicKeyRetrieval=true` —— 那等于把库口令交给冒充者。恢复 `sslMode=REQUIRED`。

### 10.4 内存不足 / OOM

```bash
# 看各容器实际内存占用
docker stats --no-stream

# 看系统内存整体
free -h

# 看有没有 OOM kill
dmesg | grep -i 'out of memory\|oom-killer' | tail -10
```

如果超预算，先查是哪个容器超了。MySQL 和 Java 都有显式内存限制，正常情况下不会超；超了说明配置被改过或有泄漏。

### 10.5 门禁失败（FAIL / SKIP）

**FAIL 怎么办？**
- 按日志里的 [FAIL] 项修
- 修复后重跑 `bash deploy/scripts/gate-check.sh prod`
- FAIL **没有绕过开关**，别找

**SKIP 怎么办？**
- 看 SKIP 的原因（缺什么前置条件）
- 补齐前置条件后重跑
- 确实凑不齐前置条件的，用 `--gate-allow-skip="理由"` 显式放行，但要知道这是你在承担风险

### 10.6 数据库表没建起来 / Flyway 迁移失败

```bash
# 看 Flyway 日志
docker logs s2s-app 2>&1 | grep -i flyway

# 直接连数据库看有哪些表
docker exec -it s2s-mysql mysql -u root -p$(grep MYSQL_ROOT_PASSWORD deploy/env/.env.prod | cut -d= -f2) -e "USE s2s; SHOW TABLES;"
```

**常见原因：**
- 数据库建了但空的 → Flyway 没跑成功，看应用启动日志里的报错
- `flyway_schema_history` 表有失败记录 → 修完后清掉失败记录重跑（生产环境不推荐，建议回滚数据后重跑）

### 10.7 升级 Docker 后容器都没了

Docker 升级有时会重置数据根目录。确认 `docker info | grep "Docker Root Dir"` 指向正确位置。
如果数据还在，只是 Docker 没认出来，不要慌，先查数据目录，**绝对不要 `docker compose down -v`**。

### 10.8 日志里有手机号 / 身份证明文

**立即做：**

1. 确认是哪条日志路径打出来的（应用日志？Caddy 日志？）
2. 定位代码位置，修复（脱敏或移除）
3. 清理已落盘的日志（涉及个人信息的日志不能留）
4. 评估影响范围（有多少条、哪些用户）
5. 按 PIPL 要求处理（必要时上报）

> 这是门禁 G9 的意义。但 G9 只是抽查，代码侧才是第一道防线。

## 11. 内测包（APK）出包与 L3 门禁

> 本节是**客户端**内测包的出包流程（服务端发版见 §7）。
> 判据源：`docs/architecture/DevSecOps接入方案.md` §4.4 的 11 步序列；执行载体：`deploy/scripts/release-gate.sh`（在 WSL 中运行，经 WSL 互操作调用 Windows 侧 `flutter.bat` / `keytool.exe` / `apksigner.bat`）。

### 11.1 一次性准备（首次出包前）

1. **正式签名 keystore**：存于**仓库外**、权限 600、独立备份、绝不入库。
   本仓库当前使用 `D:\developer\soft\s2s-keystore\s2s-release.jks`（alias `s2s-release`，CN=找鸭找，有效期至 2054-02-22）：
   - 证书 SHA-256：`4E:FB:8B:21:9F:89:7D:42:B5:1B:7D:8F:B4:F7:C7:61:16:C8:DC:F3:C5:D0:65:47:57:FD:02:E3:CD:20:5C:FA`
   - 证书 SHA-1：`18:E8:5B:D7:C5:E0:09:D9:0A:42:F7:4D:9B:5B:93:60:59:F8:96:A5`
   - **该证书一经启用不可更换**：换签名等于换应用身份，所有老用户无法覆盖安装，并需重做 P7 APP 备案。
2. **`android/key.properties`**：指向 keystore 并存放口令。该文件已被 `.gitignore` 忽略，绝不入库。缺该文件时 release 构建会因缺少签名配置而失败（fail-closed）——脚本刻意不回退 debug 签名，那正是阻塞项 B-2 要消除的形态。
3. **包名**：当前为开发期包名 `com.s2s.zhaoyazhao.dev`（待 P2/P3 落地后改正式包名，替换点仅 `android/app/build.gradle.kts` 一处）。
4. **高德 Key**：客户端地图 Key 与「包名 + 签名证书 SHA-1」绑定，换签名须在高德控制台按新 SHA-1 重新登记并签发 Key。构建时以 `--dart-define=AMAP_ANDROID_KEY=<key>` 注入；未提供时门禁记 SKIP（包内地图走降级底图，P0 五环之一不可验）。

### 11.2 出包（一条命令）

```bash
bash deploy/scripts/release-gate.sh
```

脚本按 DevSecOps §4.4 依次执行 11 步：工作区干净 → 分支/commit hash → 源码层后门 grep → `flutter analyze` → `flutter test` → `flutter build apk --release` → 产物层后门扫描（`888888` 只在 `lib/*/libapp.so` 上扫、`debugCode` 扫整包，两者均须为 0；口径见 DevSecOps §4.1 与说明文档 §2.9 DEC-21）→ `apksigner` 验签 → 计算 SHA-256 → 写 `build/release-gate.log` → FAIL 时物理删除 APK；全部通过后自动打 `rel/prod/<APP_VERSION>` 附注 tag。

常用参数：

| 参数 | 用途 |
| --- | --- |
| `--skip-build` | 跳过 analyze/test/build 三步，用于复检既有产物 |
| `--apk <path>` | 指定待检 APK（默认 `build/app/outputs/flutter-apk/app-release.apk`） |
| `--version <ts>` | 指定 APP_VERSION（默认取当前时间戳 `YYYYmmdd-HHMMSS`） |
| `--allow-skip "理由"` | 放行 SKIP 档（**对 FAIL 无效**；理由必填，写入日志与 tag） |

### 11.3 退出码与处置

| 退出码 | 含义 | 处置 |
| --- | --- | --- |
| 0 | 全部判定通过 | 可交付；`rel/prod/<ts>` 已打 |
| 1 | 存在 FAIL | 修复后重跑。**产物已被物理删除**，不会误分发 |
| 2 | 存在未判定项（SKIP） | 补齐前置条件后重跑；确需放行用 `--allow-skip="理由"` |

### 11.4 留证

- `build/release-gate.log`（自动生成，禁止手工编辑）：时间戳、分支/commit、APK 路径与 SHA-256、`888888`/`debugCode` 双计数、签名证书指纹、最终判定。
- 该日志**随内测包一起归档，两者不可分离**；缺失则该包不得分发。

> ⚠️ 已知欠账：日志与 APK 都落在 `build/` 下，而 `build/` 被 `.gitignore` 忽略、且是 `flutter clean` 的删除对象（`docs/architecture/分支与版本标记规范.md` §3.2 的 S9 待办）。「归档到 `build/` 之外」尚未落地。

### 11.5 常见问题

- **构建卡在 `:jni:configureCMakeRelWithDebInfo` 报「拒绝访问」**：本机权限/沙箱拦住了对 Pub Cache（`…\AppData\Local\Pub\Cache\…\jni-1.0.3\android\.cxx\`）与 `Android\SDK\.knownPackages` 的写入。需在放行这两条路径的终端执行，或把 `PUB_CACHE` 指到可写目录。
- **S7 报 SKIP「扫描面为空」**：`unzip`/`python3` 均不可用或 APK 不是合法 zip，产物层后门**未判定**——这不是通过，须先补齐解压通道。

### 11.6 高德 Android Key 登记（release 签名版）

**为什么必须做**：高德客户端 Key 与「Package + 签名证书 SHA1」强绑定。release 包用的是新生成的正式证书（不是本机 debug 证书），故必须按**发布版 SHA1** 重新登记；否则地图初始化会被高德拒绝（`INVALID_USER_SCODE`），App 内地图退化为降级底图。

**本项目待填的三个参数**（唯一真源，勿抄错）：

| 字段 | 值 | 来源 |
| --- | --- | --- |
| Package（应用包名） | `com.s2s.zhaoyazhao.dev` | `android/app/build.gradle.kts` 的 `applicationId` |
| 发布版安全码 SHA1 | `18:E8:5B:D7:C5:E0:09:D9:0A:42:F7:4D:9B:5B:93:60:59:F8:96:A5` | 正式证书 `s2s-release.jks`（与门禁常量 `EXPECTED_CERT_SHA256` 同一张证书） |
| 调试版安全码 SHA1 | `09:B9:EB:30:F1:F1:1A:6A:E5:F5:D2:EA:A0:98:A8:CD:A1:8D:3C:8A` | 本机 `%USERPROFILE%\.android\debug.keystore` |

**操作步骤**（入口：高德开放平台控制台 <https://lbs.amap.com/dev/> → 应用管理 → 我的应用）：

1. **创建新应用**（若已有应用可跳过）。
2. 在该应用下点 **「添加新 Key」**。
3. 填写：应用名（如 `找鸭找-Android-内测`）、绑定的服务选 **Android 平台 SDK**、**发布版安全码 SHA1**、**调试版安全码 SHA1**、**Package** —— 后三项填上表的值。
4. 阅读并勾选《高德地图 API 服务条款》→ **提交** → 复制生成的 Key（32 位十六进制）。
5. **只经构建期注入，不入库**：

```bash
flutter build apk --release \
  --dart-define=S2S_API_BASE_URL=https://s2s.build110.com \
  --dart-define=S2S_IS_RELEASE=true \
  --dart-define=AMAP_ANDROID_KEY=<上一步复制的 Key>
```

   或把 Key 写进本机未跟踪的脚本/环境变量，由门禁读取（`release-gate.sh` 读环境变量 `AMAP_ANDROID_KEY`）。
6. **复检**（出包后）：

```bash
AMAP_ANDROID_KEY=<key> bash deploy/scripts/release-gate.sh --skip-build
```

   门禁第 6 步的 `S6-Key` 由 SKIP 变为 PASS；真机验证地图不再走降级底图。

**SHA1 复核命令**（可用以核对上表，值须逐字符一致、**不得带空格**）：

```bash
# 发布版（正式证书；口令见 android/key.properties 的 storePassword）
keytool -list -v -keystore D:\developer\soft\s2s-keystore\s2s-release.jks -alias s2s-release
# 调试版（本机 debug 证书）
keytool -list -v -keystore %USERPROFILE%\.android\debug.keystore -storepass android -alias androiddebugkey
```

或 `cd android; .\gradlew.bat signingReport`（一次列出 debug / release / profile 三态）。

**失败排查（高德官方口径）**：

- 报 `INVALID_USER_SCODE`（**不是** `INVALID_USER_KEY`）或错误码 `1008 / 32 / 7` → 依次查：① SHA1 与控制台**逐字符**一致（debug 或 release **至少一个匹配**，不能带空格，**严格区分大小写**）；② Package 与 `applicationId` 一致；③ 包名大小写统一。
- **1 个 Key 只能用于一个应用**（多渠道安装包算多个应用），一 Key 多用会服务调用失败。
- **Key 与包名绑定**：P3 锁定正式包名后，`com.s2s.zhaoyazhao.dev` 一旦改名，本 Key **必须重新登记** —— 这是会随包名变更重复发生的工作，不是一次性的。

**合规前置（不做会被驳回）**：

- Key **不入库**：仓库只留占位，注入点见 `lib/features/map/amap_init_guard.dart`。
- **隐私时序**：必须**用户同意隐私政策后**才初始化地图 SDK（PRD §6.7；上架前置手册「位置权限是高频驳回点」）。未同意即初始化会白屏且被商店/监管驳回。
- 高德 SDK 必须写进隐私政策的第三方 SDK 清单（上架前置手册 P6）。

**两条别混淆的边界**：

- 未注入 Key **不会崩**：`AMapInitGuard.hasApiKey == false` → 地图渲染降级底图，其余功能可用（内测包当前即此状态）。
- 这与 P7 APP 备案要的材料**不是一回事**：备案要的是**签名证书的 MD5 / SHA-1 与公钥**，不是这个 Key。

| 4 | 安装 Docker CE + docker compose 插件 | 2-5 分钟 |
| 5 | 安装 JDK 21（Eclipse Temurin）+ Maven 3.9 | 2-5 分钟 |
| 6 | 验证基础工具版本 | 几秒 |
| 7 | 时区 Asia/Shanghai + NTP 同步 | 几秒 |
| 8 | 创建 /opt/s2s 和 /var/backups/s2s 目录 | 几秒 |

**deploy-first.sh（6 步）：**

| 步骤 | 内容 |
|---|---|
| 1 | git clone 代码到 /opt/s2s |
| 2 | 自动生成全部密钥（MySQL/Redis/AEAD/HMAC/JWT）并写入 .env.prod |
| 3 | 刷新镜像基线（images.lock） |
| 4 | 用 env-up.sh 启动服务，等待 healthy |
| 5 | 健康检查 + 分类树 / 地图 pins 接口冒烟 |
| 6 | 门禁自检（首次必有 SKIP，属正常） |

### C.3 脚本的幂等性

两个脚本都支持重复执行：

- 已安装的软件不会重新安装
- 已存在的 swap / 目录 / 配置不会被覆盖
- 已存在的 `.env.prod` 不会重新生成密钥（不会把你改过的密码冲掉）

### C.4 --no-https 模式详解

适用场景：**域名还没备案**、或者还没配 A 记录。

行为：
- 使用 `staging` 环境而非 `prod`（Caddy 用自签证书，不走 ACME）
- Caddy 监听 8443（HTTPS）和 8080（HTTP），绑定 127.0.0.1，不对外
- 应用本身是同一套，只是前端入口不同
- 备案下来之后，一条命令切换到正式 prod：

```bash
cd /opt/s2s
bash deploy/scripts/env-up.sh staging --down
# 确认 deploy/env/.env.prod 配置正确（把 staging 的密钥同步过去，或直接复制文件）
bash deploy/scripts/env-up.sh prod
```

> ⚠ 切换环境时，数据卷（MySQL/Redis）是**共用**的（同一台服务器上三环境互斥设计）。
> 也就是说 staging 的数据切换到 prod 后还在，不会丢。

### C.5 部署完成后必须做的 3 件事

1. **备份密钥**：把 `deploy/env/.env.prod`（或 staging）里的所有密钥存到密码管理器
2. **填 OSS 配置**：编辑 `.env.prod`，填入 OSS 的 AK/SK/桶名/Endpoint
3. **打系统盘快照**：云厂商控制台创建快照，命名 `s2s-init-YYYYMMDD`，作为出事时的最后兜底

## 附录 D：首次生产部署实测记录（2026-10-06）

> 本附录记录首次在真实生产服务器上部署时**实际遇到的环境差异与踩坑**，均为实测结论、非推测。当实际环境与手册前文的默认假设有出入时，**以本附录为准**。

### D.1 实测环境 vs 手册假设

| 项 | 手册假设 | 实际 | 处置 |
|---|---|---|---|
| 系统 | Ubuntu 22.04 | **CentOS 7 系**（`3.10.0-957.el7`） | 走 yum / firewalld，见附录 C |
| 内存 | 2 GB | **31 GB** | 内存预算可放宽（`mem_limit` 非瓶颈） |
| 数据盘 | 40 GB | **256 GB 挂在 `/mnt`** | 代码落 `/mnt/s2s`，工具落 `/mnt/s2s-tools` |
| Docker | 需安装 | **已装 20.10.14 + 13 个容器在跑** | 不可重启 daemon、不可停既有服务 |
| docker compose | 需安装 | **只有 v1 的 1.26.2（过老，不支持本项目的 compose 语法）** | 手装 v2 插件到 `/usr/local/lib/docker/cli-plugins/` |
| Java | 需 JDK 21 | 已有 **JDK 1.8**（系统默认，不可动） | JDK 21 绿色装 `/mnt/s2s-tools/jdk21`，不改系统 PATH |
| Maven | 需 3.9 | yum 装的 **3.0.5**（过老） | **不用宿主机构建**，走 Dockerfile 内的 maven 镜像 |
| 80 端口 | 空闲 | **被系统 nginx 占用**（服务多个 `*.build110.com` 子域名） | Caddy 不绑 80，见 D.3 |

### D.2 镜像拉取：Docker Hub 不可达时怎么办

实测 `docker pull` 直连 Docker Hub 超时；配置里的阿里云加速器 `/v2/` 虽返回 `200`，但**拉取镜像层时回源失败**。

**解法**：用第三方镜像站当前缀拉取，再 `docker tag` 回原名（**不用改 daemon.json、不用重启 Docker、不影响既有容器**）：

```bash
docker pull docker.1panel.live/library/mysql:8.4
docker tag  docker.1panel.live/library/mysql:8.4 mysql:8.4
```

本项目需要的 5 个镜像（**`library/` 前缀不能省**，它们都是官方镜像）：

- `caddy:2.8-alpine`、`mysql:8.4`、`redis:7.4-alpine`
- `maven:3.9-eclipse-temurin-21`（构建期）、`eclipse-temurin:21-jre-alpine`（运行期）

> 1panel 不可用时备选 `docker.m.daocloud.io`（其 `/v2/` 返回 `401` 属正常鉴权响应，不代表不可用）。

### D.3 80 端口被占 → ACME 必须改走 TLS-ALPN-01

宿主 80 被 nginx 占用且**不可停**（按「不影响既有服务」约束），引发两个连锁问题：

1. **Caddy 不能绑 80** → `deploy/compose/docker-compose.prod.yml` 去掉 `0.0.0.0:80:80`，只留 443
2. **但 Caddy 仍会选 HTTP-01 挑战** —— 因为容器内 80 能绑上，它**误判外部可达**；而 Let's Encrypt 的校验请求实际到达宿主机 nginx → **必然失败**
   ⇒ 解法：`Caddyfile.prod` 全局块加 **`http_port 8081`**。Caddy 据此判定「标准 80 不可用」，自动改走 **TLS-ALPN-01（443）**，证书签发成功。

**代价与恢复**：Caddy 侧不再自动跳 `https://`（门禁 **G6**）。恢复办法是在宿主机 nginx 加一条 301 跳转块 —— **本轮已实施并外网验证通过**（做法见 D.9），故 G6 最终判定 PASS。

### D.4 健康检查不能用 curl（最隐蔽的坑）

`eclipse-temurin:21-jre-alpine` **既不含 curl、也不含 wget 独立命令**，容器内只有 `busybox` 与 `nc`（镜像自带注释称其含 curl，**已过期**）。

用 curl 做 healthcheck 的后果链：healthcheck 永久失败 → app 恒 `unhealthy` → `depends_on: service_healthy` 的 **caddy 永不启动**。表象是「部署卡在启动阶段」，而应用本身完全正常。

**正确写法**（仓库已改）：

```
test: ["CMD-SHELL", "busybox wget -qO- http://localhost:8080/actuator/health | grep -q '\"status\":\"UP\"' || exit 1"]
```

**换镜像版本后必做**：`docker exec s2s-app sh -c 'command -v curl wget busybox'` 复核可用工具，再决定 healthcheck 怎么写。

### D.5 Maven 依赖下载：必须走国内镜像

直连 Maven Central 实测跑到 **13 分钟仍未完成**。仓库已提供 `deploy/maven-settings.xml`（阿里云 public 镜像），`Dockerfile` builder 阶段自动注入到 `/root/.m2/settings.xml`，**无需手动操作**，改后依赖下载降至分钟级。

### D.6 密钥 JSON 的字段名（高频错误）

`AEAD_MASTER_KEYS_JSON` / `HMAC_PEPPERS_JSON` 的字段名是 **`version`（整数）**，**不是 `id`**：

```
AEAD_MASTER_KEYS_JSON=[{"version":1,"key":"<32 字节>"}]
HMAC_PEPPERS_JSON=[{"version":1,"key":"<32 字节>"}]
```

`key` 须解出**恰好 32 字节**（hex 64 位 / base64 44 位）。写错的表现是启动即抛：

```
IllegalStateException: HMAC pepper条目的 version 字段缺失或非整数：null
```

### D.7 与既有服务共存的纪律（本机特有）

部署机上已有 **13 个容器**在跑（EMS / 若依微服务栈）。共存必须遵守：

- **不重启 Docker daemon** —— `Live Restore Enabled: false`，重启会停掉全部既有容器
- **不改动既有 nginx 配置** —— 80 端口归它
- **不占用其端口** —— 8088 / 9200 / 9804 / 9602 / 9603 / 2181 等
- s2s 自成一套：compose 项目 `s2s`、容器 `s2s-*`、网络 `s2s_s2s-net`、命名卷 `s2s_*`
- 数据面（mysql/redis/app）**不映射宿主端口**，仅 Caddy 暴露 443

### D.8 本机有两套 nginx —— 必须认准「运行中的那套」

实测 `nginx -t` 报 `nginx: [emerg] unknown directive "stream"`，但 nginx 服务却正常运行。根因是**两套 nginx 并存**：

| | 运行中的那一套 | PATH 里的那一套 |
|---|---|---|
| 二进制 | `/usr/local/nginx/sbin/nginx`（自定义编译，含 `--with-stream`） | `/usr/sbin/nginx`（yum 装，1.20.1，stream 是动态模块且未加载） |
| 配置文件 | **`/usr/local/nginx/conf/nginx.conf`** | `/etc/nginx/nginx.conf`（**当前不生效**） |

**判定方法**：

```bash
ss -tlnp | grep ':80 '          # 拿监听 80 的 pid
ls -la /proc/<pid>/exe          # 看真实二进制路径
/usr/local/nginx/sbin/nginx -t  # 输出会打印实际读取的配置文件路径
```

**纪律**：

- 改 nginx 配置 ⇒ 改 **`/usr/local/nginx/conf/nginx.conf`**
- `-t` 与 `-s reload` ⇒ 一律用 **`/usr/local/nginx/sbin/nginx`**
- **不要动** `/etc/nginx/nginx.conf` —— 那套没在跑，改它等于白改（本轮为此白跑了一轮）

### D.9 门禁自检结论与本轮 3 处判据修正

首次 `gate-check.sh prod` 得 `PASS 7 / FAIL 0 / SKIP 6`；逐项补齐后达 **`PASS 13 / FAIL 0 / SKIP 0 / N/A 1`（退出码 0，放行）**。

| 项 | 初判 | 处置 | 终判 |
|---|---|---|---|
| G5 密钥缺失快速失败 | SKIP | 实跑 `docker compose ... run -e HMAC_PEPPERS_JSON= app`，实测 `APPLICATION FAILED TO START` + `凭证未注入或占位未解析` | PASS（`GATE_MANUAL_CONFIRMED=G5`） |
| G6 HTTP 301 | SKIP | **宿主机 nginx 加 301 块**（见下） | PASS |
| G7 安全组 | SKIP | 外网端口扫描实证（见下） | PASS（声明 G7） |
| G8 备份权限 | SKIP | 跑一次 `backup-mysql.sh prod` | PASS |
| G9 日志脱敏 | SKIP→FAIL→PASS | **门禁判据两处缺陷，均已修**（见下） | PASS |
| G11 镜像基线 | SKIP | 从本地镜像读 RepoDigest 回填 `images.lock`（5 条，来源见该文件注释） | PASS |

**G6 的 nginx 301 块**（加在 `/usr/local/nginx/conf/nginx.conf` 的 http 块内；`nginx -s reload` 平滑生效，既有站点不受影响）：

```nginx
server {
    listen 80;
    server_name s2s.build110.com;
    return 301 https://$host$request_uri;
}
```

> 插入位置：http 块的顶层 `}` 之前。改前 `nginx -t` 校验，改后 `diff` 确认只新增行、无删除行，再 reload。

**G9 判据修正（`gate-check.sh`，本轮修复）**：

1. 原判据扫**宿主机** `/var/log/app` —— 而日志落**容器内** `/var/log/app`（宿主载体是命名卷 `app_logs`），宿主机并无该路径，**判据从未真正执行过**（恒 SKIP）。改为经 `docker exec s2s-app` 扫容器内。
2. 原正则 `1[3-9][0-9]{9}` **无边界**，会把 UUID 里的数字片段误判为手机号 —— 实测 `request_id:"bd19c1b2-...-315133023584"` 的子串 `15133023584` 命中，使判据在**完全合规的日志上稳定报 FAIL（假阳性）**。改为带边界：`(^|[^0-9A-Za-z])1[3-9][0-9]{9}([^0-9A-Za-z]|$)`。

**G7 的独立实证**（外网视角，证明数据面未暴露）：

```
22: OPEN   80: OPEN   443: OPEN   3306/6379/8080/9602: filtered
```

> 附带建议：22 端口当前对任意 IP 开放（无来源白名单），建议在阿里云安全组收紧为运维 IP。
